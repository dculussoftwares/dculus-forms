# S10 — PDF templates & generators

Scope reviewed (all under `apps/backend/src/`): `graphql/resolvers/pdfTemplates.ts`, `graphql/resolvers/pdfGenerators.ts`, `services/pdfTemplateService.ts`, `services/pdfGeneratorService.ts`, `services/pdfGeneratorStorage.ts`, `services/pdfGeneratorZipService.ts`, `services/pdfGenerationJobService.ts`, `services/copyPdfTemplates.ts`, `plugins/core/pdfGeneratorAutoRun.ts`. Supporting reads: `repositories/pdfGeneratorRepository.ts`, `routes/upload.ts` (PdfTemplateAsset branch), `services/fileUploadService.ts` (key/bucket handling), `services/responseService.ts` (delete/edit hooks), Prisma `PdfGenerator`/`PdfGenerationRun`/`PdfGenerationResult`, and the installed `@pdfme/common|generator|schemas` 6.2.2 dist. Review-only; no source changed. No secrets are included.

Summary: 0 Critical, 0 High, 6 Medium, 6 Low, 3 Info (15 total). Items marked PLAUSIBLE depend on behaviour that was not exercised at runtime.

Overall: the authorization layer is sound. Every template, generator, run and result operation resolves the owning `formId` from the stored row and calls `checkFormAccess` at the right level (VIEWER read/generate, EDITOR write/run). The weak spots are resource exhaustion (the PDF engine runs in the API process on attacker-influenced input), data retention of generated PDFs, and an unbounded `basePdf` string that bypasses the base-PDF upload controls.

Cross-references: S02-09 (existence oracle), S02-13 (VIEWER duplicate copies PDF configs), S04-06 (no anonymous rate limit), S04-03/S04-04 (unvalidated/unbounded response payloads), S04-07 (response-copy email), S06 (PdfTemplateAsset upload validation, temp-export keys), S09 (AI budget), S11 (filter evaluation).

## S10-01 — Medium — Blank (non-uploaded) templates accept an arbitrary string `basePdf`, so attacker-supplied PDF bytes are stored in Postgres and parsed server-side, bypassing the upload controls
- **File:line:** `graphql/resolvers/pdfTemplates.ts:171-181` (create), `:236-246` (update), `:403-416` (preview working copy); `services/pdfTemplateService.ts:182-200` (`stripBasePdf` / `validatePdfTemplate`)
- **Description:** For templates without a `fileKey`, `stripBasePdf` returns the template untouched and `validatePdfTemplate` only calls pdfme's `checkTemplate`. pdfme's `BasePdf` zod type is `z.union([CustomPdf, BlankPdf])` and `CustomPdf` accepts any string (and buffers). A client can therefore send `basePdf` as a long base64 / `data:application/pdf` string instead of `{width,height,padding}`. It is persisted in the `PdfTemplate.template` JSON column. At generation time `generate()` calls `getB64BasePdf` then `PDFDocument.load(...)` on it (generator dist `loadBasePdf`), which parses the bytes with pdf-lib. The designed path (private-bucket upload, `application/pdf` MIME check, 10 MB cap, `fileKey` prefix check) is entirely skipped. The only bound is the Express JSON body limit (10 MB, see S04-03).
- **Exploit scenario:** An EDITOR (or anyone who can obtain EDITOR on a form) calls `createPdfTemplate` or `updatePdfTemplate` with a crafted PDF (e.g. a FlateDecode decompression bomb, or an object graph with a very large page tree) as the `basePdf` string. Every later render of that template parses it inside the API process: the owner's VIEWERs through `generatePdfFromResponse` / `previewPdfTemplate`, bulk runs, and the auto-run listener on every public submission (S10-03). The same multi-MB string is returned to every VIEWER in `pdfTemplates` / `pdfTemplate` list queries (`PdfTemplate.template` field resolver), bloating responses and the DB.
- **Recommended fix:** For templates without `fileKey`, require `basePdf` to match the `BlankPdf` shape (`width`, `height`, `padding` with finite, bounded numbers, optional `staticSchema` only) and reject strings/buffers. Implement it in `validatePdfTemplate` so the create/update/preview paths share it. Also reject non-null `basePdf` strings for templates that do have a `fileKey` (they are overwritten, but reject for clarity).

## S10-02 — Medium (PLAUSIBLE) — No bounds on template JSON (schema count, page count, page dimensions, table size, string length) before rendering in-process
- **File:line:** `services/pdfTemplateService.ts:197-200` (`validatePdfTemplate`); `graphql/resolvers/pdfTemplates.ts:149,173,181` (name/fileName/template accepted unbounded); `services/pdfTemplateService.ts:503-509` (`generate`)
- **Description:** Validation is purely structural (`checkTemplate`). There is no cap on the number of pages or elements, on `BlankPdf.width/height/padding` (unbounded `z.number()`, so negative, zero, or huge values pass), on `table` content row counts, `qrcode`/`svg`/`image` content size, or on `name` / `fileName` lengths. pdfme's dynamic layout (`getDynamicTemplate`) splits table content across pages (one page per unit when the content height is tiny or non-positive), so a small JSON can yield very many pages. `inputs[name] = content` (`pdfTemplateService.ts:478`) passes template-supplied content for every non-text plugin straight to the renderer. Rendering uses the API process's event loop and heap.
- **Exploit scenario:** An EDITOR saves a template with a 10 MB table or thousands of elements and a degenerate page size, then clicks preview, or enables auto-run so that one anonymous submission triggers the render. Each render can consume seconds of CPU and hundreds of MB; a few concurrent requests stall or OOM the single backend process that also serves GraphQL and Hocuspocus. PLAUSIBLE because pdfme's page/layout limits were read, not stress-tested.
- **Recommended fix:** Add explicit limits in `validatePdfTemplate`: max pages (e.g. 20), max elements per page and total, max `content` length per schema, finite positive page dimensions within a sane range (e.g. 50-2000 mm), padding that leaves positive content height, and max table rows. Cap `name`/`fileName` length. Wrap `generate()` in a timeout and a per-process concurrency limiter (or move rendering to a worker/queue).

## S10-03 — Medium — Auto-run on submit lets anonymous submitters trigger an unthrottled PDF render + R2 write + two DB writes per submission per generator, and clutters/blocks the run table
- **File:line:** `plugins/core/pdfGeneratorAutoRun.ts:23-92`; `services/pdfGenerationJobService.ts:107-128,292-317`
- **Description:** `initializePdfGeneratorAutoRun` listens on every `form.submitted` event. For each enabled `autoRunOnSubmit` generator whose filters match (up to 6 per form) it creates a `PdfGenerationRun` row, hydrates the base PDF from R2 again (a full download per call, no cache), renders, uploads to R2, upserts the result, and updates the run, all in the submission's event handler. There is no concurrency cap, queue, debounce or per-form/org budget. Public submissions have no effective rate limit (S04-06) and respondent strings may be 10,000 chars per value (S04-03), so a submitter controls the render input size. Every submission adds a permanent `PdfGenerationRun` row. `startPdfGenerationRun` uses `findActiveRun`, which also matches these `auto` rows, so a sustained stream of submissions can make the owner's manual run fail with "already in progress".
- **Exploit scenario:** Anyone with the public form link scripts submissions at the platform's rate. For a form with auto-run on, each submission spawns up to 6 renders plus 6 R2 downloads/uploads, multiplying CPU, R2 request costs and DB rows far beyond the cost of the submission itself. The attack degrades the whole backend and inflates the owner's storage.
- **Recommended fix:** Move auto-run onto a bounded queue (global concurrency, per-form and per-org rate limit, dedupe by response). Cache the hydrated base PDF per template version. Do not create a `PdfGenerationRun` row for single auto-runs (or exclude `trigger: 'auto'` from the `findActiveRun` guard), and prune old run rows. Gate auto-run by plan.

## S10-04 — Medium — Bulk generation runs in the API process with no global concurrency cap, quota or plan gate; matching responses are fully loaded in memory
- **File:line:** `services/pdfGenerationJobService.ts:27-35,107-157,159-242`; `graphql/resolvers/pdfGenerators.ts:223-231`
- **Description:** `startPdfGenerationRun` fires `void runPdfGenerationLoop(...)` in-process. The guard allows one active run per generator, but a form can have 6 generators, and there is no cap across forms or organizations. Each loop renders sequentially with a 500 ms pause per 10 responses, so a CPU-heavy template still occupies the event loop continuously. `MAX_RESPONSES_PER_RUN = 5000` bounds the number of responses, but `getMatchingResponses` accumulates every matching response's full `data` JSON in an array before the run starts (responses can be up to 6-10 MB each per S04-03), and each of up to 5000 results writes an R2 object plus DB rows. No per-org or per-plan limit on PDFs generated exists. There is also a work-after-restart gap: a crashed process leaves rows in `running` until a status poll flips them.
- **Exploit scenario:** An EDITOR (or a free-plan org) creates many forms with 6 generators each and starts runs of 5000 responses on all of them, or a hostile tenant on a shared deployment starts several concurrent runs. The single backend process becomes CPU- and memory-bound for minutes, harming every tenant. R2 storage grows by up to 5000 PDFs per run.
- **Recommended fix:** Use a real job queue/worker with global and per-org concurrency limits; page through responses by id instead of materializing them (iterate and render per page); add a per-org monthly PDF quota tied to the plan; and make run start idempotent (S10-10).

## S10-05 — Medium — ZIP download buffers every generated PDF in memory, callable by any VIEWER with no size or count cap
- **File:line:** `services/pdfGeneratorZipService.ts:14-37`; `graphql/resolvers/pdfGenerators.ts:280-309`
- **Description:** `buildZipForGenerator` downloads each result with `downloadFileBuffer` (full body into a Buffer), adds it to a JSZip instance, then `generateAsync({type:'nodebuffer'})` builds a second full copy, and the result is then uploaded via `uploadTemporaryFile`. For a generator with thousands of PDFs this is peak memory of roughly 2x the total archive size, with sequential R2 reads (slow, long-lived request). The resolver only requires VIEWER, with no limit on result count, aggregate size, concurrency, or repeat calls. (Entry names come from server-generated, sanitized filenames, so zip-slip is not reachable; see S10-15.)
- **Exploit scenario:** A VIEWER on a form with 5000 generated PDFs of ~1 MB each repeatedly calls `downloadPdfGenerationResultsZip`; each call allocates multiple GB and holds the request open, exhausting memory and crashing the process. Each call also writes a new multi-GB temp object.
- **Recommended fix:** Cap the number/total size of entries (return a clear error above the cap), stream the archive (the `fileUploadService` has a stream download helper) into a multipart upload, enforce a per-form/user rate limit and one in-flight build per generator, and consider requiring EDITOR for the ZIP.

## S10-06 — Medium — Generated PDFs (respondent PII) are never deleted from the private bucket when a response, template or form is deleted; only hidden in the API
- **File:line:** `services/pdfGeneratorService.ts:102-117,205-221`; `services/pdfGeneratorStorage.ts:51-97`; `services/responseService.ts:840-861`; `graphql/resolvers/pdfTemplates.ts:279-289`
- **Description:** `deleteGeneratedPdfsForGenerator` is only called from `deletePdfGenerator`. Other deletion paths leave objects under `pdf-generated/{formId}/{generatorId}/{responseId}.pdf`: (a) `deleteResponse` / `deleteResponses` are soft deletes that never touch R2; `filterResultsToLiveResponses` merely hides the row, as the code comments admit; (b) `deletePdfTemplate` removes the template, and `PdfGenerator` rows cascade in Postgres (`onDelete: Cascade`), but the cascade does not delete the R2 PDFs; (c) form deletion cascades the same way. The PDFs contain every answer the template prints (names, phone numbers, addresses, ID numbers) and persist indefinitely. Anyone who retains an old presigned URL (15 minutes) loses access, but the data stays in storage, defeating erasure requests and the intended soft-delete semantics.
- **Exploit scenario:** A respondent asks for deletion (or the owner deletes responses/forms to meet a retention policy). The response data is removed or hidden but the rendered PDF with the same data stays in R2 forever, available to anyone with bucket access, backups or a leaked/old key listing.
- **Recommended fix:** Delete R2 objects when a result's response is deleted (on soft-delete and on the purge job), and in `deletePdfTemplate` and form deletion call `deleteGeneratedPdfsForGenerator` for each affected generator before the DB cascade. Add a bucket lifecycle rule or sweeper for `pdf-generated/` keys with no matching result row.

## S10-07 — Low — VIEWER can mutate durable state via `generatePdfFromGenerator`, and disabled generators still generate
- **File:line:** `graphql/resolvers/pdfGenerators.ts:252-272`; `services/pdfGenerationJobService.ts:292-317,325-337`
- **Description:** `generatePdfFromGenerator` requires only VIEWER but calls `generateSinglePdfForGenerator`, which re-renders, overwrites the persistent R2 object (key is deterministic per response) and upserts the `PdfGenerationResult` row (new filename with a random suffix). This is a write by a read-only role, and it ignores `generator.enabled` (the flag is only checked in `startPdfGenerationRun`); `regeneratePdfsForResponse` after an edit also renders for disabled generators. There is no rate limit on this or on `generatePdfFromResponse` / `previewPdfTemplate` (each uploads a temp object).
- **Exploit scenario:** A VIEWER loops the mutation to churn R2 writes and CPU, flip the stored `filename`, or force regeneration for a generator the EDITOR disabled specifically to stop new PDFs. Also an owner who "disables" a generator to stop PDF creation is not actually protected.
- **Recommended fix:** Return the stored result when it exists and is fresh (render only if missing), or require EDITOR to regenerate; honour `enabled` in `generateSinglePdfForGenerator` and `regeneratePdfsForResponse`; add a per-user rate limit to the three on-demand generation mutations.

## S10-08 — Low — "Not found" is returned before the permission check, giving an existence oracle for template/generator/run IDs
- **File:line:** `graphql/resolvers/pdfTemplates.ts:53-59,98,213,265,303,385`; `graphql/resolvers/pdfGenerators.ts:39-45,81,91,101,111,203,218,228,238-243,257,285`
- **Description:** Every by-ID operation loads the row first and throws `NOT_FOUND`, and only then calls `checkFormAccess`, which throws `NO_ACCESS`. Any authenticated user can distinguish "ID does not exist" from "exists in another tenant". Same pattern as S02-09. IDs are cuid-style and not trivially guessable, so impact is small.
- **Exploit scenario:** A user probes leaked or guessed template/generator/run IDs (e.g. from a log or shared link) to learn which are valid in other organizations.
- **Recommended fix:** Return the same generic error for missing and forbidden rows (do the access check first when the row is found, and map both outcomes to one message/code for non-members).

## S10-09 — Low — The same base-PDF `fileKey` can back several templates (and form duplication may deliberately share it), so deleting one template deletes the asset others rely on
- **File:line:** `graphql/resolvers/pdfTemplates.ts:164-171,279-289`; `services/copyPdfTemplates.ts:41-53`
- **Description:** `createPdfTemplate` only checks the key prefix (`files/pdf-template-asset/{formId}/`), not that the key was uploaded by this caller, that the object exists, or that no other template already uses it. An EDITOR can attach the same key to several templates (the form's cap is 6). `deletePdfTemplate` deletes the R2 object unconditionally. `copyPdfTemplatesToForm` falls back to sharing the source key when the asset copy fails ("sharing the source object instead"), so the cloned form's template points into the source form's key prefix, and deleting either template removes the other's base PDF. The prefix invariant that gates `createPdfTemplate` then no longer holds for the clone.
- **Exploit scenario:** An EDITOR on a duplicated or multi-template form deletes one template, silently breaking generation for the other template/form (availability/integrity). A VIEWER who duplicated a form (S02-13) obtains a template that references the original owner's asset key; if they later delete it, the original's PDF is deleted.
- **Recommended fix:** Reference-count `fileKey` (or delete only if no other `PdfTemplate` row uses it); fail the copy instead of sharing the key; require the key to exist (HEAD) and be created through the upload route.

## S10-10 — Low — Check-then-act races on the per-form caps and the active-run guard
- **File:line:** `graphql/resolvers/pdfTemplates.ts:153-159`; `graphql/resolvers/pdfGenerators.ts:163-169`; `services/pdfGenerationJobService.ts:122-154`
- **Description:** Template and generator caps (6 each) are enforced with `count` then `create`, and the "one active run per generator" rule with `findActiveRun` then `createRun`. None is atomic or backed by a unique/partial index (`PdfGenerationRun` has only `@@index([generatorId])`). Concurrent requests exceed the cap or start duplicate loops writing the same R2 keys.
- **Exploit scenario:** An EDITOR fires parallel `startPdfGenerationRun` calls to run N loops against one generator (multiplying S10-04 load), or parallel creates to exceed the template/generator cap.
- **Recommended fix:** Enforce in the DB (serializable transaction or advisory lock keyed by form/generator; partial unique index on `(generatorId)` where status in `running,cancelling`).

## S10-11 — Low — Bulk runs use a stale response snapshot and do not re-check state or the starter's permission
- **File:line:** `services/pdfGenerationJobService.ts:140-157,173-208,325-337`
- **Description:** The matching responses (id + data) are captured once, then rendered for minutes. The loop does not re-check that a response is still undeleted, that its data was not edited since, that the generator is still enabled, or that the user who started the run still has EDITOR access. A bulk render finishing after a concurrent edit can overwrite the fresher PDF produced by the edit-regeneration hook (last writer wins on the same key).
- **Exploit scenario:** An EDITOR starts a run, is then demoted/removed, and the run continues to produce PDFs. A response edited or deleted mid-run ends up with a PDF of its old data, which `filterResultsToLiveResponses` may still serve for an edited (not deleted) response, leaving stale or wrongly-disclosed data in a downloadable file.
- **Recommended fix:** Re-read each response by id inside the loop (skip if `deletedAt` set), re-check `generator.enabled`, and compare an `updatedAt`/version before upsert; optionally re-verify the starter's access periodically.

## S10-12 — Low (PLAUSIBLE) — AI sample-data budget check is not atomic with usage recording
- **File:line:** `graphql/resolvers/pdfTemplates.ts:431-452`
- **Description:** `checkAITokenBudget` runs before the model call and `recordAITokenUsage` after it. Concurrent EDITOR requests all pass the check before any usage is recorded, so the monthly credit limit can be overshot by the number of parallel calls. EDITOR gating of `aiSampleData` is correct and the check/record pair is present, as required.
- **Exploit scenario:** An EDITOR (or script with an EDITOR session) issues dozens of parallel `previewPdfTemplate(aiSampleData: true)` calls just under the limit, spending more org AI credit than the plan allows. See S09 for the broader budget design.
- **Recommended fix:** Reserve estimated tokens atomically before the call (increment-then-refund, or a transactional check) and add a per-user rate limit.

## S10-13 — Info — Respondent values are re-expanded as placeholders in template inputs (second-order substitution)
- **File:line:** `services/pdfTemplateService.ts:459-478`; `packages/utils/src/mentionSubstitution.ts:107-131`
- **Description:** Token values are substituted into the template string first, then `substitutePlaceholdersPlainText` runs over the result. A respondent value that itself contains `{{otherFieldId}}` (or another `{token}`) is expanded using the same response's data, and a lookup of keys like `constructor` returns inherited properties because the substitution map is a plain object. Impact is limited to the respondent's own response (no cross-response or cross-tenant read), so it only lets a respondent pull other answers/labels of their own submission into a position of the PDF they did not intend.
- **Exploit scenario:** A respondent types `{{field_x}}` into a name field; the generated certificate prints another of their own answers (or `[Label]`) there. Cosmetic/integrity of the document only.
- **Recommended fix:** Substitute in a single pass (escape or neutralize `{`/`}` in values before inserting) and use `Object.create(null)`/`hasOwn` for the lookup maps.

## S10-14 — Info — No SSRF path found in pdfme template handling today; protection depends on pdfme behaviour and version
- **File:line:** `services/pdfTemplateService.ts:197-200,404-411,503-509`; installed `@pdfme/common` `getB64BasePdf` and `@pdfme/generator` `fetchFontData`
- **Description:** Traced every place the installed pdfme (6.2.2; the feature doc references 6.1.11) can fetch remotely. (a) `basePdf` URL fetch in `getB64BasePdf` is gated by `typeof window !== 'undefined'` and `isUrlSafeToFetch`, so a string `basePdf` is never fetched on the Node server (it is decoded as base64 instead, see S10-01). (b) Font URL fetch in the generator applies only to `options.font` entries, which the server builds from local files in `assets/fonts` (`getPdfFonts`), never from template content. (c) The `image`, `svg`, `qrcode`, `table` plugins read `content` as inline data; no `fetch` calls were found in `@pdfme/schemas` outside font loading. So user-supplied URLs do not reach the network. This is a safe-today conclusion that rests on pdfme internals.
- **Exploit scenario:** None today. A future pdfme upgrade, a change that passes template-supplied font data, or running the generator in a `window`-defined environment (e.g. jsdom tests) could reintroduce fetch-by-URL.
- **Recommended fix:** Add a regression test that `validatePdfTemplate` rejects string `basePdf` and any schema field containing URLs for fonts/images; re-audit `fetch(` in pdfme on each upgrade; keep fonts server-only.

## S10-15 — Info — Controls verified as correct (no finding)
- Every query/mutation in both resolver files loads the owning row and runs `requireAuth` + `checkFormAccess` at the correct level; tenancy follows `template.formId` / `generator.formId`, and `generatePdfFromResponse`, `previewPdfTemplate` and `generateSinglePdfForGenerator` all verify `response.formId === template/generator.formId` and exclude soft-deleted responses (`getResponseById` filters `deletedAt: null`; the generator path checks `response.deletedAt`).
- `createPdfGenerator` / `updatePdfGenerator` verify `template.formId === formId`, preventing a generator from pointing at another form's template (`pdfGeneratorService.ts:43-46,67-72`); duplication re-maps template ids per form.
- `previewPdfTemplate` requires EDITOR for a working-copy template and for `aiSampleData`, and gates AI with `checkAITokenBudget` / `recordAITokenUsage`; the uploaded base PDF is never taken from the client (`basePdf` is nulled and re-hydrated from R2 by `fileKey`).
- `createPdfTemplate` pins `fileKey` to the form's own `files/pdf-template-asset/{formId}/` prefix; `getBucketForKey` routes that prefix and `pdf-generated/` to the private bucket; downloads use short-lived presigned URLs (900 s).
- Generated object keys and download filenames are built from DB ids and a `[a-zA-Z0-9-_ ]` allow-list (`buildPdfFilename`, `buildGeneratorFilename`, ZIP name), so path traversal / zip-slip / header injection is not reachable via ZIP entries.
- `PdfGenerationResult` lists exclude soft-deleted responses; the per-run cap `MAX_RESPONSES_PER_RUN` and per-form template/generator caps exist (but see S10-04, S10-10).
- `copyPdfTemplatesToForm` turns `autoRunOnSubmit` off on clones and copies the asset under the new form's prefix (except the fallback in S10-09).
