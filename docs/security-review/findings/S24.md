## 3. Unauthenticated endpoint abuse inventory

Limiters in `index.ts`: `authLimiter`, `uploadLimiter`, `graphqlLimiter` are each 5000 requests per minute keyed on `req.ip` (`index.ts:137-162`), disabled in test. There is no `trust proxy` setting (S01-04, S04-06), so behind a load balancer the key is likely the proxy address and every visitor shares one bucket. All three use the in-process memory store (per replica, reset on deploy). No CAPTCHA, no per-form, per-session or per-recipient limit exists anywhere in the repo.

## Findings

### S24-01 — Medium — Respondent identity survives account deletion, and respondents have no erasure path

- **File:line:** `prisma/schema.prisma:195-196` (`respondentUserId`, `respondentEmail` with no relation), `lib/better-auth.ts:178-196` (the only `user.delete` hook), `graphql/resolvers/myResponse.ts:20-23` and `graphql/schema.ts:1927` (the respondent surface is a read query plus `editMyResponse`; nothing deletes).
- **Description:** On identity-gated forms every response stores a snapshot of the respondent's verified email and user id with no foreign key. When the respondent's account is deleted the hook only nulls `ipAddress` and `userAgent` in `response_edit_history`. The email snapshot, the user id and the full answers remain on a form owned by someone else, and the respondent has no mutation to delete or anonymise their own response or draft history. The respondent self-edit rows also keep the respondent's IP (`myResponse.ts:29`) until the account row is deleted.
- **Exploit scenario:** A respondent asks to be forgotten after submitting to a third-party form. The admin deletes the account, which removes sessions and drafts but leaves `respondentEmail`, the answers and the edit-history field changes in the form owner's data indefinitely, visible to every VIEWER. The platform cannot demonstrate erasure.
- **Recommended fix:** Add an `afterDelete` step (or a `SetNull` relation plus a nulling hook) that sets `respondentEmail` and `respondentUserId` to null on every response of the deleted user and scrubs `response_field_change` values for their edits. Offer a respondent-initiated "delete my response" mutation (soft delete plus the purge job from S14-06) and document the owner's role as controller.

### S24-02 — Medium — Response and form deletion never reach external copies, and stored third-party credentials are never revoked

- **File:line:** `plugins/core/events.ts:34-75` (the only events are `form.submitted`, `response.edited`, `plugin.test`), `graphql/resolvers/responses.ts:760-800` (delete path emits no event), `services/formService.ts:432-450`, `plugins/google-sheets/handler.ts`, `plugins/microsoft-sheets/handler.ts`, `plugins/webhook/handler.ts` (no delete or revoke operation); `grep -rni revoke` over `src` finds only form-permission revocation.
- **Description:** Every submission is pushed to places the platform does not control: rows appended to Google or Microsoft spreadsheets, webhook receivers, and emailed copies or PDFs. Deleting a response (or form, user or org) emits nothing to plugins or automations, so there is no way to remove or flag the external copy, and delivery logs (`plugin_delivery`) record that the data was sent but are themselves never purged. The OAuth tokens kept in `form_plugin.config` and `automation.graph` are removed from the DB on cascade but are never revoked at Google or Microsoft, so a leaked or backed-up token still reads and writes the user's spreadsheets after the form is gone.
- **Exploit scenario:** An owner deletes a response to satisfy an erasure request. The answers remain in the connected spreadsheet, in the webhook receiver and in the respondent's inbox copy, and the owner has no signal that this is so. After the org is deleted, a refresh token recovered from a database backup (stored in plaintext, S07-02, S14-05) still grants access to the former customer's sheets.
- **Recommended fix:** Add a `response.deleted` event (and form and org delete hooks) that plugins can handle (delete the Sheets row by stored row id, send a signed deletion webhook). Revoke OAuth refresh tokens at the provider when a plugin, automation, form or org is deleted. In the UI and docs, state which sinks cannot be recalled and warn before enabling them on forms that collect personal data.

### S24-03 — Medium — Platform-branded emails interpolate user-controlled strings into HTML without escaping (phishing from the trusted sender)

- **File:line:** `templates/invitationEmail.ts:18-33` (`inviterName` and `organizationName` in `subtitle` and `preheader`; `data.to` and `invitationUrl` in the body), `:41-46` (text), `services/emailService.ts:192-197` (org name in the subject), `templates/responseCopyEmail.ts:47-50` (`formTitle`), `templates/formPublishedEmail.ts:24,43` (`formTitle`). Contrast `templates/automationFailureEmail.ts:24-39` and `services/responseCopyService.ts:142-178`, which do escape.
- **Description:** The invitation template inserts the inviter's display name and the organization name into HTML as raw strings. Both are chosen by the attacker (account name at sign-up, organization name in `createOrganization`, with no character validation seen in `graphql/resolvers/better-auth.ts:81-103`). The response-copy template inserts the owner-controlled form title raw, while only the Q&A rows are escaped. The same pattern was already reported for billing mails (S12-12, S15-09) but not for these three high-volume templates, which are the ones sent to arbitrary third-party addresses.
- **Exploit scenario:** An attacker signs up with the name `<a href="https://evil.example">Security team: verify your account</a>` and an organization named `<img src="https://evil.example/p.gif">`. They invite a victim's address. The victim receives a message from the real Dculus sender with a legitimate-looking subject, the correct invitation link and an attacker link or tracking pixel inside the branded body, so mail filters and the user trust it. The same works with a crafted form title through the response-copy path (S04-07).
- **Recommended fix:** Escape every interpolated value in all templates through one shared `escapeHtml` (and URL-validate `href` values), strip control characters and angle brackets from the organization and user name at write time, and add a unit test per template that asserts markup in inputs is neutralised.

### S24-04 — Medium — Invitation email can be repeated to any address with no cooldown, cap or metering, so the organization endpoint is an unthrottled mail relay

- **File:line:** `lib/better-auth.ts:85-102` (no `invitationLimit` override; default 100 pending per org), `node_modules/better-auth/dist/plugins/organization/routes/crud-invites.mjs:125-160` (`resend: true` updates the expiry and sends the email again on every call; `cancelPendingInvitationsOnReInvite` also allows send, cancel, send), `:167-172` (the only cap), `index.ts:194` and S01-04 (the only rate limit), `lib/planLimits.ts:11-13` (the email quota does not cover auth or invitation mail).
- **Description:** Any caller with invite permission in an organization can send the invitation email to any address (recipients need not be users). The pending-invitation cap of 100 is the only guard; resending to the same address is explicitly supported and has no cooldown. The invitation mails are not counted in `emailsUsed`, and the HTTP rate limits are ineffective (S01-04: shared 5000/min bucket, spoofable XFF key, memory store). Organizations are cheap to create: sign-up with a verified email or the email-OTP path that auto-creates verified users (S01-06) yields one org per account, and accounts are unlimited. Combined with S24-03 the message body is also attacker-controlled.
- **Exploit scenario:** An attacker creates an organization, then loops `POST /api/auth/organization/invite-member` with `resend: true` against one victim address, or sprays 100 addresses per organization across many throwaway orgs. The platform's SMTP identity sends thousands of branded mails per hour containing attacker text, which gets the sender flagged or blocked, breaking OTP and reset mail for real users, and harasses the victim.
- **Recommended fix:** Give invitations their own limits: per organization per day and per inviter per hour, a minimum interval (for example 10 minutes) between resends to one address, and a per-recipient lifetime cap. Meter them against a separate abuse counter. Pair with the S01-04 fix (trusted client IP, shared store, per-email custom rules). Consider requiring a verified, non-disposable inviter email and a paid or aged account before allowing invitations to non-members at volume.

### S24-05 — Low — Draft and analytics retention depend on a 24-hour timer that is not run at startup, so the stated 30-day and 365-day limits are not reliably enforced

- **File:line:** `index.ts:483-487` (`setInterval(..., 24h).unref()` wraps both `cleanupOldAnalytics` and `deleteExpiredDrafts`; no initial call), `services/responseDraftService.ts:161-165`, `repositories/responseDraftRepository.ts` (delete by `expiresAt`), `services/analyticsService.ts:688-701`.
- **Description:** S14-14 covered the analytics half. The same timer also drives the draft purge, which means expired drafts (30-day policy, `schema.prisma:216-222`) stay in `response_draft` after every restart-heavy period. Reads are protected (`responseDraftService.ts:46,` `isExpired`), so exposure is limited to retention, not disclosure. Nothing else enforces the policy and there is no cross-instance lock, so each replica runs it independently.
- **Exploit scenario:** The service redeploys several times a week (the repo auto-deploys `main`), so the 24-hour timer rarely fires. A privacy audit or erasure check finds drafts older than 30 days still containing respondents' partial answers.
- **Recommended fix:** Run both jobs at startup and from a single-runner scheduler (the repo already uses pg-boss for automations), and record a last-run metric so a missed run alerts.

### S24-06 — Low (PLAUSIBLE for `verification`) — Authentication side tables with PII are never purged

- **File:line:** `prisma/schema.prisma:70-85` (`session.ipAddress`, `.userAgent`), `:126-142` (`invitation.email`), `:244-265` (`response_file_export` with `filename`, `fileKey`, `errorMessage`), `:339-349` (`verification`); no `deleteMany` on these models exists outside tests and a commented seed block (`grep -rnE "session\.deleteMany|verification\.deleteMany|invitation\.deleteMany|responseFileExport" src`).
- **Description:** The only retention jobs in the code are analytics, drafts and temp R2 objects. Expired sessions (with the user's IP and user agent), expired or cancelled invitations (the invitee's email, including people who never signed up), finished file-export job rows and, unless better-auth removes them on read, expired OTP and token rows all accumulate for the life of the database. better-auth deletes a session when it is presented and found expired, but sessions that are never presented again stay. The IP column is populated by better-auth by default. I did not confirm the exact better-auth cleanup behaviour for `verification`, hence PLAUSIBLE there.
- **Exploit scenario:** A database leak or subject-access request surfaces years of session IPs and invitee addresses for people who have long left, with no business need and no documented retention period.
- **Recommended fix:** Add a daily purge: sessions expired more than 30 days ago, invitations expired or non-pending more than 30 days ago, verification rows past expiry, export job rows older than the export TTL. Consider not storing the full session IP (truncate or hash), and document the retention schedule in one place.

### S24-07 — Low (PLAUSIBLE) — `uploadLimiter` is mounted at `/`, so it acts as a hidden catch-all limiter ahead of GraphQL, the billing webhook and OAuth callbacks

- **File:line:** `index.ts:239` (`app.use('/', uploadLimiter, uploadRouter)`), `:240-246` (routes registered afterwards), `:362` (`/graphql` registered later), `:146-153`.
- **Description:** Because the limiter is attached to the root path and runs before every later route, every request that does not match an earlier route (`/api/auth/*`, `/respondent-oauth-callback`, `/health`) counts against the same 5000/min `uploadLimiter` key. That includes `/graphql`, `/api/webhooks/chargebee`, the OAuth callbacks, Pixabay and Pexels, and requests that eventually 404. The key is `req.ip`, which behind the proxy is probably one shared address (S01-04). S12-09 records that the Chargebee webhook has no rate limit; in fact it shares this bucket, which is worse because it can be starved by unrelated anonymous traffic. This is PLAUSIBLE because the effect depends on the proxy topology.
- **Exploit scenario:** An attacker sends about 5000 cheap requests a minute to any unauthenticated path. The shared bucket returns 429 for all respondents on `/graphql` and for Chargebee's webhook deliveries, so renewals and cancellations are delayed and paid orgs can be mis-gated (S12-03, S12-05) until Chargebee retries succeed.
- **Recommended fix:** Mount the upload limiter only on `/upload`. Give each public surface its own limiter with route-appropriate keys, exempt the webhook (authenticate it by credential, not by IP bucket), set `trust proxy` correctly, and move to a shared store.

### S24-08 — Low (PLAUSIBLE) — Unauthenticated utility endpoints have no endpoint-specific throttle despite doing DB or outbound work

- **File:line:** `routes/health.ts:7-14` and `index.ts:238` (mounted before any limiter; each call runs `SELECT 1`), `routes/google-oauth.ts:15-49` and `routes/microsoft-oauth.ts:14-50` (anonymous `callback` performs a token exchange with the server's client secret for whatever `code` is supplied).
- **Description:** `/health` is intentionally open but sits outside every limiter, and the production pool is very small (S04-06 notes a pool max of 2, S14-09), so a flood of health checks queues behind or ahead of real queries. The OAuth callbacks are open to anyone, need no state binding (S07-05), and each hit triggers an outbound request to Google or Microsoft with the platform's OAuth client credentials. Repeated invalid codes can trip the provider's abuse protections for the client, breaking the connect flow for all customers. PLAUSIBLE because the edge may filter these paths.
- **Exploit scenario:** An attacker loops `GET /api/integrations/google/callback?code=x` and `GET /health`, exhausting the DB pool and getting the Google OAuth client rate-limited, so health probes fail (container restarts) and customers cannot connect Sheets.
- **Recommended fix:** Make `/health` a liveness check that does not hit the DB (separate readiness with caching, for example 5 s), rate limit both OAuth callbacks per IP with a small bound, and bind the callback to a server-issued `state` (S07-05).

### S24-09 — Info — No data-subject-request tooling, retention policy or processor register exists in the repository

- **File:line:** whole repo (`grep` for GDPR, erasure, data subject, retention finds only `PRODUCTION_READINESS.md` and `apps/form-viewer/ANALYTICS.md` mentions and the analytics and draft code above); no admin or owner "export my data" or "erase subject" operation; no consent mode (S17-06).
- **Description:** There is no way for an owner or admin to locate every record for one data subject (answers, respondent email, edit history, delivery logs, automation runs, PDFs, files, sheet rows), nor to erase them atomically, and no documented retention schedule or list of sub-processors (Cloudflare R2, SMTP provider, Chargebee, Sentry, AI provider, Google and Microsoft via plugins). Many gaps above follow from this.
- **Exploit scenario:** A data subject request cannot be answered within the statutory period without manual database work that will miss the tables listed in the matrix above.
- **Recommended fix:** Build a single "erase subject" service that takes a respondent email or user id and removes or anonymises every store in section 2, plus an export counterpart. Publish a retention schedule and processor list, and have the form owner-facing settings expose the retention choices (TTL for answers, deliveries and runs).
