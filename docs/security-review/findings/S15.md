# S15 — Admin surface

**Reviewer:** general-purpose agent. **Mode:** review-only, no source changes.
**Scope reviewed:** `apps/backend/src/graphql/resolvers/admin.ts`, `apps/backend/src/scripts/*` (mainly `setup-admin.ts`, `create-e2e-user.ts`), `apps/admin-app/src/**` (auth, routing, Apollo client, email preview), the admin parts of `lib/better-auth.ts`, `services/auditLogService.ts`, `repositories/auditLogRepository.ts`, and the `ADMIN_*` wiring in `infrastructure/multi-cloud/terraform/azure`. The repo-root `scripts/` directory has no admin scripts (only `local-prod.sh`, `setup-worktree.sh`, `write-runtime-config.sh`).

## Verified controls (no finding)

- All 17 operations in `admin.ts` (8 queries, 9 mutations) begin with `requireAdminRole(context)`. It rejects a missing user with `AUTHENTICATION_REQUIRED` and any role other than `admin` or `superAdmin` with `NO_ACCESS`, using `createGraphQLError` and `GRAPHQL_ERROR_CODES`.
- Role comes from `context.auth.user.role` (the server session), never from request args.
- Self-assigned role: the better-auth admin plugin defines `role` with `input: false` (`better-auth/dist/plugins/admin/schema.mjs:4-8`), `defaultRole` is `'user'` (`lib/better-auth.ts:121`), and no custom `additionalFields` on user sets role. A regular user cannot set their own `role` at sign-up or via `update-user`.
- No ban, impersonate or role-change mutation exists in the app's GraphQL schema, and `admin-app` never calls `/api/auth/admin/*`.
- Paging bounds exist: `adminOrganizations` and `adminUsers` clamp `limit` to 100.
- Prisma is used with typed `contains` filters. There is no raw SQL in `admin.ts`.
- The admin-app route guard (`App.tsx`, `isAdmin`) is cosmetic only, and the backend re-checks every call, so UI-only gating is not a hole. `EmailPreviewsPage` renders static sample data in an `iframe` with `sandbox="allow-same-origin"` and no `allow-scripts`.
- `adminUserById` and `adminUsers` do not return `role`, password hashes, session tokens or Chargebee secrets. `adminOrganizationById` returns Chargebee customer and subscription IDs, which is acceptable for admins.
- The bootstrap script has no default credentials. It exits if `ADMIN_EMAIL`, `ADMIN_PASSWORD` or `ADMIN_NAME` is unset. Terraform variables default to empty strings.

## Findings

### S15-01 — Medium — Bootstrap `ADMIN_PASSWORD` is injected as a plain env var into the running backend container

- **File:line:** `infrastructure/multi-cloud/terraform/azure/main.tf:215-222` (also `variables.tf:175-187`)
- **Description:** The superAdmin bootstrap email and password are set as plain `env { name/value }` entries on the production backend container app, not as a secret reference. The running backend never reads `ADMIN_PASSWORD`; only `scripts/setup-admin.ts` does, and it is a one-time job. The credential therefore sits permanently in the container app definition, ARM and portal revision history, and the process environment of an internet-facing server, and it can leak through anything that dumps `process.env` or exposes crash or diagnostic output. The other secrets in this file use the same pattern, so this is a pre-existing convention (see S22); it matters more for this one because it grants superAdmin.
- **Exploit scenario:** A person with only read access to the Azure resource (for example Reader on the resource group, a CI log that prints `terraform show`, or an SSRF or env-dump bug) reads `ADMIN_EMAIL` and `ADMIN_PASSWORD` and signs in to the admin-app as superAdmin. If the password is reused or never rotated, the exposure lasts indefinitely.
- **Recommended fix:** Do not pass `ADMIN_*` to the long-running container. Run `admin:setup` as a one-shot job or release step with the secret supplied transiently, then clear the variables. If it must stay in Terraform, use a Container Apps `secret` plus `secret_name` references. Rotate the password after bootstrap and move to named per-person admin accounts.

### S15-02 — Medium — `adminCancelSubscription` and `adminReactivateSubscription` write no audit log entry

- **File:line:** `apps/backend/src/graphql/resolvers/admin.ts:1009-1043`
- **Description:** Every other billing mutation (`adminCreatePlan`, `adminUpdatePlan`, archive, unarchive, `adminAssignPlan`, `adminSetEnterprisePlan`, `adminResetUsage`) calls `auditLogService.logAction`. These two do not. They cancel or reactivate a customer's paid Chargebee subscription and then flip `status` in Postgres. The resolver does not even bind the admin (`requireAdminRole(context);` with the result discarded), so the application keeps no record of which admin did it.
- **Exploit scenario:** A rogue or compromised admin cancels a competitor-owned or high-value org's subscription (`adminCancelSubscription(orgId)`). Chargebee will show the API call but not which human admin triggered it, and the application's audit table has no trace, so the action cannot be attributed.
- **Recommended fix:** Capture `const admin = requireAdminRole(context)` and call `auditLogService.logAction({ action: 'subscription_cancelled' | 'subscription_reactivated', actorId: admin.id, resourceType: 'Organization', resourceId: orgId, metadata: { previousStatus, chargebeeSubscriptionId, changedBy: admin.email } })`. Consider requiring `superAdmin` for cancel (see S02-11).

### S15-03 — Low — `setup-admin.ts` logs the plaintext password and the full sign-up result

- **File:line:** `apps/backend/src/scripts/setup-admin.ts:76` (`logger.info('Auth result:', result)`) and `:130` (`logger.info(\`   Password: ${adminPassword}\`)`)
- **Description:** On success the script prints the admin password to the logger, and on the new-user path it logs the whole `auth.api.signUpEmail` result, which can include a session token or user record. If the script is run in CI, a container job or a shared terminal, these lines land in build or log storage. The email is printed too.
- **Exploit scenario:** Anyone with read access to the CI or deployment log of the bootstrap run obtains a working superAdmin credential, or a session token that is valid for up to 7 days.
- **Recommended fix:** Remove the password line and the `result` log. Log only a success message and the email. Do not log objects returned from the auth API.

### S15-04 — Low — Audit entries are written after the side effect, and a failed write is surfaced as an error for an action that already happened

- **File:line:** `apps/backend/src/graphql/resolvers/admin.ts` — for example `adminAssignPlan` (calls `changeOrganizationPlan`, then `logAction`), `adminSetEnterprisePlan` (`setEnterpriseSubscription`, then `logAction`, `:884-`), `adminResetUsage`. `services/auditLogService.ts` deliberately does not swallow errors.
- **Description:** The Chargebee plan change, enterprise setup (including the email to the org owner) or usage reset has already committed externally when `logAction` runs. If the audit insert fails (DB blip), the mutation returns an error even though the change took effect, and there is no audit record. There is no write-ahead intent record and no transaction spanning Postgres and Chargebee.
- **Exploit scenario:** Mostly an integrity and repudiation gap. An admin who can induce or wait for audit-table failures, or an outage during the call, performs a billing change with no trace. The caller also sees a failure and may retry, doubling the effect for non-idempotent actions such as the owner email.
- **Recommended fix:** Write an `*_requested` audit row (or a pending row) before the external call and update or append a result row after. Alternatively do the DB mutation and audit insert in one `prisma.$transaction` and treat the Chargebee call as the final step.

### S15-05 — Low — Cross-tenant PII reads by admins are not audited

- **File:line:** `apps/backend/src/graphql/resolvers/admin.ts:231` (`adminOrganizations`), `:411` (`adminUsers`), `:484` (`adminUserById`), `:566` (`adminOrganizationById`)
- **Description:** Any `admin` can list every user (name, email, verified flag, avatar) and every organization with its members' emails, plus form titles and publish state, and Chargebee customer and subscription IDs. None of these reads write an audit record. The `AuditLog` model has no read path and `auditLogRepository` is create-only, so even the writes cannot be reviewed from the app.
- **Exploit scenario:** A support-level admin enumerates all customer emails and org membership for resale or phishing. There is no record of which admin looked at which org or user.
- **Recommended fix:** Log access to detail views (`adminUserById`, `adminOrganizationById`) with `actorId` and the target ID, and consider rate-limiting or alerting on bulk list reads. Expose an audit-log viewer restricted to `superAdmin`. Consider separating a billing-support role that cannot see member emails.

### S15-06 — Low — Enterprise deal mutation has no upper bounds and lets one admin activate an unlimited free plan instantly

- **File:line:** `apps/backend/src/graphql/resolvers/admin.ts:884-` (`adminSetEnterprisePlan`); related validation in `validatePlanLimits` / `validatePlanPrices` (`:62-100`)
- **Description:** Validation only requires non-negative integers (and null for unlimited). With `priceInSmallestUnit: 0` the plan is set active immediately (`checkoutUrl: null`), and all limits can be `null` (unlimited views, submissions, emails and AI credits). There is no maximum on price or limits (`Number.isInteger` accepts very large values), no two-person control, and the role is plain `admin` (S02-11). `adminCreatePlan`/`adminUpdatePlan` can also set a plan to zero-cost prices, and `adminUpdatePlan` backfills existing organizations (`backfilledOrganizations`).
- **Exploit scenario:** A malicious or compromised `admin` account gives any org (including one they control) an unlimited, free enterprise plan, or edits a shared plan's limits so all subscribers' limits change. This is an audited action (`enterprise_plan_set`, `plan_updated`), so it is detectable but not prevented.
- **Recommended fix:** Restrict enterprise and plan-catalog mutations to `superAdmin`. Add sane maxima for price and limits. Consider an approval step for zero-price deals.

### S15-08 — Low — `setup-admin.ts` silently promotes any existing account to `superAdmin`, resets its password and force-verifies the email, without revoking existing sessions

- **File:line:** `apps/backend/src/scripts/setup-admin.ts:34-72`
- **Description:** If a user with `ADMIN_EMAIL` already exists, the script sets `role: 'superAdmin'` and `emailVerified: true`, overwrites the credential password hash, and does not delete existing sessions, linked social accounts, or API tokens for that user. Previously issued sessions for that account therefore become superAdmin sessions as soon as the role cache refreshes.
- **Exploit scenario:** If the configured `ADMIN_EMAIL` is a mistyped or shared address that already belongs to a normal customer account, that customer is silently given platform-wide superAdmin and keeps their existing logged-in sessions. I could not find a way for an outside attacker to exploit this without control of the bootstrap environment, so impact depends on misconfiguration.
- **Recommended fix:** Require an explicit `--promote-existing` flag, revoke all sessions for the target user after the role or password change (`prisma.session.deleteMany({ where: { userId } })`), and log the promotion as an audit entry (`actorId: null`, `action: 'superadmin_bootstrap'`).

### S15-09 — Info — Enterprise payment email interpolates organization and user names into HTML unescaped

- **File:line:** `apps/backend/src/services/chargebeeService.ts:435-443`
- **Description:** `owner.name` and `org?.name` are placed directly into the HTML body. Both are user-controlled (org name by the org owner, display name by the user). The email goes to the org owner's own address, so the practical impact is self-injection or a malformed email, not cross-user. The checkout URL comes from Chargebee.
- **Recommended fix:** HTML-escape interpolated values (the repo likely already has an escape helper used by other email templates).

### S15-10 — Info — `adminSystemHealth` returns raw error strings, and `admin.ts` converts NOT_FOUND to INTERNAL_SERVER_ERROR

- **File:line:** `apps/backend/src/graphql/resolvers/admin.ts:562` (`detail: String(reason)`); `:351` and `:658` (`catch` re-throws every error, including the intentional `NOT_FOUND`, as `INTERNAL_SERVER_ERROR`; same pattern in `adminOrganization`, `adminUserById`)
- **Description:** Failed health checks put the raw rejection text (possibly a database host or connection string fragment) in the response. This is visible to admins only, so low risk. The catch-all also hides real 404s from the admin-app and makes error handling and monitoring noisy.
- **Recommended fix:** Return a generic `detail` and log the raw error server-side. Re-throw `GraphQLError`s unchanged in the catch blocks.
