# S23 — Dependencies & supply chain: Security Findings

Scope: root `package.json`, `pnpm-lock.yaml` (lockfileVersion 6.0, pnpm 8), `pnpm-workspace.yaml`, and `package.json` of `apps/{backend,form-app,form-viewer,admin-app}` and `packages/{types,utils,ui,plugins}`. Supporting reads: `apps/backend/Dockerfile`, `.github/workflows/{build,multi-cloud-deployment}.yml`, `.github/dependabot.yml`, and call sites of the affected libraries. Review-only; no source, `package.json` or lockfile was modified, and no install or update was run.

Method: `pnpm audit --json` was run read-only (it reached the registry successfully; raw output kept in the scratchpad, not the repo). It returned **64 unique advisories: 3 critical, 22 high, 33 moderate, 6 low**, over 2048 dependencies. The audit does not separate dev from prod, so each advisory was triaged by hand: dependency path, then whether the vulnerable feature is configured or reachable in this code. Cross-referenced against S01–S19.

## Findings

### S23-01 — High (PLAUSIBLE reachability) — Exact-version overrides pin runtime dependencies at vulnerable releases (nodemailer, undici, dompurify) and one override downgrades a declared dependency
- **File:line:** `package.json:129-166` (`pnpm.overrides`: `nodemailer: 9.0.3`, `undici: 7.29.0`, `dompurify: 3.4.16`, `postcss: 8.5.23`, `better-call: 1.3.7`, `@better-fetch/fetch: 1.3.1`, `path-to-regexp: 0.1.13`); `apps/backend/package.json` (`"nodemailer": "^9.0.5"`); `pnpm-lock.yaml:40,45,478-480,1227,15149`.
- **Description:** These overrides were added as security pins, but exact pins freeze the version at the moment they were written. The audit now flags them: nodemailer 9.0.3 has 14 advisories (2 high: quadratic backtracking in the address parser, fixed in 9.1.0 and 10.0.6; the rest moderate, mostly recipient/domain validation bypasses), undici 7.29.0 has 18 (6 high, fixed in 7.29.1 or 7.30.1) and dompurify 3.4.16 has 3 (fixed in 3.4.17). Because the override beats the dependency range, `pnpm update` and Dependabot cannot lift them. The backend even declares `nodemailer ^9.0.5`, but the lockfile importer records the specifier as `9.0.3`: the override silently downgrades a version the maintainers asked for. Several other overrides use open-ended `>=` ranges (S23-12), so the pin style is inconsistent.
- **Exploit scenario:** `apps/backend/src/services/emailService.ts` hands recipient addresses that originate from users (invitations, plugin email notifications that can target respondent-provided email fields) to `sendMail`. A crafted address string can hit the quadratic address-parser path and burn CPU on the single backend process that also serves GraphQL and Hocuspocus (DoS), or exploit the recipient-domain validation bypasses to deliver mail to a domain an allow-list was meant to block. Reachability depends on which of these code paths a given advisory touches and on upstream validation of addresses, which was not traced per advisory, hence PLAUSIBLE. undici is only reached through `@ai-sdk/provider-utils` (S23-08).
- **Recommended fix:** Replace exact pins by a floor with a justified upper bound, or remove the override once the direct dependency range already excludes the vulnerable versions (for nodemailer, delete the override so `^9.0.5` resolves, then move to `>=10.1.4`). Move `dompurify` to `>=3.4.17`, `undici` to `>=7.30.1`. Add a comment per override naming the advisory ID, so each can be dropped when obsolete. Re-run `pnpm audit` after the change.

### S23-02 — High — `pnpm.overrides` in `package.json` is ignored by pnpm 9/10/11; only the pinned pnpm 8.15.0 honors it, and that version is end of life
- **File:line:** `package.json:128` (`"pnpm": { "overrides": ... }`), `package.json:121` (`"packageManager": "pnpm@8.15.0"`), `apps/backend/Dockerfile:9-12`, `.github/workflows/multi-cloud-deployment.yml:441-444,1566-1569` (`version: "8.15.0"`), `pnpm-lock.yaml:1-47` (`overrides:` block).
- **Description:** Verified. Running `pnpm` in this repository on the developer machine (global pnpm 11.17.0, checked with `pnpm -v` outside the repo) prints: `The "pnpm" field in package.json is no longer read by pnpm. The following keys were ignored: "pnpm.overrides"`. In the repo, `pnpm -v` then reports 8.15.0 (the `packageManager` value). The lockfile has a matching `overrides:` section and the resolved versions match the pins (for example `nodemailer 9.0.3`, `undici 7.29.0`, `dompurify 3.4.16`), so under pnpm 8.15.0 (CI, Docker image, `build.yml`) the overrides are applied today. The exposure is therefore not "no pins now", it is that all ~38 security pins depend on a single, hand-pinned, EOL toolchain version (pnpm 8, lockfile v6). The Dockerfile comment confirms newer pnpm already breaks against this lockfile. Any move to pnpm 9+ (or a developer re-resolving the lockfile with a newer global pnpm without Corepack) drops every pin silently: `pnpm install` would still succeed, the warning is easy to miss, and transitive packages that were forced to patched versions (`tar`, `qs`, `jws`, `lodash`, `follow-redirects`, `tar-fs`, `yauzl`, `handlebars`, `flatted`, `defu`, `rollup`, `better-call`, `path-to-regexp`) could regress to the vulnerable versions their parents declare.
- **Exploit scenario:** No direct attacker action. A routine tooling upgrade (the Dockerfile or CI pnpm bump that has to happen sooner or later because pnpm 8 is unsupported) regenerates the lockfile without the pins. The result is a build that passes CI and deploys with previously fixed vulnerabilities back in the production image, for example `path-to-regexp` 0.1.x ReDoS or `jws` signature handling regressions, with no failing signal beyond a one-line warning.
- **Recommended fix:** Move the overrides to `pnpm-workspace.yaml` under `overrides:` (the supported location for pnpm 10+, and read by pnpm 9 as well when the `pnpm` field is absent), plan the upgrade to a supported pnpm with a regenerated lockfile, and add a CI step that fails if `pnpm install` prints the "no longer read" warning or if the lockfile `overrides:` block is empty. Keep Corepack on in CI and document it so developers do not run a different pnpm.

### S23-03 — Medium (PLAUSIBLE) — Runtime `body-parser` (express 1.20.6 and Apollo's 2.3.0) has a high-severity DoS; `express.json` accepts 10 MB unauthenticated bodies
- **File:line:** `apps/backend/src/index.ts:231` (`app.use(express.json({ limit: '10mb' }))`), Apollo Server express4 integration (`index.ts` Apollo middleware), `pnpm-lock.yaml` (`body-parser@1.20.6`, `body-parser@2.3.0`); advisory GHSA-27r3-jxmh-p828 (fixed in 1.20.9 and 2.4.0).
- **Description:** The audit reports a denial of service in body-parser through trailing bytes after a parsed body. Both copies are in the production graph: express 4.22.2 brings 1.20.6 and `@apollo/server` 5.5.1 brings 2.3.0. The JSON body parser is applied globally and the public GraphQL mutations (form view tracking and anonymous submission, see S04) sit behind it. The exact trigger conditions were not reproduced.
- **Exploit scenario:** An unauthenticated client sends requests with crafted bodies to `/graphql`, as described by the advisory, and ties up CPU or memory of the single backend process shared by GraphQL and Hocuspocus. The rate limiter (S01-04) counts requests, not cost.
- **Recommended fix:** Override `body-parser` to `>=1.20.9` for the 1.x line and `>=2.4.0` for the 2.x line (using range selectors such as `body-parser@<1.21: 1.20.9`), or move to Express 4.22.x releases that bundle the fix. Lower the global JSON body limit (S04-03, S05).

### S23-04 — Medium — CI dependency audit is advisory only: `continue-on-error: true`, threshold `high`, run after the build
- **File:line:** `.github/workflows/build.yml:117-119` (`pnpm audit --audit-level=high` with `continue-on-error: true  # Don't block on audit warnings initially`).
- **Description:** The audit step exists but cannot fail the pipeline, so the current 22 high and 3 critical advisories (S23 raw results) ship to dev and, via `release.yml`, to production with no gate or alert. No other scanning of dependencies is configured: `.github/dependabot.yml` lists only the `npm` ecosystem for `/` (S23-13), and CodeQL analyses first-party code, not dependency CVEs. The comment says "initially", so the exemption has become permanent.
- **Exploit scenario:** A newly disclosed critical advisory in a runtime dependency (for example in `express`, `better-auth` or `@apollo/server`) is published. The step logs it, the build stays green, and a release goes out unchanged. The team learns of it only if someone reads the job log.
- **Recommended fix:** Make the step blocking for production dependencies (`pnpm audit --prod --audit-level=high`) with a short, reviewed allow-list file for accepted advisories (each with an expiry date), keep a separate non-blocking run for dev dependencies, and run it on a nightly schedule so new advisories surface without a code change. Enable GitHub Dependabot security alerts and security updates for the repository.

### S23-05 — Medium (PLAUSIBLE) — `zod` 4.6.5 memory-exhaustion advisory on server-side validation
- **File:line:** `pnpm-lock.yaml` (`zod@4.6.5`, direct dependency of `apps/backend`, `packages/types`, `packages/ui`, `apps/form-app`); advisory GHSA-mrhx-c7xc-m3w5 (fixed in 4.6.6). Backend usage: 7 files import `zod` under `apps/backend/src`.
- **Description:** The audit reports that zod can exhaust memory while validating oversized constrained collections (for example arrays or sets with size constraints). Version 4.6.5 is also what every override floor (`zod >=4.4.3`) resolves to today, so a plain `pnpm update zod` would fix it.
- **Exploit scenario:** If an unauthenticated or low-privilege endpoint validates an attacker-supplied array or record with a zod schema that carries size constraints (form schema, quiz grading, plugin config, AI tool input), a large payload within the 10 MB body limit could drive memory use up. Which schemas see attacker-controlled collections was not enumerated, hence PLAUSIBLE.
- **Recommended fix:** Bump to `zod >=4.6.6` in all package manifests (and keep a single version across the workspace). Cap array sizes at the transport level before validation.

### S23-06 — Medium — DOMPurify 3.4.16 (audit "critical") is used with default settings, so the exploitable options are not enabled; the version still needs to move
- **File:line:** `apps/form-app/src/components/form-builder/field-settings-v2/RichTextFieldSettings.tsx:2,45`, `packages/ui/src/layouts/shared/ThankYouScreen.tsx:2,184`, `package.json` override `dompurify: 3.4.16`; `@pdfme/schemas@6.2.2 > dompurify@3.4.16` in the backend; GHSA-cg2g-xh64-v4q7 (critical), GHSA-mrv2-3pqr-j5jr (high), GHSA-c6gr-qvv4-5v3f (low); fixed in 3.4.17.
- **Description:** The critical advisory concerns the `SAFE_FOR_TEMPLATES` option and the high one concerns `IN_PLACE` use with hooks. A search of `apps` and `packages` found no use of either option, and the two call sites call `DOMPurify.sanitize(html)` with defaults, so the headline bypass is not reachable as written. The low-severity SMIL attribute guard skip applies only with a non-default parser media type. The residual risk is that the sanitizer is the only barrier on user-authored rich text rendered to anonymous respondents (`ThankYouScreen`), so any further DOMPurify bypass is stored XSS in `form-viewer`. The exact pin (S23-01) prevents the patch from arriving on its own.
- **Exploit scenario:** An EDITOR stores rich thank-you content; if a future DOMPurify bypass affects default configuration, every respondent who sees the thank-you screen executes it. Today this needs a bypass beyond the three listed.
- **Recommended fix:** Move to `dompurify >=3.4.17` (drop the exact pin) and keep default configuration. Cross-reference S19-02 and S19-06 for the other sanitizer weaknesses (hand-rolled blocklist in `FormFieldRenderer`, unsanitized template HTML).

### S23-07 — Low (PLAUSIBLE) — `proxy-addr` 2.0.7 (audit "critical", IPv4-mapped IPv6 trust bypass) is not reachable because no trusted proxy is configured
- **File:line:** `pnpm-lock.yaml` (`proxy-addr@2.0.7` via `express@4.22.2`); `apps/backend/src/index.ts` (no `trust proxy` setting; a search of `apps/backend/src` found none); `apps/backend/src/graphql/resolvers/analytics.ts:46,147`, `responses.ts:568,741` (read `x-forwarded-for` directly).
- **Description:** The advisory (GHSA-jqcg-44mw-7w3h, fixed in 2.0.8) concerns IP spoofing when a `trust proxy` subnet is configured. Express defaults to `trust proxy = false`, so `req.ip` ignores forwarded headers and the trust-subnet logic is not evaluated. The impact is therefore limited to a future change (someone enabling `trust proxy` with a subnet in order to fix rate limiting behind Azure Container Apps or Cloudflare). The related, separate defect that the app trusts the raw `x-forwarded-for` header for analytics and submission IP is covered in S04/S24, not here.
- **Exploit scenario:** None today. If `app.set('trust proxy', '<subnet>')` is added later, a client could send an IPv4-mapped IPv6 address that is treated as trusted and spoof its source IP, defeating the per-IP rate limiters.
- **Recommended fix:** Override `proxy-addr` to `>=2.0.8` anyway, so the later `trust proxy` change is safe by default.

### S23-08 — Low (PLAUSIBLE) — `undici` 7.29.0 (18 advisories) is a runtime dependency of the AI SDK provider utilities
- **File:line:** `pnpm-lock.yaml:1227` (`@ai-sdk/provider-utils@5.0.57 > undici@7.29.0`, `dev: false`), `apps/backend/package.json` (`@ai-sdk/azure`, `@ai-sdk/openai`, `@ai-sdk/provider-utils`), `apps/backend/src/lib/ai.ts:31,37` (uses global `fetch`).
- **Description:** 18 undici advisories apply to 7.29.0 (6 high: TLS validation bypass via dropped options, WebSocket and decompression DoS, cache poisoning and cross-user disclosure through the cache interceptor, response splitting). The package is in the production graph but the backend's own code calls the Node built-in `fetch`, and the AI endpoints are fixed operator-configured URLs, not user-controlled. A second copy comes in through `jsdom` (dev only). Reachability depends on whether `provider-utils` constructs undici dispatchers, which was not verified.
- **Exploit scenario:** Requires an attacker able to influence the upstream AI endpoint response or the network path to it (compromised or misconfigured endpoint, MITM if a TLS bypass applied). Low likelihood for a fixed Azure/OpenAI endpoint.
- **Recommended fix:** Remove the exact `undici: 7.29.0` override and move to `>=7.30.1` (see S23-01). Confirm with `pnpm why undici` which parents actually use it.

### S23-09 — Medium — Backend production image installs the whole workspace toolchain (dev dependencies and `packages/ui` tooling) and runs every dependency install script
- **File:line:** `apps/backend/Dockerfile:15-27` (`COPY packages/`, `RUN pnpm install --frozen-lockfile` without `--prod`, `--ignore-scripts` or `--filter`), `package.json` (no `.npmrc`, `onlyBuiltDependencies`, or `ignore-scripts`), `pnpm-lock.yaml` (`requiresBuild: true` packages).
- **Description:** The image copies `packages/` and the root manifests, then installs all workspace projects present: `apps/backend` and every `packages/*` project, including their dev dependencies. That adds Storybook 10.6.1 (audit "critical" and "high", dev server issues), Vite 7.3.6, Vitest, jsdom, nodemon, tsx, supertest, `@better-auth/cli` and a darwin-only native binding into an image that serves the public API. Together with `/app` being chowned to the runtime user, this widens both the CVE surface and the post-exploitation toolbox. pnpm 8 runs every dependency's lifecycle scripts by default and nothing restricts them: `requiresBuild` packages in the lock include `prisma`, `@prisma/client` (5.22.0 and 6.19.2), `@prisma/engines`, `better-sqlite3`, `mongodb-memory-server`, `@sentry/node-cpu-profiler`, `lefthook`, `@apollo/protobufjs`, `es6-error`, `uglify-js`, `yaml`, esbuild per-platform packages. A compromised version of any of them executes during `docker build` and CI install with the runner's environment.
- **Exploit scenario:** A malicious release of any transitive package (account takeover or typosquat of a build-script package) runs arbitrary code at install in CI, where the workflow later holds Azure and registry credentials, and inside the image builder. Separately, an RCE in the backend finds a ready-made set of build tools (tsx, nodemon, esbuild, Prisma engines) in the container.
- **Recommended fix:** Build in a multi-stage Dockerfile and copy only `pnpm deploy --prod` output (production dependencies of `@dculus/backend`) into the final stage. Set `ignore-scripts=true` in `.npmrc` and explicitly rebuild only what is required (`prisma generate`, `esbuild`). On pnpm 10+, use `onlyBuiltDependencies`. Remove `mongodb-memory-server` and `better-sqlite3` from the graph if unused (S23-14).

### S23-10 — Low — Unmaintained, deprecated or end-of-life packages in security-relevant positions
- **File:line:** `apps/backend/package.json` (`exceljs 4.4.0`, `safe-regex ^2.1.1`, `graphql-depth-limit ^1.1.0`, `jsonwebtoken 9.0.3`), root `package.json` (`eslint ^8.57.1`, `supertest ^6.3.4`, `packageManager pnpm@8.15.0`), `pnpm-lock.yaml` (`deprecated:` markers at lines 3879, 3895, 11600, 12188, 12290-12326, 16696-16703, 17404).
- **Description:** `exceljs` has not had a release since 2023 and pulls `archiver@5.3.2`, `unzipper@0.10.14`, `fstream@1.0.12` ("no longer supported"), old `glob`/`rimraf` and `jszip`. In this codebase exceljs is used to write exports (`unifiedExportService.ts`); no read/load of user-supplied workbooks was found, so the parser-side issues of that stack are not reachable. `safe-regex@2` (last release 2020) is the only ReDoS guard for quiz regex grading and is demonstrably insufficient (S19-01). `graphql-depth-limit@1.1.0` (2019) is the only query-shape control and has known gaps (S05). ESLint 8, supertest 6 (superagent 8, flagged deprecated) and pnpm 8 are EOL and dev-side only, apart from pnpm (S23-02).
- **Exploit scenario:** No specific exploit. The risk is that a vulnerability in these packages will not be fixed upstream, and two of them are load-bearing security controls.
- **Recommended fix:** Plan replacements: `exceljs` to a maintained writer or pin and review its archive dependencies; RE2 for regex matching (S19-01); a maintained depth/complexity limiter (S05). Upgrade ESLint and supertest as part of toolchain refresh.

### S23-11 — Low — Dev-tool advisories in the audit (storybook, vite, vitest mocker, js-yaml, brace-expansion, qs, deepmerge, postcss-selector-parser) are build or test only
- **File:line:** `packages/ui/package.json` (`storybook ^10.6.1`, `@storybook/*`), `apps/*/package.json` (`vite ^7.3.5`, `vitest ^4.1.11`), root `package.json` (`eslint`, `jest`, `supertest`, `@istanbuljs/nyc-config-typescript`), `apps/backend/package.json` (`nodemon`).
- **Description:** Storybook 10.6.1 (critical: missing origin validation in the preview, high: dev-server code injection from the local network), Vite 7.3.6 (3 moderate, 1 high launch-editor issues, 1 low), `@vitest/mocker`, `js-yaml` 3.15.1 and 4.3.1 (high, merge-key CPU use), `brace-expansion` 1.1.18 and 5.0.9 (high recursion DoS), `qs` 6.15.3 via supertest, `deepmerge`, `postcss-selector-parser` all sit on dev-only paths (dev servers, linters, test runners, Prisma CLI config for `deepmerge-ts`). None ships in the built frontends or runs in the backend request path. The dev-server issues matter for a developer who runs Storybook or Vite on an untrusted network (a website visited in the same browser can reach the local dev server), which is real for the team but not a production issue. Exception: S23-09, where the production image installs them anyway.
- **Exploit scenario:** A developer running `pnpm ui:storybook` while visiting a malicious page has code executed through the Storybook dev server. Not reachable in deployed environments.
- **Recommended fix:** Raise `storybook` to `>=10.6.2`, `vite` to `>=7.3.7`, `@vitest/mocker`/`vitest` to `>=4.1.12`, and let Dependabot's dev group handle the rest. Do not run Storybook bound to non-loopback interfaces.

### S23-12 — Low — Open-ended `>=` overrides and caret ranges on security-critical packages let a future resolve adopt any newer version, including a compromised or breaking major
- **File:line:** `package.json:129-166` (for example `better-auth: ">=1.6.23"`, `zod: ">=4.4.3"`, `lodash: ">=4.17.23"`, `tar: ">=7.5.11"`, `rollup: ">=4.59.0"`, `playwright: ">=1.55.1"`, `drizzle-orm: ">=0.45.2"`, `mailparser: ">=3.9.3"`, `jws`, `tmp`, `yauzl`, `defu`, `flatted`, `effect`), `apps/backend/package.json` (`better-auth ^1.7.7`, `@apollo/server ^5.5.0`, `express ^4.22.2`, `helmet ^7.2.0`, `multer ^2.4.0`, `@hocuspocus/* ^4.7.0`, `@sentry/node ^10.70.0`, `pg-boss ^12.36.0`).
- **Description:** An override such as `better-auth: ">=1.6.23"` allows any later major (2.x) wherever the lockfile is regenerated, bypassing the `^1.7.7` ranges in the app manifests and any manual major-upgrade review. The same applies to `lodash`, `tar`, `zod`, `rollup`. Carets on the auth, GraphQL and web frameworks allow minor updates on regeneration. The committed lockfile and `--frozen-lockfile` in CI and Docker prevent silent drift in normal operation; the risk appears when the lockfile is refreshed (including by a Dependabot grouped "patch-updates" PR, which auto-groups minor and patch bumps).
- **Exploit scenario:** A malicious version of a widely overridden package (tar, lodash, rollup, playwright) is published as a new major. The next lockfile regeneration under an `>=` override adopts it without a major-version review.
- **Recommended fix:** Prefer bounded ranges in overrides (`">=1.6.23 <2"`), keep security-critical dependencies at exact versions, and require human review of lockfile diffs, especially after a pnpm change (S23-02).

### S23-13 — Low — Update automation and CI supply chain: Dependabot covers only npm, GitHub Actions are pinned by mutable tag, base image is not digest-pinned
- **File:line:** `.github/dependabot.yml` (only `package-ecosystem: "npm"`, directory `/`, `open-pull-requests-limit: 5`), `.github/workflows/*.yml` (`actions/checkout@v4` x32, `azure/login@v2` x14, `pnpm/action-setup@v4`, `docker/*@v3/v5`, `hashicorp/setup-terraform@v3`, `trufflesecurity/trufflehog@v3.95.5`), `apps/backend/Dockerfile:5` (`FROM node:22-alpine`).
- **Description:** There is no `github-actions`, `docker` or `terraform` ecosystem in Dependabot, so action, base-image and provider updates are manual. Actions are referenced by tag, which a compromised or re-tagged release can change; `azure/login` and `docker/login-action` run in jobs that hold cloud credentials. `node:22-alpine` is a moving tag and `.nvmrc`/CI use `22.14.0` while the image takes whatever 22.x is current. Overlaps with S20/S21 (pipeline, infrastructure), listed here only for the supply-chain angle.
- **Exploit scenario:** A tag on a third-party action is moved to a malicious commit; the next workflow run executes it with `AZURE_*` credentials and registry push rights.
- **Recommended fix:** Add `github-actions`, `docker` and `terraform` ecosystems to Dependabot, pin third-party actions by commit SHA (Dependabot keeps them current), and pin the base image by digest.

### S23-14 — Info — Likely unused or unnecessary packages that add install-time and CVE surface
- **File:line:** root `package.json` (`mongodb-memory-server 10.3.0`, `@better-auth/cli 1.4.21` in `apps/backend`, `@oxc-parser/binding-darwin-arm64 0.152.0` in `packages/ui`, `@types/dompurify`/`@types/bcryptjs`/`@types/form-data` stub packages), `pnpm-lock.yaml:9801` (`better-sqlite3@12.11.1`), `pnpm-lock.yaml:14963`.
- **Description:** `mongodb-memory-server` runs a postinstall that downloads a `mongod` binary, yet the database is PostgreSQL and no source in `apps/`, `packages/` or `test/` references it (not conclusively verified for every test file). `@better-auth/cli@1.4.21` is three minors behind `better-auth@1.7.7` and pulls `better-sqlite3` (native build at install). `@oxc-parser/binding-darwin-arm64` is a platform-specific binary declared as a direct dev dependency, which breaks Linux installs of `packages/ui` when optional dependency handling is strict. Three `@types/*` entries are deprecated stubs for packages that ship their own types.
- **Exploit scenario:** Each unused package is another maintainer account whose compromise reaches CI and developer machines through install scripts.
- **Recommended fix:** Remove packages that have no import (verify with `pnpm why` and a repo search), keep CLI-only tools out of the install path, and drop the stub `@types/*` packages.

### S23-15 — Info — Provenance checks: no non-registry sources, integrity hashes complete, no obvious typosquats
- **File:line:** `pnpm-lock.yaml` (2041 `integrity:` entries; no `tarball:`, `repo:` or git resolutions; only `link:`/workspace entries for first-party packages).
- **Description:** Every external package resolves from the registry with an integrity hash; there are no git, tarball or URL dependencies. Direct dependency names were scanned for look-alikes and none stands out.
