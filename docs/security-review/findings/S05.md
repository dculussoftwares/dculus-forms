# S05 — GraphQL layer hardening: Security Findings

Scope: `apps/backend/src/graphql/schema.ts`, `graphql/resolvers.ts`, `index.ts` (Apollo/Express setup), `middleware/errorHandler.ts`, `lib/graphqlErrors.ts`, `lib/logger.ts`, `instrument.ts`. Supporting reads: `routes/health.ts`, `lib/env.ts`, `lib/better-auth.ts` (origins), `middleware/better-auth-middleware.ts`, `services/hocuspocus.ts` (logging), `graphql/resolvers/subscriptions.ts`, `infrastructure/multi-cloud/terraform/azure/main.tf` + `variables.tf` (deployed `NODE_ENV`), and the installed `@apollo/server` 5.x source (defaults for CSRF, batching, stack traces).
Method: static review, tracing code paths. No source modified. No secrets included.

## S05-01 — High — No query breadth, alias or cost limits; depth limit is the only guard, and the rate limiter counts HTTP requests, not operations

- **File:line:** `apps/backend/src/index.ts:287` (`validationRules: [depthLimit(8)]`), `index.ts:155-163` (`graphqlLimiter`), `index.ts:231` (`express.json({ limit: '10mb' })`), `index.ts:438-441` (graphql-ws `validate` with the same single rule)
- **Description:** The only query-shape control is `graphql-depth-limit` at depth 8. There is no alias limit, no per-document field/selection count limit, no complexity or cost analysis, no maximum query-document size below the 10 MB body limit, and no operation allow-list or persisted-query enforcement. The `graphqlLimiter` (5000 requests/minute in a single shared bucket, see S01-04) counts HTTP requests, so one request can contain thousands of aliased root fields. Apollo batching is off by default (`allowBatchedHttpRequests ?? false`), so the batching vector is closed, but aliasing and repeated fields give the same amplification inside a single operation. Depth 8 also does not bound breadth: every list field (`forms`, `responses`, `Form.permissions`, nested org/user lists) can be repeated at each level.
- **Exploit scenario:** An anonymous attacker sends one POST to `/graphql` with a roughly 5 MB document containing tens of thousands of aliases of a public, DB-backed query such as `formByShortUrl(shortUrl: "...") { ... }` (S04-01/S04-02 show the public `Form` type is wide and resolves relations). Each alias runs its own resolver and Prisma query, so a handful of requests per minute, far below the 5000/min limit, saturates the PgBouncer pool and the Node event loop and degrades the service for all tenants. An authenticated low-privilege user can do the same with list queries. Parsing and validating a multi-megabyte document is also CPU-bound before any resolver runs.
- **Recommended fix:** Add a cost/complexity plugin (for example `graphql-query-complexity` or `@escape.tech/graphql-armor` with max-aliases, max-directives, max-tokens, cost limit) as validation rules for both HTTP and graphql-ws. Cap anonymous request bodies at roughly 100 KB on `/graphql` (keep a larger limit only on the multipart/upload path). Limit per-operation resolver fan-out for public queries, and make rate limiting operation-aware (count aliases) or add a per-IP/per-form limiter on public operations.

## S05-02 — Medium — Stack traces (internal file paths, line numbers) returned to clients on `dev` and `staging` deployments

- **File:line:** `apps/backend/src/index.ts:285-306` (`new ApolloServer({...})` with no `includeStacktraceInErrorResponses`), `node_modules/@apollo/server/dist/esm/ApolloServer.js:96-97` (default `nodeEnv !== 'production' && nodeEnv !== 'test'`), `errorNormalize.js:41-42`; `infrastructure/multi-cloud/terraform/azure/main.tf:170`
- **Description:** Apollo Server 5 adds `extensions.stacktrace` (the full JS stack, split into lines) to every error response unless `NODE_ENV` is exactly `production` or `test`. The deployed `NODE_ENV` for the dev and staging environments is `dev` / `staging`, so both return stack traces. The custom `formatError` (`index.ts:307-327`) spreads `formattedError.extensions` into the response, so it does not strip them. Traces expose absolute container paths, dependency names and versions, and the internal structure of the resolver and service layers.
- **Exploit scenario:** Any anonymous caller sends a malformed variable or a request that triggers an unhandled error and receives the stack in `errors[0].extensions.stacktrace`. This maps internals for a targeted attack. If staging holds production-like data or shares credentials or trusted origins with production, the leak is more serious. The same `isProduction` gate also makes staging accept `localhost` origins with credentials (S01-15).
- **Recommended fix:** Set `includeStacktraceInErrorResponses: false` explicitly, and strip `extensions.stacktrace` in `formatError`. Treat `staging` as production-like by switching to a positive `isLocalDev` flag (only `development` / `test` relax controls) instead of `isProduction`, or deploy staging with `NODE_ENV=production` and use a separate variable such as `APP_ENV` for environment naming.

## S05-03 — Medium — Internal error messages are not masked in any environment (Prisma, Chargebee and library messages reach the client)

- **File:line:** `apps/backend/src/index.ts:307-327` (`formatError` returns `...formattedError` unchanged), `lib/graphqlErrors.ts:70-77` (`deriveGraphQLErrorCode` only derives a code; the message is untouched), `graphql/resolvers/subscriptions.ts:83` and `:120` (`Failed to create checkout/portal session: ${error.message}`); resolvers that `throw error;` after catching (`analytics.ts`, `formFiles.ts`, `invitations.ts`, `forms.ts`, `templates.ts`, `unifiedExport.ts`, `fileUpload.ts`, `better-auth.ts`, `pdfGenerators.ts`)
- **Description:** `formatError` classifies unexpected errors as `INTERNAL_SERVER_ERROR` but leaves `message` as thrown. Apollo does not mask the message of non-`GraphQLError` errors by default, and the custom `GraphQLError` wrapper also forwards whatever message it is given. Prisma errors have messages such as `Invalid \`prisma.form.findUnique()\` invocation in /app/...` with the model, argument names and sometimes values, and `P2002` unique constraint messages naming columns. Chargebee client errors are interpolated into user-facing messages at `subscriptions.ts:83,120`. Resolver-level `throw error` re-throws raw errors. In production (`NODE_ENV=production`) the stack is not included, but the message still is.
- **Exploit scenario:** An authenticated user, or an anonymous user on public operations, sends crafted IDs or oversized values that make a Prisma query fail and reads the table, column or constraint names, Prisma and driver versions, or upstream billing API error text in the GraphQL error. This helps with schema and ORM fingerprinting and may leak identifiers or values from other tenants embedded in a database error message.
- **Recommended fix:** In `formatError`, return a generic message (for example `Internal server error`) whenever the original error is not a deliberate `GraphQLError` with a non-internal code, while logging the real error server-side with a correlation id returned in `extensions.requestId`. Remove `${error.message}` interpolation from `subscriptions.ts` and map known upstream errors to explicit codes. Consider `hideSchemaDetailsFromClientErrors: true` (see S05-05).

## S05-04 — Medium — Request body parsed (up to 10 MB) before the GraphQL rate limiter and for every route, including unauthenticated ones

- **File:line:** `apps/backend/src/index.ts:231-232` (`express.json({ limit: '10mb' })`, `express.urlencoded({ extended: true })`), `index.ts:362-366` (`app.use('/graphql', graphqlLimiter)` is registered after the body parsers), `index.ts:240-244` (`/health`, upload, webhook, AI, OAuth routers all behind the 10 MB parser)
- **Description:** A single global 10 MB JSON limit applies to all routes. For `/graphql`, the body parser runs before `graphqlLimiter` (which is only added later in `startServer`), so a client can make the server buffer and parse 10 MB per request before rate limiting applies. Unauthenticated endpoints (public form submission over GraphQL, Chargebee webhook before auth is checked, OAuth callbacks) have no tighter per-route limit. `compression()` is also applied globally, which adds CPU cost for large responses. The GraphQL multipart path is separately bounded (`graphqlUploadExpress({ maxFileSize: 5000000, maxFiles: 10 })`).
- **Exploit scenario:** An attacker repeatedly posts 10 MB JSON bodies (valid or nearly valid) to `/graphql` or any other route from many IPs, or a few IPs through the shared proxy bucket. Each request allocates and parses the body, creating memory and CPU pressure before any limiter or auth check. Combined with S05-01 the document is then validated at full size.
- **Recommended fix:** Use a small default (for example 100 KB to 1 MB) and raise it only for the few routes that legitimately need it (form schema save, import). Move rate limiters ahead of body parsers and add a cheap `Content-Length` pre-check. Remember `urlencoded` is not needed for most routes.

## S05-05 — Low — Introspection and field-suggestion schema leakage

- **File:line:** `apps/backend/src/index.ts:286` (`introspection: !appConfig.isProduction`), `ApolloServer.js:66` (`hideSchemaDetailsFromClientErrors` defaults to `false`)
- **Description:** Introspection is enabled on `dev` and `staging` deployments (anything but `production`) and is reachable anonymously. The Apollo Sandbox landing page is correctly disabled outside `NODE_ENV=development` (`index.ts:289-304`). In `production`, introspection is off, but with `hideSchemaDetailsFromClientErrors` left at `false`, validation errors still include "Did you mean ...?" suggestions, which allow field-name enumeration by brute force with a dictionary.
- **Exploit scenario:** An attacker introspects staging or dev, which exposes the complete schema (including admin-only operations such as `adminOrganizations`, `adminUsers`, billing mutations and AI operations), and uses it to plan attacks against production, which shares the same schema. In production, a script enumerates field and type names through error suggestions.
- **Recommended fix:** Disable introspection everywhere except local development, set `hideSchemaDetailsFromClientErrors: true`, and rely on the schema being checked into the repo for client tooling.

## S05-06 — Low — Dead graphql-ws server is exposed unauthenticated on `/graphql` upgrade with no limits

- **File:line:** `apps/backend/src/index.ts:429-465` (`gqlWss`, `useServer`), `index.ts:468-478` (upgrade router); `graphql/schema.ts` (no `type Subscription`)
- **Description:** The code comments confirm `gqlWss` is dead (the schema has no `Subscription` type, verified: only the `PlanSubscription` type and subscription-billing queries exist). It still accepts WebSocket upgrades on `/graphql` from any origin. The `ws` default `maxPayload` is 100 MiB and no connection cap, ping timeout, `connectionInitWaitTimeout` tuning, per-IP limit or origin check is configured. The Express `graphqlLimiter` does not apply to upgrade requests (acknowledged in the comment at `index.ts:425-428`). Auth is from `connectionParams.token`, so cross-site WebSocket hijacking with cookies is not possible on this endpoint.
- **Exploit scenario:** An attacker opens thousands of idle WebSocket connections, or sends very large frames, to exhaust file descriptors and memory in the same Node process that serves the API and the Hocuspocus collaboration sockets (S13), with no rate limit in the way.
- **Recommended fix:** Remove the graphql-ws server and the `/graphql` upgrade branch as the TODO says. If it is kept, set `maxPayload`, connection caps and `connectionInitWaitTimeout`, and verify `Origin` in the upgrade handler.

## S05-07 — Low — `errorHandler` returns raw `error.message` and honours `error.statusCode` for every error

- **File:line:** `apps/backend/src/middleware/errorHandler.ts:15-31`
- **Description:** The handler echoes `error.message` to the client for all errors, including 500s from non-operational errors (`isOperational` is never checked), and uses `error.statusCode` from any thrown object. Body-parser errors (invalid JSON, `entity.too.large`) and library or Prisma errors from the REST routes (`/upload`, OAuth, Pixabay/Pexels, AI routes) therefore reach the client verbatim, for example JSON parse messages quoting part of the body. The stack is only included when `isDevelopment`, which is `NODE_ENV === 'development'`, so `dev` / `staging` deployments do not return stacks from this handler (unlike S05-02). The handler also logs `req.url` with its query string and the full stack (see S05-08).
- **Exploit scenario:** An attacker sends malformed JSON or triggers a failure in an upload or OAuth route and reads internal error strings that fingerprint dependencies or reveal paths.
- **Recommended fix:** For non-operational errors and any status >= 500, respond with a generic message and a request id. Only expose `message` when `isOperational` is true.

## S05-08 — Low — Sensitive or noisy data in logs (error objects, query strings, per-request auth log)

- **File:line:** `apps/backend/src/index.ts:314-320` (logs `originalError: error`), `middleware/errorHandler.ts:20-25` (logs `req.url` with query and `stack`), `middleware/better-auth-middleware.ts:25` (logs user id and role on every GraphQL request), `services/hocuspocus.ts:214,235` (token-presence logging, no token values), `lib/logger.ts:18-35` (no `redact` config)
- **Description:** (1) `formatError` logs the full original error under the key `originalError`. Pino only applies its error serializer to the `err` key, so an `Error` under any other key is serialized by `JSON.stringify` and loses its non-enumerable `message` / `stack`, while enumerable fields on Prisma and library errors (`meta`, `code`, `clientVersion`, request or response data on HTTP client errors) are logged in full. The useful stack is missing and potentially sensitive data is present. This is PLAUSIBLE for specific error classes and was not reproduced at runtime. (2) Pino has no `redact` paths configured, so any later log of a request, header or cookie object is written as-is. (3) Morgan and the error handler log URLs with query strings (S01-11 has the token details). (4) Authenticated requests log user id and role at info level on every request, which is noisy and creates a user activity trace. No log call was found that writes passwords, session cookies or Authorization header values.
- **Exploit scenario:** Anyone with log access (or a log shipper compromise) reads tokens and identifiers from URLs and fields from third-party error objects. Debuggability is also hurt because stacks are lost.
- **Recommended fix:** Log errors under `err`, add `redact` for `req.headers.authorization`, `req.headers.cookie`, `*.password`, `*.token`, `*.secret`, strip query strings in all URL logging, and lower the per-request auth log to `debug`.

## S05-09 — Low (PLAUSIBLE) — Sentry has no scrubbing hook and forwards console output as logs

- **File:line:** `apps/backend/src/instrument.ts:13-28`
- **Description:** `sendDefaultPii: false` is set, which is good: default request headers, cookies and IPs are not attached. However there is no `beforeSend` / `beforeSendTransaction` / `beforeSendLog` scrubbing, `Sentry.consoleLoggingIntegration({ levels: ['log','warn','error'] })` plus `enableLogs: true` ships every `console.*` call as a Sentry log, and `graphqlIntegration()` / `expressIntegration()` add spans with operation names and URLs (including query strings). Whether any `console.*` call in the backend writes sensitive values was not exhaustively checked (the app mostly uses the pino `logger`, which writes to stdout and is not captured by the console integration). Validation errors thrown via Apollo are handled inside Apollo and are not reported to Sentry at all (only Express-level errors reach `setupExpressErrorHandler`), which is a monitoring gap rather than a vulnerability.
- **Exploit scenario:** A `console.error(err)` on a request or Prisma error carrying emails, tokens or response payloads is exported to a third party without redaction.
- **Recommended fix:** Add `beforeSend`, `beforeSendTransaction` and `beforeSendLog` scrubbers (strip `url` query strings, `request.data`, tokens and emails), restrict console capture to `warn` and `error` or disable it, and report unexpected GraphQL errors from the Apollo `didEncounterErrors` plugin hook with scrubbed context.

## S05-10 — Info — Rate limiting and proxy trust are not set up for the real client IP (cross-reference)

- **File:line:** `apps/backend/src/index.ts:106-163` (limiters), no `app.set('trust proxy', ...)` anywhere in `src/`
- **Description:** Without `trust proxy`, `express-rate-limit` keys on the socket address, which behind Azure Container Apps / Cloudflare is the proxy, so all clients share one bucket of 5000 requests/minute (and 429s for legitimate users once exceeded). This is already reported as S01-04 and S04-06 and is not re-scored here. It matters for S05-01 and S05-04 because the limiter is the only throttle on `/graphql`.
- **Exploit scenario:** See S01-04, S04-06.
- **Recommended fix:** See S01-04 (set an explicit `trust proxy` hop count matching the deployment, key on the verified client IP, add per-user and per-form limits).

## S05-11 — Info — CORS configuration review (no wildcard, credentialed static allow-list)

- **File:line:** `apps/backend/src/index.ts:166-185`
- **Description:** CORS uses a static array (`CORS_ORIGINS` plus, outside `production`, `DEV_ORIGINS` and Apollo Studio origins) with `credentials: true`. Reflecting arbitrary origins is not possible. A literal `CORS_ORIGINS=*` would not match any origin (the `cors` package compares strings in an array), so it fails closed. An empty `CORS_ORIGINS` in production yields an empty list and all browser cross-origin calls fail (S01-15). On `dev`/`staging`, `localhost` origins and the Apollo Sandbox origins are credentialed, as noted in S01-15 and S05-02. Requests without an `Origin` header (server-to-server, curl) are always allowed, which is expected. The log line at `index.ts:176` prints the origin list at startup, which is not sensitive.
- **Exploit scenario:** None specific beyond S01-15 (a page served from `http://localhost:<port>` on a victim's machine could make credentialed requests to a staging API).
- **Recommended fix:** Drop `DEV_ORIGINS` and the Apollo origins unless `NODE_ENV` is `development`; validate `CORS_ORIGINS` entries at startup (reject `*`, require `https://` in non-local environments).

## S05-12 — Info — `/debug` does not exist; `/health` is minimal; unauthenticated mock-storage route is dev-only

- **File:line:** `apps/backend/src/routes/health.ts:7-14`, `index.ts:247-258`, `index.ts:264` (comment: `/debug-sentry` removed), `services/temporaryFileService.ts:40,106`
- **Description:** CLAUDE.md lists a `/debug` route, but no such route exists in `src/` (verified by search), so there is no debug information disclosure. `/health` runs `SELECT 1` and returns `{status:'ok'}` or a generic `503 Database unavailable` without error details, version or environment. `/api/temp-files-mock/*` serves from an in-memory map without auth, but entries exist only when the S3 endpoint is `localhost:9000` (mock mode), so it is inert in deployed environments, as long as `PUBLIC_S3_ENDPOINT` is never set to a `localhost:9000` value in a deployed environment. `/health` runs a DB query per call without a limiter, which is a minor load factor.
- **Exploit scenario:** None identified. Only a misconfiguration (mock-S3 endpoint in a deployed env) would expose the mock route, and the keys are random.
- **Recommended fix:** Update CLAUDE.md to remove `/debug`. Optionally rate-limit `/health` or split liveness (no DB) from readiness.

## S05-13 — Info — Positive controls verified

- **File:line:** `apps/backend/src/index.ts:56-125, 285-306, 362-366`
- **Description:** (1) CSRF: Apollo `csrfPrevention` is enabled by default (`ApolloServer.js:113`) and not turned off, so non-preflighted simple requests (including multipart) without `Apollo-Require-Preflight` / a custom content type are rejected. (2) Batched HTTP requests are disabled by default (`allowBatchedHttpRequests ?? false`), and no explicit enabling was found. (3) Depth limit (8) is applied to both HTTP and graphql-ws validation. (4) `helmet` is applied (HSTS, `X-Content-Type-Options`, `x-powered-by` removal, CSP); `unsafe-inline` for scripts and the Studio origins are only added outside production. (5) The Apollo landing page is disabled unless `NODE_ENV=development`. (6) Sentry is initialized with `sendDefaultPii: false`. (7) Multipart uploads are limited to 5 MB and 10 files. (8) Morgan's format omits client IP and the unused `/debug-sentry` route was removed. CSP style directives keep `'unsafe-inline'`, which is of low value on a JSON API.
- **Exploit scenario:** n/a
- **Recommended fix:** Keep these. Add regression tests that assert `csrfPrevention` stays on and batching stays off.
