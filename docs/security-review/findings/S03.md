# S03: GraphQL authorization (part B: responses and data)

Review-only. No source was modified. Paths are relative to `apps/backend/src/`.
Authorization model checked: system role, org membership, form permission plus sharing scope.
`checkFormAccess` (`services/formSharingService.ts:47`) was read in full: it requires org membership first, then creator = OWNER, then explicit `FormPermission` (including `NO_ACCESS`), then `ALL_ORG_MEMBERS` default, else deny. It is sound, so any resolver that calls it with a form ID derived from the target object is treated as correctly gated.

## Findings

### S03-01
- **Severity:** High
- **File:line:** `graphql/resolvers/subscriptions.ts:206-261` (the leak is at `:217-224`; the membership check is only at `:236`)
- **Description:** `initializeOrganizationSubscription` calls `requireAuth` only, then does `getSubscriptionByOrganization(organizationId)` and, if a row exists, returns it ("idempotency") before `requireOrganizationMembership` and the owner check run. The membership and owner checks therefore guard only the create path. The returned `PlanSubscription` exposes `planId`, `status`, usage counters and limits, billing period, `chargebeeCustomerId`, `chargebeeSubscriptionId`, and `organization { id name slug logo }` via `Subscription.organization`.
- **Exploit scenario:** Any signed-in user (including a free account in another tenant) calls `initializeOrganizationSubscription(organizationId: "<victim org id>")` and receives the victim's plan, usage, and Chargebee customer/subscription IDs. The error branch also returns `error.message` to the caller. Org IDs are not secret (they appear in invitation links, URLs and share flows). The Chargebee IDs are useful for social-engineering Chargebee support or for correlating with leaked webhook data.
- **Recommended fix:** Move `requireOrganizationMembership(context.auth, organizationId)` and the `membership.role === 'owner'` check to the top of the resolver, before any lookup. Throw `createGraphQLError(..., GRAPHQL_ERROR_CODES.NO_ACCESS)` on failure. Return a generic message instead of `error.message`.

### S03-02
- **Severity:** Medium
- **File:line:** `services/responseService.ts:355` (`let whereClause = \`WHERE "response"."formId" = $1\``), consumed by `repositories/responseRepository.ts:157-195` (`countFilteredRaw`, `findFilteredRaw`)
- **Description:** The database-level filter path of `getResponsesByFormId` builds raw SQL with no `"response"."deletedAt" IS NULL` predicate. Every other path (unfiltered list, in-memory fallback via `listByForm`, org list, `getResponseById`, exports) excludes soft-deleted rows. Soft-deleted responses therefore reappear, with full `data`, `respondentEmail` and `metadata`, whenever the caller supplies at least one filter (including a no-op filter such as `__submittedAt`). The same path feeds `iterateResponsesByFormId`, which `collectResponseFiles` uses when `filters` are present, so files of deleted responses show up in the Files view and in ZIP export. `responseFileCatalog.ts` states in its header that soft-deleted responses "may not be browsed or exported".
- **Exploit scenario:** An OWNER deletes a response (for example a data-erasure request). Any user with VIEWER on the form calls `responsesByForm(formId, filters:[{fieldId:"__submittedAt", ...wide range}])` and reads the deleted response. An EDITOR calls `startResponseFileExport` with a filter and downloads the deleted response's uploaded files in the ZIP. This defeats delete semantics and erasure obligations.
- **Recommended fix:** Add `AND "response"."deletedAt" IS NULL` to the base `whereClause` (or inside `countFilteredRaw`/`findFilteredRaw`). Add a regression test that a soft-deleted response is excluded from a filtered query and from `collectResponseFiles`.

### S03-03
- **Severity:** Medium
- **File:line:** `graphql/resolvers/subscriptions.ts:44-86` (`createCheckoutSession`), `:91-120` (`createPortalSession`), `:133-158` (`completeEnterprisePayment`)
- **Description:** All three billing mutations require only org membership (any `member`, not `owner`). The Chargebee portal session lets the holder change or cancel the plan, update payment methods and download invoices. Additionally, `itemPriceId` is only regex-validated; it is not checked against the list returned by `getAvailablePlans()`, so any Chargebee item price ID (hidden, legacy, discounted or enterprise-only) can be used to open a checkout for the org's customer.
- **Exploit scenario:** A low-privilege org `member` (or a user removed from all forms but still a member) opens `createPortalSession` and cancels the subscription or swaps the card, causing an org-wide outage (limits drop to free). Or they call `createCheckoutSession` with a private item price ID discovered elsewhere.
- **Recommended fix:** Require `membership.role === 'owner'` (use the return value of `requireOrganizationMembership`, as `initializeOrganizationSubscription` already does) for all three. Validate `itemPriceId` against the available-plans allow-list server side. Confirm the intended business rule with product (this report assumes billing is owner-only).

### S03-04 (PLAUSIBLE)
- **Severity:** Medium
- **File:line:** `services/responseCopyService.ts:84-87, 136-141` with `services/emailService.ts:78-94`
- **Description:** The recipient of the "copy of your response" email is `response.data[emailFieldId]`, a respondent-supplied string, passed as `to` after only `.trim()`. There is no server-side format check here, and nodemailer accepts comma/semicolon separated lists in `to`. The form's schema must contain an email field, but the stored value is not validated against it in this service. In `mode: 'always'` no consent is required. This is the anonymous submission path, so no authentication is needed. Not confirmed: whether `submitResponse` validates field values server side (S04's scope). If it does not, this is exploitable as described.
- **Exploit scenario:** An attacker submits a public form that has response copy enabled with `data[emailField] = "a@x.com, b@y.com, ..."` and attacker-chosen answers. The platform's SMTP sender mails the owner's subject line plus the attacker-authored answer table to every listed address, using the product's trusted `From`. Limited only by the org's email quota and form submission limits. Useful for phishing and spam from a reputable domain.
- **Recommended fix:** Before sending, require a single valid address (`z.string().email()` plus reject `,`, `;`, whitespace and CR/LF), re-validate the field value with the form's real validation in `submitResponse`, and rate-limit copies per IP/form. Consider requiring `respondentChoice` consent or verified sign-in.

### S03-05
- **Severity:** Medium
- **File:line:** `graphql/resolvers/responses.ts:959-1014` (`responseEditHistory`), `services/responseEditTrackingService.ts:367-383`, `graphql/schema.ts:426-437` (`ResponseEditHistory.ipAddress`, `.userAgent`, `editedBy: User`); also `FormResponse.editHistory` field resolver at `responses.ts:1118`
- **Description:** Edit history is returned in full, including the editor's `ipAddress`, `userAgent`, and `User { email, name, image }`, to anyone with VIEWER on the form. For respondent self-edits (`editType: RESPONDENT`) that is the respondent's own IP and account email. Other VIEWER-visible analytics intentionally strip IP and UA, so this is inconsistent. Also, `FormResponse.editHistory`, `lastEditedBy`, and the related fields have no field-level access check and rely entirely on the parent resolver; they are reachable from `submitResponse`'s return type (currently harmless because the response is new).
- **Exploit scenario:** A read-only VIEWER (for example an auditor or an invited intern) collects IP addresses, user agents and email addresses of every editor and every self-editing respondent across a form's responses via `responses { editHistory { ipAddress userAgent editedBy { email } } }`. Responses already contain respondent email on identity-gated forms, but not their IP or device.
- **Recommended fix:** Return `ipAddress`/`userAgent` only to EDITOR or OWNER (null them for VIEWER). Optionally scope `editedBy.email` the same way. Add a field-level `checkFormAccess` guard (using `getCachedFormAccess`) to `editHistory`, `lastEditedBy` and friends, as `responseGrade` already does.

### S03-06
- **Severity:** Low
- **File:line:** `graphql/resolvers/formFiles.ts:15-44`, `services/formFileService.ts`, `repositories/formFileRepository.ts:43-47`
- **Description:** `getFormFiles(formId, type)` with `type` omitted or `FormResponse` returns every `FormFile` row for the form at VIEWER level. That table includes uploads from abandoned submissions and from soft-deleted responses (the Files view deliberately avoids it for that reason, see `responseFileCatalog.ts` header). The result exposes S3 `key`, `originalName`, `size`, `mimeType`. Download is blocked elsewhere (`isFileKeyReferencedRaw` requires a live referencing response), so impact is metadata only. Error text also includes `error.message` (`:44`).
- **Exploit scenario:** A VIEWER lists names and sizes of files uploaded by respondents whose responses were deleted, learning the existence and original filenames (often containing personal names) of erased data.
- **Recommended fix:** Exclude `FormResponse` from the `type` allow-list and from the unfiltered case (or require EDITOR, and join to live responses). Drop `error.message` from the client error.

### S03-07
- **Severity:** Low
- **File:line:** `graphql/resolvers/analytics.ts:24-35` (`validateTimeRange`), `services/analyticsService.ts:387-396, 610, 837` (`generateDateRange`)
- **Description:** `timeRange` is validated only for parseability and `start < end`. `generateDateRange` loops one entry per day with `setDate`, so a range of year 0001 to 9999 allocates about 3.6 million strings, per call, per time-series section. No maximum span is enforced.
- **Exploit scenario:** Any VIEWER (or an owner of a throwaway form) sends repeated `formAnalytics(timeRange:{start:"0001-01-01",end:"9999-12-31"})` calls to spike CPU and heap on the single Node process, degrading all tenants.
- **Recommended fix:** Cap the span (for example 366 days) in `validateTimeRange`, clamp `start` to the form's creation date, and throw `GRAPHQL_ERROR_CODES.BAD_USER_INPUT` when exceeded. Apply the same to `orgDailyUsage` (no cap there either, though it does not loop per day).

### S03-08
- **Severity:** Low
- **File:line:** `graphql/resolvers/unifiedExport.ts:62-65` and `:48-69`; `services/responseService.ts:462-491` (memory path via `listByForm`), `:554-578` (`getAllResponsesByFormId`); `services/fieldAnalyticsService.ts:157-165, 926, 970`; `graphql/resolvers/responses.ts:778-798` (`deleteResponses`)
- **Description:** Several authorized-but-heavy operations load an entire form's responses into memory before applying limits: the export loads all rows and only then enforces `MAX_EXPORT_RESPONSES` (50,000); field analytics and `allFieldsAnalytics` read every response per request (VIEWER); any filter combined with a form-field sort uses the in-memory path; `deleteResponses` accepts an unbounded `ids` list (responses ID caps exist only on the responseFiles path, 1000). No per-user rate limit on exports other than the file-ZIP export's 10/hour.
- **Exploit scenario:** A user with legitimate EDITOR rights on a large form repeatedly triggers `generateFormResponseReport` or `allFieldsAnalytics` and exhausts memory/CPU of the shared backend. Low because it requires form access, but it is cross-tenant impact.
- **Recommended fix:** Count first (`responseRepository.count`) and check the limit before loading; stream or batch via `iterateResponsesByFormId`; compute analytics with SQL aggregates; cap `ids` length in `deleteResponses`/`releaseResponseGrades`; add per-user rate limiting to export and analytics queries.

### S03-09
- **Severity:** Low
- **File:line:** `graphql/resolvers/responses.ts:686-749` (`updateResponse`), `services/responseService.ts:715-838`
- **Description:** Builder edits skip `assertResponsePayloadWithinLimits` (the respondent edit and submit paths call it), accept arbitrary keys not present in the schema, and `editReason` is unbounded. A failed update surfaces `error.message` to the client. Only deletes and grade actions call `audit(...)`; response edits are recorded in edit history but not in the audit log, and neither export (`generateFormResponseReport`) nor `getFormFiles` is audited (the ZIP export path is).
- **Exploit scenario:** An EDITOR (or a compromised EDITOR session) writes an oversized JSON blob or inserts fake keys into responses, or bulk-exports PII, with no audit trail beyond the edit history table (which they can read, but not remove).
- **Recommended fix:** Call `assertResponsePayloadWithinLimits(input.data)` and a length cap on `editReason`; restrict keys to the live schema's field IDs; add `audit('response.updated' | 'response.exported', ...)` calls; replace raw error messages with generic ones.

### S03-10
- **Severity:** Low
- **File:line:** `graphql/resolvers/analytics.ts:57-95` (`trackFormView`), `:141-190` (`trackFormSubmission`), `:99-135` (`updateFormStartTime`); `services/analyticsService.ts:279-281` (`generateAnalyticsId`)
- **Description:** These mutations are intentionally public, but: `trackFormSubmission` lets any caller attach an analytics row to any `responseId` they know (only the `formId` match is verified, not that the caller submitted it) with arbitrary `sessionId`, `userAgent`, `timezone` and unbounded `completionTimeSeconds` (no min/max); `updateFormStartTime` takes any `sessionId` for a published form and rewrites the start time of that session's row; analytics row IDs use `Math.random()`. Impact is data-quality only (completion-time percentiles, browser/country stats, which VIEWERs and billing dashboards display). `trackFormView` also feeds usage billing counters (covered in S04).
- **Exploit scenario:** A competitor or disgruntled respondent poisons a form's completion-time distribution and device/country breakdown by posting fabricated rows, or overwrites another visitor's `startedAt`.
- **Recommended fix:** Validate `completionTimeSeconds` to a sane range (0 to 86,400); bind the analytics row to the submitting session server side (record `sessionId` on the response at submit time, drop the standalone mutation or require match); use `crypto.randomUUID()`/`generateId()` for analytics IDs.

### S03-11
- **Severity:** Info
- **File:line:** `services/formSharingService.ts:52-56` (used by every resolver above)
- **Description:** `checkFormAccess` throws `FORM_NOT_FOUND` for a missing form but returns `hasAccess:false` (surfaced as `NO_ACCESS`) for an existing form the caller cannot access, so authenticated users can distinguish "exists" from "does not exist" for arbitrary form IDs. Form IDs are random, so exploitability is low. `fieldAnalytics`/`allFieldsAnalytics` already use a combined "not found or access denied" message but a different error code in the not-found branch.
- **Exploit scenario:** An authenticated user probes IDs to confirm whether a leaked or guessed form ID is real.
- **Recommended fix:** Map not-found and no-access to the same error code and message in the read paths.

### S03-12
- **Severity:** Info
- **File:line:** `graphql/resolvers/subscriptions.ts:206-275`, `graphql/schema.ts:42-72` (`PlanSubscription`)
- **Description:** `Organization.subscription` and `Subscription.organization` field resolvers (`subscriptions.ts:282-298`) perform no access check and rely on every parent resolver being gated. `PlanSubscription` returns `chargebeeCustomerId`/`chargebeeSubscriptionId` to any org member, which the front end likely does not need. This amplifies S03-01.
- **Exploit scenario:** Any new resolver that returns an `Organization` would leak subscription details by default.
- **Recommended fix:** Strip the Chargebee IDs from the non-admin type, or gate the `subscription` field on org membership of the caller.
