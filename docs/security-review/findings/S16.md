# S16 - form-app (builder dashboard)

Scope: `apps/form-app/src/**` (plus `index.html`, `public/_headers`, `vite.config.ts`). Supporting code traced: `packages/ui/src/renderers/FormFieldRenderer.tsx`, `packages/ui/src/rich-text-editor/LexicalRichTextEditor.tsx`, `packages/ui/src/layouts/shared/ThankYouScreen.tsx`, `infrastructure/multi-cloud/terraform/cloudflare/embed-framing.tf`.

Review-only; no source modified. No secrets included. Cross-references: S07-05 (OAuth state and error-fragment injection), S07-09 (OAuth token handling), S13-04 (editor strings unsanitized), S06-04/S06-07/S06-13 (upload content validation), S02/S03 (server-side authorization).

## Summary

| Severity | Count |
|----------|-------|
| Critical | 0 |
| High     | 0 |
| Medium   | 1 |
| Low      | 6 |
| Info     | 2 |

Headline: no exploitable DOM XSS sink was found in form-app. The only `dangerouslySetInnerHTML` uses inject static CSS constants, and rich text goes through a Lexical read-only editor with an allow-list of node types. The main client-side weakness is that the plugin config form accepts an OAuth token from any URL fragment with no client-side check that a Connect flow was started (completes the S07-05 exfiltration chain).

## Findings

### S16-01 - Medium (PLAUSIBLE) - Sheets plugin config form accepts an OAuth token from any URL fragment (client half of S07-05)
- **File:line:** `apps/form-app/src/plugins/google-sheets/ConfigForm.tsx:114-141`, `apps/form-app/src/plugins/microsoft-sheets/ConfigForm.tsx:122-175`; stash helper `apps/form-app/src/lib/pendingConfigFields.ts:13-40`
- **Description:** On mount, the config form checks `window.location.hash.includes('google_oauth_token=')` and, if present, base64-decodes and `JSON.parse`s the value straight into `googleToken` state (the same shape holds `accessToken`, `refreshToken`, `email`). The client never verifies that the user actually started a Connect flow in this tab: `handleConnectGoogle` writes a pending stash via `stashPendingConfigFields` (line 196), but `consumePendingConfigFields` returning `null` is ignored and the token is accepted anyway. The decoded object is not shape-validated (no check on `expiresAt`, `email` type, extra keys). S07-05 shows the server callback reflects an unencoded `error` query value into the fragment, so a crafted link can plant a second `google_oauth_token=` parameter; the client's `includes()` test then prefers the token branch over the `google_oauth_error=` branch.
- **Exploit scenario:** An attacker mints a token for their own Google account and sends a signed-in form owner a link that bounces through the backend callback (S07-05) to the plugin config page with the attacker token in the fragment. The page shows the attacker's email as the "connected account" (the only visible cue). If the owner presses Save, the connection config now points to the attacker's spreadsheet and every future submission is appended there (data exfiltration). The same works for the Microsoft form.
- **Recommended fix:** Require a valid pending-flow marker before accepting a fragment token: have `handleConnect*` store a random nonce in sessionStorage, send it through `return_to`/`state`, and only accept the token if the nonce returns and matches. Reject (and strip the fragment) when no stash exists. Validate the decoded token shape and parse with `URLSearchParams.get` rather than `includes`. Prefer completing the exchange server side (S07-05 fix) so token JSON never travels through the browser.

### S16-02 - Low (PLAUSIBLE) - Plugin overview/config links render stored URLs as `href` with no scheme allow-list
- **File:line:** `apps/form-app/src/plugins/google-sheets/OverviewSummary.tsx:59`, `apps/form-app/src/plugins/microsoft-sheets/OverviewSummary.tsx:83,95`, `apps/form-app/src/plugins/google-sheets/ConfigForm.tsx:385,395`, `apps/form-app/src/plugins/microsoft-sheets/ConfigForm.tsx:417,428`, `apps/form-app/src/components/plugins/PluginDashboardModal.tsx:514`
- **Description:** `config.spreadsheetUrl`, `config.workbookUrl`, `config.workbookFolderUrl` and `documentUrl` come from the persisted plugin config (the client itself sends `spreadsheetUrl`/`workbookUrl` back in the saved config, ConfigForm.tsx:270/285), and are used unchecked as `<a href>`. Whether a collaborator can write an arbitrary value depends on the backend plugin-config validation (see S07). Contrast with billing, which does validate (`isChargebeeUrl`, `safeRedirect`).
- **Exploit scenario:** A user with plugin-edit rights saves a Google Sheets plugin whose `spreadsheetUrl` is `javascript:...` or a phishing `https:` URL. The form owner clicks "Open spreadsheet" in the plugin overview. Modern browsers largely neutralise `javascript:` under `target=_blank rel=noopener`, so the realistic impact is phishing/redirect; script execution is not confirmed.
- **Recommended fix:** Add a small `safeExternalUrl()` helper that parses with `new URL`, allows only `https:` and the expected hosts (`docs.google.com`, `drive.google.com`, `*.sharepoint.com`, `onedrive.live.com`, `*.office.com`), and falls back to no link. Validate on the server when saving the config as well.

### S16-03 - Low (PLAUSIBLE) - Rich-text read-only render uses a denylist sanitizer; DOMPurify runs only in one editor save path
- **File:line:** `packages/ui/src/renderers/FormFieldRenderer.tsx:114-127` (used by the builder preview and page canvas), `apps/form-app/src/components/form-builder/field-settings-v2/RichTextFieldSettings.tsx:44-46`
- **Description:** `richTextField.content` is parsed with `DOMParser` and only `<script>` elements and `on*` attributes are removed before the HTML is handed to `LexicalRichTextEditor` (`editable={false}`). `<iframe>`, `<svg>`, `<style>`, `<form>`, `javascript:` hrefs, `srcdoc` and similar survive that step. DOMPurify is applied only inside `RichTextFieldSettings.onSave` in the browser of the editor who typed the value; content arriving through the Y.js document from another collaborator, the server, a template, AI-generated edits or a duplicated form is not re-sanitised (S13-04). The mitigating control is that `LexicalRichTextEditor` registers a fixed node list (`LinkNode`, `AutoLinkNode`, list/heading/quote nodes, `LexicalRichTextEditor.tsx:388-394`) and Lexical 0.52 drops unknown elements on `$generateNodesFromDOM` and sanitises link URLs, so no script-capable output was demonstrated.
- **Exploit scenario:** A malicious EDITOR writes crafted HTML into a rich-text field through the collaboration channel (bypassing the settings panel). The owner opens the builder; if any Lexical import path or a future node (image, embed) honours an unsafe attribute, the payload executes in the form-app origin where the bearer token lives (S16-04).
- **Recommended fix:** Replace the hand-rolled denylist with `DOMPurify.sanitize(content, { USE_PROFILES: { html: true }, FORBID_TAGS: ['style','iframe','svg','form'], FORBID_ATTR: ['style'] })` inside `FormFieldRenderer`, and enforce the same allow-list server side (S13-04). Add a regression test with `javascript:` links, `<img onerror>`, `<svg onload>`.

### S16-04 - Low - Bearer token kept in `sessionStorage` and no repo-controlled CSP, so any script execution becomes full session theft
- **File:line:** `apps/form-app/src/lib/auth-client.ts:6-30`, `apps/form-app/src/services/apolloClient.ts:12-35`, `apps/form-app/index.html:19` (loads `/config.js` classic script), `apps/form-app/public/_headers`
- **Description:** After sign-in the better-auth `set-auth-token` response header is written to `sessionStorage['bearer_token']` and attached to every GraphQL request, in addition to the cookie session (`credentials: 'include'`). The cookie can be HttpOnly, but the bearer copy is readable by any script on the origin. The app ships no Content-Security-Policy (neither `<meta>` nor `_headers`; `_headers` only sets `Referrer-Policy`), loads `/config.js` as an unconstrained classic script, and bundles several third-party scripts and iframes (Google Picker, OneDrive picker, Sentry). Combined with the 7-day token validity (S01-01, S01-05) a single XSS or malicious browser extension yields a long-lived credential. No concrete XSS sink was found, so this is defence-in-depth.
- **Exploit scenario:** A future XSS (for example via S16-03) runs `sessionStorage.getItem('bearer_token')` and exfiltrates it; the attacker replays it against the GraphQL API from anywhere, surviving a password change (S01-05).
- **Recommended fix:** Prefer cookie-only sessions for the SPA and drop the bearer header unless it is needed for the WebSocket/other-origin cases; if it must stay, shorten its lifetime. Add a CSP (via `_headers`/Cloudflare) with `script-src 'self'` plus the specific Google/Microsoft hosts, `object-src 'none'`, `base-uri 'self'`, and move `config.js` values to a nonce/hash or JSON endpoint.

### S16-05 - Low - OAuth/token details and form content logged to the browser console (breadcrumb capture by Sentry)
- **File:line:** `apps/form-app/src/pages/OAuthGoogleSheetsCallback.tsx:8,15,23,30,32`, `apps/form-app/src/plugins/google-sheets/ConfigForm.tsx:123`, `apps/form-app/src/store/slices/fieldsSlice.ts:193,254,320,364,565,753,860`, `apps/form-app/src/store/helpers/fieldHelpers.ts:356`, `apps/form-app/src/main.tsx:12-18`
- **Description:** The Google relay page logs `JSON.stringify(data).slice(0, 80)` where `data` is `{"token":{"accessToken":"...` (the first 80 characters include roughly 50 characters of the access token), plus the account email. The config form also logs the connected email. The field store logs field contents/labels on every edit. `Sentry.init` enables `browserTracingIntegration` with defaults, so console output is recorded as breadcrumbs and attached to any error event sent to Sentry; there is no `beforeSend`/`beforeBreadcrumb` scrubber (see S05-09 for the backend equivalent). About 22 `console.log/info/debug` calls exist in non-test code.
- **Exploit scenario:** An access-token prefix and the owner's email land in Sentry breadcrumbs (third-party data store) or a screenshot/HAR shared during support. A prefix is not directly usable but still counts as credential-adjacent PII.
- **Recommended fix:** Remove these logs (or gate them behind `import.meta.env.DEV`), never log token material even truncated, and add a `beforeBreadcrumb` that drops `console` category entries and a `beforeSend` that scrubs tokens and emails. Strip console calls in production builds (`esbuild.drop: ['console','debugger']`).

### S16-06 - Low (PLAUSIBLE) - Respondent-uploaded files are previewed in an unsandboxed `<iframe>` and the PDF/image decision trusts the client-declared MIME type
- **File:line:** `apps/form-app/src/components/Responses/files/ResponseFilePreviewDialog.tsx:53,80-88`
- **Description:** `isPdf = file.mimeType === 'application/pdf'`; if true the presigned URL is loaded in `<iframe src={url}>` with no `sandbox` attribute. `mimeType` is whatever the (anonymous) respondent declared at upload (S06-04, S06-07, S06-13 show the server does not verify bytes or enforce the field's allowed types), so the object served from the private bucket may be HTML or SVG if the storage response `Content-Type` is derived from the stored declaration. The frame is cross-origin (R2 host), so it cannot read form-app storage, but it can render attacker-controlled content inside the builder UI and attempt top-level navigation or phishing prompts.
- **Exploit scenario:** An anonymous respondent uploads an HTML page declared as `application/pdf`; when an owner opens Preview in the Responses table, the page renders a fake "session expired, sign in" form inside the trusted dialog, or navigates the frame/tab. Impact is bounded by the cross-origin frame.
- **Recommended fix:** Add `sandbox=""` (no scripts, no top navigation) to the iframe, or render PDFs with a dedicated viewer; have the server force `Content-Type` and `Content-Disposition` for inline previews from a verified type (S06 fixes) and add `X-Content-Type-Options: nosniff` on the presigned response.

### S16-07 - Low (PLAUSIBLE) - No clickjacking/frame-ancestors protection controlled in the repository for form-app
- **File:line:** `apps/form-app/public/_headers:7-9`, `apps/form-app/index.html`, `infrastructure/multi-cloud/terraform/cloudflare/embed-framing.tf:95-130`
- **Description:** `_headers` only sets `Referrer-Policy`; no `X-Frame-Options` or `frame-ancestors` is declared for the builder app. Framing protection depends on the Cloudflare zone's "Add security headers" managed transform (stamps `X-Frame-Options: SAMEORIGIN`, as noted in `embed-framing.tf`), which is outside the repo and could be altered. The Terraform rule that strips `X-Frame-Options` and sets `frame-ancestors *` is scoped by `local.embed_framing_expression` to the viewer `/embed/*` route; its expression was not verified in this section (S21 scope) so scope creep to the builder host is possible.
- **Exploit scenario:** If the managed transform is disabled or the embed expression matches the builder host, an attacker page frames the dashboard and overlays UI to trick a signed-in owner into destructive clicks (delete form, change sharing, billing).
- **Recommended fix:** Declare `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'` in `_headers` for the form-app (and admin-app) so the protection is under version control, and confirm in S21 that the embed expression is restricted to the viewer host and path.

### S16-08 - Info - Legacy Google OAuth relay page broadcasts any URL fragment on a shared BroadcastChannel
- **File:line:** `apps/form-app/src/pages/OAuthGoogleSheetsCallback.tsx:1-47`, `apps/form-app/src/App.tsx:69`
- **Description:** Route `/oauth/google/sheets` decodes whatever is in `location.hash` and posts it to `BroadcastChannel('dculus_google_oauth')`, then calls `window.close()`. A repo-wide search found no listener on that channel: the config form now uses a full-page redirect (ConfigForm.tsx:197), so the page is dead code. Any same-origin tab could still listen, and any link can make the page broadcast attacker-chosen JSON. Same-origin only, so no cross-site impact today.
- **Recommended fix:** Delete the route and component (and the `google_oauth` callback path on the server if unused), removing one more place where token JSON is handled.

### S16-09 - Info - Third-party keys and IDs are delivered to the browser via `config.js` / `VITE_*`
- **File:line:** `apps/form-app/src/lib/config.ts:57-71`, `apps/form-app/src/lib/googlePicker.ts:84-85`, `apps/form-app/src/lib/oneDrivePicker.ts:25`, `apps/form-app/src/vite-env.d.ts:6-10`, `apps/form-app/.env.example:7-20`
- **Description:** `VITE_PIXABAY_API_KEY`, `VITE_GOOGLE_PICKER_API_KEY`, `VITE_GOOGLE_APP_ID`, `VITE_MICROSOFT_CLIENT_ID` and `VITE_SENTRY_DSN` are public by design (browser-only keys). No backend secret, signing key or storage credential appears in `VITE_*` in the repo; the committed `.env.example` uses empty or placeholder values. Source maps are not enabled (`vite.config.ts` sets no `build.sourcemap`, default off).
- **Recommended fix:** Confirm in the provider consoles that the Google API key has HTTP-referrer plus API restrictions (the `_headers` comment suggests it does) and that the Pixabay key is a free-tier, rate-limited key. No code change required.

## Controls verified (no finding)

- `dangerouslySetInnerHTML`: only two uses (`PreviewTab.tsx:183`, `PageBuilderTab.tsx:573`), both injecting the constant `MOBILE_CANVAS_CSS`. No `innerHTML`, `document.write`, `eval`, `new Function` in `src/`.
- Markdown: `AIEditDrawer.tsx:88` uses `react-markdown` v10 with no `rehype-raw`, so model output cannot inject HTML and link URLs go through the default `urlTransform`. `DocsMarkdown.tsx` renders repo-owned static docs.
- Redirects: sign-in `from` comes from react-router location state (`SignIn.tsx:77`), not from a query parameter; `InviteAcceptance` passes `redirectUrl` in router state only; OAuth `callbackURL` is built from `window.location.origin`. Billing redirects are host-validated (`UpgradeModal.tsx:33-44`, `BillingSettings.tsx` `isChargebeeUrl`). Google/Microsoft Connect pass `return_to` as `pathname+search` of the current page (open-redirect risk lives in the server callback, S07).
- Thank-you content is passed through `DOMPurify.sanitize` (`ThankYouScreen.tsx:184`).
- Authorization: `ProtectedRoute` and `useFormPermissions` are UI conveniences only; every state-changing call goes to GraphQL/WebSocket, where enforcement is reviewed in S02, S03 and S13. No client-only gate was found that guards data returned to low-privilege users beyond the server-side over-exposure already listed (S02-06, S07-01).
- OneDrive picker (`OneDriveFolderPicker.tsx:96-104`): `message` events are accepted only when `event.source` is the picker iframe and `channelId` matches a per-mount `crypto.randomUUID()`; the access token is POSTed via a form rather than placed in a URL.
- `window.open` for external pages uses `noopener` on the share panel; other opens target first-party viewer URLs.
- Local/session storage holds only UI state (locale, column layout, coach marks, drafts) plus `organization_id` and the bearer token (S16-04).
