# S13 - Real-time collaboration (Hocuspocus / Y.js)

Scope: `apps/backend/src/services/hocuspocus.ts`, `apps/backend/src/repositories/collaborativeDocumentRepository.ts`, `apps/form-app/src/store/slices/collaborationSlice.ts`. ## Verified-OK controls (traced end to end)

- Connect-time authn/authz: `onAuthenticate` (hocuspocus.ts:173) always runs, resolves a bearer token or cookie via `auth.api.getSession`, then `checkFormAccess(userId, documentName, VIEWER)`. `checkFormAccess` enforces org membership first, then owner, explicit `FormPermission`, then `ALL_ORG_MEMBERS` default; unknown form throws; explicit `NO_ACCESS` fails the hierarchy check. A user cannot join another org's form document or an arbitrary document name (the name is used directly as the Form id, so any non-form name fails the lookup).
- Hocuspocus loads/creates the document only after `onAuthenticate` succeeds (`ClientConnection.ts` ~517-543), so `Database.fetch` is not reachable pre-auth. Pre-auth queue sizes are capped by the library (5 MiB / 1000 messages) and idle timeout is 60s.
- VIEWER write protection: `connectionConfig.readOnly = true` (hocuspocus.ts:248-251) is honoured by the library: `MessageReceiver.ts` drops `SyncStep2` and `Update` messages on read-only connections (lines ~217 and ~259). The `onChange` VIEWER check is therefore redundant defense-in-depth, not the real control.
- No token in the WS URL query string (header/protocol token only), per the comment at hocuspocus.ts:200.
- Y.js `Y.Map` is Map-backed; Y.js updates cannot cause global prototype pollution. Server-side reconstruction (`getFormSchemaFromHocuspocus`) whitelists keys per field type, and runs `sanitizeConditions`, `sanitizeFieldGrading`, `sanitizeGridColumnWidths`, `canonicalizeFields` at the trust boundary.

## Findings

### S13-01 - No re-authorization of live connections (revocation not enforced while connected)
- **Severity:** Medium
- **File:line:** `apps/backend/src/services/hocuspocus.ts:173-272` (only auth point); `apps/backend/src/index.ts:392-421` (server instance never retained elsewhere)
- **Description:** Session validity, org membership, and form permission are checked once, in `onAuthenticate`. The `Hocuspocus` instance is local to `index.ts`; no code calls `closeConnections`/`closeDocument` or re-evaluates permissions. `readOnly` is also fixed at connect time. Grep for `closeConnections|openDirectConnection|hocuspocusServer` finds only the creation and `handleConnection`.
- **Exploit scenario:** An EDITOR (or org member) who opens the builder and keeps the tab open is demoted to VIEWER, removed from the form, removed from the organization, signed out, or has the session revoked (e.g. offboarded employee, compromised account being locked). The socket stays authenticated indefinitely (heartbeat keeps it alive) and the user keeps receiving every live update (form schema, quiz answer keys) and can keep writing to the form document, which is persisted by `store`. They can also reconnect-free tamper with a form they no longer own.
- **Recommended fix:** Track connections by userId/formId (store in `context`) and, on permission/membership/session changes (`updateFormPermission`, `removeFormAccess`, `shareForm`, member removal, ban, sign-out), call `hocuspocus.closeConnections(documentName)` or disconnect that user's connections. Add a periodic re-check (e.g. every few minutes via `beforeHandleMessage`/interval) of `checkFormAccess` and session validity. Make the Hocuspocus instance an exported singleton so resolvers can reach it.

### S13-02 - No message-size, document-size, or rate limits; large persisted docs are amplified on the public submit path
- **Severity:** Medium
- **File:line:** `apps/backend/src/index.ts:400` (`new WebSocketServer({ noServer: true })`, no `maxPayload`); `services/hocuspocus.ts:82-171` (no limits, unbounded `store`); `services/hocuspocus.ts:454` (`Y.applyUpdate` of full stored state); consumers `graphql/resolvers/responses.ts:388,617,725`
- **Description:** `ws` defaults `maxPayload` to 100 MiB and Hocuspocus is not configured with any size limit. Any authenticated EDITOR/OWNER can push arbitrarily large (or pathologically structured: huge Y.Array, deep nesting, millions of tiny items) updates. They are held in memory, compacted via `Y.encodeStateAsUpdate`, and written to `CollaborativeDocument.state` with no cap. `getFormSchemaFromHocuspocus` does a DB read plus a full `Y.Doc` rebuild and a walk of every field, and it is called per request by the unauthenticated `submitResponse` (plus `submit` thank-you path at responses.ts:617). There is no WS message/connection rate limit (the code itself notes `graphqlLimiter` does not apply to WS, index.ts:426). Even a VIEWER can send oversized frames, which are buffered before being rejected as read-only.
- **Exploit scenario:** (a) A low-trust EDITOR (e.g. a member given EDITOR on a shared form) or someone with a stolen session inflates the form's Y.js doc to tens of MB. Every anonymous submission to that form then costs a large DB read plus CPU-heavy Y.js decode/walk, so a trivial submission flood takes down the shared backend (tenant-crossing DoS, since the backend is multi-tenant). (b) Any authenticated user (a free account suffices for a form they can view) sends repeated 100 MiB frames to exhaust memory.
- **Recommended fix:** Pass `maxPayload` (e.g. 1 MiB) to `WebSocketServer`; add a `beforeHandleMessage`/`onChange` check rejecting updates when `Y.encodeStateAsUpdate(doc).length` exceeds a cap (e.g. 2-5 MiB) and cap field/page/option counts; add per-user and per-IP connection and message rate limits for `/collaboration`; cache the reconstructed schema (invalidate on store) so the public submit path does not rebuild it every time (the repo already has `formSchemaCache`).

### S13-03 - No Origin check on the WebSocket upgrade; cookie auth fallback (CSWSH exposure)
- **Severity:** Low (PLAUSIBLE)
- **File:line:** `apps/backend/src/index.ts:465-474` (upgrade router, no Origin validation); `services/hocuspocus.ts:221-237,46-48` (cookie fallback)
- **Description:** The upgrade handler routes `/collaboration` without validating `Origin`, and `onAuthenticate` falls back to the session cookie from the upgrade request when no token is supplied. CORS (`allOrigins`) does not apply to WebSockets. Session cookie is `SameSite=Lax` (better-auth.ts:173), which blocks cross-site cookie delivery, so the practical exposure is same-site, different-origin pages (e.g. any sibling subdomain or the separately hosted form-viewer/user-content origin if it shares the registrable domain, or an XSS there).
- **Exploit scenario:** An attacker-controlled or XSS-compromised page on a same-site subdomain opens `wss://<api>/collaboration` using the victim's cookie, authenticates as the victim for any `formId` the attacker knows, reads the full form schema (including quiz answer keys) and writes edits as the victim.
- **Recommended fix:** In the upgrade handler, reject connections whose `Origin` is not in the trusted-origins list (the same list used for CORS/better-auth). Prefer requiring the explicit token and drop or origin-gate the cookie fallback.

### S13-04 - Editor-controlled strings reach public viewers unsanitized via the persisted Y.js document
- **Severity:** Low (PLAUSIBLE; confirm sinks in S17)
- **File:line:** `apps/backend/src/services/hocuspocus.ts:512-516` (rich text `content`), `:655-669` (`layout.content`, `code`, `thankYouContent`, `customCTAButtonName`, background keys), `:626-633` (labels, hints, options)
- **Description:** The server only whitelists keys; string values authored by any EDITOR are persisted and re-served as-is (the form-viewer reads this document, per the project notes). No HTML sanitation or length bound is applied at the collaboration boundary, and `layout.code`/`content` are free-form strings.
- **Exploit scenario:** A malicious/compromised EDITOR (cross-privilege: a collaborator rather than the owner) stores script/HTML in rich text, thank-you content, or labels. If the viewer renders any of these without sanitization, respondents (anonymous public) are attacked, and the form owner is exposed to the same payload when rendered in the builder.
- **Recommended fix:** Sanitize/validate string fields server-side on read-back (and ideally in `onChange`/`beforeHandleMessage` for writes): enforce max lengths, run rich text through an allow-list sanitizer, and validate `backgroundImageKey`/`backgroundVideoKey` against the expected storage key pattern. Confirm viewer rendering in S17.

### S13-05 - Authentication-failure path is unthrottled and verbose-logged
- **Severity:** Low
- **File:line:** `apps/backend/src/services/hocuspocus.ts:76-79,265-271`
- **Description:** Every failed connection attempt triggers `auth.api.getSession` (DB/session lookup), potentially `checkFormAccess` (DB join), and two `logger.error` calls including the full error object. There is no per-IP/connection rate limiting. Hocuspocus also allows many pending document names per connection (library-capped).
- **Exploit scenario:** An unauthenticated attacker opens many sockets with junk tokens, causing DB load and log flooding (cost, log-injection via attacker-influenced documentName in `logger.info('...${documentName}')`).
- **Recommended fix:** Rate-limit upgrades per IP at the `upgrade` handler, fail fast before DB access when no credentials are present, log failures at warn with truncated/sanitized `documentName`, and avoid logging full error objects.

### S13-06 - `readOnly` is fail-open for any permission other than the literal string `VIEWER`
- **Severity:** Low
- **File:line:** `apps/backend/src/services/hocuspocus.ts:248-251`
- **Description:** `readOnly = permission === PermissionLevel.VIEWER`. Today the only reachable non-VIEWER permissions after `hasAccess` are EDITOR/OWNER, so this is correct, but any future or unexpected value that passes `checkFormAccess` (a new role, a mis-cased DB value, `defaultPermission` values the hierarchy maps leniently) becomes writable by default.
- **Exploit scenario:** A new low-privilege level (e.g. COMMENTER) or data drift grants write access to the form document without any code error.
- **Recommended fix:** Invert: `readOnly = !(permission === EDITOR || permission === OWNER)`. Delete the redundant `onChange` VIEWER branch or make it log and close the connection.

### S13-07 - Mid-stream `connectionConfig.readOnly` relies on mutation of the hook payload
- **Severity:** Low (PLAUSIBLE)
- **File:line:** `apps/backend/src/services/hocuspocus.ts:248`
- **Description:** The handler mutates `connectionConfig` only `if (connectionConfig)`. If a future library change stopped passing it, the guard silently disappears and the connection is writable with only the `onChange` log line left (which does not block the change; the update is already applied and persisted). Library v4.7 behaves correctly (verified), so this is a regression risk, not a current flaw. There is no test noted covering "VIEWER update is rejected".
- **Recommended fix:** Throw if `connectionConfig` is missing; add an integration test that a VIEWER socket's update is not applied or persisted.

### S13-08 - Persisted state not tied to form lifecycle (orphaned/stale documents)
- **Severity:** Info (PLAUSIBLE)
- **File:line:** `repositories/collaborativeDocumentRepository.ts:36-52`; `services/hocuspocus.ts:122-170`
- **Description:** `CollaborativeDocument` is keyed by `documentName` string with no FK to `Form`; `store` upserts unconditionally. No reference to cleanup on form deletion was found in the reviewed scope (deletion path not reviewed). Quiz answer keys and form content may linger after deletion, and a store racing a deletion can resurrect a document.
- **Recommended fix:** Delete the document in the form-deletion transaction and close open connections; make `store` skip if the form no longer exists.

### S13-09 - Single-instance assumption; no cross-instance sync extension
- **Severity:** Info (PLAUSIBLE)
- **File:line:** `services/hocuspocus.ts:85-172`
- **Description:** Only the `Database` extension is registered (no Redis/pub-sub). If the backend runs more than one replica, editors on different replicas diverge and each `store` overwrites the other's full state (last-write-wins on the whole blob), which is an integrity risk. Deployment replica count was not verified.
- **Recommended fix:** Pin to a single replica or add `@hocuspocus/extension-redis`.

### S13-10 - Awareness and sizing not bounded for read-only clients; PII in logs
- **Severity:** Info
- **File:line:** `services/hocuspocus.ts:181-187,253-255,297-299`
- **Description:** Read-only clients can still emit awareness updates (unbounded payload, spoofed display data). Logs record user email on every auth and every change at info level, plus request header/param presence.
- **Recommended fix:** Cap awareness payload size; log user id instead of email; reduce info-level volume.

### S13-11 - Documentation drift: document name is the bare form id, not `form:{formId}`
- **Severity:** Info
- **File:line:** `services/hocuspocus.ts:197` (`const formId = documentName`); `form-app/src/store/collaboration/CollaborationManager.ts:286-298`
- **Description:** CLAUDE.md says documents are named `form:{formId}`, but both client and server use the bare id. Not exploitable (non-form names fail `checkFormAccess`), but any future non-form document type sharing the namespace would be authorized as a form. Client-side name sanitization (`replace(/[^a-zA-Z0-9_-]/g,'')`) is cosmetic; the server does not validate the name format.
- **Recommended fix:** Adopt a prefixed name and parse/validate it server-side with a strict regex before lookup.
