## High

### S21-01 - High (PLAUSIBLE) - R2 secret access key is exposed as a non-sensitive Terraform output and printed by `terraform apply` in public CI logs
- **Severity:** High (PLAUSIBLE; depends on how the runner prints outputs, which I could not observe)
- **File:line:** `infrastructure/multi-cloud/terraform/cloudflare/outputs.tf:52-63` (`nonsensitive(sha256(cloudflare_api_token.r2_access.value))`); `.github/workflows/multi-cloud-deployment.yml:571-586` (`terraform apply -auto-approve` then `terraform output -raw r2_secret_access_key >> $GITHUB_ENV`); scope of the token `cloudflare/r2-api-token.tf:5-20`
- **Description:** The S3 secret for R2 is the SHA-256 of the API token value. The output is wrapped in `nonsensitive()` so it can be passed between workflow steps. Terraform prints every non-sensitive output in the `Outputs:` block at the end of `apply` (also when there are no changes), and the plan prints it as `Changes to Outputs` the first time. The workflow only calls `::add-mask::` for the Azure storage key (line 522), never for the R2 secret, and the value is not a GitHub secret so the runner has nothing to auto-mask. The repo is public, and Actions logs of a public repo are readable by anyone. The token's policy is account-wide (`"com.cloudflare.api.account.<id>" = "*"`) with Storage Write, Bucket Item Read and Bucket Item Write, so the leaked pair reaches every bucket in the Cloudflare account, including the private response-file and export buckets.
- **Exploit scenario:** An unauthenticated person opens the Actions log of a `main` push (dev deploys on every push) in the public repo, copies the `r2_access_key_id` and `r2_secret_access_key` lines from the apply output, and uses any S3 client against `https://<account>.r2.cloudflarestorage.com` to list, download, overwrite or delete respondent uploads and PDFs, and to plant content on the public CDN bucket. Dev and production use the same account (S21-07), so this is not limited to dev data.
- **Recommended fix:** Verify first by reading a recent apply log and rotating the token if the value is visible. Drop `nonsensitive()` and read the value inside the job with `terraform output -raw` followed immediately by `echo "::add-mask::$VALUE"` before writing to `$GITHUB_ENV`. Better, stop round-tripping the key through Terraform outputs: store it in GitHub environment secrets or Azure Key Vault. Narrow the token (S21-07).

### S21-02 - High (PLAUSIBLE) - Documented production DB path is cleartext Postgres to a public Azure Container Instance FQDN
- **Severity:** High (PLAUSIBLE; carries and raises S14-07)
- **File:line:** `PGBOUNCER-MIGRATION.md:49-56,67-75`; `apps/backend/.env.example:21-33`; `infrastructure/multi-cloud/terraform/azure/main.tf:99-103` (Container App Environment has no `infrastructure_subnet_id`, so the app runs outside any VNet); `main.tf:125-133` (falls back to `var.postgres_connection_string`, which is the `DATABASE_URL` secret, when `DIRECT_URL` is empty)
- **Description:** The guide points apps at `dculus-pgbouncer.<hash>.centralindia.azurecontainer.io:5432` with `sslmode=disable`, "TLS is handled between PgBouncer and PostgreSQL". An `*.azurecontainer.io` name is the public DNS label of an ACI group. The Container Apps environment is not VNet-integrated, so the leg from the backend to PgBouncer can only cross the public internet (or Azure's backbone but still not private). That leg carries the `dculus_admin` password (a SCRAM or MD5 exchange without TLS), every SQL statement and all response data. Whether production actually uses this string is not in the repo; the Terraform comment (main.tf:125) says the direct, TLS server is used, so this applies only if `DATABASE_URL` is the PgBouncer URL or `DIRECT_URL` is empty.
- **Exploit scenario:** An on-path attacker (compromised transit network, another tenant in the same Azure region that can ARP/route-poison, a rogue hop) sniffs the cleartext Postgres stream, recovers `dculus_admin` credentials and all submitted form data, and can inject or alter queries. Separately, any scanner on the internet can reach `5432` on a public ACI IP and attempt password guessing against an admin-named role, and the hostname and role name are published in this repo (S21-17).
- **Recommended fix:** Put PgBouncer behind a private endpoint or VNet and integrate the Container Apps environment into the same VNet. Require TLS on both legs (`sslmode=require` minimum, `verify-full` with the CA preferred) and restrict the ACI group with NSG/firewall to the app egress. Replace `dculus_admin` with a least-privilege app role (S21-09). Fix `.env.example` and the migration doc, and fail startup if a non-local URL has `sslmode=disable` (see S14-07).

## Medium

### S21-03 - Medium - Backend origin is directly reachable on its `*.azurecontainerapps.io` FQDN, bypassing Cloudflare
- **File:line:** `infrastructure/multi-cloud/terraform/azure/main.tf:378-390` (`ingress` has `external_enabled = true`, no `ip_security_restriction`, no client-cert or header gate); `cloudflare-service-domain/main.tf:19-26` (proxied CNAME to the same FQDN); `outputs.tf:2-9`; `environments/staging/terraform.tfvars:6` (staging `better_auth_url` is the raw Container Apps FQDN)
- **Description:** The production hostname `form-services.dculus.com` is a proxied CNAME to the Container App's public FQDN, but nothing stops a client from calling the FQDN directly. Any WAF, rate-limit, Bot or geo rule configured at Cloudflare is skipped, and the app trusts `cf-connecting-ip` and `cf-ip*` headers without verifying the origin (S04-09), so a direct caller can also spoof client IP and geo. The FQDN is also public knowledge: it is in Terraform outputs and the staging tfvars in this public repo, and is discoverable by certificate transparency.
- **Exploit scenario:** An attacker floods `POST /graphql` submissions or auth endpoints at the FQDN to avoid any Cloudflare rate limit (S04-06), sets `cf-connecting-ip` to rotate the apparent client and dodge per-IP limits, and forges `cf-ipcountry` to pollute analytics.
- **Recommended fix:** Add `ip_security_restriction` blocks for Cloudflare's published ranges (or use Cloudflare Tunnel / authenticated origin pulls with a shared header secret checked in middleware). Make the backend honour `cf-*` headers only when the request came through that gate. Use `better_auth_url = ""` in staging so it resolves to the Cloudflare hostname like the other environments.

### S21-04 - Medium - Every secret is a plain `env` value on the Container App (carries S15-01)
- **File:line:** `infrastructure/multi-cloud/terraform/azure/main.tf:125-333` (`DATABASE_URL`, `DIRECT_URL`, `BETTER_AUTH_SECRET:141`, `PUBLIC_S3_SECRET_KEY`, `ADMIN_PASSWORD:219-222`, `EMAIL_PASSWORD`, `CHARGEBEE_API_KEY:260`, `CHARGEBEE_WEBHOOK_PASSWORD`, `AI_PRIMARY_API_KEY:286`, `AI_FAST_API_KEY:301`, Google/Microsoft client secrets, Pexels/Pixabay keys). The file has no `secret {}` block and no `secret_name` reference. `variables.tf` marks the variables `sensitive`, which only hides them from CLI output.
- **Description:** Values are stored in the Container App definition (readable with `Microsoft.App/containerApps/read`, not only `listSecrets`), in revision history, and in Terraform state. `ADMIN_PASSWORD` is used only by the one-shot `setup-admin.ts` (S15-01) but sits permanently in the internet-facing process environment. The `AI_*_API_KEY` is `azurerm_cognitive_account.ai.primary_access_key`, a management-plane secret, copied into app config as well.
- **Exploit scenario:** Anyone with Reader on the resource group, a CI step that runs `terraform show`/`az containerapp show`, or an env-dump bug (S05 `/debug`, an SSRF into the container) obtains the Better Auth signing secret (forge sessions as any user, including superAdmin, because cookie cache is on - see S01-03), the DB admin password, Chargebee key and the superAdmin password.
- **Recommended fix:** Move to Container Apps `secret` entries (ideally Key Vault references with a user-assigned managed identity) and reference them with `secret_name`. Remove `ADMIN_*` from the long-running container and run `admin:setup` as a one-off job. Prefer Entra ID auth to Azure OpenAI over the account key (the account already has a SystemAssigned identity). Rotate everything after the migration, since old values stay in state and revision history.

### S21-05 - Medium - `NODE_ENV` is set to `dev` / `staging`, which silently selects non-production behaviour (confirms S05-02, S01-03)
- **File:line:** `infrastructure/multi-cloud/terraform/azure/main.tf:169-172` (`value = var.environment`); `main.tf:69-74` (`localhost_origins` added to CORS for non-production); `variables.tf:13-17`
- **Description:** Terraform deploys `NODE_ENV=dev` and `NODE_ENV=staging`, not `development`/`production`. Backend checks that test `=== 'production'` or `=== 'development'` therefore take neither or the wrong branch (S05-02 stack traces, Apollo Sandbox origins; S01-03 better-auth rate limiting only enabled in `production`). In addition the CORS list for dev and staging includes `http://localhost:3000/3002/5173` with `credentials: true`. The two non-production environments are internet-facing, use real Chargebee, R2 and email, and share the Cloudflare zone and the Azure subscription with production.
- **Exploit scenario:** A malicious page running on a victim's `localhost` (dev tool, compromised npm package) or an attacker on a shared machine calls the staging/dev API with the victim's cookie because `localhost` is a credentialed origin; unthrottled auth endpoints on dev/staging allow credential stuffing and OTP guessing, which is the only gate on staging admin data.
- **Recommended fix:** Map the Terraform environment to a fixed `NODE_ENV` (`production` for every deployed environment) and add a separate flag such as `APP_ENV` for display purposes. Drop localhost origins from deployed environments. Treat dev/staging as internet-facing and keep rate limits, email verification and generic errors on.

### S21-06 - Medium - No WAF, rate limit, HSTS or security-header configuration in IaC; edge protection relies on an unmanaged zone setting; CSP missing on the SPAs (carries S17-03, S18-01, S16-03)
- **File:line:** `infrastructure/multi-cloud/terraform/cloudflare/embed-framing.tf:1-131` (only ruleset in the stack); `apps/form-app/public/_headers:1-11`, `apps/admin-app/public/_headers:1-11` (no CSP, `X-Frame-Options`, `X-Content-Type-Options`, HSTS); `apps/form-viewer/public/_headers:30-35` (`/*` only `frame-ancestors 'self'`, no `script-src`)
- **Description:** (a) A grep of the Terraform tree shows no `cloudflare_ruleset` for WAF custom rules, rate limiting, managed rules, `cloudflare_zone_settings_override`/`cloudflare_zone_setting` (HSTS, min TLS, always-HTTPS, TLS 1.3), or bot management. (b) The file header says that the zone's "Add security headers" Managed Transform provides `X-Frame-Options: SAMEORIGIN` and `Referrer-Policy` for every `*.dculus.com` response; that setting lives outside Terraform, so the protection can vanish with one dashboard click and no PR shows it. (c) The one rule that is managed removes `X-Frame-Options` and sets `frame-ancestors *` for viewer `/embed/*` across all environments (and the `/embed/` expression is zone-wide), which is the intended design but is the root of S17-03: the per-form opt-out is not enforced at the edge. (d) form-app and admin-app, which hold the authenticated and superAdmin UIs, ship no CSP at all (S18-01), so any XSS, for example from the sanitizer gap in S16-03, runs with no second line of defence.
- **Exploit scenario:** A stored XSS in the response viewer or rich-text path executes in the admin-app origin without a CSP, steals nothing from cookies (HttpOnly) but drives GraphQL as the superAdmin. Independently, a dashboard change to the Managed Transform removes clickjacking protection from the admin and form-app with no code review, and an attacker frames the admin UI. With no edge rate limit, auth, OTP and submission endpoints are throttled only by the app (S04-06).
- **Recommended fix:** Manage the security headers in Terraform (`cloudflare_ruleset` `http_response_headers_transform`, scoped by host) or in each `_headers` file: `Content-Security-Policy` with `script-src 'self'`, `frame-ancestors 'none'` for admin-app and form-app, `Strict-Transport-Security: max-age=31536000; includeSubDomains`, `X-Content-Type-Options: nosniff`, `Permissions-Policy`. Add Terraform-managed rate-limiting rules on `/graphql`, `/api/auth/*`, `/upload` and a WAF managed ruleset, and codify HSTS/min TLS version through zone settings.

### S21-07 - Medium - One account-wide R2 token per environment, all buckets, read and write
- **File:line:** `infrastructure/multi-cloud/terraform/cloudflare/r2-api-token.tf:5-20`; `apps/backend` uses the one key for both buckets (S06-15)
- **Description:** The policy resource is `com.cloudflare.api.account.<id> = "*"`, so each environment's token can read, write and delete objects in every R2 bucket in the account, including the other environments' private buckets. Bucket names are `dculus-forms-private-<env>` in the same account (`r2-buckets.tf:2-9`). Permission groups include Storage Write, which can create or delete buckets. The same credential serves the public CDN bucket and the private bucket in the backend.
- **Exploit scenario:** A compromise of the weaker dev or staging backend (S21-05, S21-04) gives the attacker the dev token, which reads and deletes production respondent files and exports. Likewise a leaked token (S21-01) is account-wide.
- **Recommended fix:** Scope the policy resource to the specific bucket per environment (R2 bucket-level resources) or create one token per bucket with least privilege (read+write item only, no bucket-level write). Use separate Cloudflare accounts for production or a separate token per bucket class, and rotate. Add lifecycle rules on the private bucket (`temp-exports/` 5h expiry is currently application-enforced only).

### S21-08 - Medium - `docker-compose.yml` runs Postgres with `trust` auth and pgAdmin with a default password on all host interfaces
- **File:line:** `docker-compose.yml:13-18` (`POSTGRES_HOST_AUTH_METHOD: trust`, `listen_addresses='*'`, `log_statement='all'`), `:14-15` (`"5433:5432"` binds `0.0.0.0`), `:27-35` (`dpage/pgadmin4:latest`, `PGADMIN_DEFAULT_PASSWORD: admin`, port `5050` on all interfaces)
- **Description:** Docker publishes `host:container` ports on all interfaces unless a host IP is given. Postgres accepts any connection with no password as the superuser `dculus`. pgAdmin has a published, default `admin@dculus.com` / `admin` login and can connect to that database. `log_statement=all` writes every query (including PII from form responses used in local testing) into the container log. The file's own comment warns against using it elsewhere, but developers commonly run it on laptops on shared Wi-Fi, and it is also the model that CI/E2E and the `.env.example` copy.
- **Exploit scenario:** A person on the same café or office network connects to `<laptop-ip>:5433` without credentials, dumps the development database (which may hold copied production data), and uses `COPY ... FROM PROGRAM` to run code in the container; or logs in to pgAdmin on `:5050` with `admin`/`admin`.
- **Recommended fix:** Bind to loopback (`"127.0.0.1:5433:5432"`, `"127.0.0.1:5050:5050"`), use `scram-sha-256` with a password from `.env`, drop `log_statement='all'`, pin `postgres` and `pgadmin4` to versions/digests, and set a random pgAdmin password.

### S21-09 - Medium - Runtime uses the same high-privilege DB role as migrations; TLS is only enforced on one branch of the URL builder
- **File:line:** `infrastructure/multi-cloud/terraform/azure/main.tf:125-139`; `apps/backend/Dockerfile:56-58,66-68` (migration runs on every container start)
- **Description:** `DATABASE_URL` is built from `postgres_direct_url` (the migration/DIRECT_URL credential, `dculus_admin` per the docs), and `DIRECT_URL` is passed too, so the web-facing process holds a DDL-capable credential. The `sslmode=require` suffix is appended only when the URL has no `?` at all; a URL with other query parameters (for example `?schema=public`) gets `&connection_limit=2` without `sslmode`, and a URL that already contains `connection_limit=` is passed through unchanged (including `sslmode=disable`). TLS therefore depends entirely on the secret's contents, which this repo's own docs set to `disable`.
- **Exploit scenario:** SQL injection or an RCE-class bug in any resolver (S11, S10) runs as the table owner and can `DROP`/`ALTER` tables, read other schemas on the shared server (`dculus-shared-postgres` hosts other products according to `PGBOUNCER-MIGRATION.md`, such as an `indiastats_cms_db`), and a downgraded URL silently drops transport security.
- **Recommended fix:** Split roles: a migration role used only by a release job (not present in the serving container) and a least-privilege app role (DML only on the `dculus_forms_*` database). Build the URL with a validated helper that always sets `sslmode=require` or `verify-full` (reject `disable` for non-local hosts), and add a Terraform `validation` on the variable. Use a dedicated database server (or at least role) per environment.

## Low

### S21-10 - Low - Dockerfile: ineffective `.dockerignore`, unpinned base image, single stage with build tooling and all sources, migrations run on every start
- **File:line:** `apps/backend/Dockerfile:5` (`node:22-alpine`, no digest), `:11` (global pnpm install), `:25` (`COPY . .`), `:56-58` (single-stage, TODO), `:66-68` (start script runs `npx prisma migrate deploy` for every replica, then optional seed); `apps/backend/.dockerignore` (not used, see below)
- **Description:** `build.yml:666-669` builds with `context: .` and `file: apps/backend/Dockerfile`. Docker reads `.dockerignore` from the context root (or `<Dockerfile>.dockerignore` next to the Dockerfile). The repo has no root `.dockerignore` and no `apps/backend/Dockerfile.dockerignore`, so the carefully written `apps/backend/.dockerignore` (with the "SECURITY: Exclude all .env files" note) has no effect. In CI the checkout contains no `.env` files, so impact is limited to `.git` history, `.claude/`, docs and static files being baked into a public Docker Hub image. A developer who builds locally with `.env` files present would bake secrets into layers. The image also keeps dev dependencies, TypeScript sources and pnpm, enlarging the attack surface, and `chown -R backend /app` makes the app code writable by the runtime user. Every replica start runs `migrate deploy`, so deploys with `max_replicas=10` race on the advisory lock and the failure path blocks startup (availability, not confidentiality). The `node:22-alpine` tag is mutable.
- **Exploit scenario:** A developer runs `docker build -f apps/backend/Dockerfile .` and pushes from a laptop with `apps/backend/.env` present, publishing the production keys inside a layer of a public image.
- **Recommended fix:** Add `/.dockerignore` (copy the `apps/backend/.dockerignore` rules and add `.git`, `.claude`, `**/.env*`, `docs`, `screenshot`). Use a multi-stage build that copies `pnpm deploy --prod` output, pin the base by digest, run as non-root with a read-only root filesystem, and move migrations to a one-shot release job.

### S21-11 - Low - Mutable image tag, no digest pinning or provenance
- **File:line:** `azure/environments/*/terraform.tfvars:4-5` (`container_image = "dculus/forms-backend"`, `container_image_tag = "latest"`); `azure/main.tf:26` (`local.full_container_image`); `.github/workflows/multi-cloud-deployment.yml:622` (overrides the tag at apply time)
- **Description:** The checked-in default is `latest` on a public Docker Hub repository. The workflow normally passes a version or SHA tag, but a local `terraform apply` or the destroy/re-plan paths fall back to `latest`, and tags remain mutable. The Container App is referenced by tag, not digest, so a changed tag is pulled on the next revision with no signature or SBOM check.
- **Exploit scenario:** Anyone who obtains push access to the Docker Hub namespace (stolen token) republishes a tag that production then runs, with all the secrets of S21-04 in its environment.
- **Recommended fix:** Pin by digest (`image@sha256:...`) passed from the release workflow, remove the default `latest`, sign images (cosign) and enable Docker Hub 2FA and scoped access tokens, or move to a private registry (ACR with managed identity pull).

### S21-12 - Low - `RUN_SEED=true` is forced on every deployment, including production
- **File:line:** `.github/workflows/multi-cloud-deployment.yml:641` (`TF_VAR_run_seed: true`); `azure/main.tf:269-272`; `apps/backend/Dockerfile:59-64`; `apps/backend/src/scripts/seed.ts:86-94` (idempotency check on the template table)
- **Description:** The Terraform variable defaults to `false` but the deploy workflow overrides it to `true` for all environments. The seed is idempotent (skips when any template exists), failures are swallowed (`|| echo "Seed failed, continuing anyway"`), and it uploads files from `static-files/` to the public R2 bucket under the app credentials using the unvalidated filename-to-type mapping. It is therefore low risk today, but if the templates table is ever emptied or a new environment is created it silently publishes repo files to the public CDN, and the seed code path (including `dotenv/config`) runs in production on each cold start.
- **Exploit scenario:** After a failed or partial restore that leaves the template table empty, the next deploy re-uploads every file under `static-files/` to the public bucket, overwriting same-named keys.
- **Recommended fix:** Default `run_seed` to false in the workflow for production, run seeding as an explicit one-off job, and fail loudly when seeding errors.

### S21-13 - Low - Azure AI Services account is public with key auth, one key for both models
- **File:line:** `infrastructure/multi-cloud/terraform/azure/ai.tf:7-28` (`public_network_access_enabled = true`, no `local_auth_enabled = false`, no `network_acls`); `azure/main.tf:286-307`
- **Description:** The Foundry account accepts requests from any IP with the primary key; both the "primary" and "fast" models share it, and the key is also in plain Container App env (S21-04). `project_management_enabled` and a SystemAssigned identity are set but unused for auth.
- **Exploit scenario:** A leaked key (S21-04, S21-01-style log leakage, or a backend env dump) lets an attacker run unlimited `gpt-6-luna` traffic from anywhere against the org's quota and billing (cost abuse, S09).
- **Recommended fix:** Use Entra ID (managed identity, `Cognitive Services OpenAI User` role) from the backend, set `local_auth_enabled = false`, restrict `network_acls` to the app's egress or a private endpoint, and add a budget alert and per-deployment TPM caps.

### S21-14 - Low (PLAUSIBLE) - Production CORS allows `*.pages.dev` fallback origins and staging points auth at a raw Azure hostname
- **File:line:** `infrastructure/multi-cloud/terraform/azure/main.tf:62-66,76-88` (`pages_dev_domains` added in all environments with `credentials: true`); `azure/environments/staging/terraform.tfvars:6`
- **Description:** In production CORS includes `https://form-app-production.pages.dev`, `viewer-app-production.pages.dev`, `form-admin-app-production.pages.dev`. Those names are global on the `pages.dev` namespace; if a project is ever deleted or renamed (the destroy workflow exists) another Cloudflare account can claim the same project name and obtain a credentialed origin to the production API. The origin list also lets a stale or old deployment of the SPA reach the API. Staging hard-codes a `*.eastus.azurecontainerapps.io` URL in a `centralindia` deployment, which suggests drift between the checked-in tfvars and the live environment.
- **Exploit scenario:** After a Pages project deletion, an attacker registers the same project name, serves a page on the trusted origin and makes credentialed GraphQL calls with a logged-in victim's cookie (SameSite=Lax cookies are sent on cross-site `fetch` only if the cookie is same-site; `pages.dev` is a different site, so impact depends on `SameSite` settings, hence PLAUSIBLE).
- **Recommended fix:** Remove `pages.dev` origins from production, or gate them to non-production. Keep the allow-list to custom domains only, and reconcile staging `better_auth_url`.

### S21-15 - Low - Terraform state and repo hygiene: shared storage-account key, no root ignore rules, provider binary committed
- **File:line:** `.github/workflows/multi-cloud-deployment.yml:515-523` (`az storage account keys list` then `ARM_ACCESS_KEY`); `azure/environments/*/backend.tf` (single storage account `dculusterraformstates` for every environment and component); `.gitignore` (no `*.tfstate`, `*.tfvars`, `.terraform/` rules; only `cloudflare/` and `cloudflare-pages/` carry their own `.gitignore`); tracked files under `infrastructure/multi-cloud/terraform/neon-postgres/.terraform/providers/.../terraform-provider-neon_v0.13.0`
- **Description:** (a) CI authenticates to the state backend with the storage account's full access key, retrieved at runtime, rather than Azure AD data-plane RBAC; any job that can run `az` as that principal gets read/write on every state file, and state files contain every secret listed in S21-04 and the R2 token value. (b) The root `.gitignore` has no Terraform rules, and `azure/`, `neon-postgres/`, `cloudflare-service-domain/` and `cloudflare-pages-*` have no `.gitignore`, so a local `terraform apply` followed by `git add .` would commit `terraform.tfstate` (including all secrets) to a public repo. (c) A downloaded provider binary under `neon-postgres/.terraform/` is tracked in git; unreviewed binaries in the tree are a supply-chain and hygiene issue (see S22, S23). Soft delete, versioning, firewall and private networking of the state storage account cannot be checked from the repo.
- **Exploit scenario:** A contributor runs Terraform locally for the azure stack, then commits all files; the state with plaintext secrets lands in the public repo. Or a malicious PR replaces the committed provider binary (which `terraform init` may reuse when the lock hash matches an earlier install in a developer's working copy).
- **Recommended fix:** Add Terraform patterns to the root `.gitignore` (`**/.terraform/`, `*.tfstate*`, `*.tfvars` except the reviewed per-env files via an explicit allow-list, `tfplan`), `git rm -r --cached` the provider binary, and enable `use_azuread_auth = true` with RBAC roles (Storage Blob Data Contributor scoped per container) instead of the account key. Split the state account per environment or at least restrict production state to the release pipeline identity.

### S21-16 - Low - Public CDN (R2 custom domain) serves user-uploaded content without nosniff/CSP sandbox and caches everything
- **File:line:** `infrastructure/multi-cloud/terraform/cloudflare/r2-custom-domains.tf:12-37` (`cache_level = "cache_everything"`, `edge_cache_ttl = 7200`, `browser_cache_ttl = 3600`; legacy `cloudflare_page_rule`; no response-header transform for `public-cdn-*`)
- **Description:** User-controlled uploads (avatars, logos, backgrounds, templates; types are client-declared per S06-04) are served from `public-cdn-<env>.dculus.com`, a sibling host of the application domains under the same registrable domain, with no `X-Content-Type-Options: nosniff`, no `Content-Security-Policy: sandbox`/`default-src 'none'`, and no `Content-Disposition` for non-image types. This amplifies S06-04 (SVG/HTML stored XSS). The stack's own `cloudflare_ruleset` is limited to one zone entrypoint (embed-framing.tf), so adding rules needs care. Cache-everything with a 2 hour edge TTL also means a deleted or replaced object (S06-06) stays served for hours.
- **Exploit scenario:** An authenticated user uploads an HTML/SVG file declared as `image/png`; R2 serves it with the stored content type and the browser renders it on a `*.dculus.com` origin, where script runs and can target other `*.dculus.com` sites (cookie tossing, phishing under a trusted domain).
- **Recommended fix:** Add a response-header transform rule for the `public-cdn-*` hosts (`X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`), restrict served types, and move to a separate registrable domain for user content. Replace the deprecated Page Rule with a cache ruleset and purge on delete.
