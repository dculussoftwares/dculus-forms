# S17 - form-viewer (public)

Scope: `apps/form-viewer/src/**`, `index.html`, `public/_headers`, `public/config.js`, `vite.config.ts`. Because the viewer renders forms through shared code, I also traced the sinks in `packages/ui` that it calls: `renderers/FormFieldRenderer.tsx`, `layouts/shared/ThankYouScreen.tsx`, `introContent.tsx`, `surface.tsx`, `rich-text-editor/LexicalRichTextEditor.tsx`, plus `@lexical/link` and `lexical` 0.52.0 sources, `packages/utils` (`getImageUrl`, `mentionSubstitution`), and `apps/backend/src/index.ts` (`/respondent-oauth-callback`). Server-side enforcement is covered by S04, S06 and S01 and is cross-referenced, not repeated.

Review-only; no source modified. No secrets included.

## S13-04 resolved: editor-written strings do NOT reach respondents as executable HTML

Definitive answer: **No XSS path exists from Y.js-authored content to a public viewer.** S13-04 can be closed as "not exploitable in the viewer" and downgraded to Info (unbounded length and unvalidated content remain a hygiene point, see S17-07 and S17-10). The traced sinks:

| Content (editor-controlled) | Viewer render path | Result |
|---|---|---|
| Titles, labels, hints, placeholders, prefix/suffix, option text, CTA button name (`layout.customCTAButtonName`, `StandardIntroLayout.tsx:99`) | Plain React text/attribute children | Escaped by React. |
| Rich-text field `content` | `FormFieldRenderer.tsx:115-125` (weak strip) then `LexicalRichTextEditor value=` (`InitialContentPlugin`: `DOMParser` then `$generateNodesFromDOM`) | `DOMParser` documents are inert (no script, no image loads). Lexical rebuilds a node tree from only the registered nodes (Heading, Quote, List, Link, AutoLink, Mention, text). `<script>`, `<img>`, `<svg>`, `<iframe>`, `style`, `class` and `on*` are dropped, not copied. |
| `layout.content` (intro) | `introContent.tsx:134` into the same Lexical component | Same as above. |
| `layout.thankYouContent` and the server's resolved `thankYouMessage` | `ThankYouScreen.tsx:184` runs `DOMPurify.sanitize` and then Lexical. The server step (`substituteMentions`) HTML-escapes respondent values. | Triple-layered. |
| Links inside rich text | `@lexical/link` `LinkNode.sanitizeUrl` (`LexicalLinkNode.ts:190-196`) allows only http, https, mailto, sms and tel, and applies on `createDOM` (`:165`) and on click (`ClickableLinkExtension.ts:84`) | `javascript:` and `data:` hrefs are neutralised to `about:blank`. |
| `backgroundImageKey` / `backgroundVideoKey` | `getImageUrl` (`packages/utils/src/index.ts:164-184`) enforces `^[a-zA-Z0-9/_.-]+$` and rejects `..`, then the key is appended to the fixed CDN host. The result goes into `url(...)` and `<video src>`. | The character class excludes `)`, quotes, spaces and `:`, so there is no CSS or URL breakout and no host change. |
| `customBackGroundColor`, `textColor`, `backgroundDominantColor` | React `style` objects (single property, assigned through the CSSOM) | No cross-property injection. A non-colour value is simply invalid CSS. |
| `layout.code`, theme and spacing enums | Used only as lookup keys with fallbacks | No sink. |

There is no `dangerouslySetInnerHTML` or `innerHTML` anywhere in `apps/form-viewer/src` or the viewer's `packages/ui` render paths (the one `innerHTML` hit in `FormFieldRenderer.tsx:124` is a read of an inert `DOMParser` document). There is also no custom thank-you redirect URL feature: `redirectUrl` and `thankYouRedirect` do not exist in `packages/types`, the backend or the form-app, so that part of the section brief has nothing to attack. The only `window.location` navigations are the OAuth `returnTo` (S17-02), `/f/${shortUrl}` in `QuizResultPage.tsx:146` (the `:shortUrl` route param is placed in a path, so it cannot change host or scheme), and a reload.

## Verified-OK controls

- `embedBridge.ts` outbound `postMessage` always targets one exact origin (never `'*'`), and the origin is re-parsed with `new URL` and compared to `url.origin === raw` (`parseHostOrigin`, `:96-105`). Inbound messages require both `event.source === window.parent` and `event.origin === targetOrigin` (`:263-265`). Only ids and a height cross the frame; no answer data is posted.
- `embed.js` (host side) trusts only `VIEWER_ORIGIN` derived from its own `<script src>`, pins each message to the frame it created (`event.source === record.iframe.contentWindow`), uses `encodeURIComponent` on every URL part, uses `textContent` for the label, and its only `innerHTML` is a constant (`&times;`).
- `public/_headers`: `/*` gets `frame-ancestors 'self'` (hosted `/f/*` is not frameable by other sites) and only `/embed/*` is `frame-ancestors *`; `X-Content-Type-Options: nosniff`; `Referrer-Policy: strict-origin-when-cross-origin`. The header ordering comment (`! Content-Security-Policy`) is correct for Cloudflare Pages.
- `OAuthCallback.tsx` does verify the `ott` before navigating, and `SignInOptions` builds `returnTo` from `pathname + search` with `encodeURIComponent`.
- Sign-in/domain gating is enforced by the server (`accessStatus`, `SIGN_IN_REQUIRED`, `DOMAIN_REJECTED` returned by `formByShortUrl` and re-checked in `submitResponse`; see S04-14). The viewer's `emailDomainLooksAllowed` is only a UX pre-check and the code says so. No password-gated form mode exists in the viewer.
- `getOrCreateSessionId` uses `crypto.randomUUID()` with a 24 h TTL; the session id is a tracking identifier, not a credential.

## Findings

### S17-01 - `/auth/callback` accepts an attacker-supplied one-time token (login CSRF / session fixation into the victim's browser)
- **Severity:** Medium (PLAUSIBLE; depends on better-auth one-time-token lifetime and on the attacker being able to mint a token for their own account, which the default `oneTimeToken()` plugin allows for any signed-in user)
- **File:line:** `apps/form-viewer/src/pages/OAuthCallback.tsx:16-44` (reads `ott` straight from the query string and calls `authClient.oneTimeToken.verify`); `apps/form-viewer/src/lib/auth-client.ts:12-21` (any `set-auth-token` response header is stored as the respondent bearer); `apps/form-viewer/src/lib/respondentAuth.ts:15-17`
- **Description:** The callback has no binding between the browser that started the sign-in and the browser that redeems the token (no `state`, nonce or pending-login marker in storage). Whoever opens `https://<viewer>/auth/callback?ott=<token>&returnTo=/f/<form>` gets the session that the token belongs to. The token is not tied to the victim.
- **Exploit scenario:** An attacker signs in to their own account (Google or email OTP), generates a one-time token for it, and sends the victim a link to the callback with that token and a `returnTo` pointing at a real, trusted form on the same domain. The victim's browser verifies the token, stores the attacker's bearer in localStorage, and shows the form as signed in as the attacker (`signedInEmail` is set, so `draftsEnabled` is true at `FormViewer.tsx:237` and the save-and-resume autosave starts writing the victim's in-progress answers into the attacker's `ResponseDraft`). On identity-gated forms the victim's submission is attributed to the attacker's identity, and the attacker can later open "my response". A careful victim sees the attacker's email in `RespondentBadge`, which is the only visible signal.
- **Recommended fix:** Bind the redemption to the initiating browser: before the Google redirect (`SignInOptions.tsx:30-40`), write a random nonce to `sessionStorage` and carry it through `returnTo`/`state` to the backend, which should embed it in the one-time token request, and refuse to verify if the callback does not echo the stored nonce. Alternatively, mint the token only for the browser that holds a first-party "sign-in pending" cookie. Keep OTT lifetime at or below 60 s and strip `ott` from the URL via `history.replaceState` before the network call (also addresses the S01-11 leak vector on the error path, where `ott` stays in the address bar).

### S17-02 - `returnTo` open-redirect guard is bypassable with a tab/newline after the first slash
- **Severity:** Low
- **File:line:** `apps/form-viewer/src/pages/OAuthCallback.tsx:11-13` (`/^\/[^/\\]/`), used at `:16,41,53,57`; the same regex is duplicated in `apps/backend/src/index.ts:209-211` (S01 reported the backend check as correct)
- **Description:** The pattern rejects `//x` and `/\x` but accepts `/%09/evil.example` (a literal TAB, CR or LF as the second character), because that character is not `/` or `\`. The WHATWG URL parser strips ASCII tab and newline from the input before parsing, so `window.location.replace("/\t/evil.example")` resolves to `//evil.example`, a protocol-relative URL to another host. The viewer route is directly reachable, so the viewer-side check is the only gate for a hand-crafted `/auth/callback?...&returnTo=/%09/evil.example` link (the backend check is bypassed identically, so it is not a second layer).
- **Exploit scenario:** An attacker mails a link `https://<viewer>/auth/callback?error=x&returnTo=/%09/evil.example` (no token needed; `?error` or a missing `ott` produces the error screen). The victim sees the branded "Sign-in was cancelled or failed" page and clicks "Back to form", landing on the attacker's phishing page. With a valid attacker `ott` (S17-01) the redirect fires automatically with no click.
- **Recommended fix:** Parse instead of pattern-match: `const u = new URL(value, window.location.origin); return u.origin === window.location.origin ? u.pathname + u.search + u.hash : '/'`. Reject any control character (`/[\u0000-\u001f\u007f]/`) first. Fix the backend copy the same way and add the `/\t/` and `/\n/` cases to the tests.

### S17-03 - Per-form embed opt-out is enforced only in the client, while `/embed/*` is frameable by every site
- **Severity:** Low
- **File:line:** `apps/form-viewer/src/pages/EmbedFormViewer.tsx:79,135-143` (`settings.embed.enabled === false` renders a card but the Apollo query has already fetched the full public form); `apps/form-viewer/public/_headers` (`/embed/*` gets `frame-ancestors *` unconditionally)
- **Description:** The owner's "disable embedding" switch changes only what the React app draws. The HTTP framing policy is static and `formByShortUrl` still returns the schema. The same form is also reachable framed through `/embed/<shortUrl>` regardless of the opt-out, so any site can frame it and overlay a transparent decoy (clickjacking). Impact is limited because the public form carries no session-bound action: sign-in is refused inside frames (`requiresSignIn` card, cookies are `sameSite: 'lax'`), and an anonymous submission does not use ambient authority. The residual risk is forced or tricked anonymous submissions and counting, plus branding or content reuse that the owner explicitly turned off.
- **Exploit scenario:** An attacker frames `/embed/<shortUrl>` on a hostile page, positions it under a decoy button, and gets a respondent to submit an answer set or burn the owner's plan quota (S04-05) while believing they clicked something else.
- **Recommended fix:** Treat the opt-out as a server decision: have `formByShortUrl` (or a dedicated `embedAllowed` field) refuse form content when the request arrives with `Sec-Fetch-Dest: iframe` for a form with embedding disabled, and do not rely on UI for it. Optionally allow-list embed hosts per form and emit a matching dynamic `frame-ancestors` from a Pages Function. Keep the `/f/*` policy as is.

### S17-04 - Respondent bearer token lives in `localStorage` for days, with the same privileges as a normal account session
- **Severity:** Low
- **File:line:** `apps/form-viewer/src/lib/respondentAuth.ts:1-18`, `auth-client.ts:12-21`, `services/apolloClient.ts:14-24`
- **Description:** The better-auth session token (7-day lifetime per project config, the same `User` identity as a form-app builder; S01) is persisted in `localStorage` and attached as `Authorization: Bearer` to every GraphQL request. Any script execution on the viewer origin can read it. The viewer origin hosts only the sanitised render paths traced above, so this is not currently exploitable, and it is a deliberate design choice (the file comment explains it), but it turns any future XSS or compromised dependency in the viewer bundle into account takeover rather than a respondent-only compromise. Anyone who is both a respondent and a builder (same email) gets the builder-grade token exposed in the public app.
- **Exploit scenario:** A future XSS (new field type, plugin, third-party script) or a malicious npm update runs `localStorage.getItem('dculus_respondent_token')` and exfiltrates a 7-day token that also works against the builder GraphQL API and the Hocuspocus socket.
- **Recommended fix:** Issue respondents a narrowly scoped, short-lived credential (separate better-auth session type, or a token that only the respondent resolvers accept, 1-24 h), keep it in memory with a refresh route, and consider `HttpOnly` cookies for the first-party `/f/*` flow (the embed frame already cannot use cookies, so only the embed needs the bearer). Pair with S17-05.

### S17-05 - No `script-src` CSP and no `Permissions-Policy` on the viewer; third-party fonts loaded without integrity
- **Severity:** Low
- **File:line:** `apps/form-viewer/public/_headers` (only `frame-ancestors` in CSP); `apps/form-viewer/index.html:7-10`
- **Description:** The viewer ships no script/style/connect/img CSP, so there is no second line of defence against an injected script (S17-04 makes that more valuable here than usual). It also ships no `Permissions-Policy`, and `Strict-Transport-Security` is not set in this file (it may be added at the zone; S21 covers the edge). `index.html` pulls Inter and JetBrains Mono from `fonts.googleapis.com` as render-blocking stylesheets. A third-party stylesheet is a trusted-origin dependency, and every respondent's IP and referrer leak to Google (see S17-06).
- **Exploit scenario:** If an XSS appears later, nothing restricts `connect-src` or inline script, so a token exfiltration (S17-04) succeeds with a single `fetch`.
- **Recommended fix:** Add a CSP to `/*` and `/embed/*`, for example `default-src 'self'; script-src 'self'; connect-src 'self' <API origin> <Sentry>; img-src 'self' data: <CDN>; media-src <CDN>; style-src 'self' 'unsafe-inline'; base-uri 'none'; object-src 'none'` (note that `/config.js` is same-origin, so `script-src 'self'` works). Keep `frame-ancestors` per route. Self-host the fonts. Add `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()` and HSTS if not set at the zone.

### S17-06 - Analytics identifiers collected from respondents without consent, including inside third-party embeds
- **Severity:** Low
- **File:line:** `apps/form-viewer/src/lib/sessionId.ts:10-21`; `hooks/useFormAnalytics.ts:65-77,89` (view and start time); `hooks/useFormSubmissionAnalytics.ts:25-35`; `pages/FormViewer.tsx:419-436` (re-sent on submit); `lib/embedBridge.ts:129-137,280` (host hostname)
- **Description:** On every visit the viewer writes a persistent identifier to `localStorage` (random UUID, 24 h TTL) and sends it with the full `navigator.userAgent`, timezone and language to the backend, which adds IP-derived geolocation (S04-09). Inside a host page the embedding site's hostname is also recorded (`embedHost`). There is no consent prompt, no Do-Not-Track/GPC check and no opt-out; the only suppressor is the internal `preview=1` flag. Reading and writing device storage for statistics normally needs consent under ePrivacy for EU respondents, and the form owner (controller) has no UI to enable a consent banner. The `form_start_time_<session>_<form>` keys (`useFormAnalytics.ts:89`) are removed only on successful submit, so abandoned forms accumulate keys indefinitely. The 24 h expiry is good practice but is not a legal basis.
- **Exploit scenario:** A privacy complaint or audit finds a tracking identifier set on first load for a form embedded on an EU site, with no consent mechanism available to the embedding party. Not an attacker scenario; a compliance exposure (see S24 for the privacy review).
- **Recommended fix:** Add a per-form or per-org setting for consent mode: skip the `localStorage` identifier and send only coarse server-side counts until consent is given, honour `navigator.globalPrivacyControl`/DNT, and document the data collected. Clean up stale `form_start_time_*` keys by TTL when `getOrCreateSessionId` rotates.

### S17-07 - Rich-text field uses an ad hoc "sanitiser" that is not a sanitiser, and intro content has none (safe only because of Lexical)
- **Severity:** Info
- **File:line:** `packages/ui/src/renderers/FormFieldRenderer.tsx:115-125` (removes only `<script>` and `on*` attributes, leaving `javascript:` hrefs, `<svg>`, `<iframe>`, `style`, `srcdoc`); `packages/ui/src/layouts/shared/introContent.tsx:134-137` (no sanitising before Lexical, unlike `ThankYouScreen.tsx:184`)
- **Description:** Resolution detail for S13-04: today these strings are re-parsed by Lexical, which discards every non-registered element and attribute, so nothing unsafe reaches the DOM. The protection is an incidental property of the editor's node set, not a security control, and the three call sites protect themselves differently (DOMPurify, a hand-rolled strip, nothing). If anyone adds an `ImageNode`, `EmbedNode`, `CodeNode` with raw HTML, `style` import, or switches the viewer to `innerHTML` for performance, the rich-text field and intro content become stored XSS with no review trigger. Content also has no length bound at the collaboration boundary (S13-04), which can make a form arbitrarily heavy to render.
- **Exploit scenario:** None today. A future change to the editor node set or render path exposes anonymous respondents to a malicious EDITOR's HTML.
- **Recommended fix:** Introduce one shared `sanitizeRichText()` (DOMPurify with an explicit allow-list: `p, br, strong, em, u, s, h1-h6, ul, ol, li, blockquote, a[href|target|rel]`, URI regexp limited to http/https/mailto/tel) and call it from all three sites and from the server on persist. Add a viewer unit test that feeds `<img onerror>`, `<a href="javascript:...">`, `<svg onload>` and asserts the rendered DOM contains none. Cap string lengths in `hocuspocus.ts` (S13-04).

### S17-08 - File upload flow validates type and size only on the client; upload goes out without credentials
- **Severity:** Info
- **File:line:** `apps/form-viewer/src/pages/FormViewer.tsx:50-80` (`validateFiles`, limits from the schema), `:93-114` (`fetch(uploadUrl, { method:'POST', body })` with no `credentials` and no `Authorization`), `:118-131`
- **Description:** Max size and allowed MIME types come from the public schema and are checked by the browser only; the server enforcement gaps are S06-07 (field limits client-side only), S06-04 (no content validation) and S06-02 (upload ignores access control, window and caps). Because the request carries no bearer or cookie, the server cannot attribute an upload to the signed-in respondent for identity-gated forms. On a failed submit after a successful upload the already stored key is not reused or deleted (orphaned files, S06-06). Nothing new beyond the cross-referenced items; recorded so the viewer side is explicit.
- **Exploit scenario:** See S06-02/S06-07: an attacker skips the viewer and posts to `/upload` directly.
- **Recommended fix:** Fix server-side per S06; additionally send the respondent bearer on the upload request for identity-gated forms so the server can authorise it.

### S17-09 - Embed attribution and preview flag are fully attacker-controlled
- **Severity:** Info
- **File:line:** `apps/form-viewer/src/lib/embedBridge.ts:112-118` (`?preview=1` disables view tracking; `?mode=`, `?origin=`, `?i=` all caller-set), `:280` (`dculus:host` hostname from the host page), `:129-137` (`document.referrer` hostname)
- **Description:** Any visitor can append `preview=1` to skip view counting, and any host page can report any hostname in `dculus:host`. `embedHost`/`embedContext` are recorded server-side from the client body (S04-08), so embed statistics can be forged or suppressed. The `origin` parameter is parsed strictly, so this does not enable a postMessage leak (verified above).
- **Exploit scenario:** A site owner or visitor skews the owner's "views by embedding host" report, or avoids FORM_VIEWED quota consumption on purpose.
- **Recommended fix:** Treat these as untrusted hints in the UI ("reported by the embedding page"). Do not use them for billing or abuse decisions. Optionally derive the host from `Sec-Fetch-Site`/`Referer` at the backend.

### S17-10 - Editor-authored links and content are accepted as-is, enabling phishing on the trusted form domain
- **Severity:** Info
- **File:line:** `packages/ui/src/rich-text-editor/LexicalRichTextEditor.tsx` (`LinkNode`/`AutoLinkNode`); `@lexical/link` `LexicalLinkNode.ts:74-80,190-196`
- **Description:** Links in intro, thank-you and rich-text content may point to any http(s), mailto, sms or tel target. This is expected product behaviour, not a script-injection flaw. It does mean an EDITOR (or a compromised editor account) can put arbitrary outbound links on a page that carries the product's domain, which a respondent will trust.
- **Exploit scenario:** A malicious collaborator adds a "Verify your account" link to a thank-you message on an org-owned form; respondents follow it to a credential-harvesting page.
- **Recommended fix:** Optional hardening: add `rel="noopener noreferrer nofollow"` to rendered links, show the destination host on hover/click, and offer an org-level allow-list of link domains for regulated tenants.
