Scope: `routes/chargebee-webhooks.ts`, `services/chargebeeService.ts`, `services/subscriptionService.ts`, `subscriptions/`, `lib/planLimits.ts`, `graphql/resolvers/subscriptions.ts` (plus enforcement call sites and the admin billing mutations they interact with). ## Findings

### S12-01 — High — PLAUSIBLE — `syncCheckoutSession` re-applies a stale hosted-page snapshot, letting any member restore a paid plan after it was cancelled or downgraded
- **File:line:** `services/chargebeeService.ts:720-775` (`syncFromHostedPage`; retrieve at `:724`, state check `:727-738`, customer check `:748-755`, sync at `:757`); `graphql/resolvers/subscriptions.ts:170-200` (`syncCheckoutSession`)
- **Description:** The mutation takes a caller-supplied `hostedPageId`, retrieves the hosted page, and if its `state` is `succeeded` and the customer matches, passes the page's embedded `content.subscription` object to `syncSubscriptionFromWebhook`. That object is a snapshot taken when checkout completed, not the live subscription. The page is never acknowledged (`hostedPage.acknowledge`) and nothing records that an ID was already consumed, so the same ID can be replayed. The snapshot supplies `planId`, `status` (`active`) and `current_term_*`, so a replay writes the old plan, active status and old limits (re-derived from the catalog) onto the local row. The only authorization is org membership plus the customer check; `hostedPageId` is also handed to every member by `createCheckoutSession` and sits in the `/subscription/success?id=` URL in browser history.
- **Exploit scenario:** An org upgrades to `advanced` through hosted page H. Later the subscription is cancelled (portal, dunning, admin) or downgraded. A member (any role, see S03-03) calls `syncCheckoutSession(hostedPageId: H)`. If Chargebee still reports H as `succeeded`, the local row flips back to `advanced`/`active` with `advanced` limits. For a cancelled Chargebee subscription no further webhooks arrive to correct it, so the org keeps paid limits indefinitely without paying. Also resets the AI-credit period via the stale `currentPeriodStart`.
- **Verify:** In the Chargebee test site, complete a checkout, cancel the subscription, then replay the ID through the mutation and check whether the page state is still `succeeded`. Chargebee only moves a page to `acknowledged` when the API is called to do so.
- **Recommended fix:** After confirming the hosted page, re-fetch the live subscription with `chargebee.subscription.retrieve(subscriptionData.id)` and sync that, never the page snapshot. Reject if the live subscription's customer or item does not match, acknowledge the hosted page after the first successful sync, and reject IDs that were not created for this org (store `hostedPageId` against the org when `createCheckoutSession` issues it). Restrict the mutation to owners (S03-03).

### S12-02 — High — PLAUSIBLE — Self-serve checkout opens a second Chargebee subscription; the free subscription keeps renewing and its webhooks overwrite the paid plan
- **File:line:** `services/chargebeeService.ts:461-500` (`createCheckoutHostedPage` uses `checkoutNewForItems` at `:476`), `:109-140` (free sub created at signup), `:570-715` (`syncSubscriptionFromWebhook` upserts `chargebeeSubscriptionId`/`planId`/limits from whatever subscription the event is for), `:777-795` (`handleSubscriptionRenewal`)
- **Description:** Every org has a real `$0` `free-usd-monthly` Chargebee subscription from signup. The upgrade flow creates a brand-new subscription for the same customer (`checkoutNewForItems`) instead of modifying the existing one (`checkoutExistingForItems` is used only for enterprise). I found no code that cancels the free subscription after an upgrade. Webhook sync is keyed only by `customer_id`, and `planId`/`chargebeeSubscriptionId` come from the event's own subscription. Both subscriptions therefore write to the same local row.
- **Exploit scenario (reliability/billing rather than attacker-driven):** An org pays for `starter`. At the next free-subscription renewal, `subscription_renewed` for the free subscription arrives, sets `planId: free`, free limits and `chargebeeSubscriptionId` to the free subscription, and `handleSubscriptionRenewal` zeroes the usage counters. The paying customer is wrongly downgraded and blocked at free limits, and later admin actions (`changeOrganizationPlan`, `adminCancelSubscription`) operate on the wrong subscription ID, which can double-bill or cancel the wrong one. The customer-facing pricing flow can also leave two live subscriptions.
- **Verify:** Chargebee dashboard, customer `org_<id>` after a self-serve upgrade: if two active subscriptions exist, this is real. A Chargebee site setting (single-subscription-per-customer behaviour) may mask it.
- **Recommended fix:** For orgs with an existing Chargebee subscription use `checkoutExistingForItems` with `replace_items_list: true`. Alternatively cancel the free subscription on the first paid `subscription_created`. In `syncSubscriptionFromWebhook`, ignore events whose `subscriptionData.id` differs from the stored `chargebeeSubscriptionId` unless the event is a creation that is intentionally taking over.

### S12-03 — Medium — PLAUSIBLE — Any non-failure webhook sync overwrites `past_due` with `active`
- **File:line:** `services/chargebeeService.ts:639-641` (status defaults to `'active'`), `:660-687` (written unconditionally); `routes/chargebee-webhooks.ts:75-126`
- **Description:** `past_due` is only ever set by `handlePaymentFailed` (`:801-815`). Every other handled event (`subscription_changed`, `subscription_activated`, `subscription_renewed`, the cancel/pause events, and `syncCheckoutSession`) recomputes status from Chargebee's subscription status, where a subscription in dunning is still `active`. The code comment says only `payment_succeeded` clears `past_due`, but nothing enforces that. The pending-enterprise skip (`:597-607`) covers only `enterprise` + `past_due` for non-enterprise events and not a genuinely failed enterprise renewal.
- **Exploit scenario:** A renewal payment fails and the org is correctly blocked. Before the invoice is paid, a `subscription_changed`/`subscription_renewed` event arrives (portal edit, admin change, dunning-driven change, or event reordering with `payment_failed`). Status flips back to `active` and the org is unblocked without paying. A member can also trigger a sync himself via `syncCheckoutSession` with any previously succeeded hosted page (S12-01).
- **Recommended fix:** Do not overwrite `past_due` with `active` in the generic sync. Clear it only from `payment_succeeded` (or when Chargebee reports no outstanding dues, e.g. `subscription.due_invoices_count === 0`). Apply the same guard to `adminReactivateSubscription` (S12-10).

### S12-04 — Medium — No webhook idempotency, deduplication or ordering checks; replays and late events reset counters and roll back plan/period
- **File:line:** `routes/chargebee-webhooks.ts:64-135`, `services/chargebeeService.ts:570-715`, `:777-795`, `subscriptions/usageService.ts:361-378`
- **Description:** `event.id` and `occurred_at` are logged but never stored or compared. Handlers accept any payload, in any order, any number of times. Chargebee documents at-least-once delivery without ordering guarantees, and the route always returns 200 so the sender never learns of failures. Concretely: (a) a duplicate or delayed `subscription_renewed` calls `resetUsageCounters`, zeroing `viewsUsed`/`submissionsUsed`/`emailsUsed` mid-period; (b) an older event written after a newer one restores the previous plan, limits and `currentPeriodStart/End` (the AI credit period key, so the AI budget resets/forks too); (c) a stale `subscription_cancelled` can overwrite a later reactivation.
- **Exploit scenario:** Not attacker-reachable without the webhook password, but a retried, duplicated or reordered delivery gives an org a fresh usage allowance mid-cycle or flips a paid org to a stale state. An attacker who obtains the password (S12-09) gets arbitrary subscription writes.
- **Recommended fix:** Persist processed `event.id`s (unique index) and skip duplicates. Compare `current_term_start` against the stored period and reset counters only when it advances. Skip events whose `occurred_at`/`updated_at` is older than the last applied one, and return non-2xx for transient failures so Chargebee retries.

### S12-05 — Medium — PLAUSIBLE — Webhook event coverage and status mapping can leave paid orgs on free limits or cancelled orgs unblocked
- **File:line:** `routes/chargebee-webhooks.ts:75-135` (event switch), `services/chargebeeService.ts:639-641` (status mapping)
- **Description:** (1) Events not handled: `subscription_resumed`, `subscription_scheduled_cancellation_removed`, `subscription_deleted`, `customer_deleted`, `payment_refunded`. A paused subscription is stored as `expired` (free limits); if the customer resumes, Chargebee emits `subscription_resumed`, which is ignored, so the org stays on free limits. Removing a scheduled cancellation leaves local `cancelled` the same way. (2) The cancellation-scheduled case is spelled `subscription_cancelled_scheduled`; Chargebee's event name is `subscription_cancellation_scheduled`, so the case likely never matches. (3) `non_renewing` is mapped to `cancelled`, which switches enforcement to free limits immediately although the customer has paid through the end of the term; the real cancellation event later is idempotent.
- **Exploit scenario:** A customer who scheduled a cancellation (or paused and resumed) loses paid limits and is wrongly blocked for the rest of a paid term or indefinitely. Conversely nothing re-syncs a deleted customer.
- **Verify:** Compare against the event list in Chargebee Settings > Webhooks and the event names in the API docs. The spelling in (2) is the thing to confirm.
- **Recommended fix:** Handle the resume / cancellation-removed / deleted events with the same sync, fix the event name, map `non_renewing` to `active` with an end-of-term marker, and apply the free-limit floor only after `current_term_end`.

### S12-06 — Medium — PLAUSIBLE — Unvalidated `itemPriceId` lets a member bypass a pending enterprise deal at list price (extends S03-03)
- **File:line:** `graphql/resolvers/subscriptions.ts:44-85`, `services/chargebeeService.ts:461-500`, `:597-607`, `:625-686`
- **Description:** S03-03 notes that `itemPriceId` is only regex-checked. A specific consequence on top of it: `enterprise-{currency}-{period}` item prices are accepted. A completed checkout produces a `subscription_created` webhook with item `enterprise`, which is exempt from the pending-enterprise skip, sets `enterprisePendingActivation: false` and `status: active`, and leaves the admin-set limits untouched. Charging happens at the item price's catalog `unit_price`, not the negotiated `enterprisePriceInSmallestUnit`.
- **Exploit scenario:** An admin sets a $5,000/month enterprise deal. The org is `past_due` and blocked. Any member opens `createCheckoutSession("enterprise-usd-monthly")` (not shown on the pricing page but not rejected), pays the shared item price's list price (often nominal, since real prices are applied via `unit_price` overrides), and the org is unblocked on enterprise with the negotiated limits at a fraction of the price.
- **Verify:** Check the list price of the `enterprise-*` item prices in the Chargebee catalog.
- **Recommended fix:** Server-side allow-list for `createCheckoutSession`: item price must be in `getAvailablePlans()` and never `enterprise-*`. Consider a webhook check that, for enterprise, the subscription item `unit_price` equals the stored negotiated price before activating.

### S12-07 — Medium — Usage gates use check-then-act with an asynchronous, error-swallowing in-process counter
- **File:line:** `subscriptions/usageService.ts:42-69` (listeners swallow errors), `:81-154`, `:240-280`; `graphql/resolvers/responses.ts:371-374, 658`; `graphql/resolvers/forms.ts:101-104`; `plugins/email/handler.ts:400`
- **Description:** Enforcement reads the counter (`checkUsageExceeded`), while the increment happens later through an in-process `EventEmitter` (fire-and-forget) on a separate Prisma client with a 2-connection pool. Counters can be exceeded by any burst of concurrent submissions, and increments are lost if the process restarts, the listener throws (logged only), or the 2-connection pool is saturated. Each increment also performs a redundant `findUnique` before `update`. Views are only gated in `formByShortUrl`, so any path that returns form data without that query is un-gated (not confirmed; see S04). The emails path reserves a batch upfront, which is the correct pattern, but single-send paths do not. Related: S04-05 (inflation), S04-12 (non-atomic).
- **Exploit scenario:** An attacker (or a legitimate traffic spike) sends N parallel submissions to a free-plan form near its cap. All pass the check, so the org exceeds its plan's submissions limit by roughly the concurrency level; repeated bursts keep it ahead of the counter. Lost increments from handler errors give permanent under-counting.
- **Recommended fix:** For hard limits, do a conditional atomic increment in the same transaction as the insert (`updateMany ... where submissionsUsed < limit`) and reject if zero rows are updated. Keep the event for notifications only. Remove the pre-read in `trackFormView/Submission/EmailSent` and surface listener failures to Sentry.

### S12-08 — Low — PLAUSIBLE — Dunning and recovery depend on `event.content.subscription` being present
- **File:line:** `services/chargebeeService.ts:801-803`, `routes/chargebee-webhooks.ts:121-131`
- **Description:** `handlePaymentFailed` returns silently if the payload lacks `content.subscription`; `payment_succeeded` is only synced when the same field exists. Chargebee's payment events always carry `transaction`, `invoice` and `customer`, but the subscription object is not guaranteed (for example for one-off invoices). If it is absent for `payment_failed`, the org is never marked `past_due` (fail open, revenue leakage). If it is absent for `payment_succeeded`, an org stays blocked after paying.
- **Recommended fix:** Fall back to `content.customer.id` (strip `org_`) or resolve via `content.invoice.subscription_id` / `customer_id`. Log and Sentry-capture when neither is present rather than returning silently.

### S12-09 — Low — Webhook endpoint hardening gaps (no rate limit, 10 MB body parsed before auth, username ignored, error text echoed)
- **File:line:** `routes/chargebee-webhooks.ts:40-62, 139-143`; `index.ts:231, 240`
- **Description:** The password comparison itself is sound (fail-closed when unset, zero-padded `timingSafeEqual`, `:15-31`). Weaknesses around it: the global `express.json({ limit: '10mb' })` runs before the route, so unauthenticated callers can make the server parse 10 MB bodies; there is no per-IP rate limit or lockout on the password, and no Chargebee IP allow-list; the Basic-auth username is ignored (accepts any username); on handler errors the response includes `error.message` (`:142`), though only to authenticated callers. A guessed or leaked webhook password gives full control over any org's plan, status and limits (S12-04 shows there is no replay protection to compensate).
- **Recommended fix:** Mount a small JSON limit (for example 1 MB) and the auth check before body parsing for this route, add rate limiting, optionally restrict by Chargebee source IP ranges, require a fixed username, and return a generic body on error.

### S12-10 — Low — Admin cancel/reactivate set local status without regard to Chargebee state
- **File:line:** `graphql/resolvers/admin.ts:1009-1043`
- **Description:** `adminCancelSubscription` cancels at end of term (`cancelChargebeeSubscription(id, true)`) but immediately writes `cancelled` locally, so enforcement drops to free limits before the paid term ends. `adminReactivateSubscription` always writes `active`, which clears `past_due` (including a pending unpaid enterprise deal, un-blocking it without payment) and ignores that reactivation may fail to restore payment. Admin-only (see S02-11 for the role question).
- **Recommended fix:** Derive local status from the Chargebee response (or wait for the webhook) and refuse to reactivate a pending enterprise deal.

### S12-11 — Low — Raw Chargebee error messages returned to clients
- **File:line:** `graphql/resolvers/subscriptions.ts:83, 120`; also `:277` (`initializeOrganizationSubscription`, see S03-01)
- **Description:** `createCheckoutSession` and `createPortalSession` throw `Failed to ... : ${error.message}`, which can disclose Chargebee API error text (site name, resource IDs, configuration hints). `completeEnterprisePayment` already does this correctly (generic message, details logged).
- **Recommended fix:** Use the same pattern: log server-side, return a generic `createGraphQLError`.

### S12-12 — Info — HTML interpolation of org and user names in billing emails
- **File:line:** `services/chargebeeService.ts:~429-444` (enterprise payment email), `:829-836` (dunning email)
- **Description:** `org.name`, `owner.name` and the payment link are placed into HTML without escaping. Recipients are the org owner themselves, who also controls the org name, so this is self-injection today. It becomes relevant if org names ever become editable by non-owners or the template is reused for third parties. The `portalUrl` also derives from `BETTER_AUTH_URL` via `.replace(':4000', ':3000')`, which is wrong outside local dev.
- **Recommended fix:** HTML-escape interpolated values and use `FRONTEND_URL` for the link.

### S12-13 — Info — PLAUSIBLE — No Chargebee cleanup path found when an organization is deleted
- **File:line:** `repositories/organizationRepository.ts:36` (bare `prisma.organization.delete`); no caller found that cancels the Chargebee subscription
- **Description:** I found no hook that cancels the org's Chargebee subscription or deletes the customer when an organization is removed (the local `Subscription` row presumably cascades). Whether org deletion is reachable (better-auth organization plugin `deleteOrganization` default) was not confirmed.
- **Exploit scenario:** An owner deletes the org while on a paid plan; Chargebee keeps invoicing, later webhooks create/update rows for a non-existent org and fail on the FK (caught and logged, 200 returned).
- **Recommended fix:** If deletion is allowed, cancel the Chargebee subscription in a `beforeDelete` hook and block deletion on failure.

## Positive controls verified
- Webhook auth is fail-closed and compares in constant time (`routes/chargebee-webhooks.ts:45-62`).
- Checkout, portal, enterprise-resume and sync mutations all derive the org from the session's `activeOrganizationId` and run `requireOrganizationMembership`; none takes an `organizationId` argument (apart from `initializeOrganizationSubscription`, S03-01). `syncFromHostedPage` verifies the hosted page's customer is `org_<caller org>` (`:748-755`).
- Enterprise limits are never overwritten by webhooks, and pending enterprise (`enterprise` + `past_due`) is protected from non-enterprise events (`chargebeeService.ts:597-607, 625-627`).
- `past_due` blocks views, submissions and emails consistently and cancelled/expired fall back to free limits (`usageService.ts:258-278`); `0` limits are treated as a real cap and `null` as unlimited.
- Admin billing mutations call `requireAdminRole`, validate currency/period/non-negative integers, and write audit logs (`admin.ts:905-955`). Chargebee failures abort before Postgres is touched in `setEnterpriseSubscription` / `changeOrganizationPlan`.
- Plan limits are server-side only; no client-supplied limit or plan value reaches the Subscription row.
