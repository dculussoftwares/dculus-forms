# S02 — GraphQL authorization (resolvers, part A: core)

Review-only. Paths are relative to `apps/backend/src/`. All findings were traced by reading code; none were exercised against a running instance.

Scope covered: `graphql/resolvers/{forms,formSharing,invitations,templates,tags,admin}.ts`, `lib/accessControlEnforcement.ts`, `services/{formService,formSharingService,invitationService,organizationService,userService,templateService,tagService}.ts`, plus the repositories and `graphql/resolvers.ts`/`schema.ts` as needed to trace field resolvers.

## Summary

| Severity | Count |

## Verified-correct areas (no finding)

- Every `admin*` Query/Mutation in `resolvers/admin.ts` calls the local `requireAdminRole` (admin|superAdmin). Schema fields `admin*` map 1:1 to guarded resolvers.
- Template create/update/delete require `requireSystemLevelRole`; template reads require any authenticated user; `createFormFromTemplate` requires org membership.
- `formSharingService` OWNER-gates `shareForm`, `updateFormPermission`, `removeFormAccess`, `formPermissions`. Grantees must be members of the form's org. The creator's permission cannot be changed or removed. `checkFormAccess` checks org membership before ownership, so an ex-member loses access.
- `deleteForm` and `regenerateShortUrl` are OWNER only. `duplicateForm` needs VIEWER on the source and produces an unpublished, PRIVATE copy owned by the caller.
- `tags.ts` is now properly bound: tag IDs are verified against the authorized `formId` in `tagService` (`tag.formId !== formId` returns false), and `responseId` is resolved to its own `formId` first. The earlier IDOR (see agent memory) appears fixed.
- `forms(organizationId, ...)` calls `requireOrganizationMembership` and scopes the query by `organizationId`. `limit` is clamped to 100.
- `getInvitationPublic` is intentionally public, validates the ID format, and checks status and expiry. Acceptance and email binding happen in better-auth (S01).

## Findings

### S02-01 — High — Unauthenticated read of builder-only `Form` fields through public `formByShortUrl`

- **File:line:** `graphql/resolvers/forms.ts:96-118` (public query), `forms.ts:140-145` (`Form.formSchema`), `forms.ts:232-293` (`responseCount`, `dashboardStats`), `graphql/resolvers/formSharing.ts:100-102` (`Form.permissions`), `graphql/schema.ts:222-272` (`Form` type), `graphql/resolvers.ts:28-34` and `graphql/resolvers/better-auth.ts:20-28` (`User.organizations`), `graphql/resolvers/subscriptions.ts:282-287` (`Organization.subscription`), `repositories/formRepository.ts:5-8` (`defaultFormInclude`)
- **Description:** `formByShortUrl` is public (intended). It returns the full `Form` object, and the `Form` GraphQL type exposes builder-only fields whose resolvers have no auth or permission check. The GraphQL type system, not the resolver, decides what an anonymous caller can select, and a caller can pick any field. Reachable anonymously:
  - `formSchema` returns the builder schema, including each field's `grading` answer key (accepted answers, point values). The comment at `forms.ts:146-165` says `formSchemaPublic` strips grading because "leaking it here would hand out the answer key", but `formSchema` is not stripped and not gated. It also ignores the `accessStatus` gate (`formSchemaPublic` returns null unless `OPEN`).
  - `permissions { user { email name } grantedBy { email } }` returns every collaborator's email and permission level (`Form.permissions` calls `listFormPermissions` with no check).
  - `createdBy { email }` returns the creator's email (`defaultFormInclude`).
  - `createdBy { organizations { ... subscription { chargebeeCustomerId chargebeeSubscriptionId planId usage ... } } }` returns every organization the creator belongs to, including billing identifiers and usage. `User.organizations` and `Organization.subscription` are unguarded field resolvers.
  - `organization { subscription { ... } }` returns the billing identifiers for the form's org.
  - `responseCount` and `dashboardStats` return response counts, trends, response rate and completion time for any published form.
- **Exploit scenario:** An unauthenticated attacker takes any public form link (`/f/:shortUrl`) and sends `query { formByShortUrl(shortUrl:"X") { formSchema permissions { user { email } } createdBy { email organizations { name subscription { chargebeeCustomerId planId } } } responseCount } }`. Results:
  1. On a quiz form they read the answer key before answering, which breaks quiz integrity.
  2. On a form gated by sign-in or a domain allowlist they read the full schema without passing the gate.
  3. They harvest collaborator and owner emails, and see the creator's other organizations and plan details, across tenants.
- **Recommended fix:** Add auth-aware guards to every non-public `Form` field resolver. For example, `formSchema`, `permissions`, `dashboardStats`, `responseCount`, `createdBy` and `organization` should require `requireAuth` plus `checkFormAccess(..., VIEWER)`, or return null for unauthenticated or non-member callers. Alternatively, return a separate `PublicForm` type from `formByShortUrl` with an explicit allowlist of fields (`id, title, description, shortUrl, formSchemaPublic, settings subset, accessStatus, ...`). Also guard `User.organizations` and `Organization.subscription` with a caller-is-member check (see S02-04). Add a regression test that runs a selection of builder-only fields as an anonymous caller.

### S02-02 — High — EDITOR can erase OWNER-only security settings (`accessControl`, `collectRespondentEmail`) by omitting them from `settings`

- **File:line:** `graphql/resolvers/forms.ts:518-565` (owner-gate only fires when the key is present), `forms.ts:636-640`, `services/formService.ts:379` (`updateData.settings = formData.settings`), `repositories/formRepository.ts:~157-165` (`prisma.form.update({ data })` replaces the JSON column)
- **Description:** `updateForm` requires OWNER only if the incoming `settings.accessControl` or `settings.collectRespondentEmail` differs from the persisted value. Both checks are skipped when the key is `undefined` (`incomingAccessControl !== undefined`, `incomingCollectEmail !== undefined`). `settings` is an EDITOR-level field, and the service writes `settings` as a full replacement, not a merge. An EDITOR who sends `settings` without those keys passes every check, and the persisted `accessControl` and `collectRespondentEmail` are deleted. The code comment at `forms.ts:518-524` shows the intent was that EDITORs cannot change who may respond; this bypasses it. The frontend happens to always resend the full object, but the API does not enforce that.
- **Exploit scenario:** A user with EDITOR on a form restricted to `@corp.com` accounts sends `updateForm(id, input: { settings: { saveProgress: { enabled: true } } })`. The domain allowlist and sign-in requirement are dropped, and the form now accepts anonymous submissions. The same call removes `collectRespondentEmail`. The same replace semantics let an EDITOR strip other OWNER-protected state.
- **Recommended fix:** In `updateForm`, merge `input.settings` onto the persisted settings (deep-merge by key, treating `undefined` as "unchanged") before comparing and persisting. Alternatively, when `input.settings` is present, always compute the effective `accessControl`/`collectRespondentEmail` from the persisted values and reject (`GRAPHQL_ERROR_CODES.NO_ACCESS`) if the stored value would change for a non-OWNER caller, including the case where the key is dropped. Enforce the same in `services/formService.ts#updateForm`.

### S02-03 — High (PLAUSIBLE) — EDITOR can delete arbitrary responses through the reserved `__preview__` tag, bypassing OWNER-only `deleteResponse`

- **File:line:** `graphql/resolvers/tags.ts:34-45` (`createTag`, EDITOR), `tags.ts:60-71` (`addTagToResponse`, EDITOR), `tags.ts:86-97` (`deletePreviewResponses`, EDITOR), `services/tagService.ts:84-96`, `repositories/tagRepository.ts:51-56`; compare `graphql/resolvers/responses.ts:750-795` (`deleteResponse`/`deleteResponses` require OWNER)
- **Description:** The reserved tag name `__preview__` is not protected from user creation. `createTag` accepts any name from an EDITOR. `addTagToResponse` lets an EDITOR attach any tag of the form to any response of the form. `deletePreviewResponses` then deletes every response carrying that tag with `responseRepository.deleteMany`. The OWNER-only gate on direct response deletion is therefore bypassable. Not run live; reading `deleteMany({ where: { id: { in: responseIds } } })` shows no formId re-scope or origin check on the responses.
- **Exploit scenario:** EDITOR calls `createTag(formId, "__preview__")`, `addTagToResponse(responseId, tagId)` for each real response, then `deletePreviewResponses(formId)`. Real submission data is permanently deleted (hard delete), with no OWNER involvement and no audit entry.
- **Recommended fix:** Reject user-created tags whose names start with `__` in `createTag`. Have `deletePreviewResponses` delete only responses whose `metadata` marks them as preview (as `deleteAiGeneratedResponses` does with `metadata.source`), not by tag assignment. Consider requiring OWNER for both bulk-delete mutations, to match `deleteResponses`. Add an audit entry.

### S02-04 — Medium — `User.organizations` and `Organization.subscription` leak other tenants' org and billing data to any caller who can obtain a `User`

- **File:line:** `graphql/resolvers/better-auth.ts:20-28` (`User.organizations`), `graphql/resolvers/subscriptions.ts:282-287` (`Organization.subscription`), `graphql/resolvers/formSharing.ts:58-64` (`organizationMembers` returns `User` objects), `graphql/resolvers/invitations.ts:42-44` (`inviter`)
- **Description:** Both resolvers return data for any parent object with no check that the caller belongs to the org. `User.organizations` lists every organization of that user, and `Organization.subscription` returns Chargebee IDs, plan, status, and usage and limits. `User` objects are reachable by non-owners: any org member can call `organizationMembers` and select `organizations { subscription { ... } }` for each colleague, which exposes the colleague's other organizations. `getInvitationPublic` exposes the `inviter` `User`, so a holder of a valid invitation ID can do the same. (The anonymous path via public forms is in S02-01.)
- **Exploit scenario:** A member of Org A calls `organizationMembers(organizationId: A)` and selects `organizations { id name slug subscription { chargebeeCustomerId chargebeeSubscriptionId planId viewsUsed } }`. They learn the other tenants a colleague belongs to and those tenants' billing identifiers. Impact depends on how sensitive Chargebee identifiers are on their own; the cross-tenant exposure is the issue.
- **Recommended fix:** In `User.organizations`, return only organizations where the caller is also a member (or the caller is the user, or an admin). In `Organization.subscription`, require `requireOrganizationMembership(context.auth, parent.id)` and return null otherwise. Keep admin paths on separate admin types.

### S02-05 — Medium — Per-user `NO_ACCESS` cannot block access on `ALL_ORG_MEMBERS` forms

- **File:line:** `services/formSharingService.ts:323-331` (`shareForm` drops `NO_ACCESS` rows), `formSharingService.ts:387-406` (`updateFormPermission` with `NO_ACCESS` deletes the row), `formSharingService.ts:73-98` (`checkFormAccess` falls through to the `ALL_ORG_MEMBERS` default), `formSharingService.ts:133-146` (`listForms` filter)
- **Description:** The documented rule is that `NO_ACCESS` explicitly blocks a user even when org-wide sharing would grant access. The implementation never stores a `NO_ACCESS` row: both write paths delete the user's `FormPermission` row instead. `checkFormAccess` then sees no explicit row and applies `ALL_ORG_MEMBERS` `defaultPermission`, so the user regains the default level. `checkFormAccess` itself does honor a stored `NO_ACCESS` row (hierarchy 0), but nothing can create one.
- **Exploit scenario:** A form is `ALL_ORG_MEMBERS` / `VIEWER`. The owner sets a departing contractor (still an org member) to `NO_ACCESS`; the UI reports success. The contractor can still open the form, view its responses, and export them.
- **Recommended fix:** Persist `NO_ACCESS` as an explicit `FormPermission` row (upsert, do not delete) and have `listForms` and `listAccessibleByOrganization` exclude users with such rows. Add a test for `ALL_ORG_MEMBERS` plus per-user `NO_ACCESS`.

### S02-06 — Medium — `Form.permissions` is returned to every VIEWER, including the list view

- **File:line:** `graphql/resolvers/formSharing.ts:100-102`, `services/formSharingService.ts:105-106`, `formSharingService.ts:211-221` (`listForms` includes all permission rows)
- **Description:** The `formPermissions` query correctly requires OWNER, but `Form.permissions` returns the same list for any caller who can load a `Form`, including VIEWER, and the `forms`/`form` queries reach it. This reveals who else has access, their permission levels, who granted them, and their emails. It is the same unguarded field as S02-01, exposed in the authenticated path. It contradicts the OWNER-only rule for sharing data.
- **Exploit scenario:** A VIEWER or ALL_ORG_MEMBERS reader selects `permissions { user { email } permission grantedBy { email } }` on `form(id)`, enumerating all collaborators and their roles.
- **Recommended fix:** In `Form.permissions`, run `checkFormAccess(caller, parent.id, OWNER)` and return `[]` (or throw `NO_ACCESS`) otherwise. Rely on `userPermission` for non-owners.

### S02-07 — Low — `createForm` copies a caller-supplied storage key from the public bucket

- **File:line:** `graphql/resolvers/forms.ts:419-436`, `services/fileUploadService.ts:486-505`
- **Description:** With the `formSchema` input path, `formSchema.layout.backgroundImageKey` is user-controlled and passed to `copyFileForForm`, which issues an S3 `CopyObject` from the public bucket with `CopySource` built from the raw string. The copy lands under the caller's new form. Impact is limited because the public bucket is public by design and the destination key is server-generated. The key is not validated, so the string could carry S3 `CopySource` suffixes (for example `?versionId=`) or point at objects of any tenant (avatars, logos, other forms' backgrounds). `backgroundVideoKey` is stored without validation. The same unvalidated key is trusted in the schema when it later flows through `duplicateForm` (`services/formService.ts:224, 238`).
- **Exploit scenario:** Any org member crafts a `backgroundImageKey` equal to another tenant's known background key. The platform copies it into the attacker's form, and a `FormFile` row records it. This only helps if the attacker already knows the key.
- **Recommended fix:** Validate that keys match the expected `files/form-background/{formId}/...` pattern and belong to the caller's own forms or to a known template asset before copying; reject `?` and `..`.

### S02-08 — Low — Soft-deleted (inactive) templates remain usable and readable by ID

- **File:line:** `repositories/formTemplateRepository.ts:41-44` (`fetchById` has no `isActive` filter), `services/templateService.ts:66-82`, `graphql/resolvers/templates.ts:63-80,176`, `graphql/resolvers/forms.ts:354`
- **Description:** `listActive` filters `isActive`, but `getTemplateById` does not. Any authenticated user who knows an ID can read, or create a form from, a template an admin has deactivated. Deactivation is the only way admins retire a template, so withdrawn content (or a template with a mistake) stays usable.
- **Exploit scenario:** An admin deactivates a template containing an outdated legal disclaimer. A user with a cached ID still calls `createFormFromTemplate` with it.
- **Recommended fix:** Filter `isActive: true` in the by-ID lookup used by non-admin paths, or check `template.isActive` in `template`, `createFormFromTemplate` and `createForm`.

### S02-09 — Low — Form-ID existence oracle via `checkFormAccess`

- **File:line:** `services/formSharingService.ts:52-56`
- **Description:** A non-existent form returns `FORM_NOT_FOUND`, while an existing form the caller cannot access returns `NO_ACCESS`. Any authenticated user can distinguish existing form IDs from non-existent ones across tenants. Form IDs are random, so the practical risk is low.
- **Exploit scenario:** An authenticated attacker tests a leaked or guessed ID to confirm that a form exists in another tenant.
- **Recommended fix:** Return the same error and message for "not found" and "no access" in `checkFormAccess` callers.

### S02-10 — Low — `createForm` skips the domain validation that `updateForm` performs

- **File:line:** `graphql/resolvers/forms.ts:296-333` versus `forms.ts:539-549`
- **Description:** `updateForm` validates and lowercases `accessControl.allowedDomains`; `createForm` stores `input.settings` (including `accessControl`) without that validation. Malformed or mixed-case domains can be stored, which `emailDomainAllowed` compares case-insensitively but never normalizes. This is a consistency gap rather than a bypass.
- **Exploit scenario:** A form creator stores a malformed allowlist that silently fails closed or open depending on the string, causing confusing behavior. No cross-tenant impact found.
- **Recommended fix:** Share one `validateAccessControl` helper between `createForm` and `updateForm`.

### S02-11 — Info — Admin (not only superAdmin) can run destructive billing mutations

- **File:line:** `graphql/resolvers/admin.ts:674-1044` (`adminCreatePlan`, `adminSetEnterprisePlan`, `adminCancelSubscription`, `adminAssignPlan`, `adminResetUsage`, ...)
- **Description:** Every mutation uses `requireAdminRole` (admin or superAdmin). The business model describes superAdmin as owning destructive operations. If `admin` is meant to be a lower-trust role, subscription cancellation, enterprise pricing and plan archival should require `requireSuperAdminRole`. Confirm intent; no bypass found. All mutations write audit log entries.
- **Recommended fix:** Decide the policy; if destructive billing actions are superAdmin-only, use `requireSuperAdminRole` for them.

### S02-12 — Info — `shareForm` is not transactional

- **File:line:** `services/formSharingService.ts:274-336`
- **Description:** The form row update, `removeManyForUsers`, and `createManyForUsers` are separate statements. A failure between them leaves a form with a changed `sharingScope` and removed grants. This is an integrity risk rather than an auth bypass.
- **Recommended fix:** Wrap in `prisma.$transaction`.

### S02-13 — Info — `duplicateForm` by a VIEWER copies plugin, automation and PDF-template configs into a form the VIEWER owns

- **File:line:** `services/formService.ts:313-318`, `services/copyFormPlugins.ts:22-42`
- **Description:** VIEWER on the source is sufficient. `formPlugins` already lets VIEWER read plugin configs, so no new disclosure results, but VIEWER also obtains OWNER on an editable copy that contains the destination configs (disabled/draft). If plugin configs ever carry secrets, the VIEWER-readable `formPlugins` is the underlying issue (S07). No change needed in S02.
- **Recommended fix:** Consider requiring EDITOR for duplication when plugins, automations or PDF generators exist, or strip secrets on copy.

### S02-14 — Info — Dormant guard divergence between `utils/auth.ts` and `middleware/better-auth-middleware.ts`

- **File:line:** `utils/auth.ts:25-87`, `graphql/resolvers/admin.ts:141-149`
- **Description:** Templates use `utils/auth.ts` (`context.user`), tags/forms use `context.auth` guards, and `admin.ts` defines its own `requireAdminRole`. All three read the same session, so no bypass, but three copies of the role check can drift. The `role` comes from the cached better-auth session; staleness after a role change is an S01 concern.
- **Recommended fix:** Consolidate to one admin guard.
