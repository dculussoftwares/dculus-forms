# S19 — Shared packages (`packages/types`, `packages/utils`, `packages/ui`, `packages/plugins`)

Review-only. No source code was modified. Method: read the scope files, traced each consumer in `apps/backend` and `apps/form-viewer` that sends untrusted data into them, and cross-checked `docs/security-review/findings/S01–S13`.

## Summary

| Severity | Count |
|----------|-------|
| Critical | 0 |
| High     | 0 |
| Medium   | 1 |
| Low      | 4 |
| Info     | 4 |
| **Total**| **9** |

Findings marked PLAUSIBLE (S19-01, S19-02, S19-04) depend on library behaviour or runtime conditions that code reading alone cannot confirm.

Overall: the shared packages are in better shape than most of the app. ID generation is cryptographic, the one regex built from user input is escaped, the email check avoids backtracking, `getImageUrl` rejects traversal, and the rich-text surfaces sanitize in at least one layer. The weak spots are all "shared logic that is only as strong as its caller": regex grading limits, a hand-rolled HTML blocklist, deserializers with no structural validation, and no shared server-side response validator.

## Findings

### S19-01 — Medium (PLAUSIBLE) — Quiz "regex" grading: `safe-regex` star-height check misses overlapping-alternation ReDoS; the shared validator only checks syntax and length
- **File:line:** `packages/types/src/validation.ts:10,45-60` (shared pattern check); consumer `apps/backend/src/services/quiz/gradingEngine.ts:117-130`.
- **Description:** The shared `gradingFormSchema` accepts any pattern that is at most 200 characters and compiles with `new RegExp`. It does not check for catastrophic backtracking. The only backtracking defence is `safeRegex(pattern)` in the backend engine. `safe-regex` v2 only bounds star height (default 1) and repetition count. A pattern with a single quantified group of overlapping alternatives, such as `(a|aa)+` or `(\w|\d)+`, has star height 1 and passes. The engine wraps it as `^(?:…)$` and runs it with `.test()` on the submitted text, capped at 500 characters (`MAX_REGEX_INPUT_LENGTH`). On V8, `^(?:(a|aa)+)$` against 40 to 50 `a` characters followed by a non-matching character already takes seconds to minutes. A 500-character input is effectively unbounded. The match runs synchronously on the Node event loop.
- **Exploit scenario:** An org member with EDITOR access to a quiz form (or an AI/agent tool or template that writes grading) sets a text question to regex mode with `(a|aa)+` as the accepted answer. They then submit an answer of `aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaab`. Public submissions to that form, or the editor's own, hang the single backend process, which also serves GraphQL and Hocuspocus WebSockets. This is a one-request denial of service for every tenant. The editor privilege is low because any org member can be granted EDITOR.
- **Recommended fix:**
  - Run grading regexes with a linear-time engine (RE2 via `re2` or `re2-wasm`), or in a worker thread or `vm` context with a hard timeout.
  - If the engine is kept, treat `safe-regex` as advisory only and reject `|` inside a quantified group.
  - Add the same structural check to `gradingFormSchema` so client and server agree.
  - Server-side, re-validate grading when the schema is persisted (see S19-07).

### S19-02 — Low (PLAUSIBLE) — `FormFieldRenderer` rich-text "sanitizer" is a two-rule blocklist
- **File:line:** `packages/ui/src/renderers/FormFieldRenderer.tsx:115-125`.
- **Description:** `RichTextFormField.content` is cleaned by removing `<script>` elements and attributes whose names start with `on`, and the result is passed to `LexicalRichTextEditor` as read-only HTML. It leaves `javascript:` / `data:` URLs on `href` and `src`, `<iframe>`, `<object>`, `<embed>`, `<form action>`, `<svg>`, `<meta http-equiv=refresh>`, `<base>` and `style` attributes in the HTML string. The string is not injected into the DOM as markup: `LexicalRichTextEditor` runs `$generateNodesFromDOM` (`LexicalRichTextEditor.tsx:189-199,402-413`), which keeps only registered node types, and `LinkNode` in Lexical 0.52 sanitizes `javascript:` URLs. For that reason this is rated Low and PLAUSIBLE: safety depends on Lexical's importers, not on the sanitizer. `ThankYouScreen.tsx:184` uses `DOMPurify.sanitize`, so the two public rich-text render paths are inconsistent.
- **Exploit scenario:** An EDITOR (or a Y.js client, see S13-04) writes rich-text content with an anchor `<a href="javascript:…">` or an unusual tag. If a Lexical upgrade, a new node registration (for example an image or iframe/embed node), or the legacy fallback in `LexicalRichTextEditor` ever renders unknown HTML more literally, the content executes in the form-viewer origin for every respondent.
- **Recommended fix:** Replace the blocklist with `DOMPurify.sanitize(content, { USE_PROFILES: { html: true }, ALLOWED_URI_REGEXP: /^(?:https?|mailto|tel):/i })`, as `ThankYouScreen` already does. Put it in one shared helper in `@dculus/ui` and use it on every `LexicalRichTextEditor value=` path where `editable={false}`. Also sanitize server-side when a form is saved (S13-04).

### S19-03 — Low — `deserializeFormSchema` / `deserializeFormField` do no structural validation; one malformed element throws and takes the whole operation with it
- **File:line:** `packages/types/src/index.ts:767-950` (`deserializeFieldByType`), `:958-971` (`deserializeFormField`), `:982-1013` (`deserializeFormSchema`).
- **Description:** The functions use `any` input and read properties directly. Verified by reading:
  - `deserializeFormSchema(null)` and `data.pages` containing `null` or non-objects throw a `TypeError` (`data.layout`, `fieldData.type`).
  - A non-array `page.fields` throws on `.map` (`page.fields || []` only guards falsy values).
  - Field `id`, `label`, `options`, `allowedMimeTypes`, `maxFileSizeMb`, `min`/`max` and the validation numbers are passed to constructors without type, length or count checks. `options` can be a string or a million-entry array.
  - `deserializeFormSchema` spreads `...data` and `...page`, so unknown keys round-trip. This is intended, but there is no prototype pollution: object spread creates own data properties, so `__proto__` from JSON stays an own key.
  - Conditions are the only part validated at this boundary (`sanitizeConditions`).
- **Exploit scenario:** The formSchema comes from the persisted JSON / Y.js document, which any EDITOR can write (S13-02, S13-04). An editor stores a page containing `null` or a field with `type: "X"` plus `options: "x"`. Every consumer then throws: the public submit path (`responses.ts:495,620,835`), email/Sheets plugin handlers, exports and PDF generation. The submit path uses `stripConditionallyHiddenValues`, which catches and fails open (S04-15), but the other consumers have no catch, so submissions, exports or automations fail for the form. Impact is limited to that form (and to that tenant's availability), hence Low.
- **Recommended fix:** Add a Zod schema for the persisted form (bounded page count, field count per page, string lengths, `options` as a bounded string array, numbers as finite integers) and make `deserializeFormSchema` drop or repair invalid entries the way `sanitizeConditions` and `sanitizeGridColumnWidths` already do. Apply the same schema when the backend persists or loads Y.js state.

### S19-04 — Low (PLAUSIBLE) — Conditional-logic evaluator has no cap on rules, terms or action fields and is run server-side on every anonymous submission
- **File:line:** `packages/types/src/conditions.ts:85-109` (schema without `.max()`), `:550-600` (iteration, per-iteration sorted signature); consumer `apps/backend/src/lib/conditionalStrip.ts:38-60`.
- **Description:** `conditionalRuleSchema` allows unlimited `terms`, `actions` and `fieldIds`. `evaluateConditions` iterates up to `rules + fields + pages + 2` times. Each iteration evaluates every rule and builds a sorted string signature of the full visibility state. The work is therefore roughly quadratic to cubic in schema size, and it is repeated for every `submitResponse` call. `findConditionCycles` (Tarjan) is also unbounded. The cap comment in the code (`maxIterations`) bounds iterations but not per-iteration cost.
- **Exploit scenario:** An EDITOR creates a form with a few thousand rules chained so that visibility changes one step per iteration (each rule shows the next rule's field). The public form is then submitted repeatedly by anyone (no rate limit, S04-06). Each request costs seconds of synchronous CPU, which starves the event loop. Not exploitable without a prior large schema, and the Y.js document size is the only brake, hence PLAUSIBLE.
- **Recommended fix:** Cap rule count (for example 200), terms per rule (50), `fieldIds` per action (200) and id lengths in the Zod schemas, and drop rules beyond the cap in `sanitizeConditions`. Cache the evaluated "strip plan" per `schemaVersion` (S04 formSchemaCache) instead of recomputing from scratch on each submit.

### S19-05 — Low — Placeholder substitution reads `responses[fieldId]` with no own-property check, so `{{constructor}}`, `{{__proto__}}` and similar tokens resolve to prototype members
- **File:line:** `packages/utils/src/mentionSubstitution.ts:38-41, 70-72, 115-118` (also the `fieldLabels[fieldId]` lookups at `:50,:60,:120`).
- **Description:** The token between `{{ }}` (up to 500 characters) or the `data-value` of a mention span is used directly as a key on a plain object. If the object is a normal literal or parsed JSON (the usual case), `responses['constructor']` returns the `Object` function and `String()` of it yields `function Object() { [native code] }`; `{{__proto__}}` gives `[object Object]`; `{{toString}}`, `{{hasOwnProperty}}` and so on behave likewise. The output is HTML-escaped in the HTML variant, so there is no injection, only unintended content. `fieldLabels[...]` has the same issue.
- **Exploit scenario:** An editor writes an email, thank-you or PDF template containing `{{constructor}}`. The sent output shows engine internals instead of a field fallback. No secrets live on these prototypes, so impact is cosmetic and an information-quality bug rather than a data leak. It becomes more serious only if the caller ever passes an object that holds sensitive own or inherited data (for example a `Response` row instead of `response.data`).
- **Recommended fix:** Use `Object.prototype.hasOwnProperty.call(responses, id)` (or `Map`, or `Object.create(null)` copies) for both lookups. Also convert array values with `join` in the HTML variant the way the plain-text variant does (`:119-121`).

### S19-06 — Info — `substituteMentions` escapes substituted values but passes the surrounding template HTML through unsanitized
- **File:line:** `packages/utils/src/mentionSubstitution.ts:31-92`.
- **Description:** Respondent values are escaped with `escapeHtml` (`:172-176`), which is correct and covers `& < > " '`. Substitution is single-pass, so a respondent value containing `{{other}}` or a mention span is not re-expanded (verified: the first `replace` output is not scanned by the placeholder regex again, and the second regex requires literal `<span`, which escaping removes). The template HTML is editor-authored and returned as-is, so callers that send it as email HTML or render it in a browser own its sanitization. The regexes are length-limited (`{1,500}`, `{0,500}`) and I found no ReDoS: all character classes are negated and bounded.
- **Exploit scenario:** None attributable to this package. This is an obligation on callers (email plugin, thank-you page, PDF). I did not trace the plugin email handler. See the S08/S13-04 follow-ups.
- **Recommended fix:** Document the contract in the function header, and have the email plugin run the template through a sanitizer (DOMPurify-equivalent for Node, such as `sanitize-html`) before sending.

### S19-07 — Info — Shared "validation" in `packages/types` is builder-form validation only; there is no shared response validator that the server re-runs
- **File:line:** `packages/types/src/validation.ts` (all schemas are for field-settings forms, such as `textInputFieldValidationSchema`, `gradingFormSchema`), `packages/types/src/index.ts` (`Validation` classes only describe constraints).
- **Description:** The shared package defines constraints (`minLength`, `maxLength`, `required`, `options`, `allowedMimeTypes`, `maxFileSizeMb`) and the form viewer enforces them through react-hook-form, but nothing in `@dculus/types` or `@dculus/utils` turns a form schema plus an answer into a server-side verdict. This confirms S04-04 and S06-07 from the shared-package side. The conditional strip (`stripConditionallyHiddenValues`) is the only schema-derived server check that was found.
- **Exploit scenario:** See S04-04: an anonymous caller bypasses the viewer and submits arbitrary values for required, typed, option-limited or length-limited fields. Not duplicated here.
- **Recommended fix:** Add `validateResponseAgainstSchema(schema, data, visibility)` to `@dculus/types`, built from the same constraint classes, and call it from `submitResponse`, `updateResponse` and `myResponse` edits. This closes S04-04, S06-07 and the "server must re-run client validation" requirement in one place.

### S19-08 — Info — Positive controls verified
- `generateId()` and `generateRandomString()` use `nanoid` / `customAlphabet` (CSPRNG). `generateShortUrl` falls back to `crypto.randomUUID`, not `Math.random` (`packages/utils/src/index.ts:7,138-162`). No security token (session, invitation, OTP, temp-export key) is built from `Math.random`: the only `Math.random` in scope is a loading-skeleton width (`packages/ui/src/sidebar.tsx:594`). Backend uses of `generateId` are record IDs only (response, plugin delivery, PDF run). Public short URLs are identifiers, not secrets (62^8, about 2.2e14 combinations).
- `getImageUrl` allow-lists `[A-Za-z0-9/_.-]` and rejects `..` (`packages/utils/src/index.ts:164-185`).
- `isEmailAddress` is written without backtracking (`packages/utils/src/emailList.ts`), `parseEmailList` splits with a simple class. Noted for S04-07: this check is permissive by design and does not bound the number of recipients.
- `MentionPlainTextEditor.tsx:153-156` escapes regex metacharacters before building `new RegExp`.
- `FormRenderer.tsx:149-160` skips `__proto__`, `constructor` and `prototype` response keys and uses `hasOwnProperty`.
- `sanitizeGridColumnWidths`, `sanitizeGridId`, `sanitizeGridColumn` bound untrusted layout data; `sanitizeConditions` drops malformed rules.
- `apps/form-app/src/lib/embedSnippets.ts` escapes attribute and text values for the generated embed snippets, so `EmbedSettings.buttonLabel` and `width` from `packages/types/src/embed.ts` do not give snippet injection. The `width` value is only attribute-escaped, not CSS-escaped, in the `style=""` attribute of the iframe snippet; that snippet is copied by the form owner, so impact is self-inflicted.
- No `dangerouslySetInnerHTML`, `innerHTML` assignment, `eval`, `new Function`, `document.write` or `window.open` in `packages/*/src` (the only `innerHTML` is a read in the S19-02 sanitizer).

### S19-09 — Info — `packages/plugins` and `packages/types/src/plugins.ts` have no executable security surface, but the shared config types are loose
- **File:line:** `packages/plugins/src/**` (7 static manifests, 139 lines, no I/O); `packages/types/src/plugins.ts:25-45`.
- **Description:** The plugins package contains only display manifests (name, icon, category, availability). `BasePluginConfig` is `[key: string]: any`, `WebhookPluginConfig.secret` and `headers` are plain strings, and `PluginType` (`'webhook' | 'email' | 'slack'`) is out of date compared with the registered handlers (quiz, ai-tagger, sheets). The type-level `any` means the compiler gives no help to prevent secrets or credentials from flowing into API responses. Webhook URL validation, SSRF protection and secret handling are backend concerns; see the plugin findings (S07/S08, not in this section).
- **Exploit scenario:** None directly. The loose types make an accidental over-exposure of `config.secret` in a GraphQL type easier to introduce.
- **Recommended fix:** Make plugin configs a discriminated union with per-type Zod schemas shared by backend validation and frontend forms, and mark secret fields explicitly so serializers can redact them.
