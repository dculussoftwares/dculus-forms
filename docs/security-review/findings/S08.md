## Findings

### S08-01
- **Severity:** High
- **File:line:** `graphql/resolvers/responses.ts:638-651` (spread of respondent keys), `services/automation/engine.ts:248-269` (`buildPluginEvent` forwards `triggerData` as `event.data`), `engine.ts:800-806` (per-response email gate), `plugins/email/handler.ts:355-366` and `sendPerResponseDigestEmails` (`:200-300`), `plugins/google-sheets/handler.ts:387-391`, `plugins/microsoft-sheets/handler.ts:411-415`, `lib/conditionalStrip.ts` (unknown keys pass through, see S04-04)
- **Description:** The engine reuses the reserved key `__digestResponses` as the in-band channel for digest batches: handlers branch on `Array.isArray(event.data.__digestResponses)` and then treat each entry's `data` as a response. For `form.submitted` runs, `event.data` is `{...respondentAnswers, responseId, submittedAt, isPreview}`. Only the three control fields are protected; reserved `__digest*` keys are not stripped, and S04-04 confirms the server stores arbitrary unknown answer keys verbatim (max 500 keys, 10,000 chars per top-level string; nested arrays only bound by a ~6 MB total). A respondent can therefore submit an answer key `__digestResponses` whose value is a crafted array of `{id, submittedAt, data}` entries. With an email action that has `recipientFieldId` set (the standard "email the submitter" setup), `isPerResponseEmailAction` is true, the engine skips its own substitution, and the handler runs the per-response loop, sending one message per forged entry to `entry.data[recipientFieldId]`. The same array drives batch row writes in the Google and Microsoft sheets actions. No `event.type` check exists in any of these paths.
- **Exploit scenario:** An anonymous attacker finds a public form that has an active `form.submitted` automation with an email action using a recipient field. They submit directly through GraphQL with the normal answers plus `__digestResponses: [{id:"a",submittedAt:"x",data:{<recipientFieldId>:"victim1@example.com", ...}}, ... thousands of entries]`. One submission produces one email per entry, from the owner's branded, trusted sender, using the owner's message template with attacker-controlled field text (HTML-escaped but free text, so phishing wording and plain URLs work). The per-response path reserves quota against the org's remaining email allowance, so the attacker exhausts the org's monthly email budget in a few requests (and, where no subscription row exists, `remaining` is `Infinity`, see S07-07). With a Sheets action the attacker appends arbitrary forged rows to the owner's spreadsheet beyond one per submission. Side effects on other reserved keys: see S08-15.
- **Recommended fix:** Never carry engine control data in the same namespace as respondent data. Either (a) pass digest data out of band (a typed `event.digest` field on `PluginEvent`, never merged from answers), or (b) in `emitFormSubmitted`/`emitResponseEdited`, strip any answer key beginning with `__` before building `event.data`, and reject such keys at submission (this also closes S04-04 for these names). Additionally gate the per-response digest paths on `event.type === 'schedule'`. Add server-side validation that `recipientFieldId` is an email field and the value is a single address (S07-06).

### S08-02
- **Severity:** High
- **File:line:** `services/automation/graphValidator.ts:184-188` (`WebhookActionConfigSchema`: `url: z.url()` only), `plugins/webhook/handler.ts:49-53, 56-71` (fetch follows redirects, body stored), `services/automation/engine.ts:847-862` (result stored in step output and run context), `resolvers/automations.ts:103-136, 301-318`, `schema.ts:1489-1512` (`AutomationStepRun.output`, `AutomationRun.context` exposed as JSON)
- **Description:** A webhook action in an automation POSTs to an arbitrary URL with the same unprotected `fetch` as the legacy plugin (S07-01): no scheme or host allow-list, no private/link-local/metadata IP block, redirects followed, no timeout, unbounded body read. The only validation is that `url` parses as a URL (`file:`, `http://169.254.169.254/`, `http://localhost:4000/...` all pass `z.url()`). What is new in the automation route is (1) the privilege: EDITOR is enough, not OWNER, and (2) an immediate, low-friction read-back: `testAutomation` runs the graph at once, the handler returns `{statusCode, responseBody}`, and `engine.ts:847-862` persists it as `AutomationStepRun.output` and `context.stepOutputs`, which any VIEWER can query through `automationRun`/`stepRuns` (`resolvers/automations.ts:120-136`, `schema.ts:1489-1512`).
- **Exploit scenario:** Any registered user who is EDITOR on a form (they can also simply create their own org and be OWNER) creates an automation with a webhook action pointing at `http://169.254.169.254/latest/meta-data/...`, an internal service, or an attacker server that 302-redirects to one; presses Test; then reads `stepRuns[].output.responseBody` from `automationRun`. Cloud credentials or internal-only API responses are returned in the GraphQL response. Because the action runs in the API/worker process, internal services reachable from the backend (Hocuspocus, `/debug`, database admin ports) are in range.
- **Recommended fix:** As S07-01, but enforce it in the shared webhook handler and in `WebhookActionConfigSchema` (https only, reject credentials in the URL, resolve DNS and block loopback/RFC1918/link-local/ULA/CGNAT/metadata, pin the resolved IP to defeat rebinding, `redirect: 'manual'`, `AbortSignal.timeout`, cap the body read). Do not persist or return the webhook response body to the client; store only status code and a short truncated excerpt, and only for EDITOR+. Consider requiring OWNER to add or change an outbound destination (S08-05).

### S08-03
- **Severity:** High
- **File:line:** `resolvers/automations.ts:29-37, 76-100` (`withoutDraft` hides only draft fields; `graph` is returned to VIEWER), `schema.ts:1437-1476` (`graph: JSON!`), `engine.ts:487-497` (refreshed OAuth tokens written back into the live graph), `schema.ts:1501-1512` (`AutomationRun.context`)
- **Description:** Action configs live inline in `Automation.graph`. Per the handlers this includes the webhook `secret` (HMAC key) and `headers` (typically `Authorization: Bearer ...`), the Google/Microsoft `googleToken`/`microsoftToken` objects with `accessToken` and long-lived `refreshToken`, and the connected account email. `formAutomations`/`automation` return the full `graph` to any caller with VIEWER on the form; the draft-hiding logic protects only the unpublished draft, not the credentials in the published graph. This is the automation counterpart of S07-02. Additionally, `AutomationRun.context` (readable by VIEWER) carries full respondent data and `stepOutputs`, and each run's frozen `graphSnapshot` is a second plaintext copy of the same secrets per run row (not exposed through GraphQL, but multiplies the data at rest, see S08-08).
- **Exploit scenario:** A user shared on a form as VIEWER (or any org member when the form is `ALL_ORG_MEMBERS` with a VIEWER default) queries `formAutomations(formId)`, reads the webhook secret and bearer header, and forges signed webhook calls to the owner's receiver, or takes the Google/Microsoft refresh token and calls Drive/Sheets/Graph as the owner (Microsoft scope `Files.ReadWrite`, see S07-09).
- **Recommended fix:** Return a public projection of `graph` to callers below EDITOR (and ideally below OWNER) that masks `secret`, header values and token objects (expose booleans like `hasSecret`, `connectedEmail`). Store secrets encrypted at rest (AES-GCM with an app key, versioned) outside the graph JSON, referenced by id from the node config; keep OAuth tokens server side (see S07-02/S07-05 recommendations). Do not copy secrets into `graphSnapshot`; resolve them at execution time.

### S08-04
- **Severity:** Medium
- **File:line:** `services/automation/copyAutomation.ts:31-50` (`EXTERNALLY_BOUND_CONFIG_KEYS`), `copyAutomation.ts:129-158` (`copyAutomationsToForm`), `services/formService.ts` (duplicateForm), `services/automationService.ts:159-184` (`duplicateAutomation`)
- **Description:** The copy path removes spreadsheet identity and OAuth token objects but not webhook `secret`, webhook `headers`, or any other credential-like key. A form duplicate (needs only VIEWER on the source, S02-13) therefore lands on a new form owned by the caller with the owner's webhook HMAC secret and `Authorization` header in the copied graph, readable by the copier. The tokens are stripped, which makes the unstripped fields the remaining leak. `copyAutomation` also preserves `triggerConfig` and, for `duplicateAutomation`, copies the editor's draft (`effectiveGraph`) rather than the published graph, so unpublished work-in-progress (possibly with secrets typed into the draft) is duplicated to anyone with EDITOR (that requires EDITOR, so lower risk).
- **Exploit scenario:** A VIEWER duplicates a form, opens the copy's automation list, and reads the webhook secret and bearer header that S08-03 would already show them; because the copy is theirs, they can also enable it against the owner's receiver using the owner's credentials (the automation is created DRAFT but the new owner can publish and activate it).
- **Recommended fix:** Switch to an allow-list: copy only known non-secret config keys per action type, drop `secret`, `headers` values, tokens and external identifiers, and mark the node "setup required". Require EDITOR (or OWNER when the form has outbound integrations) for `duplicateForm`. For `duplicateAutomation` copy the published graph unless the caller explicitly chooses the draft.

### S08-05
- **Severity:** Medium
- **File:line:** `resolvers/automations.ts:150-155, 233-248, 267-282` (EDITOR required to create, publish, activate), compare `resolvers/plugins.ts` (OWNER required, see S07), `services/automation/triggerService.ts:41-80` (runs have no actor), `engine.ts:766-825`
- **Description:** The capability to send every future response to an external endpoint (webhook, email to an arbitrary fixed address, sheets with a caller-supplied token) is OWNER-only when configured as a plugin but EDITOR-only when configured as an automation, so the plugin restriction is bypassable by lowering the role needed. Automations also run with no identity: they execute as the platform on the org's behalf, authorized once at publish time, and are not re-checked when the publisher is demoted, removed from the form, removed from the org, or banned. `publishedById`/`createdBy` are recorded but never consulted at run time.
- **Exploit scenario:** A user given EDITOR for "layout and field changes" publishes and activates an automation that posts every new submission to their own server and emails a copy to a personal address. When the owner later removes their access, the automation keeps running indefinitely, and only the owner of the form can notice it in the list.
- **Recommended fix:** Require OWNER (or a dedicated permission) to add or change action nodes that deliver off-platform, or to publish/activate them; at minimum require OWNER to change `webhook` URLs/headers and `email` recipients. Re-validate the publisher's membership and permission when a run is created (or auto-pause automations whose publisher lost access), show "published by" prominently, and emit audit events (S08-12).

### S08-06
- **Severity:** Medium
- **File:line:** `services/automationService.ts:447-495` (`updateAutomation`), `resolvers/automations.ts:184-204`, `automationService.ts:187, 310` (the `MAX_DRAFT_BYTES` limit exists only in `saveAutomationDraft`), `triggerService.ts:66`, `automationService.ts:647`
- **Description:** The older `updateAutomation` mutation writes straight to the live `graph`/`triggerConfig`/`name`, bypassing the draft/publish workflow that the rest of the service enforces. Consequences: (1) no size cap (draft saves cap at 512 KB, this path has none beyond the HTTP body limit, S05), and every run copies the full live graph into `AutomationRun.graphSnapshot`, so one oversized graph is multiplied into every run row; (2) no `draftRevision` compare-and-swap and no audit entry (publish writes `automation.published`, this does not), so changes made here have no `publishedBy`/audit trail and can overwrite an active automation silently while another editor has an unpublished draft (the draft is neither cleared nor rebased); (3) when the automation is not ACTIVE the graph is stored with no validation at all (cycles, unknown action types, invalid configs), and `triggerConfig` for non-schedule triggers is stored unvalidated and unbounded; (4) `name` is accepted unvalidated (empty or unbounded) on update although create requires non-empty.
- **Exploit scenario:** An EDITOR (or a script using the API) calls `updateAutomation` with a multi-megabyte graph on an automation that is then activated through `setAutomationStatus`. Activation validates structure but not size, so each submission to the form stores a multi-megabyte `graphSnapshot` and `context`, bloating the database and slowing every run query. Separately, an editor changes the live graph of an active automation without going through publish, so the audit log shows nothing.
- **Recommended fix:** Remove `updateAutomation` for graph/triggerConfig (keep rename only) or route it through the same draft/publish path; apply `MAX_DRAFT_BYTES` and node/edge/action-config count limits in `validateAutomationGraph`; validate and bound `triggerConfig` and `name` on every write; audit every graph-changing mutation.

### S08-07
- **Severity:** Medium
- **File:line:** `services/automation/cronValidator.ts:18-54` (any valid 5-field cron accepted, including `* * * * *`), `services/automationService.ts:108-152` (no per-form/per-org automation cap), `triggerService.ts:51-79` (one run per active automation per submission), `graphValidator.ts` (no max nodes/edges), `engine.ts:197-220` (a pg-boss job per step), `repositories/automationRepository.ts` (no pruning of runs)
- **Description:** Nothing bounds the amount of work an org can schedule. Cron expressions can fire every minute with no minimum interval; the number of automations per form or org is unlimited; each submission creates a run (with a full graph snapshot and context copy) and at least two queue jobs for every active `form.submitted` automation on the form; a digest node can embed up to 5,000 responses into one run context (`DIGEST_RESPONSE_SAFETY_CEILING`); delays up to 30 days hold WAITING runs and queued jobs open. There is no plan gating on automation count, run volume or schedule frequency (`lib/planLimits.ts` has nothing for automations), and run history is never pruned. Combined with the unauthenticated submission surface (S04), a free-plan tenant can generate unbounded row growth and queue load that is shared with every other tenant on the single pg-boss queue (`automation-step`).
- **Exploit scenario:** A free-plan user creates hundreds of automations with `* * * * *` schedules (each with a digest node and email/webhook action) and many `form.submitted` automations on a public form, then floods the form. The shared worker spends its capacity on this tenant, delaying other tenants' runs, and `automation_run`/`automation_step_run` grow without limit.
- **Recommended fix:** Enforce per-plan limits (automations per org, minimum cron interval such as 15 minutes on free, max steps per graph), cap runs per automation per time window and drop or skip beyond it, cap per-org concurrency on the queue (separate queues or per-tenant concurrency), reduce stored snapshot/context size (store a graph version reference, not a copy), and add retention/pruning for completed runs.

### S08-08
- **Severity:** Medium
- **File:line:** `prisma/schema.prisma:735-756` (`AutomationRun.context`, `responseId` with no FK; `AutomationStepRun.output`), `services/automation/triggerService.ts:55-69`, `engine.ts:861-862`, no deletion path (grep: `automationRun` is only used by `repositories/automationRepository.ts`, the resolver and the schema)
- **Description:** Every run stores the full submitted answers (`context.triggerData`), up to 5,000 digest response bodies for schedule runs, step outputs (recipient addresses, webhook response bodies, error text) and a graph snapshot containing the action secrets. The `responseId` has deliberately no foreign key, so deleting a response (or erasing a data subject, or soft-deleting) leaves the PII in `automation_run` indefinitely; only deleting the whole automation or form cascades. There is no retention job. Run history is also readable by any VIEWER (see S08-03), including data from responses that were later deleted or restricted.
- **Exploit scenario:** A respondent exercises a deletion request; the owner deletes the response. Their full submission remains in the runs list and is visible to every viewer of the form and in backups, indefinitely. A VIEWER reads historical `context` of deleted responses.
- **Recommended fix:** Store a minimal context (response id plus a reference), or redact `context`/`output` when the source response is deleted (`responseService` delete path should purge `automation_run` rows for that `responseId`); add a retention period (for example 30-90 days) for run history; do not persist secrets in snapshots.

### S08-09 (PLAUSIBLE)
- **Severity:** Medium
- **File:line:** `services/automation/runOutcome.ts:54-87` (`consecutiveFailureCount`, auto-pause after 5), `plugins/email/handler.ts:500-560` (throws on send failure), `engine.ts:826-831, 878-920` (retries then FAILED), `lib/conditionalStrip.ts` / S04-04 (no server-side validation of the recipient field)
- **Description:** An automation is auto-paused after five consecutive FAILED runs, and any COMPLETED/PARTIAL run resets the streak. A run fails when the email handler throws, which happens when `recipients` includes a value the SMTP layer rejects. Because the recipient field is not validated server side (S04-04, S07-06), a respondent controls whether the run fails. I did not confirm how `emailService.sendEmail` reacts to every malformed address (nodemailer normally rejects an invalid envelope address with an error), hence PLAUSIBLE.
- **Exploit scenario:** An anonymous attacker submits the form five times in a row with an invalid or oversized value in the recipient field (or an address the SMTP relay rejects). Each run burns three retries with backoff, then fails; after the fifth, the owner's confirmation/notification automation is paused and stays paused (and only the creator is told). The attacker repeats after the owner re-enables it.
- **Recommended fix:** Validate recipient field values at submission and again before send, treat an invalid recipient as `SKIPPED` rather than a failure of the run, and base auto-pause on failures that are not attributable to respondent-supplied data (for example infrastructure/credential errors), or require a failure ratio over a time window instead of a raw streak.

### S08-10
- **Severity:** Low
- **File:line:** `services/automation/engine.ts:351-364, 804-806` (`substituteConfigMentions` applied to the whole action config), `packages/utils/src/mentionSubstitution.ts:28-58`
- **Description:** Respondent answers are substituted into every string in the action config, recursively, including `url`, `headers` values and `secret`, not only message/subject text. The substitution applies HTML escaping, which is the wrong encoding for URL path/query and header contexts (functional bug: `&` becomes `&amp;`) and gives no protection against path traversal (`.` and `/` are unchanged). A webhook URL such as `https://hooks.example.com/{{submissionKey}}` is accepted by `z.url()` at publish and then resolves against attacker-chosen text at run time. Header injection with CRLF is blocked by undici's header validation, so this is limited to value control. Single-pass replacement means a respondent value containing `{{other}}` is not re-expanded.
- **Exploit scenario:** An owner who builds a URL template with a form field lets any respondent steer the path or query of the request made from the platform to the owner's receiver (`../admin/...`), or inject query parameters (`?x=1&y=...` survives the escape except for `&`).
- **Recommended fix:** Do not substitute into `url`, header names/values or `secret`; if URL templating is wanted, add a dedicated step that URL-encodes (`encodeURIComponent`) each substituted value and re-validates the final URL (host unchanged, scheme https, SSRF checks from S08-02).

### S08-11
- **Severity:** Low
- **File:line:** `services/automationService.ts:619-697` (`testAutomation`), `resolvers/automations.ts:301-318`, `engine.ts:316-349, 742-748`
- **Description:** A test run executes every non-email action for real: webhook deliveries (with real response data and `__isTest` set), Sheets appends (real rows written to the owner's sheet), `ai-tagger` runs (consumes AI credits), `quiz-grading` writes. Only email is redirected. The mutation is unthrottled and has no per-user or per-automation rate limit, so an EDITOR (or a script holding an EDITOR session) can enqueue unlimited test runs, spending email quota (test emails count as sends), AI credits and pg-boss capacity, and amplifying S08-02 reads. A test run on a never-published automation uses the live placeholder graph, so it is mostly harmless there.
- **Exploit scenario:** An EDITOR loops `testAutomation` on a graph with an `ai-tagger` or webhook action to burn AI credits or hammer a third-party receiver.
- **Recommended fix:** Rate limit `testAutomation` (per user and per automation), skip or stub side-effecting non-email actions in test mode (or show a dry-run payload preview), and make the UI state clearly which actions fire for real.

### S08-12
- **Severity:** Low
- **File:line:** `services/automationService.ts:413` (only `automation.published` is audited); no `audit(` call in create, duplicate, update, status change, delete, test, cancel or retry; `engine.ts:487-497` (system config write-back)
- **Description:** Security-relevant automation changes are not audited: activating or pausing, deleting, `updateAutomation` writes, test runs that deliver real data, run retries, and engine-driven config write-backs that overwrite the live graph (tokens, spreadsheet ids). Without these entries, S08-05 and S08-06 are not detectable after the fact.
- **Exploit scenario:** An editor activates and later deletes an exfiltration automation; the only trace is run rows that disappear with the automation (cascade delete).
- **Recommended fix:** Audit create, duplicate, update, status change, delete, test and retry with actor, form id, action types and (hashed) webhook host; keep audit rows independent of automation deletion.

### S08-13
- **Severity:** Low
- **File:line:** `resolvers/automations.ts:103-118` and `repositories/automationRepository.ts:67-76` (`limit`/`offset` taken as-is, default 50, no max), `resolvers/automations.ts:87-136` (lookup before access check)
- **Description:** (a) `automationRuns(limit, offset)` accepts any integer; a VIEWER can request a very large page, and each run row carries full `context` JSON (and `stepRuns` resolve per run, one query each: N+1), so a single request can force a large read; negative values surface as raw Prisma errors. (b) `automation`, `automationRun`, and the mutations call `getAutomationById`/`getAutomationRunWithAutomation` before the access check, so a caller can distinguish "not found" from "no access" for guessable IDs (ids are cuids, so this is an unlikely oracle, Info-level in practice).
- **Exploit scenario:** A VIEWER requests `automationRuns(limit: 100000)` on a busy form, loading hundreds of MB of response context and issuing one `stepRuns` query per run.
- **Recommended fix:** Clamp `limit` (for example 1-100) and `offset`, drop `context` from the list type or return a summary, batch `stepRuns` with a dataloader, and perform the form access check before returning distinguishable errors (return a generic not-found for both cases).

### S08-14
- **Severity:** Low
- **File:line:** `services/automationService.ts:30, 53-58, 241-258`, `graphValidator.ts:109-112, 228-233`, `plugins/core/registry.ts:20` (`getAvailablePluginTypes`)
- **Description:** Any registered handler is accepted as an action type, including legacy `quiz-grading` and `ai-tagger`, and only `email`, `webhook` and `slack` have per-type config schemas; other action configs are `z.record(z.any())` with no size limit. The gaps documented for plugins therefore apply to automation actions as well, reachable at EDITOR: `tagId` values not scoped to the org's tags (S07-11), unvalidated `spreadsheetId`/`workbookId` interpolated into provider URLs (S07-10), and an `attachPdfTemplateId` that is only checked at send time. The front end hides some of these types, but the GraphQL API does not.
- **Exploit scenario:** An EDITOR crafts an automation through the API with a `quiz-grading` or `ai-tagger` action carrying another tenant's tag id, or a path-manipulated `workbookId`, which the engine executes with the target's token or against another org's tag.
- **Recommended fix:** Restrict automation actions to an explicit allow-list (`email`, `webhook`, `google-sheets`, `microsoft-sheets`), give each a strict zod schema (strict objects, max sizes, ownership checks of every referenced id against the form/org), and validate on save and on every run.

### S08-15
- **Severity:** Info
- **File:line:** `services/automation/engine.ts:248-269` and `:184-195`, `resolvers/responses.ts:638-651`
- **Description:** Other reserved keys can also be injected by a respondent into `event.data` on `form.submitted` runs. `__isTest` is only added server-side for test runs and not removed otherwise, so a respondent can set `__isTest: true` and make a receiver that honours the flag drop a real submission. `__digestUntil`/`__digestSince`/`__digestCount` are forwarded as given; `advanceDigestWatermark` reads `context.triggerData.__digestUntil` without checking that a digest node ran, but it only moves the watermark of the same (non-digest) automation, so there is no practical effect today. Fixing S08-01 by stripping `__`-prefixed answer keys removes all of these.
- **Exploit scenario:** A respondent submits `__isTest: true` so an external system ignores their (real) submission.
- **Recommended fix:** As S08-01: reject or strip `__*` keys from respondent data before building the event.

### S08-16
- **Severity:** Info
- **File:line:** `services/automationService.ts:741-826` (`retryAutomationRun`), `repositories/automationRepository.ts:280-302`
- **Description:** Retrying a failed run refreshes the failed node's config from the LIVE graph into the run's frozen snapshot (by node id, without checking the node's `actionType` is unchanged) and re-executes it with the run's original context, including the original response data. An EDITOR can therefore retarget an old failed run to a new destination (a different webhook URL or recipient) and replay its data there. This is by design (retries follow fixes) and equivalent to what an EDITOR can already do with `testAutomation`, but it also works for non-test runs on real data after the original publisher lost access, and combines with S08-02.
- **Exploit scenario:** After an automation's webhook fails, an editor changes the URL to an attacker-controlled endpoint and retries every failed run to receive the stored submissions.
- **Recommended fix:** Require OWNER to retry across a changed destination, or refuse the refresh when the node's `actionType`/destination changed since the run started; audit retries (S08-12).

### S08-17
- **Severity:** Info
- **File:line:** `services/automation/runOutcome.ts:90-123`, `services/emailService.ts:234-256`
- **Description:** Failure and auto-pause notifications go to `Automation.createdBy`, who may no longer be a member of the org or have any access to the form, and the subject line interpolates the editor-controlled automation name verbatim (HTML body escapes it; nodemailer strips CR/LF from the header). The email also links to run detail via a form id and run id. Not exploitable in practice, but a departed creator keeps receiving run and form identifiers and an editor can place free text in a platform-sent subject line.
- **Exploit scenario:** A user who was removed from the org keeps receiving notification mail with form and run identifiers; an editor names an automation with phishing wording that the owner receives in a platform-branded subject.
- **Recommended fix:** Resolve the recipient at send time to the current owner or to members with EDITOR+ on the form, and constrain the automation name length/characters used in subjects.
