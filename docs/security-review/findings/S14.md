## S14-01 — High — Deleting a user cascades to every form (and all its responses) that user created

**File:line:** `apps/backend/prisma/schema.prisma:169` (`Form.createdBy ... onDelete: Cascade`), `:138` (`Invitation.inviter ... onDelete: Cascade`), `:252-261` (`ResponseFileExport`), `:884` (`AIChatConversation.user`); `apps/backend/src/lib/better-auth.ts:178-196` (the `user.delete` hook).

**Description:** `Form.createdById` is a required column with `ON DELETE CASCADE` to `user`. Forms are shared inside an organization (`ALL_ORG_MEMBERS`, `SPECIFIC_MEMBERS`, explicit `FormPermission` rows), but the form is owned in the database by its creator. When that user row is deleted, Postgres deletes every form they created, and through the form cascades (`response`, `response_grade`, `form_file`, analytics, `pdf_template`, `plugin`, `automation`, `form_permission`, tags, drafts) all of that data goes with it. The same applies to invitations the user sent. The code clearly anticipates user deletion (the `databaseHooks.user.delete.after` hook nulls IP and user agent in edit history), but the hook does nothing about forms.

The user delete path is reachable today through the better-auth `admin` plugin (`removeUser`), which S01-02 shows is exposed to the `admin` role through better-auth's own HTTP endpoints. Any future self-service "delete my account" feature, or the Organization plugin removing a member who is also the sole creator of the team's forms, would hit the same cascade.

**Exploit scenario:** An organization has 5 members. The form builder who created all 40 shared forms leaves the company. An admin (or the person, if self-delete is enabled) deletes the user. All 40 forms and every response collected through them are removed in one statement, with no soft delete, no confirmation of ownership transfer, no audit entry, and no R2 object cleanup (S06-06). Backups are the only recovery. A malicious or compromised `admin` account can do the same to any organization by deleting one user.

**Recommended fix:** Change `Form.createdBy` to `onDelete: Restrict` (or make `createdById` nullable with `SetNull` and keep an `ownerId` / `FormPermission OWNER` row as the real owner). Add a `user.delete.before` hook that refuses deletion while the user still owns forms, or reassigns them to an org owner first. Audit the deletion. Apply the same review to `Invitation.inviter`, `ResponseFileExport.requestedBy` and `AIChatConversation.user`.

## S14-02 — Medium (PLAUSIBLE) — Organization deletion cascades the whole tenant with no audit, billing cancel or grace period

**File:line:** `apps/backend/src/lib/better-auth.ts:85-101` (organization plugin config, no `disableOrganizationDeletion`, no `beforeDeleteOrganization` / `afterDeleteOrganization` hook); `apps/backend/prisma/schema.prisma:119`, `:168`, `:843` (`onDelete: Cascade` from `organization`); `apps/backend/src/repositories/organizationRepository.ts:36` (generic `delete`).

**Description:** The `organization()` plugin is configured with only `allowUserToCreateOrganization`, limits, invitation email and an `afterCreateOrganization` hook. The plugin's organization-deletion endpoint is, by default, available to owners. Nothing is configured to disable it or to intercept it. A delete removes the `organization` row and the database cascades `member`, `invitation`, `form` (and everything under it), `subscription`, `ai_usage` and `ai_chat_conversation`. Consequences: the Chargebee subscription is not cancelled (the local `subscription` row is gone while billing continues), nothing is written to `audit_log`, R2 objects are orphaned, and the deletion is immediate and irreversible. I did not confirm the default of the installed better-auth version, hence PLAUSIBLE.

**Exploit scenario:** An owner (or an attacker holding an owner session, see S01-01 for cookie-cache staleness) calls the org-delete endpoint. All forms and responses are destroyed instantly, billing keeps running at Chargebee, and the operator has no audit trail of who did it.

**Recommended fix:** Set `disableOrganizationDeletion: true` and provide an explicit, audited GraphQL mutation that soft-deletes the org, cancels the Chargebee subscription, schedules R2 purge after a grace period, and requires re-authentication. If deletion must stay, add `beforeDeleteOrganization` / `afterDeleteOrganization` hooks that audit and cancel billing.

## S14-03 — Medium — Audit log misses most privileged actions

**File:line:** `apps/backend/src/graphql/resolvers/admin.ts:1009-1046` (`adminCancelSubscription`, `adminReactivateSubscription`: no `logAction`), `apps/backend/src/lib/better-auth.ts:120-126` (`admin()` plugin) and `:85` (`organization()` plugin) with no audit hooks; call-site inventory from `grep audit(` / `logAction(`.

**Description:** Audit coverage today is exactly: 7 admin plan/billing mutations (`plan_created`, `plan_updated`, `plan_archived`, `plan_unarchived`, `plan_changed`, `enterprise_plan_set`, `usage_reset`), response delete / bulk delete / grade override / grade release, form delete, `permission.granted` (four sites), `automation.published`, and the two response-file-export events. Not audited:

- `adminCancelSubscription` and `adminReactivateSubscription` (they change billing state at Chargebee and locally, only `adminResetUsage` etc. are logged).
- Everything done through better-auth's own endpoints, which bypass the GraphQL resolvers (S01-08): `setRole`, `banUser`, `unbanUser`, `impersonateUser`, `removeUser`, `revokeUserSessions`, organization `updateMemberRole`, `removeMember`, `inviteMember`, `deleteOrganization`.
- Sharing scope and `defaultPermission` changes on a form, and the `accessControl` / `collectRespondentEmail` settings (the OWNER-only settings of S02-02).
- Plugin create / update / delete (webhook URLs, email recipients, OAuth connections; S07).
- Response export and data downloads (only the file-export ZIP is audited; Excel/CSV exports, PDF ZIP, `unifiedExport` are not).
- Automation edit, pause and delete (only publish is logged).
- PDF template and generator deletes, `generateFakeResponses`, response edits by editors (edit history exists but is a separate table with no actor-independent integrity).
- Sign-in, password change, session revoke, OTP failures.

**Exploit scenario:** A compromised `admin` account promotes itself to `superAdmin`, impersonates an owner and exports every response of a victim organization. The only records produced are better-auth session rows; `audit_log` shows nothing, so incident response cannot reconstruct what happened or who did it.

**Recommended fix:** Add better-auth `hooks` / `databaseHooks` (and `organizationHooks`) that call `audit()` for role changes, bans, impersonation, user and member removal, invitations, org deletion and org settings. Add audit calls to the two admin billing mutations, form sharing-scope / settings changes, plugin and automation mutations, and every export path. Define the required-coverage list in code and add a test that fails when a mutation in `admin.ts` has no audit call.

## S14-04 — Medium — Audit log is not tamper resistant and has no tenant scope, retention or read path

**File:line:** `apps/backend/prisma/schema.prisma:779-792` (`AuditLog`), `apps/backend/prisma/migrations/20250521200000_add_audit_log/migration.sql`, `apps/backend/src/lib/audit.ts:11-27`, `apps/backend/src/services/auditLogService.ts`, `apps/backend/src/repositories/auditLogRepository.ts:5-38`.

**Description:**
1. **Mutable by the app role.** `audit_log` is an ordinary table in the application database. The runtime role (the same role Prisma uses for everything, see S14-17) can `UPDATE` and `DELETE` rows. There is no trigger preventing updates or deletes, no `REVOKE UPDATE, DELETE`, no hash chaining, and no shipping to an external append-only store. Any SQL injection, any code path with a generic Prisma passthrough, or any compromised backend process can rewrite history. (Repository exposes only `create`, which is good, but the database enforces nothing.)
2. **Best-effort writes.** `lib/audit.ts` swallows all errors and logs a warning, and every caller invokes it after the action, outside the action's transaction. If the database write fails, the privileged action has already happened with no record. Admin plan mutations use the unguarded `logAction`, which has the opposite problem (a failed audit write fails the mutation after the effect may already be applied, see Chargebee calls before the log call in `adminSetEnterprisePlan`).
3. **No tenant scope.** The table has no `organizationId` and no foreign keys (`actorId`, `resourceId` are bare strings). Entries cannot be filtered per tenant, cannot be exposed to organization owners, and rows for a deleted organization cannot be purged selectively. `resourceType`/`resourceId` is the only handle, so listing "what happened in org X" requires joining through live tables that may already be gone.
4. **No read path and no retention.** The repository comment confirms no read path exists. Nothing prunes the table, and `metadata` is free-form JSON (it already stores the acting admin's email, `changedBy`).

**Exploit scenario:** An attacker who obtains code execution or a SQL-capable foothold in the backend deletes the `audit_log` rows for their own actions. Separately, a transient DB error during a `response.bulk_deleted` write leaves a bulk deletion with no record, silently.

**Recommended fix:** Add `organizationId` (nullable for system events) and index it. Make writes transactional with the action where it matters. Use a separate DB role or trigger so the app role can only `INSERT` (and `SELECT` through an admin role). Forward events to an append-only external sink (log service, object lock bucket). Define retention and an owner-visible read API. Keep `audit()` non-fatal only for low-risk events and make the privileged ones fail closed.

## S14-05 — Medium — OAuth access, refresh and ID tokens are stored in plaintext in `account`

**File:line:** `apps/backend/prisma/schema.prisma:54-56` (`accessToken`, `refreshToken`, `idToken`); `apps/backend/src/lib/better-auth.ts` (Google `socialProviders`, no `account.encryptOAuthTokens`).

**Description:** better-auth stores social-login tokens exactly as received unless `account.encryptOAuthTokens` is set. A grep of `better-auth.ts` finds no `account:` configuration, so Google access/refresh/ID tokens are plaintext columns. A database read (backup leak, read-replica access, SQL injection, a log of an `account` row) yields usable long-lived refresh tokens for every Google-signed-in user and respondent. Plugin OAuth tokens (Google/Microsoft Sheets) are a separate and equally plaintext store in `FormPlugin.config` (tracked as S07-02). Verification values are also stored raw (S01-12). The `password` column holds better-auth's scrypt hash, which is acceptable.

**Exploit scenario:** An attacker with read access to a database snapshot extracts refresh tokens from `account` and uses them against Google until they are revoked, acting as the users within whatever scopes were granted (profile and email today, more if scopes are widened later).

**Recommended fix:** Set `account: { encryptOAuthTokens: true }` (and migrate existing rows by re-encrypting or by dropping stored tokens that are not needed; the app never reads them). If tokens are unused, avoid storing them at all. Restrict DB read access and encrypt backups.

## S14-06 — Medium — Nothing is ever purged: soft-deleted data and PII-bearing side tables are kept forever

**File:line:** `apps/backend/src/services/responseService.ts:840-861` (`deleteResponse`, `deleteResponses` set `deletedAt` only); `apps/backend/src/repositories/formRepository.ts:169-173` (`deleteForm` sets `deletedAt`); `apps/backend/src/plugins/core/executor.ts:52-79` (`PluginDelivery.payload` / `response`); `apps/backend/prisma/schema.prisma:484-525` (`ResponseEditHistory`, `ResponseFieldChange.previousValue/newValue`), `:735-775` (`AutomationRun.context`, `graphSnapshot`, `AutomationStepRun.output`), `:891-903` (`AIChatMessage`).

**Description:** There is no job that hard-deletes soft-deleted responses or forms. Worse, the PII is duplicated into tables that are not soft-deleted and do not follow the response when it is "deleted":
- `plugin_delivery.payload` stores the entire submission event (all answers, respondent email) for every plugin execution, plus `response` (the downstream service's reply), including failed attempts. Never pruned.
- `response_field_change.previousValue` / `newValue` keep the old and new answer values of every edit.
- `automation_run.context` and `automation_step_run.output` keep trigger payloads and step outputs.
- `ai_chat_message` keeps whatever was sent to the AI.
- `FormViewAnalytics` and `FormSubmissionAnalytics` (geo, IP-derived location, user agent) are pruned after 365 days only if the cleanup job runs (S14-14).

So when an owner deletes a response (or a form) to satisfy a data-subject request, copies remain in at least four tables and in R2 (S06-06, S10-06). The only cleanups that exist are analytics (365 days) and expired drafts.

**Exploit scenario:** A respondent asks the form owner to erase their submission. The owner deletes it in the UI and believes it is gone, but the full answers remain in `plugin_delivery` and `response_field_change`, and in any database backup, indefinitely. A later database leak exposes data the controller thought it had erased.

**Recommended fix:** Add scheduled hard-purge jobs (soft-deleted responses/forms older than N days, with R2 deletion), TTLs for `plugin_delivery`, `automation_run`, `automation_step_run`, `ai_chat_message`, and cascade-on-soft-delete cleanup of the side tables. Store minimal payloads (response id, status, error) instead of full answer data in `plugin_delivery.payload`. Document the retention schedule.

## S14-07 — Medium (PLAUSIBLE) — Documented production connection string disables TLS between the app and PgBouncer

**File:line:** `apps/backend/.env.example:15-33`; `apps/backend/src/lib/prisma.ts:27-33`.

**Description:** The checked-in guidance tells operators to use `?pgbouncer=true&connection_limit=2&sslmode=disable` for production, on the grounds that TLS exists on the PgBouncer-to-Postgres leg only. The app-to-PgBouncer leg then carries the database password, every SQL statement and all response data in cleartext. `prisma.ts` builds the `pg` pool straight from the string with no `ssl` option, so `sslmode` in the URL is the only control. Also, `pgbouncer=true` and `connection_limit` are Prisma-engine query flags that the `@prisma/adapter-pg` driver adapter does not read (the file's own comment says so), so the guidance is stale. Whether production actually uses this string is not visible in the repo (hence PLAUSIBLE); the documented default makes it the likely setup. If the PgBouncer host is on another machine or subnet, this exposes traffic to anyone with network position (other tenants of a shared VNet, compromised sidecar).

**Exploit scenario:** An attacker with a foothold on the same virtual network sniffs the app-to-PgBouncer connection, captures the DB credentials and response data, then connects directly.

**Recommended fix:** Require `sslmode=require` (or `verify-full` with the CA) on both legs, or co-locate PgBouncer on localhost / a private link with enforced TLS. Update `.env.example` and drop the obsolete query flags. Fail startup in production if the URL asks for `sslmode=disable` on a non-local host (extend `isLocalDatabase`).

## S14-08 — Medium (PLAUSIBLE) — Soft-deleted forms keep running plugins and scheduled automations

**File:line:** `apps/backend/src/repositories/formRepository.ts:169-173` (`deleteForm` only sets `deletedAt`); `apps/backend/src/services/formService.ts:431-450`; `apps/backend/src/plugins/core/executor.ts:35-52` (loads plugin by id, no form check); `apps/backend/src/repositories/automationRepository.ts:48-51` (`listActiveByFormAndTrigger` filters on `status` only); `apps/backend/src/services/automation/triggerService.ts` (no `deletedAt` check).

**Description:** Deleting a form flips `Form.deletedAt` and nothing else. `FormPlugin.enabled`, `Automation.status = 'ACTIVE'`, registered cron jobs, PDF auto-run generators and pending backfill jobs are untouched. Grepping the plugin and automation code finds no `form.deletedAt` condition (the only `deletedAt` checks there are on `response`). Public submission is blocked for deleted forms by `findByShortUrl`, but scheduled automations (digest emails, webhooks, sheet syncs) are driven by cron and select data by `formId`, so a deleted form's automations can keep emailing or posting existing responses on schedule. I traced the absence of checks but did not run a scheduled tick against a deleted form (PLAUSIBLE).

**Exploit scenario:** A user deletes a form because it collected data it should not have. A weekly digest automation continues to email response data to external recipients, or a webhook keeps firing, because nothing disabled them.

**Recommended fix:** On form delete, in one transaction, disable plugins, set automations to `PAUSED`/`ARCHIVED`, cancel pg-boss schedules and backfill jobs. Also guard the executors and tick handlers with a `form.deletedAt IS NULL` check.

## S14-09 — Medium (PLAUSIBLE) — Two-connection pool and no statement timeout make slow queries a cheap availability attack

**File:line:** `apps/backend/src/lib/prisma.ts:22-33`; `apps/backend/src/subscriptions/usageService.ts:19-23`; `apps/backend/src/repositories/responseRepository.ts:155-206` (dynamic `$queryRawUnsafe`), `apps/backend/src/repositories/responseRepository.ts:76-125`.

**Description:** In production each process gets a `pg` pool of at most 2 connections (plus 2 for the separate `usageService` client, S14-15). No `statement_timeout`, `idle_in_transaction_session_timeout`, `query_timeout` or Prisma `timeout` options are set anywhere in `prisma.ts` or the repositories (also noted for the filter path in S11-05). Several paths run unbounded work against `response.data` JSONB: dynamic filter queries built from user filters, `countPerFieldRaw` (a LATERAL `jsonb_each` over every response of the form), `isFileKeyReferencedRaw`, org-level analytics joins, and the response-suggestion `ILIKE '%...%'` queries. Interactive `$transaction` blocks use Prisma's default 5 s timeout, but plain queries have none. Two long-running queries from a single user, or a handful of anonymous requests that trigger expensive work (S04-06, S10-03), are enough to occupy the entire pool, so every other request waits for a connection until the app-level timeout.

**Exploit scenario:** An authenticated VIEWER on a form with a large response set repeatedly issues filter queries with `contains` on a JSON field across many pages. Each query holds one of the two connections for seconds; the API (including `/health`, sign-in, and anonymous form submission) stalls for all tenants.

**Recommended fix:** Set `statement_timeout` (for example 10-15 s for request traffic, longer for a separate export role) via the connection string `options` or `pool.on('connect')`, add `query_timeout`, size the pool from config rather than a hard 2 (PgBouncer already multiplexes), and run exports and bulk jobs on a separate pool or queue worker. Add per-user concurrency limits on heavy query endpoints.

## S14-10 — Low — Audit records are inaccurate

**File:line:** `apps/backend/src/graphql/resolvers/responses.ts:773-775` and `:795-797`; `apps/backend/src/services/formSharingService.ts:391`, `:416`, `:443`; `apps/backend/src/graphql/resolvers/admin.ts:722` (`changedBy: admin.email`).

**Description:**
- `deleteResponse` / `deleteResponses` return `false` on any error (they swallow exceptions), but the resolver writes `response.deleted` / `response.bulk_deleted` regardless of the result, so the log can claim a deletion that did not happen.
- `response.bulk_deleted` records only the form id. The deleted response ids and count are not stored, so it cannot be known which responses were deleted.
- Permission revocation (`removeForUser` at `formSharingService.ts:440-443`) and the `NO_ACCESS` branch (`:388-391`) are recorded with the action `permission.granted`, so a query for grants returns revocations and vice versa. The actor is `grantedById`; the target `userId` is only in `metadata` if the caller included it.
- Admin entries store the acting admin's email as `changedBy` in free-form metadata alongside `actorId`, duplicating personal data into an append-only table that has no retention (S14-04).

**Exploit scenario:** During an investigation, the log shows 50 responses deleted when 0 were, or cannot show which were deleted. A revoked access looks like a grant.

**Recommended fix:** Write the audit entry only on success and include counts and ids (capped) in metadata. Use distinct actions (`permission.revoked`, `permission.updated`). Store only `actorId` and resolve email at read time.

## S14-11 — Low (PLAUSIBLE) — Stale permission rows and ownership survive org membership removal and return on re-join

**File:line:** `apps/backend/src/lib/better-auth.ts:85-101` (only `afterCreateOrganization` hook; no `afterRemoveMember`); `apps/backend/prisma/schema.prisma:461-479` (`FormPermission` has no link to `Member`); `apps/backend/src/services/formSharingService.ts:60-71`.

**Description:** `checkFormAccess` correctly requires a current `member` row first, so removing someone from the organization blocks access immediately. But removing a member deletes only the `member` row. Their `form_permission` rows (up to `OWNER`) and the `Form.createdById` ownership stay. If the same user is invited again, whether months later, whether by another admin who does not know the history, or by an attacker who controls that email address, they instantly regain every previous grant, including OWNER on forms they created. The database does not tie `form_permission.userId` to organization membership (no composite key with `organizationId`), so nothing prevents rows for users who never belonged to the org either (that side is the sharing logic in S02).

**Exploit scenario:** A contractor with EDITOR/OWNER on 10 forms is removed. Six months later their personal email address is invited again to a different, narrower role. They log in and silently regain the old, higher permissions on the old forms.

**Recommended fix:** Add an `afterRemoveMember` / `beforeRemoveMember` organization hook that deletes the user's `form_permission` rows in that org and reassigns or flags the forms they created. On invitation acceptance, recompute rather than trust old rows.

## S14-12 — Low — Repositories expose ID-only reads and writes; tenant isolation depends entirely on callers

**File:line:** `apps/backend/src/repositories/formRepository.ts:26-40`, `:70-75`; `pluginRepository.ts:18-35`, `:51`; `automationRepository.ts:19-40`; `pdfTemplateRepository.ts:15-45`; `memberRepository.ts:22-40`; `invitationRepository.ts:22-50`; `responseRepository.ts:44-47`; `apps/backend/src/services/responseService.ts:840-846`; `apps/backend/src/services/tagService.ts:84-113`.

**Description:** Every repository exposes generic Prisma passthroughs (`findUnique`, `update`, `delete`, `deleteMany` with arbitrary `args`) and `findById(id)` helpers that take only an ID. Child tables (`response`, `form_plugin`, `pdf_template`, `automation`, analytics, files) carry only `formId`, and some carry `organizationId` (`automation`, `ai_chat_conversation`) while others do not, so isolation is a chain of "resolve the form, check access" steps that every caller must remember. There is no row-level security and no org-scoped repository variant. I found no exploitable break in the repository layer itself (callers in S02/S03 carry the findings), but several write paths are one bug away from cross-tenant impact: `deleteResponse(id)` updates by ID only, and `tagService.deletePreviewResponses` hard-deletes with `where: { id: { in: responseIds } }` without a `formId` condition. Today that is safe only because `addTagToResponse` is called by the resolver with the response's own `formId` (`graphql/resolvers/tags.ts:60-70`); the service does not itself verify that the response belongs to the form.

**Exploit scenario:** A future resolver (or a plugin/automation action) calls `deleteResponse(id)` or `tagService.addTagToResponse(responseId, tagId, formId)` with a caller-supplied `formId` and no ownership check. A tag from the attacker's form is attached to a victim's response and `deletePreviewResponses` then hard-deletes it.

**Recommended fix:** Provide scoped repository methods that always take the tenant key (`updateByIdAndForm`, `findByIdInOrg`), remove or restrict the generic passthrough methods, add `formId` to every bulk write `where`, and verify `response.formId === formId` inside `tagService`. Consider Postgres RLS keyed on a session variable as defense in depth.

## S14-13 — Low — Role, plan, status and permission columns are free-text strings

**File:line:** `apps/backend/prisma/schema.prisma:24` (`User.role`), `:113` (`Member.role`), `:129-130` (`Invitation.role`, `status`), `:161-164` (`Form.sharingScope`, `defaultPermission`), `:805-808` (`Subscription.planId`, `status`); the `TODO(P3-05)` comments confirm this is known.

**Description:** None of the security-relevant enumerations have a Postgres enum or `CHECK` constraint. Any write path (better-auth's admin `setRole`, a migration, a script, a future bug) can store an arbitrary string. Code compares these with strict equality or with default branches that fail open: S01-10 (`requireOrganizationRole` strict equality) and S13-06 (`readOnly` only for the literal `'VIEWER'`) are direct consequences. A stray value such as a differently-cased permission string results in authorization behavior that differs between code paths.

**Exploit scenario:** A value like `"Viewer"` or `"editor "` is written through an admin endpoint or an import. One check treats it as no permission, another treats it as full access (the S13-06 pattern).

**Recommended fix:** Convert to Prisma enums (or add `CHECK` constraints in a migration, validating existing data first as the TODO says) and have the code fail closed on unknown values.

## S14-14 — Low — Analytics retention job may never run and its delete cannot use an index

**File:line:** `apps/backend/src/index.ts:483-487`; `apps/backend/src/services/analyticsService.ts:688-701`; `apps/backend/prisma/schema.prisma:421-424`, `:454-457`.

**Description:** `cleanupOldAnalytics` (365-day retention of geo, user agent and device data) is scheduled with `setInterval(..., 24h).unref()` and is not invoked at startup (unlike the periodic cleanup immediately above it). The service restarts on every deploy; with frequent deploys (the repo auto-deploys `main` to dev) the 24-hour timer rarely or never fires. It also runs once per instance with no lock, so multi-instance deployments run it concurrently. The delete filters on `viewedAt` / `submittedAt` alone, but the only indexes lead with `formId` (`(formId, viewedAt)`, `(formId, submittedAt)`), so each run is a sequential scan plus a large single-statement delete.

**Exploit scenario:** Retention promised to users or auditors (365 days) is not honored in practice because the job does not execute between deploys. Visitor geolocation data accumulates indefinitely.

**Recommended fix:** Run the cleanup on startup and via a pg-boss scheduled job (single-runner), delete in batches, and add standalone indexes on `viewedAt` and `submittedAt`.

## S14-15 — Low — Second `PrismaClient` created in `usageService.ts` bypasses the shared client

**File:line:** `apps/backend/src/subscriptions/usageService.ts:19-23`.

**Description:** At import time the module reads `process.env.DATABASE_URL ?? ''`, builds its own `PrismaPg` pool and `PrismaClient`. This bypasses the singleton and its `globalThis` guard (`lib/prisma.ts:35-38`), doubles the connections each process uses against the small pool budget (S14-09), cannot participate in transactions via `withPrisma`, and silently falls back to an empty connection string instead of failing fast like `prisma.ts` does. This is also where usage counters used for billing are written, so failures here are quiet (they are caught and logged in the event handlers).

**Exploit scenario:** Not directly exploitable. A misconfigured environment loads this module with an empty URL, the usage service fails on first use rather than at boot, and usage/billing counters silently stop updating.

**Recommended fix:** Import the shared `prisma` client (or inject one), and remove the `?? ''` fallback.

## S14-16 — Low — `migrate-deploy.ts` marks failed migrations as applied on an error-code match

**File:line:** `apps/backend/src/scripts/migrate-deploy.ts:76-100` (and `:56-66` for the baseline branch).

**Description:** If a migration is recorded as started but not finished and its log text contains `42P07` or `42701`, the script runs `prisma migrate resolve --applied`. A multi-statement migration that failed on its second statement with "already exists" had its first statement possibly applied, the rest never run. Resolving it as applied leaves the schema partially migrated and Prisma reports success. The same holds for the baseline branch: when `_prisma_migrations` is missing but a `user` table exists, all migrations are marked applied without checking that the schema matches. Matching on substrings of free-text `logs` is also brittle. The repo convention (`ADD COLUMN IF NOT EXISTS`) mitigates the common case but not partial application of other statement types (`CREATE INDEX`, `ADD CONSTRAINT`, data `UPDATE`s).

**Exploit scenario:** A deploy applies half of a migration that adds an access-control related column or constraint; the script marks it done; the application runs against a schema without the intended constraint or backfill, with no failed-deployment signal.

**Recommended fix:** Fail the deploy and require an operator decision for any failed migration; if auto-resolve is kept, verify the schema (run `prisma migrate diff --exit-code`) before marking applied, and log loudly. Add a CI check that the checked-in migrations reproduce `schema.prisma` on an empty database.

## S14-17 — Info — Runtime and migration use the same database role in the documented setup

**File:line:** `apps/backend/.env.example:22-39`; `apps/backend/src/lib/prisma.ts:23-33`; `apps/backend/src/scripts/migrate-deploy.ts:12`.

**Description:** `DATABASE_URL` and `DIRECT_URL` use the same user in the example, and the production example shows an admin-style account. The running API therefore has DDL rights (`DROP TABLE`, `ALTER`), can rewrite `audit_log` (S14-04) and can read `_prisma_migrations`. Any SQL injection or compromised dependency in the API process gets full control of the schema.

**Recommended fix:** Use a migration role for `DIRECT_URL` only, and a least-privilege runtime role (DML on application tables, no DDL, no `UPDATE`/`DELETE` on `audit_log`).
