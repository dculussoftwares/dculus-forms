# S01 — Authentication & sessions: Security Findings

Scope: `apps/backend/src/lib/better-auth.ts`, `middleware/better-auth-middleware.ts`, `graphql/resolvers/better-auth.ts`, `lib/env.ts`. Supporting reads: `index.ts` (auth mount, rate limiters, CORS, morgan), `utils/auth.ts`, `graphql/resolvers/admin.ts` (role gate), `services/emailService.ts`, `apps/form-app/src/lib/auth-client.ts`, and the installed better-auth 1.7.7 source (defaults and plugin behaviour).
Method: static review, tracing code paths. No source modified. No secrets included. Review-only.

Summary: 1 High, 5 Medium, 7 Low, 3 Info. Findings marked PLAUSIBLE depend on deployment details (proxy layout, cookie reachability) not visible in the repo.

## S01-01 — Cookie cache lets revoked sessions, bans and role changes stay valid for up to 7 days
- **Severity:** High (PLAUSIBLE for exploitation; the config is confirmed)
- **File:line:** `apps/backend/src/lib/better-auth.ts:58-61` (`cookieCache.maxAge` = 7 days, equal to session lifetime); consumer `middleware/better-auth-middleware.ts:20`; role gates `graphql/resolvers/admin.ts:145-146`, `utils/auth.ts:35,71`
- **Description:** `cookieCache.maxAge` is the full 7 days. better-auth's `getSession` (`dist/api/routes/session.mjs:39-48`) trusts a valid signed `session_data` cookie and skips the database. The cached payload includes the user (with `role`, `banned`) and the session (with `activeOrganizationId`). Anything that changes server-side is not seen until the cookie expires: sign-out-everywhere, `admin/ban-user`, `admin/revoke-user-sessions`, user deletion, a role demotion, and a password reset or change. `requireAdminRole`, `requireSuperAdmin` and `requireAuth` all read `context.auth.user` from this cached object. Only org membership is re-checked in the database (`requireOrganizationMembership`), so tenant data is somewhat protected, but system-role gates are not.
- **Exploit scenario:** An admin is demoted, banned or deleted after misuse, or a user resets their password after a device theft. The holder of the old browser cookies keeps `admin` or `superAdmin` GraphQL access (admin dashboard, all organizations and users) for up to 7 days, because the role in the signed cookie is never re-validated. The same applies to a stolen cookie after the victim "revokes" the session. This needs the browser to send both `session_token` and `session_data` cookies. The form-app also uses bearer tokens (which go through the database path), so exposure depends on same-site cookie delivery in production. Hence PLAUSIBLE.
- **Recommended fix:** Set `cookieCache.maxAge` to about 60-300 seconds. Alternatively, for role-sensitive checks (`requireAdminRole`, `requireSuperAdmin`) call `auth.api.getSession({ query: { disableCookieCache: true } })` or read `User.role` and `banned` from Prisma. Add `revokeSessionsOnPasswordReset: true` (see S01-05).

## S01-02 — `admin` role can escalate to `superAdmin` and take over any account via better-auth's admin endpoints
- **Severity:** Medium (High if admins are not fully trusted)
- **File:line:** `apps/backend/src/lib/better-auth.ts:120-127` (`superAdmin: adminAc`); `/api/auth/*` mounted at `index.ts:194`
- **Description:** `admin` and `superAdmin` are both mapped to the identical `adminAc`. In better-auth 1.7.7 `adminAc` grants `set-role`, `set-password`, `set-email`, `ban`, `delete`, `impersonate`, `create` and session `revoke/delete` on users. The plugin's `set-role` and `set-user-password` handlers only check the caller's permission, not the target's role (`dist/plugins/admin/routes.mjs` around lines 65-77 and 821-833). The comment "superAdmin inherits full admin permissions" matches the config, but the application treats `superAdmin` as strictly more privileged (`utils/auth.ts:71`, used by templates and fileUpload resolvers). Impersonating an admin is correctly blocked because `impersonate-admins` is not in `adminAc`.
- **Exploit scenario:** A user holding `admin` (for example a support staff account) calls `POST /api/auth/admin/set-role` with their own id and `role: "superAdmin"`. Or they call `admin/set-user-password`, `ban-user` or `remove-user` against an existing `superAdmin`, then sign in as that user. The result is full `superAdmin` rights in the app, bypassing the app-level separation.
- **Recommended fix:** Define a separate, narrower `admin` role (no `set-role`, `set-password`, `delete`, or any action on users who are admin or superAdmin). Keep the full set only for `superAdmin`. Optionally add `adminUserIds` or a `before` hook that blocks admin actions whose target holds a higher role.

## S01-03 — Production-safety of the test environment relaxations depends solely on `NODE_ENV`; known fallback secret
- **Severity:** Medium (conditional on misconfiguration)
- **File:line:** `lib/env.ts:48,61-63`; `lib/better-auth.ts:45,84,140`; also S3 test fallbacks `lib/env.ts:51-56`
- **Description:** When `NODE_ENV === 'test'` the code (a) uses the hard-coded public fallback secret `test-only-secret-for-unit-tests-not-used-in-production` if `BETTER_AUTH_SECRET` is unset (the string is in the public repo), (b) disables `requireEmailVerification`, (c) raises `organizationLimit` to 100, (d) drops the `haveIBeenPwned` plugin. Rate limiting in better-auth is also off outside `production` (`dist/context/create-context.mjs:172`, `enabled ?? isProduction`). A staging or preview deployment that runs with `NODE_ENV=test` (a common mistake when reusing test scripts or Docker images), or with `NODE_ENV` left unset or set to `staging`, silently loses all of these protections. No guard prevents `test` mode against a non-localhost `BETTER_AUTH_URL` or a real `DATABASE_URL`.
- **Exploit scenario:** A deployment with `NODE_ENV=test` and no `BETTER_AUTH_SECRET` uses the publicly known secret. An attacker forges a valid `session_data` cookie payload (HMAC signed with the known secret) containing `role: "superAdmin"` and a chosen user id, and gets admin access without any database lookup (cookie cache is on, S01-01). Unverified email sign-ups, unlimited orgs and no rate limits also apply.
- **Recommended fix:** In `env.ts`, refuse to start if `isTest` and (`BETTER_AUTH_URL` is non-localhost or `DATABASE_URL` is not a local or test database). Enforce a minimum secret length (at least 32 chars) and reject known placeholder values in every environment. Drive relaxations from an explicit flag, not `NODE_ENV`. Also set `rateLimit.enabled: true` explicitly (see S01-04).

## S01-04 — Auth rate limiting is ineffective: global-bucket Express limiter, XFF-spoofable and in-memory better-auth limiter
- **Severity:** Medium (PLAUSIBLE; depends on proxy topology)
- **File:line:** `index.ts:137-144,194` (authLimiter 5000/min, no `trust proxy` anywhere); `lib/better-auth.ts:34-177` (no `rateLimit` / `advanced.ipAddress` config)
- **Description:** (1) `authLimiter` allows 5000 requests per minute per key. With no `app.set('trust proxy', ...)`, `req.ip` is the reverse proxy's address, so behind a load balancer all users share one bucket (a 5000/min cap per whole product, which can also lock out legitimate users). (2) better-auth's own limiter (which holds the sign-in, OTP and password special rules) keys on the leftmost `x-forwarded-for` value by default (`core/dist/utils/ip.mjs:196-212`) with no `trustedProxies` configured, so a client can rotate a spoofed header to get a fresh bucket per request unless the edge overwrites it. (3) Its default storage is process memory, so limits reset on deploy and are per-replica. `rateLimit.enabled` is only true in production by default.
- **Exploit scenario:** An attacker brute-forces passwords on `/api/auth/sign-in/email` or `/api/auth/email-otp/*` by sending a different `X-Forwarded-For` value on each request. The limiter never trips, and the 3-attempt OTP cap (per issued code) is bypassed by requesting new codes (see S01-06). The same technique mass-sends OTP, magic-link and reset emails to arbitrary addresses (email bombing, domain reputation damage).
- **Recommended fix:** Set `app.set('trust proxy', <hop count>)`. Configure `advanced.ipAddress.ipAddressHeaders` (for example `cf-connecting-ip`) and `trustedProxies`. Use a shared store (`secondaryStorage` or `rateLimit.storage: 'database'`). Add `customRules` for `/email-otp/*`, `/sign-in/*`, `/request-password-reset`, `/magic-link/*` (for example 3-5 per 10-60s) and per-email throttling. Lower `authLimiter` to a realistic value.

## S01-05 — Password reset and password change do not revoke existing sessions
- **Severity:** Medium
- **File:line:** `lib/better-auth.ts:43-53` (`emailAndPassword` has no `revokeSessionsOnPasswordReset`); `graphql/resolvers/better-auth.ts:186-189`
- **Description:** better-auth only deletes the user's sessions on password reset when `revokeSessionsOnPasswordReset` is true (`dist/api/routes/password.mjs:169`, `plugins/email-otp/routes.mjs:600`). It is unset. Combined with S01-01, a stolen session survives the owner's password reset for up to 7 days.
- **Exploit scenario:** A victim's session is stolen (shared computer, XSS exfiltrating the bearer token from `sessionStorage`). The victim notices and resets the password via the emailed link. The attacker's session remains fully valid.
- **Recommended fix:** `emailAndPassword.revokeSessionsOnPasswordReset: true`, and pass `revokeOtherSessions: true` on change-password calls from the client.

## S01-06 — emailOTP: sign-in OTP silently creates accounts; bypasses the "must sign up with org and billing" rule; email-bomb vector
- **Severity:** Medium
- **File:line:** `lib/better-auth.ts:128-139` (no `disableSignUp`), contrast `:146` (magicLink sets `disableSignUp: true` with the comment that new users must go through /signup)
- **Description:** In better-auth, `emailOTP` without `disableSignUp` creates a verified user on first successful `sign-in` OTP (`plugins/email-otp/routes.mjs:103,413`; user created with `emailVerified: true`). The `sendVerificationOTP` request for `type: "sign-in"` is also sent for non-existent emails (`shouldSendOTP = type === 'sign-in' && !opts.disableSignUp`), which sends mail to arbitrary addresses. The app intends signup to create an org and a Chargebee subscription (see the magicLink comment) but this path creates users with neither. The org plugin endpoint `/api/auth/organization/create` is also directly reachable (S01-08), so such a user can obtain an org with no subscription row.
- **Exploit scenario:** (a) Anyone can create unlimited accounts for emails they control (or send OTP mail to any third-party address) without the signup flow. (b) The resulting user calls `/api/auth/organization/create` and obtains an organization with no Subscription record. The resolver comment at `graphql/resolvers/better-auth.ts:136-138` states such orgs get "free unlimited access", which sidesteps plan limits.
- **Recommended fix:** `emailOTP({ disableSignUp: true, ... })`. Do org plus subscription creation in a `databaseHooks.organization` or `organizationHooks.afterCreateOrganization` hook so every creation path provisions the free subscription, or disable the plugin's HTTP org-create endpoint. Make plan enforcement default-deny when a Subscription row is missing.

## S01-07 — Session cookie `Secure` flag keyed on `NODE_ENV === 'production'` only; cookie overrides replace better-auth defaults
- **Severity:** Low
- **File:line:** `lib/better-auth.ts:164-177`
- **Description:** `secure: process.env.NODE_ENV === 'production'` forces `Secure=false` for any non-production `NODE_ENV` (staging, dev server on a public HTTPS URL, `test`) even when `BETTER_AUTH_URL` is https. better-auth would otherwise derive `Secure` and the `__Secure-` cookie prefix from the base URL. Only `session_token` is overridden. `session_data` and the other cookies use library defaults, so the flags are inconsistent. `sameSite: 'lax'` with bearer auth on the same API means state-changing GET endpoints are the only CSRF concern (none seen in scope). HttpOnly and SameSite are correctly set.
- **Exploit scenario:** On a staging environment served over HTTPS but run with `NODE_ENV=staging`, the session cookie is also sent over any plain-HTTP request to the host (downgrade or mixed content), enabling network-level theft.
- **Recommended fix:** Remove the `secure` override or use `advanced.useSecureCookies: authConfig.baseUrl.startsWith('https://')`. Set `defaultCookieAttributes` once for all cookies.

## S01-08 — better-auth organization/admin HTTP endpoints bypass the app's GraphQL rules (single-org rule race, no subscription provisioning)
- **Severity:** Low (single-org rule bypass is a TOCTOU race; subscription gap overlaps S01-06)
- **File:line:** `graphql/resolvers/better-auth.ts:86-119`; `lib/better-auth.ts:82-84,219-240`
- **Description:** `createOrganization` (resolver) checks for an existing membership then inserts the organization and member with direct Prisma calls. The check and insert are not atomic and not in a transaction, so two concurrent requests both pass the "one org per user" check. The better-auth `member.create` hook that enforces the same rule (`better-auth.ts:219-240`) is skipped because the resolver writes through Prisma, not the better-auth adapter. The better-auth `/api/auth/organization/create` endpoint enforces `organizationLimit: 1` with a similar count-then-create pattern. A failed Chargebee call leaves the org without a subscription, handled only by a Sentry alert. The slug is derived with a regex that yields an empty string for non-Latin names (for example Tamil, a supported locale) and the `Organization.slug` column is `@unique` (`schema.prisma:91`), so the second such org fails with a raw Prisma error, and colliding names leak the existence of another tenant's slug.
- **Exploit scenario:** A user fires parallel `createOrganization` mutations and ends up in several organizations, defeating the single-org model (which other code, for example `member.findFirst` in the session hook at `better-auth.ts:202-206`, assumes). Session `activeOrganizationId` is then ambiguous and may point at a different org than the caller expects. Impact is limited because `requireOrganizationMembership` verifies membership at use time.
- **Recommended fix:** Wrap check and create in a Prisma transaction with a unique constraint on `Member.userId` (or a serializable transaction). Generate slugs with a random suffix and handle `P2002`. Provision billing in a hook common to both creation paths.

## S01-09 — Session lifecycle: `activeOrganizationId` frozen at sign-in; `setActiveOrganization` is a no-op
- **Severity:** Low
- **File:line:** `lib/better-auth.ts:197-216`; `graphql/resolvers/better-auth.ts:150-169`; `middleware/better-auth-middleware.ts:52-61`
- **Description:** `setActiveOrganization` only verifies membership and returns the organization. It never updates the session (the comment admits this). The session's `activeOrganizationId` is set once at creation (first membership found) and is also frozen in the cookie cache (S01-01). `requireOrganization()` trusts `session.activeOrganizationId` without re-checking membership; callers that rely on it alone (rather than `requireOrganizationMembership`) would accept an org the user has since left. I did not trace all callers (out of S01 scope).
- **Exploit scenario:** A user removed from an organization keeps `activeOrganizationId` of that org in a cached session for up to 7 days. Any resolver that uses `requireOrganization` and the session value without a membership query would still authorize them. PLAUSIBLE, depends on callers.
- **Recommended fix:** Make `requireOrganization` verify membership in the database, or invalidate and refresh sessions on member removal (`deleteUserSessions` or update `activeOrganizationId`). Implement `setActiveOrganization` through `auth.api.setActiveOrganization`.

## S01-10 — `requireOrganizationRole` uses strict equality, so owners fail `'member'` checks
- **Severity:** Low (fails closed; availability or logic bug)
- **File:line:** `middleware/better-auth-middleware.ts:112`
- **Description:** `membership.role !== requiredRole` means `requireOrganizationRole(ctx, org, 'member')` rejects owners. Any caller that intends "at least member" is broken for owners. If a developer works around this with an `owner` check, nothing is exposed. No callers found in the backend source outside this file at review time (grep of `requireOrganizationRole` returned none), so currently dead code with a latent trap.
- **Exploit scenario:** None directly. A future caller may implement role hierarchies incorrectly. Mentioned for correctness.
- **Recommended fix:** Implement a role-rank comparison (`owner >= member`) or remove the unused helper.

## S01-11 — Auth tokens and OTP-related PII in logs (Morgan logs query strings; emails logged)
- **Severity:** Low (overlaps S05; token exposure affects S01 flows)
- **File:line:** `index.ts` morgan line (`':method :url :status ...'`, comment claims "path without query strings" but `:url` includes the query string); `services/emailService.ts:149,171,199,216`; `lib/better-auth.ts:200-208`; `middleware/better-auth-middleware.ts:25`
- **Description:** Morgan's `:url` is `req.originalUrl`, which includes the query string. Several auth flows carry secrets there: `GET /api/auth/magic-link/verify?token=...`, OAuth callbacks (`code`, `state`), `/respondent-oauth-callback?returnTo=...`, the one-time token consumption, and `reset-password/:token` (token is in the path). Single-use and short-lived, but readable by anyone with log access (and any log shipping or Sentry breadcrumbs) within the validity window. Recipient email addresses are logged on every OTP, reset and magic-link send. User id and role are logged on every authenticated request (acceptable). The OTP is also placed in the email subject line (`emailService.ts:127`), which is exposed in notification previews and mail logs.
- **Exploit scenario:** A person with log read access replays a still-valid magic-link or reset token seen in the logs and takes over the account within the 5-60 minute window.
- **Recommended fix:** Log `req.path` (not `originalUrl`) or strip the query string. Redact tokens in the path. Hash or mask emails in logs. Remove the OTP from the subject.

## S01-12 — OTP and one-time tokens stored in plaintext; OTP verification rate limiting and attempt model
- **Severity:** Low
- **File:line:** `lib/better-auth.ts:128-139` (`storeOTP` unset, default plain), `:81` (`oneTimeToken()` defaults), `:144-157` (magic link tokens stored plain by default)
- **Description:** OTPs are 6 digits (about 20 bits), 5 min expiry, `allowedAttempts: 3`. That is reasonable per issued code, but codes are stored in plain text in the `verification` table, so database read access yields live sign-in codes. Because each new request issues a fresh code, the practical online guess budget is governed by the request rate limiter (S01-04), not the 3-attempt cap. Responses for `verify` do return generic errors, but `reset-password`, `check-verification-otp` and `sign-in` paths map unknown users to `USER_NOT_FOUND` (`plugins/email-otp/routes.mjs:261,326,589,727`), which allows account enumeration on those endpoints. Note `forget-password` OTP sends silently for unknown users in the default configuration, so enumeration is mainly through the reset and check endpoints.
- **Exploit scenario:** An attacker enumerates registered emails by calling the OTP reset or check endpoints with candidate addresses and distinguishing `USER_NOT_FOUND` from `INVALID_OTP`. With S01-04 rate-limit bypass this scales.
- **Recommended fix:** `emailOTP({ storeOTP: 'hashed' })`. Hash (or at least encrypt) magic-link and one-time tokens (`storeToken: 'hashed'` for `oneTimeToken`). Normalize error responses to a single generic message on enumeration-prone endpoints. Add per-email limits.

## S01-13 — `setAccountPassword`: weak validation, no current-credential check, hook bypass
- **Severity:** Low
- **File:line:** `graphql/resolvers/better-auth.ts:175-192`
- **Description:** The resolver only requires an authenticated session and `password.length >= 8` (no maximum, no breach check). better-auth's server API `setPassword` rejects only when a credential account already exists. The `haveIBeenPwned` plugin hooks specific paths (`/sign-up/email`, `/change-password`, `/reset-password`) and does not cover `set-password`. Any holder of a live session on an account without a password (OTP/Google/magic-link users) can attach a permanent password with no re-authentication, and sessions are not revoked afterward. `context.req` is typed optional and dereferenced without a guard (`context.req.headers`), so a missing `req` (for example in a WebSocket subscription context) would throw an unhandled TypeError rather than a clean error.
- **Exploit scenario:** A short-lived stolen session (XSS reading the bearer token from `sessionStorage`, an unattended laptop) is converted into a durable password credential. The attacker logs in later even after the victim signs out everywhere. Also users can set breached or 8-character passwords the sign-up path would reject.
- **Recommended fix:** Require fresh authentication (recent OTP or magic-link within minutes, `session.freshAge` check) before setting a password. Enforce the same policy (min 12, max 128, breach check) as sign-up. Guard `context.req`. Revoke other sessions after setting.

## S01-14 — Bearer plugin and one-time-token handling
- **Severity:** Info
- **File:line:** `lib/better-auth.ts:76-81`; `index.ts:213-231`; `apps/form-app/src/lib/auth-client.ts:7-30`
- **Description:** `bearer()` runs with the default `requireSignature: false` (`dist/plugins/bearer/index.mjs:36`), so a raw session token is accepted as well as a signed one. The token is random and secret, so this is acceptable, but it means the token alone (no HMAC) authenticates. The token lives in `sessionStorage`, readable by any XSS in form-app (the CSP in the repo covers the backend only). `/respondent-oauth-callback` redirects with `?ott=` in the URL to form-viewer. The `returnTo` open-redirect check (`isSafeReturnPath`) is correct and the redirect host is fixed to `FORM_VIEWER_URL`, but if that variable is unset it falls back to `http://localhost:5173` in production. The token can leak via browser history, `Referer`, and logs (S01-11); it is single use and short lived.
- **Exploit scenario:** None direct. Hardening notes only.
- **Recommended fix:** Set `requireSignature: true` if the clients can send the signed form. Require `FORM_VIEWER_URL` and `FORM_APP_URL` (fail startup in production rather than defaulting to localhost, both here and in `better-auth.ts:153`). Strip `ott` from the URL immediately after consumption in form-viewer.

## S01-15 — Trusted origins and CORS: dev origins enabled on every non-`production` NODE_ENV; empty origin list in production if `CORS_ORIGINS` is unset
- **Severity:** Info
- **File:line:** `lib/better-auth.ts:26-32`; `index.ts:171-186`
- **Description:** `trustedOrigins` is `CORS_ORIGINS` plus `DEV_ORIGINS` (localhost on 8 ports) for any `NODE_ENV` other than `production`. Credentials are allowed by CORS for the same list (`credentials: true`). Wildcards are not used and origins are explicit, which is good. On a non-production but internet-reachable environment, any local page or process on a user's `localhost` port (for example a malicious local dev server) is a trusted origin for credentialed requests. In production an unset `CORS_ORIGINS` yields an empty list (fails closed, which is correct, but would also break the apps without a clear startup error).
- **Exploit scenario:** On a staging host, a user visits a malicious page served from their own localhost (for example a compromised dev tool) that makes credentialed cross-origin requests to the staging API with the user's cookies.
- **Recommended fix:** Gate `DEV_ORIGINS` on `NODE_ENV === 'development'` only. Validate that `CORS_ORIGINS` is non-empty and https in production at startup.

## S01-16 — `requireEmailVerification` with no `emailVerification.sendVerificationEmail` configured
- **Severity:** Info
- **File:line:** `lib/better-auth.ts:43-53`
- **Description:** Email verification is required for password sign-in, but only the `emailOTP` plugin is configured to send codes and `emailVerification.sendVerificationEmail` is absent. Unverified users signing in with a password cannot get a verification link from better-auth's default flow, so verification depends on the OTP flow in the frontend. This is a functional dependency, not a vulnerability: unverified accounts are correctly blocked from signing in. Verified status of OTP, magic-link and Google sign-ups is set true by better-auth on proof of mailbox or provider assertion. Google account linking follows better-auth defaults (verified Google email links to an existing account); confirm that `account.accountLinking` should stay at defaults.
- **Exploit scenario:** None identified.
- **Recommended fix:** Document the flow. Consider explicit `account.accountLinking.trustedProviders` configuration.

## Verified as correct (no finding)
- `createBetterAuthContext` fails closed (returns unauthenticated on error). `requireAuth` correctly checks both `isAuthenticated` and `user`.
- `requireOrganizationMembership` queries `Member` by `(organizationId, userId)` from the authenticated user, not from client input, so no cross-tenant bypass there. `activeOrganization` re-verifies membership.
- `BETTER_AUTH_SECRET` is required (throws) outside the test environment; `session.expiresIn` is 7 days with a 24-hour refresh; cookie flags `HttpOnly` and `SameSite=Lax` are set; `crossSubDomainCookies` is off.
- `/respondent-oauth-callback` `returnTo` handling rejects absolute, protocol-relative and backslash-prefixed URLs.
- Admin role gate in `admin.ts` and `utils/auth.ts` uses an allow-list of role names.
