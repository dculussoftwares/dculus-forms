## Findings

### S11-01 - Medium - CSV formula injection: respondent-controlled cells are exported verbatim
- **Severity:** Medium
- **File:line:** `services/unifiedExportService.ts:79-149` (`formatFieldValue`, CSV branch `:137-146`), `:152-162` (`escapeCsvFieldName`), `:545`, `:558`, `:578-640` (row assembly); plugin values `:613-618`
- **Description:** CSV output only applies RFC 4180 quoting (comma, quote, CR, LF). No cell is checked for a leading `=`, `+`, `-`, `@`, TAB or CR, and none is prefixed with a neutralizing apostrophe. Attacker-influenced cells include every form answer (`response.data[...]`), `respondentEmail`, tag names, plugin values (AI tag names), the filename part of file-upload keys (`:114-121`), and, when the schema is empty, the column header derived from a raw response key (`:461-475`, `label = fieldId` for short keys). Anonymous respondents can place arbitrary strings in any of these because submissions are not validated server side (S04-04). Excel (.xlsx) output is not affected in the same way: ExcelJS writes JS strings as string cells (`:781-784`), so they are not evaluated as formulas when opened. Only the CSV format is exploitable.
- **Exploit scenario:** An anonymous visitor to a public form submits a text answer that begins with `=` followed by a spreadsheet function (for example a hyperlink or external-data function pointing at an attacker host). An EDITOR clicks Export, chooses CSV and opens it in Excel or LibreOffice. The spreadsheet evaluates the cell and, depending on the client's protected-view and external-content settings, leaks adjacent row data (other respondents' PII) to the attacker host or prompts the user to launch content. The attacker needs no account.
- **Recommended fix:** Add one `sanitizeCsvCell(value: string)` helper applied to every data cell and header in `generateCsvContent` (including plugin values, tag names, emails, derived labels): if the string starts with `=`, `+`, `-`, `@`, `\t` or `\r`, prefix it with `'`. Keep the quoting step after sanitizing. Apply the same helper to Excel cells that start with those characters as defence in depth (or set them explicitly as string cells with `quotePrefix`). Add unit tests with payloads in each cell category, including the `-` case for negative numbers (only prefix non-numeric strings to avoid corrupting real numbers).

### S11-02 - Medium - Export builds one column per distinct unknown response key: unauthenticated DoS of the export path
- **Severity:** Medium
- **File:line:** `services/unifiedExportService.ts:483-520` (`extractFieldInfo`, orphan columns), `:563-565`, `:624-640` and `:766-782` (per-cell schema scan), `:787-795` (auto-size pass)
- **Description:** In the normal (non-empty schema) branch, every response key that holds a non-empty value and is not a known field ID becomes a column headed "Unknown field (deleted)" (`:511-519`). Response `data` keys are not validated against the schema on submit (S04-04) and `assertResponsePayloadWithinLimits` only caps the key count per response at 500 (`lib/responsePayloadLimits.ts:5,22`). For each cell the code also does a linear `pages.find(...)` over the schema (`:628-637`, `:769-779`), so the work is `columns x rows x fields`. Nothing bounds the number of columns before generation; the 50,000-row cap is checked on rows only (`graphql/resolvers/unifiedExport.ts:81`).
- **Exploit scenario:** An anonymous attacker submits N responses to a public form, each with 500 distinct random keys. The submission count is bounded by the plan (1,000 on free) but that already yields up to 500,000 unique columns. When an EDITOR (or an automated flow) runs an export, the single Node process allocates a row array of that width for every response and spends minutes in CPU, spiking memory for all tenants on the instance. The resulting spreadsheet is also unusable (Excel supports 16,384 columns). The same keys inflate the memory path of filtered queries (S03-08).
- **Recommended fix:** Primary fix is server-side validation that drops or rejects keys that are not in the form schema (S04-04). In the export: cap orphan columns (for example 200 total, collapse the rest into one JSON "Other answers" column), precompute a `Map<fieldId, FieldType>` once instead of scanning pages per cell, and check `columns x rows` against a budget before building the workbook.

### S11-03 - Medium - Stored respondent values can make every DB-level date or number filter throw, forcing a full in-memory load on each query
- **Severity:** Medium
- **File:line:** `services/responseQueryBuilder.ts:846-930, 950-976` (date operators), `:704-789` (numeric operators); catch/fallback `services/responseService.ts:394-401`
- **Description:** The SQL date operators guard with an unanchored regex `~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}'` (prefix only) and then cast `(data->>'x')::timestamp` / `::date`. A stored value such as `2024-99-99` or `2024-01-01xyz` matches the guard but the cast raises a Postgres error. The epoch branch matches `^[0-9]+$` and casts to `bigint`, which raises for values with 20 or more digits. Numeric operators cast values matching the numeric regex to `numeric`, and a digit string longer than numeric's limit overflows. `CASE ... WHEN` ordering does not help because the failing expression is inside the selected branch. Any such value in any response of the form makes the whole statement fail. `getResponsesByFormId` swallows the error (`catch (error)` at `:394`), logs it and re-runs the query by loading every response of the form into memory (`:397-399`). Because answer values are not validated server side (S04-04), an anonymous respondent can poison a date, text or number field with one submission, after which every VIEWER's date or numeric filter on that field takes the memory path permanently for that form.
- **Exploit scenario:** An anonymous attacker submits one response with an invalid date string in a date field (or a 30-digit number in a numeric field). From then on each filtered page load by any VIEWER or EDITOR loads and filters all responses in Node memory (`listByForm`, `attachFilterContext`), and the same applies to the iterated pages used for file exports and PDF batches (`iterateResponsesByFormId` calls this function once per 100-row batch, so the whole table is reloaded per batch). On a large form this multiplies memory and CPU by the page count. Results may also differ between the two evaluators (S11-06).
- **Recommended fix:** Make casts total: anchor the regex fully (`'^[0-9]{4}-[0-9]{2}-[0-9]{2}(T.*)?$'` plus a validity check), use a safe-cast helper (a SQL function that returns NULL on failure) or move parsing into SQL with `to_date` guarded by `CASE`, and cap digit counts in the numeric and epoch regexes (`{1,15}`). Do not silently fall back to loading the entire form: return a clear `BAD_USER_INPUT`/`INTERNAL_SERVER_ERROR` via `createGraphQLError` or fall back only for a whitelisted error class, and page the fallback with a bound.

### S11-04 - Low - `__submittedAt` conditions use an unqualified `"submittedAt"` column that becomes ambiguous when submission-analytics is joined
- **Severity:** Low
- **File:line:** `services/responseQueryBuilder.ts:217-248` (`const col = '"submittedAt"'`), join at `:84-85`; `prisma/schema.prisma:445` (`FormSubmissionAnalytics.submittedAt`)
- **Description:** `buildSubmittedAtCondition` does not qualify the column, while `__browser`, `__operatingSystem`, `__country` and `__completionTimeSeconds` add `LEFT JOIN "form_submission_analytics" fsa`, which also has a `submittedAt` column. Postgres rejects the query as ambiguous. The common UI combination (a date-range scope filter plus a browser or country filter) therefore always fails on the DB path and silently falls back to the in-memory path (same fallback as S11-03). Similar unqualified names exist elsewhere in the same file for `data` (`:592-593`), which is currently safe only because no joined table has a `data` column.
- **Exploit scenario:** Not an exploit by itself. Impact is availability and cost: any VIEWER using the supported filter combination causes whole-form loads and the filters are evaluated by the second implementation (S11-06). Business rules such as soft delete (S03-02) are enforced differently between the two paths.
- **Recommended fix:** Qualify as `"response"."submittedAt"`, `"response".data` everywhere in the builder, and add a regression test that runs every meta filter combination through the SQL path against a real database.

### S11-05 - Low (PLAUSIBLE) - Filter input has no limits on count, array size or string length, and no query timeout was found
- **Severity:** Low
- **File:line:** `graphql/schema.ts:1601-1608` (`ResponseFilterInput`), `graphql/resolvers/responses.ts:238-283`, `services/responseQueryBuilder.ts:544-557, 570-572, 559-564`, `repositories/responseRepository.ts:157-206`
- **Description:** `filters`, `values`, `value` and the `ids` lists are unbounded other than by the 10 MB JSON body limit (`index.ts:231`) and `depthLimit(8)`, which does not limit breadth. A VIEWER can send thousands of filters. Some predicates are correlated per row: `__duplicateEmail` adds an `EXISTS` sub-select over `response`, `__completenessPercent` runs `jsonb_each` per row, `__lastEditedAt`/`__lastEditedByEmail` add a `LATERAL` join. Large `values` arrays also create tens of thousands of bound parameters (Postgres allows 65,535), which fail and trigger the fallback of S11-03. Unescaped `%`/`_` in user text is passed to `ILIKE` (`:354-363, 660-702`), so repeated-wildcard patterns are quadratic on long strings (values up to 10,000 characters per field are allowed). No `statement_timeout` or Prisma query timeout was found in the repo, but infrastructure configuration was not reviewed, hence PLAUSIBLE.
- **Exploit scenario:** A user with VIEWER on a throwaway form in their own org sends a `responsesByForm` request with several thousand `__duplicateEmail` filters or heavy wildcard patterns against a form seeded with many long answers. The query occupies a pooled DB connection and CPU for a long time, degrading other tenants.
- **Recommended fix:** In the resolver, enforce maxima (for example 25 filters, 200 `values`, 500 characters per `value`, lengths on `fieldId`) with `createGraphQLError(..., GRAPHQL_ERROR_CODES.BAD_USER_INPUT)`. Escape `\`, `%` and `_` in `ILIKE` operands (and add `ESCAPE '\'`). Set a per-role Postgres `statement_timeout` (or `SET LOCAL` in the raw query) for the filtered queries.

### S11-06 - Low (PLAUSIBLE for item 3) - Two independent filter evaluators disagree, so UI list, export, PDF batches and auto-run select different rows
- **Severity:** Low
- **File:line:** SQL: `services/responseQueryBuilder.ts:653-658, 690-702, 791-822, 846-860`; in-memory: `services/responseFilterService.ts:251-254, 274-278, 401-425, 322-331`; export path uses only in-memory (`graphql/resolvers/unifiedExport.ts:73-76`); also `plugins/core/pdfGeneratorAutoRun.ts:46`
- **Description:** The paginated list uses SQL; the export, the PDF generator auto-run and the fallbacks use `applyResponseFilters`. Verified divergences: (1) `NOT_EQUALS` on a missing answer: SQL evaluates `LOWER(NULL) != ...`, which is NULL, so the row is excluded; in memory `isValueEmpty` returns true so the row is included. (2) `STARTS_WITH`/`ENDS_WITH`/`CONTAINS` treat `%` and `_` as wildcards in SQL but literally in memory. (3) `IN`/`NOT_IN` in SQL only match JSON strings and arrays (`jsonb_typeof` check), so answers stored as JSON numbers never match; memory compares `String(value)`. (4) Date comparisons use `::timestamp` in SQL and server-local time in memory (`parseDate`, `toDateString`).
- **Exploit scenario:** An EDITOR filters the Responses table to "Country is not X" and exports "the filtered view", but the export contains a different set. Or a PDF generator's match preview (SQL path) says N matches while auto-run (memory path) generates PDFs for a different set. Over-disclosure stays within the caller's own EDITOR rights, so this is a correctness and data-minimization issue, not an escalation.
- **Recommended fix:** Use a single evaluator. Either run exports through the same SQL path (stream via `iterateResponsesByFormId`, also removing S03-08) or generate both from one operator table and add property tests that assert parity on a random corpus.

### S11-07 - Low - Offset pagination with a non-unique sort key can skip or duplicate responses in paged consumers
- **Severity:** Low
- **File:line:** `services/responseService.ts:367-372` (ORDER BY `submittedAt` only), `:375-381` memory sort, `:507-540` (`iterateResponsesByFormId`); `services/fakeResponseService.ts:118` (bulk insert with identical `submittedAt` default)
- **Description:** `ORDER BY "response"."submittedAt" <dir>` has no tiebreaker. `createMany` (fake responses, imports) gives all rows of a statement the same `now()` value, so ties are guaranteed, and rows inserted between page fetches shift `OFFSET`. `iterateResponsesByFormId` fetches page after page with `LIMIT/OFFSET`, and is used by file ZIP export, PDF batch generation and the automation engine (`services/responseFiles/responseFileCatalog.ts:105`, `pdfGeneratorService.ts:194`, `automation/engine.ts:447`).
- **Exploit scenario:** A bulk file export or PDF batch silently omits or duplicates some responses when responses are created or deleted during the run (or when many share a timestamp). A data-subject export or erasure workflow relying on it is incomplete without any error.
- **Recommended fix:** Add a deterministic tiebreaker (`, "response".id`) to both SQL and Prisma `orderBy`, and switch the iterator to keyset pagination on `(submittedAt, id)`.

### S11-08 - Low - Suggestion queries expose editor emails and analytics values without `deletedAt` or access narrowing
- **Severity:** Low
- **File:line:** `services/responseFieldSuggestions.ts:65-76` (`__lastEditedByEmail`), `:35-64` (browser/OS/country), caller `graphql/resolvers/responses.ts:285-305`
- **Description:** `distinctResponseFieldValues` is VIEWER-level. For `__lastEditedByEmail` it returns the distinct `user.email` of everyone who edited any response of the form, including edits on soft-deleted responses (no `r."deletedAt" IS NULL`), with an `ILIKE` search that allows prefix probing. The analytics-based suggestions come from `form_submission_analytics` by `formId` only, so they also include rows of soft-deleted responses. `__respondentEmail` correctly filters deleted rows. This matches the VIEWER-level exposure already reported for edit history in S03-05 and the soft-delete gap in S03-02.
- **Exploit scenario:** A VIEWER enumerates the emails of all EDITORs/OWNERs who ever touched responses, and of editors on responses an OWNER deleted for erasure, by typing prefixes into the filter combobox.
- **Recommended fix:** Add `AND r."deletedAt" IS NULL` (and join analytics to non-deleted responses); restrict `__lastEditedByEmail` suggestions (and the filter itself) to EDITOR, or return only names for VIEWER; escape wildcards in `pattern`.

### S11-09 - Low - Fake-response generator has no environment gate, per-form cap or atomic budget reservation
- **Severity:** Low
- **File:line:** `graphql/resolvers/responses.ts:800-846`, `services/fakeResponseService.ts:76-134`
- **Description:** The mutation is reachable in production for any EDITOR (intended). The check-then-spend pattern (`checkAITokenBudget` before, `recordAITokenUsage` after the model call) is not atomic, so concurrent requests overshoot the monthly AI credit budget by up to the number of in-flight calls. There is no cap on total fake rows per form and no per-user rate limit, only 10 rows per call; rows bypass submission usage counters and plan limits by design (documented in the service comment), but they persist as normal responses, appear in exports and in PDF/automation selections (only a tag and `metadata.source` mark them), and are excluded only from field analytics. Form title and field labels are sent to the model as the prompt, which is builder-controlled content, but output is coerced to the schema (`coerceAiSampleData`) so no tool or code path is exposed.
- **Exploit scenario:** A malicious or compromised EDITOR in a paid org loops the mutation (parallel calls) to burn the org's AI credits past the limit and to fill the form with unmetered rows (storage, export size), or an unaware owner exports a mix of real and synthetic data that is only distinguishable by a tag column.
- **Recommended fix:** Reserve budget before calling the model (atomic decrement or advisory lock per org) and reconcile after; cap fake rows per form (and per day per user); emit an explicit "Synthetic" marker column in exports and exclude `metadata.source = ai_generated` from exports/automations by default; add an audit entry (`audit('response.fake_generated', ...)`).

### S11-10 - Info - Unsafe-input errors are plain `Error`s swallowed by a blanket catch; dead query-builder entry point ignores OR logic
- **Severity:** Info
- **File:line:** `services/responseQueryBuilder.ts:23-28, 460-465` (`throw new Error(...)`), `:187-214` (`buildPostgreSQLFilter` with unused `_filterLogic`), `services/responseService.ts:394-401`
- **Description:** `ensureSafeFieldId` and `ensureSafeGeneratorId` throw raw `Error` rather than `createGraphQLError(..., BAD_USER_INPUT)`. The only caller wraps them in the catch that falls back to the in-memory evaluator, so a malicious fieldId is neither rejected nor reported as a client error; it simply produces an empty or odd result from the second evaluator (property lookup on `response.data` with attacker-chosen key such as `__proto__`/`constructor`, which is harmless here but unnecessary). The guard still fails safe: the unsafe value never reaches SQL. `buildPostgreSQLFilter` is exported but not used (the service builds conditions inline), and it ignores `_filterLogic`, so any future caller would silently turn OR filters into AND.
- **Exploit scenario:** None today. Risk is a future refactor that reuses `buildPostgreSQLFilter` and changes result semantics, or the swallowed validation errors hiding probing attempts.
- **Recommended fix:** Validate `fieldId` at the resolver boundary (reject with `BAD_USER_INPUT`), do not catch validation errors in the fallback, and delete or fix `buildPostgreSQLFilter`.
