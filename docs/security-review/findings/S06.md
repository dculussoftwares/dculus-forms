# S06 — File upload & storage (R2/S3)

Scope reviewed (all under `apps/backend/src/`): `routes/upload.ts`, `graphql/resolvers/fileUpload.ts`, `formFiles.ts`, `responseFiles.ts`, `services/fileUploadService.ts`, `formFileService.ts`, `temporaryFileService.ts`, `services/responseFiles/*`, `lib/contentDisposition.ts`. Also read for context: `index.ts` (limiter, graphql-upload, mock route), `services/formSharingService.ts` (`checkFormAccess`), `graphql/resolvers/pdfTemplates.ts` (fileKey handling), `repositories/formFileRepository.ts`, `responseRepository.ts`, and the avatar flow in `form-app`. Review-only; no source changed. No secrets are included.

Summary: 0 Critical, 1 High, 5 Medium, 7 Low, 3 Info (16 findings). Items marked PLAUSIBLE depend on deployment behaviour (Cloudflare/R2 config) that cannot be confirmed from the repository.

Cross-references: S04-10 (verified and expanded as S06-02), S04-04 (no server-side validation of file refs in `submitResponse`), S04-06 (no effective anonymous rate limiting), S01-07 (session cookie flags; SameSite=lax is what limits CSRF on `/upload`), S10 (PDF templates/generators), S03 (response/respondent-email exposure in `responseFiles`).

## S06-01 — Anonymous requests buffer up to 50 MB in memory (about 3x copies) before any auth or type validation
- **Severity:** High
- **File:line:** `routes/upload.ts:31-38` (multer `memoryStorage`, 50 MB limit, `upload.single('file')` runs before the handler), `routes/upload.ts:181-189` and `services/fileUploadService.ts:159-167` (buffer copied again), `index.ts:146-152,239` (limiter)
- **Description:** `POST /upload` is mounted publicly (needed for respondent uploads). Multer parses and fully buffers the file body in RAM before the handler checks `type`, session, or form. Any request that carries a 50 MB file part costs memory even if it is then rejected (invalid type, unauthenticated for `FormTemplate`, unknown form). The buffer is then re-wrapped in a `Readable`, copied chunk-by-chunk with `Buffer.from(chunk)` and concatenated again in `streamToBuffer`, so peak memory per request is roughly 2-3x the file size. The only throttle is `uploadLimiter`: 5000 requests/min per IP (and per S04-06 the key may be the shared proxy IP). The same Node process serves GraphQL, Hocuspocus WebSockets and auth.
- **Exploit scenario:** An unauthenticated attacker opens a few dozen concurrent slow or fast multipart POSTs of about 50 MB with `type=anything`. Each holds 50-150 MB of heap until finished. The container hits its memory limit and is OOM-killed, taking down the API and live collaboration for all tenants. Repeating is trivial.
- **Recommended fix:** Stream to R2 instead of buffering (multer-s3 or busboy piped into `@aws-sdk/lib-storage` `Upload`, as `uploadTemporaryStream` already does). Perform auth, type and form checks before consuming the body (an early middleware on headers/query, or require `type` and `formId` as query parameters or headers). Enforce `Content-Length` caps per type up front, add a small global concurrency limit for uploads, and a much lower per-IP limit for anonymous uploads.

## S06-02 — `FormResponse` upload ignores form access control, time window, response caps and soft-delete (S04-10 verified and expanded)
- **Severity:** Medium
- **File:line:** `routes/upload.ts:126-172` (form lookup selects only `isPublished/organizationId/createdById`), `routes/upload.ts:195-212` (unbounded `FormFile` row per upload)
- **Description:** Verified: for anonymous callers the only gate is `form.isPublished === true` (`:169`). The route never evaluates the settings that `submitResponse` enforces: `accessControl` (sign-in required, allowed email domains; `lib/respondentAccess.ts` / `accessControlEnforcement.ts`), `submissionLimits.timeWindow`, `maxResponses`, and subscription submission limits. Additional gaps found beyond S04-10:
  1. `Form.deletedAt` is not checked (`schema.prisma` has `deletedAt` on `Form`), so a soft-deleted but still `isPublished` form keeps accepting uploads.
  2. Each upload writes a `FormFile` row (`size Int`, unbounded count) and an R2 object, with no per-form, per-IP or per-session quota and no total storage cap per form or organization.
  3. Nothing ties an upload to a later submission (S04-04: `submitResponse` does not validate file keys), so abandoned uploads accumulate forever (see S06-06).
  4. The field's own `maxFileSizeMb` / `allowedMimeTypes` are enforced only in the viewer client (`form-viewer/src/pages/FormViewer.tsx:59-63`), not on the server (see S06-07).
  5. Uploads do not count against the subscription, so storage use is invisible to billing.
- **Exploit scenario:** (a) A competitor loops 50 MB uploads against a published form of a victim, including forms that are closed, sign-in-only, or already at their cap. R2 storage and egress grow at the victim's expense, and the victim's builder file listing (`getFormFiles`, S06-05) fills with junk rows. (b) A form the owner "deleted" still accepts uploads from anyone who has its `formId`.
- **Recommended fix:** Share one gate with `submitResponse`: load form with `deletedAt: null`, run `resolveAccessStatus`, `enforceTimeWindow`, and the response/usage cap checks before accepting the body. Require a signed, short-lived upload token minted by a GraphQL mutation (per form + field, with size/MIME constraints from the schema) and consume it on submit. Add per-form and per-IP quotas, a total bytes cap per form, and a reaper for uploads not referenced by a response within N hours.

## S06-03 — `deleteFile` ownership check can be bypassed by setting your own `User.image` / `Organization.logo` to a victim's object key
- **Severity:** Medium
- **File:line:** `graphql/resolvers/fileUpload.ts:236-258` (ownership by `findUserByImageKey` / `findOrganizationByLogoKey`), `repositories/userRepository.ts:33-34`, `services/fileUploadService.ts:321-327,375-390`; avatar written as a URL at `form-app/src/components/account/AccountSettings.tsx:37-38`
- **Description:** For keys without a `FormFile` row, `deleteFile` decides ownership with `prisma.user.findFirst({ where: { image: key } })` and an equivalent org-logo lookup. The app itself stores a CDN URL in `User.image` (`updateUser({ image: result.url })`), so a legitimate owner never matches by key (a real avatar delete falls through to the admin-only branch), but a malicious user can call better-auth `updateUser({ image: "<victim key>" })`. No `user.additionalFields` / input restriction exists in `lib/better-auth.ts`, so `image` is a free-form string. After that, `findUserByImageKey(key)` returns the attacker as the owner and `deleteFile` proceeds. The same works with `Organization.logo` for any org owner. `deleteFile` performs no key-prefix validation; the bucket is inferred from the key prefix (`getBucketForKey`), so any non-private-prefixed key resolves to the public bucket.
- **Exploit scenario:** Any registered (free) user reads another tenant's logo or avatar URL (public CDN, visible in shared UI/emails/viewer headers), derives the key (`files/organization-logo/...`), sets their own `image` to that key through better-auth, then calls `deleteFile(key)`. The victim's logo/avatar/template thumbnail (or any untracked public-bucket object whose key is known) is deleted. Cross-tenant integrity/availability impact on public assets; no confidentiality impact found.
- **Recommended fix:** Do not infer ownership from user-controlled columns. Record uploads (`FormFile`-like `StoredFile` table with `ownerUserId` / `organizationId`, type, key) for avatars and logos and authorize on that; or restrict `deleteFile` to keys whose prefix matches the caller (`files/user-avatar/<userId>/...`). Make `user.image` / `organization.logo` writable only to server-issued values (better-auth `input: false` + a dedicated mutation), and validate that stored values are CDN URLs/keys the caller uploaded. Reject keys outside the allow-listed prefixes in `deleteFile`.

## S06-04 — No content validation on uploads to the public CDN: client-declared MIME is trusted, extension is independent of MIME, no magic-byte check
- **Severity:** Medium (stored XSS via CDN is PLAUSIBLE only, see below)
- **File:line:** `services/fileUploadService.ts:198-248` (MIME allow-list on `mimetype` from the multipart part header), `:112-128` (extension taken from the filename), `:284-292` (`ContentType: finalMimetype`), `routes/upload.ts:42-55`
- **Description:** For `FormBackground`, `UserAvatar`, `OrganizationLogo` and `FormTemplate` (public bucket, CDN) the allow-list is applied to the `Content-Type` of the multipart part, which the client chooses. The filename extension is preserved separately in the key (`...-name.<ext>`). Nothing verifies that the bytes match the declared type (no magic-byte/`file-type` sniffing, no image decode/re-encode, no extension-vs-MIME match). `FormBackground` additionally allows `video/mp4`/`video/webm` up to 45 MB, which makes it a convenient 45 MB hosting slot for any byte stream. The allow-list correctly excludes `image/svg+xml` and `text/html`, but an attacker can upload an SVG/HTML/EXE payload with `Content-Type: image/png` and filename `x.svg` / `x.html` / `x.exe`.
- **Exploit scenario:** Any signed-up user (open registration) hits `UserAvatar` (no formId or membership needed) and hosts arbitrary content on the company's trusted CDN domain with an HTML/SVG/EXE extension, usable for phishing or malware distribution under the platform's domain. Stored XSS is PLAUSIBLE: R2 serves the stored `Content-Type` (`image/png`), which modern browsers will not render as HTML, so script execution is unlikely unless a Cloudflare transform/rule derives type from extension or the response lacks `nosniff`. Not verifiable from the repo.
- **Recommended fix:** Verify magic bytes (e.g. `file-type`) and require the detected type to be in the allow-list and consistent with the declared one; derive the stored extension and `ContentType` from the detected type, not from the filename. For avatars/logos/backgrounds, decode and re-encode with `sharp` (strips polyglots and metadata, bounds dimensions). Serve the CDN with `X-Content-Type-Options: nosniff` and a `Content-Security-Policy: sandbox` response header rule. Consider a dedicated cookieless domain for user-generated public assets.

## S06-05 — `getFormFiles` exposes metadata of respondent files from deleted responses and abandoned uploads to VIEWERs
- **Severity:** Medium
- **File:line:** `graphql/resolvers/formFiles.ts:15-40` (allows `type: FormResponse`, no type filter by default), `repositories/formFileRepository.ts:43-47`, `routes/upload.ts:195-212`, `services/responseFiles/responseFileCatalog.ts:9-14` (states intent)
- **Description:** `FormFile` rows are created for every `FormResponse` upload, including uploads from abandoned submissions and uploads belonging to soft-deleted responses. `responseFileCatalog.ts` explicitly documents that these "may not be browsed or exported" and builds its listing from live responses. `getFormFiles` bypasses that contract: any VIEWER on the form receives `key`, `originalName`, `size`, `mimeType`, `createdAt` for every row, and with no `type` argument it returns all of them. Downloading is still blocked (`createResponseFileDownloadUrl` requires a live response reference), so this is metadata only. Spam uploads (S06-02) are also surfaced here.
- **Exploit scenario:** A VIEWER (or a collaborator whose rights were reduced after a response was deleted for erasure reasons) lists `getFormFiles(formId)` and sees original filenames such as `passport-john-doe.pdf` from responses the owner deleted, plus sizes and timestamps. A hostile uploader can also plant offensive filenames that appear in the builder.
- **Recommended fix:** Restrict `getFormFiles` to builder asset types (`FormBackground`) or require EDITOR and exclude `FormResponse`; serve respondent file metadata only through `responseFiles` (live responses only). Delete the `FormFile` row and R2 object when a response is deleted (S06-06).

## S06-06 — No deletion or cleanup of R2 objects for deleted responses/forms, replaced avatars/logos, or orphaned uploads
- **Severity:** Medium
- **File:line:** `services/fileUploadService.ts:375-390` (`deleteFile` only called from `fileUpload.ts` and `pdfTemplates.ts:283`), `services/temporaryFileService.ts:199-267` (sweep covers only `temp-exports/`), `graphql/resolvers/fileUpload.ts:157-160`
- **Description:** Only `temp-exports/` is swept. Not removed anywhere: respondent files when a response is deleted (soft or hard) or a form is deleted (the `FormFile` rows cascade but the objects stay), files of drafts and abandoned submissions, avatars and logos replaced by new uploads (or removed with the user/org), `FormBackground` objects replaced in the builder, and `FormResponse` uploads made through GraphQL without a form (`files/form-response/<name>`, no DB record at all). There is no R2 lifecycle rule in the repository.
- **Exploit scenario:** (a) Privacy/GDPR: a data subject's erasure request is honoured in the DB, but their uploaded ID scans remain in the private bucket indefinitely (accessible to anyone with R2 credentials, backups, or via the cascade-orphaned keys). Public avatars of deleted users stay fetchable from the CDN permanently. (b) Cost: junk uploads (S06-02) and normal churn grow storage without bound.
- **Recommended fix:** On response/form/user/org deletion, enqueue deletion of the referenced keys (including soft-delete purge after retention). Add a reaper that lists `files/form-response/` and deletes objects with no `FormFile`/response reference older than 24 h. Replace-on-upload for avatars/logos/backgrounds should delete the previous object. Add R2 lifecycle rules for `temp-exports/` (1 day) and orphan prefixes as defence in depth.

## S06-07 — Respondent uploads: server only blocks a short exact-match MIME list; field `allowedMimeTypes`/`maxFileSizeMb` are client-side only
- **Severity:** Low
- **File:line:** `services/fileUploadService.ts:93-107,213-218,258-278`, `form-viewer/src/pages/FormViewer.tsx:57-66`
- **Description:** For `FormResponse`, any type outside a 13-entry blocklist is stored, up to the global 50 MB. The blocklist is an exact string match on a client-supplied header and omits `image/svg+xml`, `text/xml`, `application/x-msdownload`, `application/x-msdos-program`, `application/java-archive`, `application/octet-stream` with `.exe`/`.js` extension, etc. The per-field `maxFileSizeMb` and `allowedMimeTypes` configured by the form owner are not available to or checked by the route. Impact is limited because download links are `attachment` with a vetted pinned type for previews (see S06-16), and there is no antivirus scanning.
- **Exploit scenario:** A respondent bypasses a "PDF only, max 2 MB" field by calling `/upload` directly with a 50 MB executable; the form owner's staff later download it (individually or via the ZIP export) and run it. No malware scanning exists.
- **Recommended fix:** Pass the form's field constraints into the server-side check (resolve the field from the live schema; reject on size/MIME mismatch; verify magic bytes). Switch the blocklist to an allow-list defined by the field (default: documents/images). Optionally scan with ClamAV or an R2 worker.

## S06-08 — Excel/CSV and PDF export links are 5-hour bearer URLs that survive access revocation
- **Severity:** Low
- **File:line:** `services/temporaryFileService.ts:32-92` (5 h presign, `uploadTemporaryFile`), callers `graphql/resolvers/unifiedExport.ts:171`, `pdfTemplates.ts:338,466`, `pdfGenerators.ts:299`
- **Description:** `uploadTemporaryFile` returns a presigned GET valid for 5 hours with no way to revoke it. The newer ZIP export deliberately uses 5-minute links re-issued after a fresh access check (`responseFileExportService.ts:262-275`, "revoking someone's access also revokes downloads"). The unified export contains the whole response table (PII, respondent emails, quiz data); anyone who obtains the URL (browser history, proxy/CDN logs, shared screen, chat) can download it for 5 h. Key unguessability is fine: `temp-exports/{ts}-{uuid}-{name}` with a v4 UUID.
- **Exploit scenario:** An editor exports all responses, then is removed from the org; the URL already copied to their personal device still downloads the dataset for up to 5 hours.
- **Recommended fix:** Use the same pattern as the ZIP export: store `fileKey` plus requester in a DB row and mint a 5-minute presigned URL on demand after re-checking form access. Keep the 5 h object TTL only as the cleanup horizon.

## S06-09 — GraphQL `uploadFile` and REST `/upload` implement divergent authorization
- **Severity:** Low
- **File:line:** `graphql/resolvers/fileUpload.ts:106-160,179-182` vs `routes/upload.ts:61-125`
- **Description:** The two entry points to the same service differ: (1) `OrganizationLogo` requires org **owner** on REST (`upload.ts:117-119`) but only membership via GraphQL (`requireOrganizationMembership`, `:156`), so any `member` can write logo objects through GraphQL. (2) `FormResponse` via GraphQL needs only `requireAuth` and no `formId`, so any signed-up user can create private-bucket objects at `files/form-response/<name>` with no `FormFile` row and no cleanup path (S06-06); GraphQL cap is 5 MB x 10 files per request (`index.ts:365`). (3) `uploadFile` is called without `formId` (`:179-182`), so `FormBackground` keys lack the `{formId}` path segment that REST uses. (4) The GraphQL allow-list omits `PdfTemplateAsset` while REST includes it. Security controls evolve in only one place.
- **Exploit scenario:** A low-privilege org member replaces nothing directly (the logo DB field is set elsewhere) but pushes unlimited orphaned private objects and public-logo-prefixed objects at no cost; authorization reviews of one path miss the other.
- **Recommended fix:** Make the REST route (or a shared `authorizeUpload(type, caller, params)` function) the single policy, called from both. Delete the GraphQL upload mutation if the client uses only REST.

## S06-10 — Upload route re-implements "editor" check and diverges from `checkFormAccess`
- **Severity:** Low
- **File:line:** `routes/upload.ts:145-172` vs `services/formSharingService.ts:47-100`
- **Description:** For `FormResponse` the route treats the form creator, any `FormPermission` of `EDITOR`/`OWNER`, or any org `owner` as "authorised editor" and lets them upload to **unpublished** forms. It does not require current organization membership for creators and permission holders (`checkFormAccess` documents "membership first"), so a user removed from the organization keeps the bypass. The route also does not honor `sharingScope = ALL_ORG_MEMBERS` + `defaultPermission = EDITOR`, which `checkFormAccess` does, and the logic costs three sequential DB queries.
- **Exploit scenario:** A former employee (removed from the org but still `createdBy` or holding a `FormPermission` row) can still upload objects into an unpublished form's prefix. Impact is small (uploads only), but it contradicts the membership-first invariant.
- **Recommended fix:** Replace the inline logic with `checkFormAccess(userId, formId, PermissionLevel.EDITOR)` wrapped to return a 403/404 rather than throwing.

## S06-11 — Filename handling: extension is unsanitized and unbounded; original name stored raw
- **Severity:** Low
- **File:line:** `services/fileUploadService.ts:112-128` (only the base name is sanitized; `path.extname(originalName).toLowerCase()` is appended as-is), `routes/upload.ts:201-210` (stores `originalName` verbatim)
- **Description:** The base name is reduced to `[a-z0-9_-]`, but the extension may contain any characters other than `/` and `\0` (spaces, `?`, `#`, `%`, unicode, control characters, any length). Key length is not bounded either (R2 limit 1024 bytes). Path traversal is **not** possible (basename only, `formId` validated against the DB, S3 keys have no traversal semantics). The raw name is stored in `FormFile.originalName` and later reused in the ZIP (sanitized by `zipLayout.ts`) and in `Content-Disposition` (encoded safely by `contentDisposition`), so no injection sink was found, only malformed keys/CDN URLs (a `?` or `#` in the extension breaks the generated CDN URL).
- **Exploit scenario:** A user uploads `a.p?x=1` as an avatar; the object is stored under a key containing `?`, the generated CDN URL resolves to a different key, causing broken assets and confusing support/cleanup (self-inflicted); extremely long names cause a 500.
- **Recommended fix:** Restrict the extension to `^\.[a-z0-9]{1,10}$` (or derive it from detected MIME, see S06-04) and cap `originalName` length (for example 200 chars) before storing.

## S06-12 — Upload route returns internal error text and has an authenticated form-existence oracle (500 instead of 404/403)
- **Severity:** Low
- **File:line:** `routes/upload.ts:78,92,230-233` (calls `checkFormAccess`, which throws `FORM_NOT_FOUND`), `routes/upload.ts:218-235`
- **Description:** For `FormBackground`/`PdfTemplateAsset` the route calls `checkFormAccess`, which throws for a non-existent form; the surrounding `catch` returns `500 "Failed to upload file: Form not found"`, versus `403` for an existing form without access, so an authenticated user can enumerate valid form IDs (cuid, low value). The generic handler also echoes `error.message` of any failure, including AWS SDK/R2 errors (bucket names, endpoints, request ids).
- **Exploit scenario:** An authenticated user probes IDs and reads S3 client error text when R2 is misconfigured or rate-limited, learning bucket and endpoint names.
- **Recommended fix:** Catch `FORM_NOT_FOUND` and respond with a uniform 403; return a generic `UPLOAD_FAILED` message and log details server side (Sentry).

## S06-13 — `PdfTemplateAsset` accepts any bytes declared as `application/pdf`
- **Severity:** Low (PLAUSIBLE)
- **File:line:** `services/fileUploadService.ts:220-225,262-267`
- **Description:** The base-PDF upload requires only a declared `Content-Type: application/pdf` and at most 10 MB; no `%PDF-` header check. The object is later read with `downloadFileBuffer` and parsed server-side by the pdfme/pdf-lib stack at generation time (`pdfTemplateService.ts:402-410`). Hostile or malformed input reaches the parser inside the API process. Whether this yields a practical DoS depends on the parser (PLAUSIBLE); detailed analysis belongs to S10.
- **Exploit scenario:** An EDITOR uploads a crafted PDF (huge xref/object counts) that makes each "generate PDF" call hang or consume memory, degrading the API for others.
- **Recommended fix:** Verify the `%PDF-` magic and optionally parse with a size/time-bounded pre-flight at upload; run generation with timeouts and in a worker.

## S06-14 — Unauthenticated mock temp-file route and env-driven storage switch
- **Severity:** Info
- **File:line:** `index.ts:247-256`, `services/temporaryFileService.ts:40-52,106-108,153-156`
- **Description:** `GET /api/temp-files-mock/*` is registered unconditionally with no authentication and serves from an in-process map; it writes `Content-Disposition: attachment; filename="${file.filename}"` unescaped. Mock mode is selected at runtime when `PUBLIC_S3_ENDPOINT`/`s3Config.endpoint` contains `localhost:9000`, outside `VITEST`. In a correctly configured production the map is always empty, so the route is inert. If that environment variable were ever misconfigured in a deployed environment, exports would be held in memory and served without presigning (the keys contain a UUID, so unguessable, but unauthenticated and unrevocable).
- **Recommended fix:** Register the route only when `NODE_ENV !== 'production'`; make the mock switch an explicit `USE_MOCK_S3` flag that is rejected in production; encode the filename with `contentDisposition()`.

## S06-15 — One S3 credential for both buckets; `copyFileForForm` trusts the source key
- **Severity:** Info
- **File:line:** `lib/env.ts:50-57`, `services/fileUploadService.ts:36-44,486-526`, `graphql/resolvers/forms.ts:424`, `services/formService.ts:224,238`
- **Description:** `fileUploadService` and `temporaryFileService` both use `PUBLIC_S3_ACCESS_KEY/SECRET_KEY` for the public and private buckets, so a single leaked credential grants read/write to the private respondent-file bucket. `ACL: 'public-read'` is sent on public uploads but R2 ignores ACLs (public access is bucket/domain configuration), which gives a false sense of access control in code. `copyFileForForm` copies `layout.backgroundImageKey` / `backgroundVideoKey` from the form schema (editor-controlled) with `CopySource` from the public bucket without a prefix check; only already-public objects can be copied, so no confidentiality impact.
- **Recommended fix:** Use separate R2 API tokens scoped per bucket (private token with no public-bucket write and vice versa; no `ListBucket` on the public token). Validate the source key prefix (`files/form-background/` or `files/form-template/`) in `copyFileForForm`. Remove the ineffective ACL parameter.

## S06-16 — Positive controls verified
- **Severity:** Info
- **Description:** Verified by tracing; no action needed.
  - Type allow-list is enforced on both entry points; the `type` query/body value cannot inject path segments (`ALLOWED_UPLOAD_TYPES`, `upload.ts:16-23,53-58`); an array-valued `type` is rejected by `Set.has`.
  - Per-type authorization on REST: `FormTemplate` admin/superAdmin only; `FormBackground`/`PdfTemplateAsset` EDITOR via `checkFormAccess` (org membership first); `UserAvatar` any authenticated user; `OrganizationLogo` org owner.
  - Key generation uses `timestamp-uuid-sanitizedBase`; `formId` placed in the key is always a DB-validated id; no traversal. Unknown types default to the private bucket (`getBucketForType`); `getBucketForKey` routes `files/form-response/`, `files/pdf-template-asset/` and `pdf-generated/` to the private bucket.
  - Public bucket never receives respondent files; `FormResponse` and `PdfTemplateAsset` return no CDN URL.
  - `getResponseFileDownloadUrl` constrains keys with a strict regex, checks VIEWER on the form encoded in the key, and `createResponseFileDownloadUrl` additionally requires the key to be referenced by a live response of the same form (`isFileKeyReferencedRaw`), 300 s expiry, `attachment` with the original name; inline preview only for `image/png|jpeg|gif|webp` and `application/pdf` with `ResponseContentType` pinned, so a mislabelled HTML/SVG cannot render. Cross-form key reuse is blocked by `isResponseFileKeyForForm` (also in field analytics).
  - `contentDisposition()` strips non-printable ASCII, quotes and backslashes and RFC 5987-encodes `filename*`, so header injection is not possible; export filenames are additionally sanitized (`generateExcelFilename`, `buildPdfFilename`).
  - `deleteFile` for form-associated keys requires EDITOR on the owning form; `pdfTemplates` `createPdfTemplate` requires `fileKey` to start with `files/pdf-template-asset/{formId}/`.
  - ZIP export (`zipLayout.ts`): segments sanitized (no separators, `..`, control chars, reserved names), uniqueness handling, formula-prefix guard in the manifest CSV, streamed (not buffered) to R2, 300 s links re-authorized on every download and bound to the requesting user (`getResponseFileExport` checks `requestedById`), and an audit record.
  - Temp export keys are unguessable (`temp-exports/{ts}-{uuid}-...`) in the private bucket; the 30-minute sweep deletes by key timestamp older than 5 h and presigned expiry also caps access at 5 h. Session cookie is SameSite=lax, which limits cross-site POSTs to `/upload` (S01-07 for caveats).
