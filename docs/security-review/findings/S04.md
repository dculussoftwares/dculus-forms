# S04 — Public form submission surface (unauthenticated)

Scope reviewed: public GraphQL operations used by `apps/form-viewer` (`formByShortUrl` + its `Form` field resolvers, `submitResponse`, `trackFormView`, `trackFormSubmission`, `updateFormStartTime`, `saveResponseDraft`, `editMyResponse`), `lib/respondentAccess.ts`, `lib/timeWindowEnforcement.ts`, `lib/responsePayloadLimits.ts`, `lib/conditionalStrip.ts`, `lib/formSchemaCache.ts`, `lib/embedAttribution.ts`, `middleware/edge-geolocation.ts`. All paths are under `apps/backend/src/`. Review-only; no source changed. No secrets are included.

Summary: 2 High, 5 Medium, 4 Low, 3 Info. Items marked PLAUSIBLE depend on deployment behaviour that cannot be confirmed from code alone.

---

## S04-01 — Builder-only `Form.formSchema` (incl. quiz answer keys) readable anonymously, bypassing the access-control gate
- **Severity:** High
- **File:line:** `graphql/resolvers/forms.ts:140` (`Form.formSchema`), exposed via `graphql/resolvers/forms.ts:96` (`formByShortUrl`), `graphql/schema.ts:227`
- **Description:** `formSchemaPublic` (forms.ts:166) is carefully gated: it returns `null` unless `accessStatus === 'OPEN'` and strips each field's `grading` (quiz answer key). But the sibling field `Form.formSchema` is a plain resolver with no auth, no access-status check and no `grading` stripping. The code comment calls it the "builder-only counterpart", yet it is selectable on the public `Form` type returned by the unauthenticated `formByShortUrl` query. `formByShortUrl` deliberately returns the Form (not an error) for sign-in-gated and domain-restricted forms so the viewer can render a gate, so the gate is bypassable by selecting the other field.
- **Exploit scenario:** An anonymous attacker who knows a form's short URL runs `query { formByShortUrl(shortUrl:"X") { formSchema } }`. For a quiz form they receive every question's `acceptedAnswers` / point values and answer all questions correctly. For a form restricted to a company email domain or requiring sign-in, they read the full form structure (field labels, options, hidden/conditional fields, thank-you content, internal notes in rich-text) without authenticating, defeating the purpose of `accessStatus` gating.
- **Recommended fix:** Make `Form.formSchema` require `requireAuth` + `checkFormAccess(VIEWER)` (return null otherwise), or remove it from the public type and add a separate builder-only query. Add a regression test that an unauthenticated `formByShortUrl { formSchema }` returns null/denied. Prefer a field-level authorization layer (graphql-shield style or a shared helper) so new `Form` fields default to deny.

## S04-02 — Public `Form` exposes organization billing identifiers, creator email, and the full sharing list
- **Severity:** High
- **File:line:** `graphql/resolvers/subscriptions.ts:286` (`Organization.subscription`), `repositories/formRepository.ts:5-8` (`defaultFormInclude` selects `createdBy.email`), `graphql/resolvers/formSharing.ts:100` (`Form.permissions`), `graphql/schema.ts:40-66, 219-256`
- **Description:** `formByShortUrl` returns a `Form` row whose relation fields are resolved by resolvers/default property access with no auth:
  1. `organization { subscription { chargebeeCustomerId chargebeeSubscriptionId planId status viewsUsed submissionsUsed viewsLimit ... } }` — `Organization.subscription` has no auth check and `PlanSubscription` carries Chargebee customer/subscription IDs and exact usage counters.
  2. `createdBy { email name image organizations { id name slug } }` — the creator's email address is included by `defaultFormInclude`; `User.organizations` resolves all of the creator's orgs.
  3. `permissions { user { email name } grantedBy { email } permission }` — `Form.permissions` calls `listFormPermissions(parent.id)` with no check, and the repository includes full `user` and `grantedBy` rows. This lists every person the form is shared with.
- **Exploit scenario:** Anyone with a public form link harvests the form owner's and collaborators' email addresses (phishing/spam target list, PII disclosure), learns the org's Chargebee customer ID and plan/usage (useful for social engineering the billing provider and for timing view/submission-limit exhaustion attacks, see S04-05), and learns the org structure of the creator.
- **Recommended fix:** Add field-level guards: `Form.permissions`, `Form.createdBy`, `Form.organization.subscription`, `Form.dashboardStats`, `Form.responseCount`, `Form.metadata` should require authenticated form access (VIEWER+). For the public viewer, return a dedicated minimal public type (title, description, shortUrl, public settings, org name/logo only). Do not select `email` in `defaultFormInclude` for the public path. Mask `chargebee*` IDs from every non-admin response.

## S04-03 — `submitResponse` payload limits are skipped for non-object `data` (string / array / number) and nested values are only bounded by total size
- **Severity:** Medium
- **File:line:** `lib/responsePayloadLimits.ts:18` (early return), `graphql/resolvers/responses.ts:377`, schema `data: JSON!` at `graphql/schema.ts:634`
- **Description:** `assertResponsePayloadWithinLimits` returns immediately when `typeof data !== 'object'`. `submitResponse` does not otherwise require `data` to be a plain object (compare `editMyResponse`, `myResponseService.ts:100`, which rejects non-objects and arrays). A JSON scalar string up to the 10 MB `express.json` limit (`index.ts:231`) passes, bypassing the 10,000-char per-string cap and the 6 MB aggregate cap. Arrays are measured with `Object.entries` (index keys) so a large array of short items is bounded only by the 6 MB total. Nesting depth is never bounded (GraphQL depth limit applies to the query, not to the `JSON` variable value).
- **Exploit scenario:** An anonymous caller submits `data` as a 9 MB string or a deeply nested array/object. It is persisted as the response's JSON. Downstream code that assumes an object (response table, filters, exports, quiz grading, PDF generation, webhook/automation payloads built with `...input.data`, `emitFormSubmitted`) misbehaves: a single poisoned row can break the owner's responses list or export (stored DoS), and storage is inflated (up to 10 MB/row, 6 MB for objects).
- **Recommended fix:** In `submitResponse`, reject unless `data` is a plain object (`!Array.isArray`). Put the same check inside `assertResponsePayloadWithinLimits` (throw instead of return). Bound nesting depth and the number of keys and key length. Validate values per field type (see S04-04). Lower the aggregate cap to what real forms need.

## S04-04 — No server-side validation of answers against the form schema (required, type, options, email, min/max, file refs); unknown keys stored verbatim
- **Severity:** Medium
- **File:line:** `graphql/resolvers/responses.ts:330-470` (submit path), `lib/conditionalStrip.ts:34-37` (unknown keys pass through)
- **Description:** The only server-side semantic processing of `input.data` is conditional-logic stripping. There is no check that required fields are present, that values match the field type, that select/radio/checkbox values are among the defined options, that email/number/date constraints or `minLength/maxLength/min/max/minSelections` hold, or that keys correspond to real fields. `stripConditionallyHiddenValues` explicitly passes keys unknown to the schema through untouched, and fails open on any exception (`conditionalStrip.ts:68`). Server and client validation are therefore decoupled: anything the viewer enforces is advisory.
- **Exploit scenario:** An anonymous attacker submits directly via GraphQL with missing required answers, out-of-range numbers, invalid option values, arbitrary extra keys (up to 500, each up to 10k chars), or values for deleted fields. Consequences: polluted data, bypassed quiz/option integrity (e.g. a "pick one" with an arbitrary value), stored content that exports render as spreadsheet formulas (CSV/Excel injection against the owner who opens the export; see S11), and attacker-controlled key names that flow into webhook/automation payloads (`...input.data` spread at `responses.ts:645`, S07/S08).
- **Recommended fix:** Add a server-side validator driven by the deserialized live schema (required, type, options, length/range, email format, selection counts, file key prefix `files/form-response/{formId}/`), reject unknown keys, and apply it to `submitResponse`, `saveResponseDraft` (relaxed) and `editMyResponse`. Fail closed if the schema cannot be loaded or if conditional stripping throws.

## S04-05 — Usage counters (views/submissions) used for billing/blocking are trivially inflatable by anonymous callers, enabling DoS of a victim's form
- **Severity:** Medium (High for free-plan orgs; mitigated by nothing in code)
- **File:line:** `graphql/resolvers/analytics.ts:38-95` (`trackFormView` → `emitFormViewed`), `subscriptions/usageService.ts:80-110` (unconditional `viewsUsed +1`), `graphql/resolvers/forms.ts:101-104` (`VIEW_LIMIT_EXCEEDED`), `graphql/resolvers/responses.ts:371-374, 658` (`SUBMISSION_LIMIT_EXCEEDED`)
- **Description:** `trackFormView` is public, only validates `sessionId` with a regex (any 8-128 char string) and a non-empty userAgent, and every call increments the org's `viewsUsed`. There is no per-session de-duplication, no per-IP throttle (see S04-06) and no verification that a real `formByShortUrl` view happened. The `formId` needed is returned by the public `formByShortUrl`. Likewise `submitResponse` is anonymous on open forms and every success increments `submissionsUsed` (preview submissions too, `responses.ts:658` is not gated by `isPreview`). Free plan limits are 10,000 views / 1,000 submissions, and exceeding them makes `formByShortUrl` / `submitResponse` throw for everyone. GraphQL aliasing lets one HTTP request carry many mutations (no alias/complexity limit; `graphql-depth-limit` only bounds depth), so the HTTP rate limiter is not a barrier.
- **Exploit scenario:** A competitor sends a few hundred aliased `trackFormView` mutations with random session IDs against a victim's form ID. The org's `viewsUsed` hits its limit within minutes and the form shows "view limit exceeded" to all respondents until the period resets. The same works for submissions (1,000 junk anonymous submissions), also filling the response table with spam and consuming email-copy / automation / webhook quota.
- **Recommended fix:** Count views server-side from `formByShortUrl` (or de-duplicate on a signed, server-issued session token) rather than a client-called mutation; de-duplicate by (formId, sessionId) with a unique constraint; add per-IP + per-form rate limits and a CAPTCHA/proof-of-work option for anonymous submissions; cap aliases/operations per request; do not count builder preview submissions toward `submissionsUsed`.

## S04-06 — No effective anonymous rate limiting: shared proxy-IP bucket, no per-form limits, no CAPTCHA/spam control, alias amplification
- **Severity:** Medium (PLAUSIBLE for the shared-bucket aspect, depends on the Azure Container Apps/Cloudflare path)
- **File:line:** `index.ts:155-162, 362` (`graphqlLimiter`, 5000 req/min), no `trust proxy` setting anywhere in `apps/backend/src`, `index.ts:287` (only `depthLimit(8)`), `infrastructure/multi-cloud/terraform/azure/main.tf:378` (external ingress)
- **Description:** (a) The only limiter on `/graphql` is `express-rate-limit` keyed on `req.ip` with 5000 requests/min. `app.set('trust proxy', ...)` is never called, so behind the Azure ingress / Cloudflare `req.ip` is very likely the proxy's address and all visitors share one bucket: one attacker can exhaust it and 429 every legitimate respondent (and, for the auth limiter on its own bucket, sign-in), while a rotating attacker is never individually limited. (b) 5000/min is far above human use anyway and there are no per-form, per-session or per-respondent limits and no bot challenge on submission. (c) No cap on aliases/operations per request and no query-cost limit, so one request can execute hundreds of `submitResponse`/`trackFormView` mutations. (d) Each `submitResponse` for a conditional form triggers a DB read plus a full Y.js document rebuild (`getFormSchemaFromHocuspocus`, noted in the resolver's own comment at responses.ts:384-388), a cost amplifier.
- **Exploit scenario:** Scripted spam of any public form at thousands of submissions per minute, each with up to ~6 MB of data (S04-03), exhausting DB storage, Y.js rebuild CPU and the connection pool (production pool max is 2, `usageService.ts`), or denying the shared bucket to all users.
- **Recommended fix:** Configure `trust proxy` for the exact hop count (or key on `CF-Connecting-IP` only when the request provably comes from Cloudflare), add per-IP and per-(IP, form) limits specifically for `submitResponse`/`trackFormView`, use a store shared across replicas, add an alias/operation-count limit and cost analysis plugin, add optional CAPTCHA (Turnstile) per form, and reject oversize bodies earlier for the public route (the 10 MB global JSON limit is generous for this endpoint).

## S04-07 — Response-copy email recipient is unvalidated attacker input (open mail relay of owner-branded email, possible multi-recipient)
- **Severity:** Medium (multi-recipient aspect PLAUSIBLE, depends on mail transport address parsing)
- **File:line:** `services/responseCopyService.ts:85, 130-134` (called from `graphql/resolvers/responses.ts:668-676`)
- **Description:** When a form enables `responseCopy`, the recipient is `response.data[emailFieldId]` taken as-is (only `typeof === 'string'` and non-empty), with no email format validation, no restriction to one address, and no check that the address belongs to the submitter. The email is sent from the platform's SMTP identity with the owner-controlled subject, the form title and (optionally) a PDF of the answers. Combined with no server-side validation (S04-04) and no rate limit (S04-06), the consent flag is just a client-supplied boolean. The plugin schema check also uses `form.formSchema` from the DB column, which may lag the live Y.js schema.
- **Exploit scenario:** An attacker submits a form in "always" mode with a victim's address (or a comma-separated list of addresses if the SMTP library splits them) in the email field. The platform sends the victim branded mail with attacker-influenced content (other answer fields are rendered in the Q&A table), consuming the org's email quota and damaging sender reputation. At scale it is a harassment/spam amplifier.
- **Recommended fix:** Validate the recipient with a strict single-address parser, reject separators/CR/LF, require the form's email field validation server-side, and add per-form and per-recipient send throttling. Consider requiring verified ownership (sign-in or confirmation link) before sending PDFs of answers.

## S04-08 — `trackFormSubmission` / `updateFormStartTime` / analytics inputs are attacker-controlled and unauthenticated
- **Severity:** Low
- **File:line:** `graphql/resolvers/analytics.ts:102-135, 139-195`, `services/analyticsService.ts:345-385`
- **Description:** `trackFormSubmission` verifies the response exists and belongs to the form but not that the caller submitted it, and it is not idempotent (any number of rows per `responseId`). `completionTimeSeconds` (Int) has no bounds (negative/huge values accepted) and feeds average/percentile dashboards. `updateFormStartTime` only needs a valid sessionId format and a published form. `sessionId` is fully client chosen, so unique-session/visitor metrics are forgeable. `timezone`/`language` are used as geolocation fallbacks (`analyticsService.ts:262-285`) so the geographic charts can be steered. Embed fields are well sanitised (`embedAttribution.ts`), the one area handled correctly.
- **Exploit scenario:** An attacker with a form ID skews the owner's analytics (fake countries, fake completion times, fake devices) or pollutes the table with junk rows.
- **Recommended fix:** Treat analytics as untrusted: clamp `completionTimeSeconds` to a sane range, make submission analytics idempotent (unique on `responseId`), bind to the submitting session (server-issued token), cap per-form analytics write rate, and cap string lengths for `timezone`/`language`.

## S04-09 — Client IP and Cloudflare geo headers are trusted without origin verification
- **Severity:** Low (PLAUSIBLE, depends on whether the Azure origin is reachable directly)
- **File:line:** `middleware/edge-geolocation.ts:36-56`, `graphql/resolvers/analytics.ts:43-47, 144-148`, `graphql/resolvers/responses.ts:564-571, 598 area`, `infrastructure/multi-cloud/terraform/azure/main.tf:378`
- **Description:** `edgeGeolocationMiddleware` copies any `cf-ipcity`, `cf-ipcountry`, `cf-iplatitude`, etc. header from the request into `req.visitorGeo` unconditionally. These are only trustworthy if the origin accepts traffic exclusively from Cloudflare; the Terraform shows a public external Container App ingress with no IP/header restriction visible in the files reviewed. The fallback client IP is `req.ip || remoteAddress || x-forwarded-for[0]`, where the last term is directly spoofable, and with no `trust proxy` configured `req.ip` is not the real visitor. `editMyResponse` also records `req.ip` as the edit IP (`myResponse.ts:29`).
- **Exploit scenario:** An attacker hitting the origin FQDN directly sets arbitrary `cf-*` headers (or `X-Forwarded-For`) to forge geolocation in analytics and the IP stored in response edit history, evading attribution/forensics.
- **Recommended fix:** Restrict origin ingress to Cloudflare (IP allowlist or authenticated origin pulls / shared secret header) and only honour `cf-*` headers when that proof is present; set `trust proxy` explicitly; drop `x-forwarded-for` parsing in favour of the validated `req.ip`.

## S04-10 — Public file-upload endpoint ignores the form's access control, time window and response caps
- **Severity:** Medium (cross-reference to S06, which owns the route)
- **File:line:** `routes/upload.ts:126-172`
- **Description:** For `type=FormResponse` the only gate for anonymous callers is `form.isPublished`. Sign-in requirement, email-domain allowlist, `submissionLimits.timeWindow`, `maxResponses`, and subscription submission limits that `submitResponse` enforces are not applied to uploads. (The later key-prefix check in `responseFileCatalog.ts:isResponseFileKeyForForm` correctly stops cross-form key reuse.)
- **Exploit scenario:** An anonymous attacker uploads up to 50 MB files repeatedly to any published form, even one that is closed, sign-in-only or at its response cap, consuming R2 storage/egress at the owner's expense. Abandoned uploads are never tied to a response.
- **Recommended fix:** Apply the same `resolveAccessStatus` / time-window / usage checks as `submitResponse` before accepting uploads, add per-IP/per-form upload quotas, and reap orphaned uploads. Detailed upload review belongs to S06.

## S04-11 — `Form.settings` over-exposes owner configuration to anonymous visitors
- **Severity:** Low
- **File:line:** `graphql/resolvers/forms.ts:225-231`, `graphql/schema.ts:164-176`
- **Description:** `Form.settings` returns the full settings object to any caller of `formByShortUrl`, including `accessControl.allowedDomains` (the organisation's internal email domains), `responseCopy` (field IDs, PDF template ID, subject), `submissionLimits.maxResponses.limit`, quiz thresholds/release schedule, and embed config, regardless of `accessStatus`. For sign-in-gated forms the settings leak even though the schema is withheld.
- **Exploit scenario:** Recon: an attacker enumerates which email domains are accepted (to register an account that passes the allowlist, e.g. a lookalike/free-mail domain if one is listed), and learns internal identifiers (PDF template IDs) to target elsewhere.
- **Recommended fix:** Expose a dedicated `publicSettings` type containing only what the viewer needs; omit `allowedDomains` (the server can state whether the viewer is allowed) and internal IDs.

## S04-12 — Time-window parsing for legacy date-only values uses server-local time and the quiz/limit checks are not atomic with insert on the non-limit path
- **Severity:** Low
- **File:line:** `lib/timeWindowEnforcement.ts:7-13`, `graphql/resolvers/responses.ts:371-374, 436-466`
- **Description:** `YYYY-MM-DD` boundaries are built with `new Date(value + 'T00:00:00')`, i.e. the server's local timezone, so the open/close instant depends on deployment TZ and differs from what the owner and respondent expect. The time window is checked once before insert; a submission that starts before the end and completes after is accepted (acceptable) but the subscription submission limit (`checkUsageExceeded`) is a check-then-act against a counter incremented asynchronously via an event emitter after the response is saved (`responses.ts:658`), so a burst can exceed `submissionsLimit` significantly before the counter updates.
- **Exploit scenario:** Respondents accepted a few hours outside a date-only window; a burst of concurrent anonymous submissions overshoots the plan's submission limit (revenue leakage for the platform, not a data exposure).
- **Recommended fix:** Store/parse boundaries as UTC instants (migrate legacy values with an explicit timezone), and increment/check the subscription counter atomically in the same transaction as the insert for hard limits.

## S04-13 — `formSchemaCache.ts` is not on the public path (no cache poisoning of access settings found)
- **Severity:** Info
- **File:line:** `lib/formSchemaCache.ts:1-53`
- **Description:** The cache is keyed by `formId` with a 10 s TTL and is only used by the AI editor (`aiChat`), not by `formByShortUrl` / `submitResponse`; both of those read the live Y.js document or DB each time, so stale `accessControl`/`submissionLimits` from this cache cannot loosen public access. `settings` always comes from the DB row. Noted as a positive; keep it out of public paths. (Cache is unbounded and per-process, a minor memory growth note only for authenticated AI use.)
- **Recommended fix:** None required. Add an invalidation call on settings/schema writes if the cache is ever reused for public reads.

## S04-14 — Positive controls verified
- **Severity:** Info
- **File:line:** `graphql/resolvers/responses.ts:337-367`, `lib/respondentAccess.ts:63-92`, `lib/embedAttribution.ts`
- **Description:** Verified correct server-side enforcement: `isPreview` requires authentication and EDITOR permission before bypassing publish/access checks; `submitResponse` re-enforces publish state, sign-in and domain allowlist (`enforceAccessControlForSubmission`) independent of the viewer; respondent identity is only recorded when the form requires it and is taken from the session, never from client input; `requireSignedInRespondent` mirrors the submit gates for drafts and my-response (publish, sign-in, domain, time window); `maxResponses` and one-per-respondent are enforced atomically under Serializable isolation with retry; `emitFormSubmitted` spreads `input.data` first so attacker keys cannot override `responseId`/`isPreview`/quiz fields; `formSchemaPublic` strips `grading` and soft-deleted fields; embed context/host are strictly sanitised to a hostname/enum; `formByShortUrl` and `submitResponse` use `deletedAt: null` lookups; short URLs are 8 chars of 62 symbols from nanoid (non-enumerable in practice).

## S04-15 — Conditional-logic stripping fails open on error and does not cover required/forced fields
- **Severity:** Info
- **File:line:** `lib/conditionalStrip.ts:68-72`
- **Description:** On any exception the payload is returned unstripped (by design, "never take submission down"). Hidden-field values can then be stored. Because there is no server-side required-field check (S04-04), "forced" visible fields are also not enforced. Low practical impact on its own.
- **Recommended fix:** Log and alert on the catch path; if validation (S04-04) is added, fail closed for form schemas that deserialize but cannot be evaluated.
