## Findings

### S22-01 — Medium — PLAUSIBLE — Production database topology and admin account name published in a public repo
- **File:line:** `PGBOUNCER-MIGRATION.md:5,14,45,53,73-76,98,100`
- **Description:** The doc publishes the shared PostgreSQL flexible server host (`dculus-shared-postgres.postgres.database.azure.com`), the PgBouncer ACI FQDN (`dculus-pgbouncer.<...>.centralindia.azurecontainer.io:5432`), the admin role name (`dculus_admin`), the names of four databases (including `dculus_forms_prod_db` and the unrelated `indiastats_cms_db`, `dculus_home_site_db`), and DSNs with `sslmode=disable` (`:73-76`, `:100`). It also says the password contains a `+` (`:64`), a tiny hint about character set. The password itself is a placeholder (verified). The banner at the top says PgBouncer was disconnected in September 2026, but the host, role and DB names stay valid for the shared server. If the Postgres server or the ACI still accept connections from the internet, this is a ready-made target list.
- **Exploit scenario:** An unauthenticated attacker reads the public repo, then credential-stuffs or brute-forces `dculus_admin` on the named host/port, aimed at the shared server holding the production forms DB and other products' DBs. The doc also tells readers that traffic was configured with `sslmode=disable`, so a network position (or a leaked DSN used from a client) yields plaintext sessions. Impact depends on server firewall rules (S21), which I did not verify.
- **Recommended fix:** Remove hostnames, role name, DB names and DSN templates from the public repo (move to a private runbook or use `<host>` placeholders). Verify the Postgres firewall and the ACI no longer accept public connections, delete the PgBouncer ACI, and enforce `sslmode=require`. Consider rotating the `dculus_admin` password and moving apps to per-app least-privilege roles.

### S22-02 — Medium — PLAUSIBLE — AWS SES access key ID in `GITHUB_SECRETS_SETUP.md`, in tree and history
- **File:line:** `docs/deployment/GITHUB_SECRETS_SETUP.md:68`. History: added in `0fa56e9f` (2025-11-12) as `GITHUB_SECRETS_SETUP.md` (root, since removed), and re-added under `docs/deployment/` in `c0b3dfd3` (2025-11-21).
- **Description:** The "Example Value" for `EMAIL_USER` is a 20-character string with the AWS access key ID format, starting `AKIA` (full value redacted here). All other rows use obvious placeholders (`your-ses-smtp-password`), so this one looks like a real key ID pasted into the example column, or at least a realistic one. An access key ID alone is not enough to authenticate, but it identifies the AWS account/IAM user and pairs with the secret in `EMAIL_PASSWORD` (not committed). Not found anywhere else in the tree or history (`-G'AKIA[0-9A-Z]{16}'` hits only the two commits above plus local agent checkpoint refs that contain the same text).
- **Exploit scenario:** If this is a real SES SMTP/IAM key ID, an attacker who obtains or guesses the secret (for example from another leak) already knows the paired ID. Scanners also flag it, causing alert noise and possible AWS abuse notices; GitHub secret scanning may auto-notify AWS. Low direct risk until the secret leaks.
- **Recommended fix:** Replace with an obviously fake value (`AKIAXXXXXXXXXXXXXXXX`). Confirm in IAM whether the ID is live; if it is, rotate the key and check CloudTrail for use. History rewrite is optional once the key is dead.

### S22-03 — Medium — PLAUSIBLE — Shared E2E login uses a public mailinator inbox and its password equals its email
- **File:line:** `package.json:59,61-63` (fallbacks `E2E_EMAIL=${E2E_EMAIL:-<name>@mailinator.com}` and `E2E_PASSWORD=${E2E_PASSWORD:-<same string>}`); repeated in `.github/instructions/testing.instructions.md:47-48`.
- **Description:** CLAUDE.md declares this a deliberately public disposable local account, and by default the other `E2E_*_URL` variables resolve to `localhost` (`package.json:59`), so default use is local. The risks are that: (a) the password is the email address, so anyone who knows the address knows the password; (b) mailinator inboxes are public and readable by anyone, so any email-verification, OTP, or password-reset message for that address can be read by a third party; (c) nothing in the script prevents `E2E_FORM_APP_URL`/`E2E_BACKEND_URL` being overridden to a hosted environment while leaving the credentials at their defaults, and `.github/instructions/testing.instructions.md` calls them "Test Credentials" without a local-only warning. The hosted CI path correctly uses secrets (`multi-cloud-deployment.yml:1537-1557`, `E2E_INTEGRATION_TEST_PASSWORD`).
- **Exploit scenario:** If a developer ever created this user on a hosted environment (dev/staging) to run the same E2E, an anonymous attacker signs in with the repo-published credentials, or uses the public inbox to complete reset/OTP, and gets that account's org, forms and responses. Also, if the user does not exist yet on a hosted env, an attacker registers it first and verifies via the public inbox, then observes whatever the team's tests create. Either path is limited to the data in that account.
- **Recommended fix:** Add a guard in `test/e2e/steps/helpers/common.ts` (or the npm script) that refuses default credentials when the target URL is not `localhost`/`127.0.0.1`. Rotate to a CI-generated password for any hosted copy of the user and delete the account in hosted environments. Add a "local only" warning in `.github/instructions/testing.instructions.md`.

### S22-04 — Medium — PLAUSIBLE — Production-targeting test scripts and a documented weak superAdmin credential
- **File:line:** `package.json:52,55,56` (`test:integration:production`, `:auth:production`, `:health:production` with hard-coded production backend host); `test-production-backend.sh:7`; `test/integration/utils/test-data.ts:134-135,178-179`; `apps/admin-app/README.md:53-56,159-160`; `.github/copilot-instructions.md:301`; `test-users-management.sh:73`.
- **Description:** Three separate things combine. (1) `test:integration:production` runs the entire Cucumber suite (sign-ups, org creation, form lifecycle, admin features) against the live production backend and the host is hard-coded in `package.json`. (2) The repo documents and defines a "default" superAdmin account, `admin@dculus.com` with a weak, guessable password (`admin123...`), in the admin-app README, copilot instructions, a root shell script and `test-data.ts`. No code in the repo seeds it (`setup-admin.ts` requires `ADMIN_EMAIL`/`ADMIN_PASSWORD` from env), and `getDefaultSuperAdminCredentials` / `DEFAULT_ADMIN_PASSWORD` are defined but unused, so whether a real environment ever used it is unknown. (3) `test-production-backend.sh:7` prints the production URL and then runs `pnpm test:integration:health` and `:auth`, which do not set `TEST_BASE_URL` and therefore actually run against localhost; the script's banner is misleading about what was tested.
- **Exploit scenario:** If any hosted environment was bootstrapped with the documented credentials (someone following the README), an attacker reading the public repo tries the published email and password on the admin-app and obtains superAdmin (plan assignment, org data, user list). Separately, running the production script pollutes prod with test users/orgs and, with real CI secrets, could mint admin sessions on prod.
- **Recommended fix:** Remove the documented default password from the README, `copilot-instructions.md`, `test-users-management.sh` and `test-data.ts`; tell readers to set `ADMIN_PASSWORD` to a strong value. Confirm no hosted superAdmin uses the documented credential, and rotate if it does. Replace the `*:production` scripts with a read-only smoke check (`/health`) or remove them; fix the misleading banner in `test-production-backend.sh`.

### S22-05 — Low — Secret scanner in CI is non-blocking and skips verification; no local secret hook
- **File:line:** `.github/workflows/build.yml:49-57` (TruffleHog step: `--no-verification`, `continue-on-error: true`, `--exclude-paths=...,.env.example`); `lefthook.yml:1-5` (pre-commit runs only `lint-staged`).
- **Description:** A secret scanner exists, but a finding never fails the build because of `continue-on-error: true`. The `base:`/`head:` arguments scan only the pushed range, not full history, and `--no-verification` reports unverified matches too, which pushes toward ignoring noisy output. There is no pre-commit scanner, which matters because CLAUDE.md states this is a public repo. Since the repo is public, any pushed secret is exposed immediately and must be rotated regardless of later removal.
- **Exploit scenario:** A contributor commits a real key; CI "passes" with a warning nobody reads; bots harvest the key from the public repo within minutes.
- **Recommended fix:** Remove `continue-on-error` (or gate the deploy jobs on the result), run verified-only mode in PR gating plus a periodic full-history scan, add a gitleaks/trufflehog pre-commit hook in `lefthook.yml`, and enable GitHub secret scanning with push protection on the repository.

### S22-06 — Low — PLAUSIBLE — Terraform provider directory and binary committed; `.gitignore` lacks coverage for common secret and state files
- **File:line:** `infrastructure/multi-cloud/terraform/neon-postgres/.terraform/providers/registry.terraform.io/kislerdm/neon/0.13.0/darwin_arm64/*` (4 tracked files, including a ~16 MB provider binary, blob `c172b517`, added in `0a6d49f3`); `.gitignore:13-16,152,185`.
- **Description:** `.terraform/` is tracked in one module and is not ignored anywhere. `.gitignore` also has no rule for `*.tfstate`, `*.tfstate.*`, `*.tfplan`, `crash.log`, `.env.production`, `.env.staging`, `.env.development`, `.env.*` (only `.local` variants and `.env.test` are covered), `*.pem`, `*.key`, `*.p12`, `.npmrc`, `*.sql`/`*.dump`. Nothing sensitive of those kinds is currently tracked (verified), so this is preventive. The terraform provider artifact is third-party binary content that belongs in `.terraform.lock.hcl` plus a registry download, and it bloats the repo.
- **Exploit scenario:** A developer running `terraform apply` locally in a module (state may contain DB role passwords, Neon connection strings, R2 keys) and then `git add -A` would commit `terraform.tfstate`, publishing every secret in it. The `.env.production` filename (commonly used for Vite builds) also would not be ignored.
- **Recommended fix:** `git rm -r --cached` the `.terraform` directory and add `**/.terraform/`, `*.tfstate*`, `*.tfplan`, `.env.*` (with `!.env.example`), `*.pem`, `*.key`, `*.p12`, `.npmrc` to `.gitignore`. Keep Terraform state in the remote backend only.

### S22-07 — Low — Historical hard-coded production test password in `package.json` scripts
- **File:line:** History only. `package.json` scripts `test:integration:production`, `:auth:production`, `:health:production` carried `CI_TEST_PASSWORD=<literal>` next to the production backend URL until commit `512da7ce` (2026-05-21, "resolve all P0 launch-blocker vulnerabilities (#13)"); the same literal was also the default in `test/integration/utils/test-data.ts` (`DEFAULT_PASSWORD`). `PRODUCTION_READINESS.md:31` records the removal; the literal begins `Test`. It is still used as a unit-test fixture in `apps/backend/test/signup-organization-id.test.ts:15`. Also present in older e2e files in history (`test/e2e/features/signin.feature`, `.../signup.steps.ts`, 2025-08 to 2025-11).
- **Description:** The password was committed together with a production host, and the removal commit does not remove it from history. Anyone can run `git log -S` and read it.
- **Exploit scenario:** If any real production account or the integration test users created by the production run were created with that password and never rotated, an attacker signs in as them. Accounts created by prior production test runs (`test-user-*` style) are the likeliest candidates.
- **Recommended fix:** Search production for accounts created by the test suite and delete or reset them; confirm no real user uses that password. Treat the value as burned; no history rewrite needed if no live account uses it.

### S22-08 — Low — Infrastructure identifiers (Azure subscription IDs, service principal instructions, container-app hosts) published in docs
- **File:line:** `docs/superpowers/plans/2026-05-30-azure-subscription-migration.md:126,133,197,203,668` (two Azure subscription GUIDs, beginning `dc87` and `0457`); `README.md:177-178`; `.github/agents/deployment-guide.agent.md:37-70`; `.github/copilot-instructions.md:442`; `infrastructure/multi-cloud/terraform/azure/environments/staging/terraform.tfvars` (container app hosts); `package.json:52-56` and `test-production-backend.sh:7` (production backend host).
- **Description:** Subscription IDs, the service-principal role-assignment procedure (Contributor on the subscription, Storage Blob Data Contributor for TF state) and real production/staging container-app FQDNs are public. None are credentials, but they shorten reconnaissance and help phishing and targeted attacks on the Azure tenant and the Terraform state storage account.
- **Exploit scenario:** An attacker targets the Azure AD tenant/SP with password spraying or consent phishing citing real resource names, or probes the named container apps directly (covered by S05/S21).
- **Recommended fix:** Replace GUIDs and hostnames in docs with placeholders; keep the real values in private runbooks. This is hygiene, not an emergency.

### S22-09 — Low — Committed agent config enables broad auto-approved commands and network access
- **File:line:** `.claude/settings.json:3-40` (allow list includes `Bash(rm:*)`, `Bash(curl:*)`, `Bash(git push:*)`, `Bash(git commit:*)`, `Bash(gh:*)`, `WebFetch(domain:*)`, `WebSearch`).
- **Description:** A checked-in project settings file pre-approves destructive and exfiltration-capable commands for every contributor and any agent that opens the repo. In a public repo this is a supply-chain/prompt-injection amplifier: a malicious issue, PR or fetched web page that steers an agent can run `curl` with local `.env` content, `git push`, or `rm`. It is not a secret leak but is repository hygiene relevant to credential theft from developer machines (where `.env` files live).
- **Exploit scenario:** A contributor opens a PR containing a doc or code comment with injected instructions; a maintainer's agent session reads it and, with `curl:*` and `WebFetch(domain:*)` pre-approved, posts `apps/backend/.env` to an attacker host with no prompt.
- **Recommended fix:** Move permissive entries to the personal `.claude/settings.local.json` (already ignored, `.gitignore:196`). Keep only read-only/safe commands in the committed file; remove `rm`, `curl`, `git push`, `gh:*` and wildcard `WebFetch`.

### S22-10 — Info — CI-only literal secrets in workflow files
- **File:line:** `.github/workflows/build.yml:260-261,449-450,458-463`; `test/integration/support/hooks.ts:228` (fallback DSN with dev password for the local docker DB); `apps/backend/test/setup.ts:15`.
- **Description:** Literal DB passwords, `BETTER_AUTH_SECRET` (`e2e-test-secret-at-least-32-chars-long-ok`), stub S3 keys and the CI E2E password are visible in public. They are bound to ephemeral localhost service containers and `NODE_ENV=test`, so there is no direct exposure. The risk is operator error: if the same strings were ever reused for a hosted environment.
- **Exploit scenario:** None directly. If the CI `BETTER_AUTH_SECRET` literal were reused in a hosted environment, session cookies could be forged.
- **Recommended fix:** Optional: generate these per run (`openssl rand -hex 32`) so they cannot be reused by accident; keep the guard that production boot fails when `BETTER_AUTH_SECRET` is a known weak value (S01).

### S22-12 — Info — Local agent refs contain historic baseline snapshots (not pushed)
- **File:line:** `refs/agents/*/checkpoints/turn*` and `refs/codex/turn-diffs/*` (local refs; commits titled "Agent host session ... baseline checkpoint", 2026-10-18).
- **Description:** Local-only refs created by agent tooling contain full working-tree snapshots, including any untracked-but-present files such as local `.env` copies. Pattern scans over `--all` hit only these refs for a few strings that were also in tracked docs. They are not branches and are not pushed by default, but `git push --mirror` or `git push --all`/tag-style pushes of `refs/*` would publish them.
- **Exploit scenario:** A maintainer runs `git push --mirror` (for example while migrating the repo) and publishes snapshots that may include `.env` files.
- **Recommended fix:** Prune the local `refs/agents` and `refs/codex` namespaces (`git update-ref -d`) before any mirror push, and never use `--mirror` against the public remote.
