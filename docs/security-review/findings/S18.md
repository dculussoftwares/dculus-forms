# S18 — admin-app: Security Findings

Scope: `apps/admin-app/src/**` (about 4,600 lines of TS/TSX). Supporting reads: `apps/admin-app/{index.html,vite.config.ts,public/_headers,public/config.js,.env.example}`, and backend `graphql/resolvers/admin.ts` (role gate, billing mutations) to confirm what the UI relies on. Cross-referenced against S01, S02, S05, S06.
Method: static review, tracing code paths. No source modified. No secrets included. Review-only.

## Summary

| Severity | Count |
|----------|-------|
| Critical | 0 |
| High     | 0 |
| Medium   | 1 (PLAUSIBLE) |
| Low      | 4 (1 PLAUSIBLE) |
| Info     | 5 |

The admin-app is a thin client. Every admin operation is a GraphQL call guarded server-side by `requireAdminRole` (S02), so UI gating is cosmetic but not exploitable on its own. The tokens/session are HttpOnly cookies (never in JS), and there is no `dangerouslySetInnerHTML`, no `eval`, no `postMessage`, no redirect-from-input, and no `localStorage` use beyond the locale. The remaining issues are missing browser hardening headers, UI-only privilege tiers, untrusted image URLs, and no step-up auth.

## Verified-correct areas (no finding)

- **XSS sinks:** grep for `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `document.write`, `window.open`, `postMessage`, `document.cookie` returns nothing in `src/`. User-controlled strings (user name, email, org name, template name/description, subscription fields) are rendered only as React text nodes (auto-escaped).
- **Token storage:** no token, bearer or password is stored by the app. `services/auth.ts:34,56,79` and `services/apolloClient.ts:8` use `credentials: 'include'` (cookie auth). The only `localStorage` key is `admin-locale` (`contexts/LocaleContext.tsx:19`). No `Authorization` header, no admin token in `VITE_*` vars (`.env.example` holds only URLs). `public/config.js` is an empty runtime-config shim.
- **Source maps:** `vite.config.ts` does not enable `build.sourcemap` (Vite default is off). `dist/` is gitignored.
- **Open redirect:** no `redirect`/`returnTo`/`next` query param is read anywhere; `Navigate` targets are hard-coded (`App.tsx:80-91`). `window.location.reload()` only (`App.tsx:43`).
- **CSRF:** all state-changing admin actions are GraphQL POSTs with `Content-Type: application/json` (Apollo `createHttpLink`, which forces a CORS preflight), against a server with Apollo `csrfPrevention` on (S05-13), a static credentialed CORS allow-list (S05-11) and `SameSite=Lax` session cookies (S01-07). No state-changing GET exists in the admin client. Sign-out is a POST (`services/auth.ts:77`). No separate CSRF finding; residual risks are in S01-15 (dev origins on non-prod) and S18-01 (clickjacking).
- **Email preview iframe:** `pages/EmailPreviewsPage.tsx:82-92` renders `srcDoc` HTML with `sandbox="allow-same-origin"` and no `allow-scripts`, so even if the template HTML contained script it would not run. Input is static sample data (`EmailPreviewsPage.tsx:45,60`).
- **Admin check ordering:** `App.tsx:61-63` shows `LoginPage` when `!isAuthenticated || !isAdmin`, so admin routes and queries are not mounted for plain users. The backend independently enforces `requireAdminRole` on all `admin*` operations (S02 verified-correct list).
- **Checkout URL modal:** the Chargebee checkout URL is shown only in a read-only `<input value>` and copied to the clipboard (`OrganizationDetailPage.tsx:775-805`). It is never used as an `href`, so there is no `javascript:` URL risk.
- **Destructive confirm:** `resetUsage` requires typing the org name (`OrganizationDetailPage.tsx:723-729`).

## Findings

## S18-01 — No clickjacking or CSP protection defined for the admin SPA
- **Severity:** Medium (PLAUSIBLE; depends on what the edge/CDN adds)
- **File:line:** `apps/admin-app/public/_headers:1-3` (only `Cache-Control` for `/config.js`); `apps/admin-app/index.html:1-16` (no CSP meta, no `frame-ancestors`)
- **Description:** The admin-app ships no `X-Frame-Options`, `Content-Security-Policy` (`frame-ancestors`, `script-src`, `connect-src`), `Referrer-Policy`, or `X-Content-Type-Options`. The only static-host header file sets cache control. Nothing in the repo shows the admin origin gets these headers elsewhere (the helmet config in the backend applies only to the API, S05-13). The project memory notes that a Cloudflare zone rule sets `X-Frame-Options` for the form viewer, which may incidentally cover this host, but that is not in code and is not a CSP. The page also loads Google Fonts CSS from a third party and an unpinned-origin `/config.js` with no integrity or CSP restriction.
- **Exploit scenario:** An attacker lures a logged-in admin to a page that frames the admin SPA (if framing is not blocked at the edge) and uses UI redressing to trick a click on a sensitive one-click action, for example cancelling or reactivating an organization subscription (`OrganizationDetailPage.tsx` confirm modals) or archiving a plan (`PlansPage.tsx`). A missing CSP also removes the second line of defence if any future XSS appears in the privileged origin.
- **Recommended fix:** Add to `public/_headers`: `/*` with `X-Frame-Options: DENY`, `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' https://fonts.googleapis.com 'unsafe-inline'; font-src https://fonts.gstatic.com; img-src 'self' data: https:; connect-src 'self' <api origin>; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` (`frame-src` is not needed; the email preview uses `srcdoc`), `Referrer-Policy: strict-origin-when-cross-origin`, `X-Content-Type-Options: nosniff`. Confirm the deployed response headers.

## S18-02 — Role tiers are UI-only: `admin` can reach every destructive billing action, and `superAdmin` is only a cosmetic badge
- **Severity:** Low (cross-reference S02-11, S01-02)
- **File:line:** `apps/admin-app/src/components/AdminLayout.tsx:22,93` (only use of `isSuperAdmin`); `src/App.tsx:61-81` (all routes available to any admin); backend `graphql/resolvers/admin.ts:141-149,674-1044`
- **Description:** `isSuperAdmin` is used solely to render a "Super admin" badge. The plan catalog (`PlansPage`), enterprise deals (`adminSetEnterprisePlan`), assign plan, usage reset, cancel and reactivate are all available to the plain `admin` role in the UI, and the backend authorizes them with `requireAdminRole` (admin or superAdmin) only (already noted in S02-11). There is no client-side separation, and the client could not provide one anyway, so the fix belongs on the server and the UI should mirror it.
- **Exploit scenario:** A support-level `admin` account (or one that is compromised, see S01-01 for stale role caching, and S01-02 for admin to superAdmin escalation via better-auth endpoints) sets an organization to a zero-price enterprise plan with unlimited limits, or cancels a paying customer's subscription, with no second approval.
- **Recommended fix:** Decide the policy server-side (`requireSuperAdminRole` for plan CRUD, enterprise, cancel, reset). Then hide or disable those controls for plain admins in the UI using `isSuperAdmin`, as a convenience only.

## S18-03 — Admin role is read once at load and never re-validated client-side; no idle timeout or step-up authentication
- **Severity:** Low
- **File:line:** `apps/admin-app/src/hooks/useAuth.ts:30-52,74-83`; `src/services/auth.ts:89-96`; `src/pages/LoginPage.tsx:16-22`
- **Description:** The role comes from `/api/auth/get-session` once at mount (and after sign-in). If an admin is demoted or banned, the open tab keeps rendering the admin UI until a GraphQL call fails or the page reloads (server calls still use the cached session role up to 7 days, S01-01). There is no inactivity timeout, no re-authentication before high-impact actions (enterprise pricing, cancel, plan archive), and no MFA or password prompt: admin sign-in is the same `/sign-in/email` email+password endpoint as regular users (rate-limit weaknesses in S01-04). The login page accepts any user's credentials and then simply re-renders the login form for non-admins, with no error message (`App.tsx:61-63`), which slightly aids confusion but not enumeration.
- **Exploit scenario:** A shared or unlocked admin workstation, or a phished admin password, gives full admin access with no second factor and no re-prompt for actions that move money or cancel customers.
- **Recommended fix:** Require 2FA (better-auth `twoFactor` plugin) for `admin`/`superAdmin`, add re-authentication or a recent-session check for billing mutations (server-enforced via session `createdAt`), a shorter admin session lifetime, and a periodic `get-session` revalidation (for example on window focus) that signs out on role loss. Show an explicit "not an admin" message to non-admin sign-ins.

## S18-04 — Attacker-controlled image URLs rendered in the admin console (`user.image`, `org.logo`, `member.userImage`)
- **Severity:** Low (PLAUSIBLE; depends on whether the image field can be set to an arbitrary URL, see S06-03)
- **File:line:** `components/users/UserCard.tsx:38-40`; `pages/users/UserDetailPage.tsx:72-73`; `pages/OrganizationsPage.tsx:149`; `pages/organizations/OrganizationDetailPage.tsx:258,349`
- **Description:** These `<img src={...}>` values come straight from `User.image` and `Organization.logo`, which any customer can set on their own profile or organization (S06-03 shows these fields are accepted as arbitrary strings without being tied to an uploaded object). There is no scheme/host allow-list and no `referrerPolicy`. `javascript:` in `<img src>` does not execute in modern browsers, so this is not XSS, but the admin's browser will fetch the attacker's URL.
- **Exploit scenario:** A malicious customer sets their avatar or org logo to `https://attacker.example/pixel.png?x`. When an admin opens the user or organization list (or a support search), the admin's IP, user agent, time and Referer (the admin origin and path) are sent to the attacker, confirming the admin's activity and fingerprinting the admin's network. It can also be pointed at an internal URL to probe the admin's own network via blind GET requests.
- **Recommended fix:** Only render images whose URL matches the CDN origin (`PUBLIC_S3_CDN_URL`, or the same allow-list the backend enforces on write), otherwise show initials. Add `referrerPolicy="no-referrer"` and `loading="lazy"`, and restrict `img-src` in the CSP (S18-01). Validate the value server-side on `updateUser`/org logo writes (S06-03).

## S18-05 — Raw server error messages displayed in the admin UI and toasts
- **Severity:** Low
- **File:line:** `pages/OrganizationsPage.tsx:83`, `pages/TemplatesPage.tsx:64`, `pages/DashboardPage.tsx:117`, `pages/users/UsersPage.tsx:63`, `pages/users/UserDetailPage.tsx:48`, `pages/PlansPage.tsx:146-178`
- **Description:** `error.message` from Apollo is shown verbatim. Combined with S05-03 (Prisma, Chargebee and library messages are not masked on the server), this surfaces internal details (table or column names, Chargebee API error text) to whoever is looking at the admin console. The rendering is as React text, so there is no XSS. The audience is already privileged, which keeps this Low.
- **Exploit scenario:** Low-value disclosure to screen-sharing or screenshots of the admin console, or to a low-trust `admin` who can read more internals than needed.
- **Recommended fix:** Fix server-side masking (S05-03) and show a generic localized message in the UI, with the detail kept in the console or Sentry.

## S18-06 — Admin-authored template content is unvalidated JSON on the client; downstream rendering safety depends on S16/S17
- **Severity:** Info
- **File:line:** `components/templates/TemplateModal.tsx:225-262` (`JSON.parse` of `formSchema` and `layout`, client-only check at lines 173 and 186)
- **Description:** The template editor takes raw JSON for `formSchema` and `layout`, validates it only with `JSON.parse`, and sends it to `createTemplate`/`updateTemplate`. Server-side validation of the shape is covered by S02/S19. Templates are copied into customers' forms, so any markup in rich-text or labels inside a template reaches form-app and form-viewer. This is not an admin-app flaw, but the admin tool is the author of that content, so a compromised admin account is also a stored-XSS or phishing-content vector against all customers.
- **Exploit scenario:** A compromised admin adds a template with a malicious rich-text/thank-you redirect, and customers instantiate it from the gallery. Whether it executes depends on the sanitization in S16/S17.
- **Recommended fix:** Validate template payloads server-side with the same schema deserializer (`deserializeFormSchema`) and sanitization as normal forms; keep this as a cross-check item for S16/S17.

## S18-07 — Admin bundle imports backend source files directly
- **Severity:** Info
- **File:line:** `pages/EmailPreviewsPage.tsx:12-16` (`../../../backend/src/templates/*`); `vite.config.ts:9-14`
- **Description:** The preview page imports backend template modules by relative path into the browser bundle (templates import `emailLayout.js` and `FormPublishedEmailData` from `services/emailService.js`). If a template ever imports a server-only module (config, env, nodemailer, Prisma) the admin bundle will either break or bundle server code and its constants. Currently the imported modules appear to be pure string builders. The `formPublishedEmail` import of `../services/emailService.js` is a value-style import of a type, which only works because TypeScript or esbuild elides it.
- **Exploit scenario:** None today. A later change that adds an env-reading helper to a template could ship server defaults (including hard-coded fallback strings) to every browser that loads the admin SPA.
- **Recommended fix:** Move the templates into a shared package (for example `@dculus/utils`) or use `import type` and a lint rule that forbids importing `apps/backend` from front-end apps.

## S18-08 — `useTranslation` builds a `RegExp` from placeholder names
- **Severity:** Info
- **File:line:** `hooks/useTranslation.ts:34-36`
- **Description:** `new RegExp(\`{{\\s*${token}\\s*}}\`, 'g')` uses the placeholder key unescaped. Keys are developer-supplied literals in this app (not user input), and values are inserted as strings, so there is no ReDoS or injection today. Noted so that nobody passes user-supplied keys.
- **Exploit scenario:** None.
- **Recommended fix:** Escape the token, or use `String.prototype.replaceAll` with a literal pattern.

## S18-09 — External Chargebee link built from build-time env and DB value
- **Severity:** Info
- **File:line:** `pages/organizations/OrganizationDetailPage.tsx:25,419-427`
- **Description:** The `href` is `https://${VITE_CHARGEBEE_SITE}.chargebee.com/customers/${chargebeeCustomerId}`. The scheme and host suffix are fixed, so `javascript:` is not possible. `VITE_CHARGEBEE_SITE` is public by design (a site subdomain, not a key). The `chargebeeCustomerId` is a server-written value; if it ever contained `/` or `?` it could alter the path under the same Chargebee host only.
- **Exploit scenario:** None.
- **Recommended fix:** `encodeURIComponent(sub.chargebeeCustomerId)` and add `rel="noopener noreferrer"` if not already present.

## S18-10 — Console logging of auth and save errors
- **Severity:** Info
- **File:line:** `services/auth.ts:44,70,82`; `hooks/useAuth.ts:48`; `components/templates/TemplateModal.tsx:260`; `pages/TemplatesPage.tsx:54`
- **Description:** `console.error` is called with error objects only (no credentials, no tokens, no request bodies). The sign-in request body (email and password) is never logged. Fetch failures could include the request URL, which carries no secrets.
- **Exploit scenario:** None.
- **Recommended fix:** None required; optionally strip console output in production builds.

- Deployed response headers at the Cloudflare/Azure edge for the admin hostname (cannot be seen from the repo; see S18-01) and the deployment pipeline that writes `config.js` (S20, S21).
- Shared UI package components used here (`@dculus/ui` `Button`, `Input`, `Toaster`, `toastError`) for unsafe HTML rendering (S19).
- `src/locales/**` JSON string content for HTML or script payloads (skimmed by grep only; strings are rendered via text interpolation).
- Dependency vulnerabilities for `apps/admin-app/package.json` (S23).
- Runtime verification: nothing was exercised against a running instance; browser behaviour claims (for example `javascript:` in `<img src>`, iframe sandbox) are from standard browser semantics.
